# MIGRATE-001 · Coze/Dify 迁移到本地化 AI 决策卡

> ID: MIGRATE-001 | 创建: 2026-09-02 v3.0 | 状态: ⭐ 正式  
> 作者: Hermes (M3 队长)

## 这个决策卡在解决什么问题（一句话）

**你已经在用 Coze 或 Dify（云端 SaaS 平台），现在想搬到本地（数据可控+成本可控+定制灵活）——这张卡告诉你「迁移路径 / 哪些值得搬 / 哪些保留云端 / 报价多少」。**

## 适用客户

### 画像
- 已有基础: 已经在用 Coze / Dify / 飞书多维表格 AI / 类似 SaaS 平台
- 痛点: **数据出云担心合规** / **按次计费太贵** / **想加私有模型** / **团队规模变大需要 RBAC**
- 预算: ¥15,000-50,000（迁移项目，工作站档）
- 关键约束: **业务不能中断**（白天用的 bot 不能停）

## 推荐架构：分层迁移 + 灰度切换

### 模式：3 层逐步迁移（不是一夜切换）

```
原架构（云 SaaS）：
┌──────────────────────┐
│ Coze/Dify 云端平台  │
│ ├── LLM API（云）    │
│ ├── 工作流（云）      │
│ ├── 知识库（云）      │
│ └── 数据库（云）      │
└──────────────────────┘

目标架构（混合）：
┌──────────────────────────────────────────────┐
│ 入口层：用户无感（域名/IP 切换在后台）       │
│ ├── 保留云端作为兜底                          │
│ ├── 本地优先（新请求走本地）                  │
│ └── 灰度切换（10%→50%→100%）                  │
└──────────────────────────────────────────────┘
                ↓ 分层
┌──────────────────┬──────────────────┐
│ 立即搬：         │ 不搬：            │
│ ├── 知识库 RAG   │ │ 大模型 API       │
│ ├── 数据存储     │ │（云 API 反而便宜）│
│ ├── 触达逻辑     │ │                  │
│ └── 工作流引擎   │ │                  │
└──────────────────┴──────────────────┘
```

### 迁移阶段（4 阶段）

**阶段 1：盘点（1 周）**
- 列出当前 SaaS 上的所有工作流、知识库、API key
- 标出哪些是「云端必须」哪些是「可以本地」
- 输出：迁移清单 + 风险评估

**阶段 2：搭建本地（2-3 周）**
- 本地 LLM（LlamaIndex / LangChain / Ollama）
- 本地知识库（Chroma / Milvus / LanceDB）
- 本地工作流引擎（LangGraph / AutoGen）
- 不动生产，先做并行环境

**阶段 3：灰度切换（1-2 周）**
- 10% 流量走本地，90% 走云端
- 对比两边结果，差异 < 5% 才继续
- 50% → 100%

**阶段 4：完全切换 + 云端兜底（1 周）**
- 100% 切到本地
- 云端保留为「备用」
- 紧急时切回云端（< 5 分钟）

## 必选组件

### 本地栈（替代 Coze/Dify）
- **LLM**: Ollama（本地大模型） + LibTV API（云端，按需）
- **RAG**: LlamaIndex 或 LangChain + Chroma（向量库本地）
- **工作流**: LangGraph（替代 Coze 工作流）
- **数据库**: PostgreSQL + Redis（本地存储）
- **Web**: FastAPI 或 Flask（替代 Coze/Dify 的 web 入口）

### 云端保留（兜底 + 高难度）
- **LLM API**: DeepSeek / MiniMax M3 / GPT-4o（云端）
- **服务**: LibTV（图像/视频生成，云端优势明显）

### 推荐部署
- **本地**: Mac mini M4/M5（Apple Silicon NPU） 或 Linux 服务器
- **开发**: 客户机 launchd 自愈（沿用 NIFTY 实战）
- **监控**: Hermes cron + Baidu 网盘备份

## 我们的实战（基于 NIFTY/阿尔泰 + 用户实战经验）

### NIFTY（本地栈实战）
- **起点**: 客户机 launchd + Pillow + rembg + basicsr（本地优先）
- **云端**: LibTV Seedream 5.0（高难度图像生成）
- **效果**: 端到端 8-13 秒（白底 + 抠图）/ 40-80 秒（云端 AI 生图）
- **结论**: 80/20 原则——80% 本地，20% 云端

### 阿尔泰（云 SaaS 实战教训）
- **起点**: 云端 LLM API（按量计费）
- **问题**: 单月 1-2 万 API 费用（vs 本地模型部署一次性 ¥3-5k）
- **教训**: 客户量大时**本地模型 = 1 个月回本**

## 不推荐（反模式）

❌ **一夜切换**（业务中断 + 数据丢失风险）
❌ **大模型也搬本地**（单卡 GPU 跑不动 70B 模型，云端更划算）
❌ **完全脱离云端**（紧急时无兜底）
❌ **不写迁移 SOP**（团队换人能力丢失）
❌ **不做灰度**（出问题定位难）
❌ **知识库搬过来不清理**（旧数据污染新系统）
❌ **不监控切换后质量**（用户无感不代表体验一致）

## 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **业务中断** | 高 | 高 | 灰度切换 + 云端兜底 |
| **数据丢失** | 中 | 高 | 迁移前完整快照 |
| **切换后效果差** | 中 | 高 | 双跑对比 + A/B 测试 |
| **本地模型质量差** | 中 | 中 | 用云端 API 补本地短板 |
| **客户换人能力丢失** | 中 | 中 | 完整 SOP + 录屏 |
| **超出预算** | 中 | 中 | 分阶段付费（每阶段验收） |
