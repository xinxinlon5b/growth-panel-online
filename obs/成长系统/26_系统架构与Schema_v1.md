# 成长系统 · 系统架构与 Schema v1（批次 A/B 总案）

> 创建：2026-09-09 | 状态：v1（批次 A+B 已按本文件落地）
> 用途：这是「内容怎么存、状态怎么标、项目怎么走、网页怎么读」的唯一结构权威。
> 关联：00（目标/铁律）、08（需求基线）、09/10/12/23/24/25（领域知识）

## 一、一句话架构

**项目是主轴，判断是弹药，审核是闸门，网页是镜子。**
知识不是先囤后用的内容库，而是从每个真实项目里长出来、又在下一次项目决策里被调用的判断。

## 二、系统六层图

```text
输入层：新客户 / 项目缺口 / 你丢的素材 / 学习任务
        ↓
智能层：Hermes 主脑（体检/决策/审核派发/复盘回填）
        ↓
真相源：Obsidian（唯一正文，下面四区）
        ├─ 项目舱：项目档案 + 决策记录 + 关卡证据
        ├─ 判断库：方法论/坑/案例/术语（原子化+来源+状态）
        ├─ 证据源：原文 raw（不可改）
        └─ 审核台账：三审报告 + 变更记录
        ↓
编译层：schema 校验 → md → JSON 索引 → build
        ↓
展示层：一个网页（项目舱/判断库/学习线/审核台）
        ↓
回到项目：决策被使用，坑被复用，飞轮才转
```

## 三、唯一真相源规则

1. **正文只存在于 Obsidian md**；网页卡、JSON、build 都算“编译产物”。
2. 原始素材进 `raw/` 或“原始库”后不修改；加工产物必须指向原文。
3. 网页能读、能发起流程、能人工批准；不能成为绕过 Obsidian 的另一套数据。
4. `_` 开头的 md 是说明/schema，不是知识条目或项目卡。
5. 正式沉淀必须带状态和来源；“已验证”必须能在文件里指到证据。

## 四、通用状态词

| 状态 | 意思 | 谁能改 |
|---|---|---|
| `原始` | 原文/素材，未经提炼 | 只读 |
| `候选` | 已提炼，等待三审 | Agent 可改 |
| `正式` | 通过三审，可被检索/引用 | 人批准后落 |
| `冲突` | 来源间有矛盾，双方都保留 | 审核台账记录 |
| `过期` | 有日期/版本失效风险 | 定期复审 |
| `作废` | 错误或不再适用，留原因 | 三审 |

项目状态固定用：`已停（经验全保留）` / `进行中` / `已交付` / `待确认`。

## 五、项目档案字段（机器可读）

每份项目档案开头必须按顺序包含：

```text
> 档案类型：project-archive
> 状态：进行中 / 已交付 / 已停（经验全保留） / 待确认
> 当前阶段：按 09 七阶段写
> 下一关：一句话，明确下一步要交什么
> 更新时间：YYYY-MM-DD
> 可信度说明：老项目必须写“事后复盘对照，不是当年实时门禁”
```

每份档案必须包含段落：`## 一句话`、`## 项目画像`、`## 关卡进度`、`## 已验证零件/打法`、`## 已验证的坑`、`## 可复用判断`、`## 关联证据`。

关卡进度表列固定为：`阶段 | 状态 | 证据/说明`。

## 六、判断库条目最小字段

以后新沉淀（非说明/非项目档案）按此结构写：

```text
类型：方法 / 坑 / 案例 / 原则 / 模板
状态：候选 / 正式 / 冲突 / 过期 / 作废
来源：链接或项目文档 + 访问/发生日期
适用：出现什么信号时必须用
不适用：什么时候别用
做法：可执行步骤
反模式：不该怎么做
已验证：哪个项目/哪一关/结果（没有就写“待验证”）
关联：[[相关卡]]、[[相关坑]]、[[相关项目]]
审核：AUDIT-xxx（通过后回填）
```

## 七、新项目主流程（项目舱标准动作）

```text
1 建档：项目档案 + 最像历史档案参考
2 体检：Hermes 读 23/24/25 + 最像档案 → 开工方案
3 落决策：方案存回项目档案，带日期与假设
4 过关卡：每过一关，补产出物与证据
5 复盘：结束或阶段性复盘，回填坑与可复用判断
6 回放：新项目建档时自动命中最像档案
```

当前网页动作映射：

| 动作 | 路径 |
|---|---|
| 建档 | 项目工作台 / 新项目向导 |
| 体检 | 项目卡片或档案里的「项目体检」按钮 |
| 落决策 | `/api/attach_project_check` 追加到档案 |
| 看关卡 | 打开档案全文，关卡进度表在文件内 |
