# 24 项目零件装配清单（怎么知道这个项目该装哪些零件）

> 创建：2026-09-09 | 更新：v2.0（完整版，90+ 零件全集 + 判定法 + 3 项目解剖） | 用途：用 6 个问题推导出「必须装哪些零件」，而不是靠感觉/靠别人提醒
> 一句话：软件行业把「什么系统要什么保障」总结成了可推导的规则——问 6 个问题，答案就是零件清单。
> 溯源：零件全集来自 AWS Well-Architected / Google SRE / OWASP / 12-Factor / 多个 AI 生产清单，3 个解剖来自 Cal.com / Supabase / Dify 官方仓库，出处见文末。

---

## 〇、30 秒看懂

「回滚、幂等、重试、熔断、审计……」这些不是装点门面的术语，是**项目出现某个信号时，必须配上的零件**。

**核心问题不是「什么是幂等」，而是「我这个项目什么时候必须有幂等」**。答案是：只要涉及支付/创建资源/客户端会重试，就必有幂等。

本页给你三样东西：
1. **零件全集**（9 大维度 90+ 个，每个配「触发条件」——出现什么信号就必装）
2. **6 步判定法**（问 6 个问题，答案出来零件清单就出来）
3. **3 个真实项目解剖**（Cal.com / Supabase / Dify 各自怎么配零件，照着当模板）

## 一、零件全集：9 大维度 MECE（每个零件配「触发条件」）

> 「触发条件」= 项目里出现什么信号，这个零件就必须存在。这是术语词典「是什么」之外最缺的「什么时候必须有」。

### 维度 1 · 可靠性（Reliability）

| 零件 | 一句话作用 | 触发条件（什么时候必须有） |
|---|---|---|
| 重试 + 指数退避 | 网络抖动时自动恢复 | 调用任何外部 HTTP/RPC/DB，且失败可恢复（不是 4xx 业务错误） |
| 超时 | 防止慢请求拖死线程 | 所有 I/O 调用必须设，否则一个慢下游就耗光线程池 |
| 熔断 | 下游崩溃时快速失败，不雪崩 | 依赖 ≥2 个外部服务，任一可视为不稳定（公网 API/第三方 SaaS） |
| 幂等 | 重复请求结果一致 | 涉及支付/创建资源/消息消费，或客户端会重试 |
| 限流 | 保护系统不被超量请求压垮 | 公网暴露 API，或资源有限（GPU/数据库连接池） |
| 降级 | 核心功能可用，非核心可关 | 用户体验 SLA 比功能完整更重要（电商大促、客服系统） |
| 队列 + 死信队列 | 异步解耦、削峰 | 任务处理 > 200ms，或并发突发 > 平时 5x，或需要重试语义 |
| 缓存 | 减少重复计算/DB 查询 | 读多写少，或数据可容忍短时不一致，或热点数据明显 |
| 健康检查 | 负载均衡/容器判断存活 | 部署在 K8s/容器平台/任何 LB 后面 |
| 备份与恢复 | 数据可恢复 | 任何持久化数据 + RPO/RTO ≠ 0（几乎所有业务） |
| 灾难恢复 | 整机房/区域故障下恢复 | 业务连续性要求 ≥99.9%，或数据是关键资产 |
| 混沌工程 | 主动注入故障验证韧性 | 系统 ≥6 个月生产，关键路径多服务依赖 |

来源：AWS Well-Architected Reliability Pillar；Google SRE Workbook Ch.30；Manuel Blinkert AI Production Readiness Checklist。

### 维度 2 · 安全（Security）

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 鉴权 | 验明「你是谁」 | 任何多用户系统，或任何需要登录的功能 |
| 授权 | 决定「你能做什么」 | 角色/权限差异（管理员/普通用户/租户） |
| 审计日志 | 谁/何时/做了什么 | 合规要求（等保/GDPR/SOC2），或事后追溯需要 |
| 加密传输（TLS） | 数据不被中途偷窥 | 任何公网传输，含内网（内网 ≠ 安全） |
| 加密存储 | 数据库/磁盘被偷也不可读 | 含 PII/支付/商业机密；云数据库默认应开 |
| 密钥管理 | 集中、轮换、不落代码 | 任何需要 API Key/DB 密码/证书的项目 |
| CSRF 防护 | 防跨站请求伪造 | 浏览器 + Cookie 会话 |
| XSS/注入防护 | 用户输入不可信 | 任何接受用户输入的地方（含 Markdown/AI 输出） |
| 输入校验 | 数据进系统前先过校验 | 任何接受外部输入（API/表单/上传） |
| 安全头（CSP/HSTS/X-Frame-Options） | 浏览器层防御 | 任何 Web 应用 |
| 最小权限 | 服务账号只给必需权限 | 任何含多角色或多环境（dev/stg/prod） |
| 速率限制（应用层） | 防暴力破解/撞库 | 登录/注册/密码重置/敏感接口 |
| WAF / 异常流量检测 | 滤掉常见 Web 攻击 | 公网 Web 应用，且有合规要求 |
| 依赖漏洞扫描（SCA） | 第三方库已知 CVE | 任何用第三方库的项目（基本所有） |

来源：OWASP Top 10；Microsoft Azure / AWS Well-Architected Security Pillar。

### 维度 3 · 可观测（Observability）

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 结构化日志 | 可搜索、可聚合 | 任何非 demo 项目 |
| 指标 | 量化系统状态（QPS/P99/错误率） | 有 SLA/SLO 目标，或需要容量规划 |
| 追踪 | 一个请求在多个服务里走了多久 | 微服务/多组件调用链 |
| 告警 | 出问题叫人 | 有 on-call 或工作时间外需要响应 |
| 仪表盘 | 让状态一眼可见 | 任何需要人监控的系统 |
| 错误聚合 | 异常集中、自动去重 | 任何用户会遇错的客户端/服务 |
| SLI/SLO/SLA 定义 | 量化可靠性目标 | 外部用户/有 SLA 承诺 |
| 业务监控（北极星指标） | 业务健康度量化 | 业务方要量化效果（留存/转化） |

来源：Google SRE Workbook；OpenTelemetry 项目。

### 维度 4 · 数据（Data）

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 数据校验 | 进库前确保格式/范围正确 | 任何写操作 |
| 事务 | 多步写入要么全成要么全不成 | 多表/多写操作，且需要原子性 |
| 数据迁移 | schema 变更可追踪、可回滚 | DB 结构会变（所有成长中的项目） |
| 主数据管理 | 关键实体唯一源 | 多系统共享同一关键实体 |
| 数据血缘 | 数据从哪来到哪去 | 数据仓库/BI/合规审计 |
| 数据备份 + 异地 | 防数据丢失 | 任何生产数据 |
| 数据归档 | 老数据不在线但可查 | 数据保留期 > 1 年，或合规要求 |
| 软删除 | 误删可恢复 | 用户产生的内容（避免误删纠纷） |
| 数据脱敏 | 测试/分析时保护 PII | 含 PII/敏感字段，需在非生产环境使用 |
| 分区/分片 | 单表/单库太大 | 单表 > 5000 万行，或 QPS > 单实例承载 |
| 读写分离 | 读多写少优化 | 读 QPS > 写 QPS 5x 以上 |

### 维度 5 · 部署与运维（Deployment & Ops）

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| CI/CD | 自动化构建测试部署 | 任何团队项目（单人项目也强烈建议） |
| 环境隔离（Dev/Stg/Prod） | 不同阶段不同环境 | 任何对外服务或严肃项目 |
| 配置管理 | 配置和代码分离 | 配置会因环境不同（DB 地址/密钥/特性开关） |
| 灰度发布 | 新版本先给 1% 用户 | 影响用户的变更、任何有回滚成本的项目 |
| 蓝绿部署 | 零停机切换 | 关键业务 + 有双倍资源预算 |
| 特性开关 | 功能可独立于发版启停 | 需要分批推、紧急关闭、A/B 测试 |
| 容器化 | 环境一致、易迁移 | 任何长生命周期项目 |
| 编排（K8s/Docker Swarm） | 多容器协同 | 容器数 ≥5，或需要自愈/弹性 |
| IaC（Terraform/Pulumi） | 基础设施可代码化 | 多环境/多 region/团队协作 |
| 镜像仓库 + 镜像签名 | 制品管理 + 防供应链攻击 | 任何用 CI/CD 的项目 |
| GitOps | 通过 Git 同步环境状态 | K8s + ≥2 环境 |

来源：12-Factor App；CNCF Cloud Native Landscape。

### 维度 6 · AI 特有（AI-Specific）—— 最容易被忽略的维度

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| Prompt 版本管理 | 不同版本 Prompt 可追溯对比 | 任何用 LLM 的项目 |
| LLM 评测集 | 用量化指标选模型/迭代 | LLM 在关键路径（不能只靠肉眼） |
| 幻觉治理 | RAG/Grounding/约束解码 | LLM 输出会被用户/系统信任并采纳 |
| 输出审核 | 拦截不安全/不合规输出 | C 端/对外服务，涉敏感行业 |
| 成本预算与告警 | 防止 token 烧钱 | 用 GPT-4/Claude 等贵模型 |
| 多模型路由 | 不同任务用不同模型 | 长流程 LLM 调用，性能/成本权衡 |
| 上下文管理 | 处理超长上下文 | 文档/对话类应用 |
| Token 限流 | 防止单用户滥用 | 多租户 LLM 应用 |
| 模型可降级 | 主模型不可用时切备用 | SLA 要求高，单点依赖关键 |
| Embedding 版本管理 | 切模型后向量仍可比 | 任何用向量库的项目 |
| AI 审计日志 | 记录每次 LLM 调用的输入输出 | 合规 + 排错 |
| Prompt 注入防护 | 用户输入不能覆盖系统指令 | 用户输入会进入 Prompt |

来源：Anyscale LLM Production Guide；Manuel Blinkert / asq-sheriff AI-Production-Checklist。

### 维度 7 · 性能（Performance）

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 性能基准测试 | 量化性能 | 关键路径需要量化保证 |
| 压测 | 找瓶颈 | 上线前 / 大促前 |
| 性能剖析 | 找慢点 | 性能问题 |
| CDN | 静态资源加速 | 任何公网 Web 应用 |
| 连接池 | 复用 TCP/DB 连接 | DB / HTTP 客户端 |
| 异步处理 | 不阻塞 UI/线程 | I/O 密集 |
| 浏览器/客户端缓存 | 减少重复请求 | 任何 Web 应用 |

### 维度 8 · 成本（Cost）—— 团队容易忽略

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 云成本监控 | 看每月账单分布 | 用云服务（基本所有） |
| 资源标签 | 按项目/部门分账 | 多项目/多客户 |
| 自动伸缩 | 用多少付多少 | 流量有峰谷 |
| 预留实例/Saving Plan | 长期资源省钱 | 资源 24x7 跑 |
| 大模型成本看板 | 看每个调用花多少 | LLM 应用 |
| 数据库/存储生命周期策略 | 老数据降级存储 | 长期保存数据 |

### 维度 9 · 合规与法律（Compliance）—— 客户大、政府/医疗/金融必有

| 零件 | 一句话作用 | 触发条件 |
|---|---|---|
| 隐私政策/用户协议 | 法律要求 | 任何收集用户数据的应用 |
| 数据出境合规 | 数据不能随便出 | 政府/金融/医疗 |
| 个人信息保护（PIPL/GDPR） | 用户权利保障 | 含个人信息 |
| 等保/SOC2/HIPAA | 行业强制 | 行业要求 |
| 知识产权审查 | 输出不侵犯第三方 | AI 内容生成 |

**零件全集统计**：9 大维度 ≈ 90+ 零件；传统软件工程 ≈ 65 个，AI 特有 ≈ 12 个，合规 ≈ 6 个。一个项目不需要全部具备，但判定法会告诉你**该有的必须一个不缺**。

## 二、判定法：6 步「需求 → 零件」推导（照单问客户，答案出来清单就出来）

> 把「靠老司机经验」变成「可培训、可审计、可复盘」的流程。每个项目关键属性映射到一组必装零件。

### 第 1 步 · 业务关键性 —— 决定底线深度
- 问：「这系统挂了，业务损失是什么？」（零/小/大/灾难）
- 灾难级 → 必备：灾备 + 混沌 + 24x7 on-call + SLO < 99.95%
- 大 → 必备：备份 + 监控告警 + 回滚方案 + 健康检查
- 小 → 必备：健康检查 + 基本日志 + 备份
- 零 → demo 级，可酌情

### 第 2 步 · 并发与规模 —— 决定横向能力
- 问：「峰值并发多少？峰值/均值比？数据量？增长曲线？」
- QPS > 1000 或数据 > 1TB → 必备：缓存 + 读写分离 + 分库分表 + 压测
- 增长不可预测 → 必备：自动伸缩
- 长尾但量大 → 必备：CDN + 队列削峰

### 第 3 步 · 数据敏感 —— 决定安全深度
- 问：「数据里有什么？PII？支付？健康？商业机密？」（无/PII/敏感/极敏感）
- 极敏感（金融/医疗/政府）→ 必备：加密存储 + 加密传输 + 审计 + 数据脱敏 + 合规
- 敏感 → 必备：TLS + 加密 + 审计 + 密钥管理
- PII → 必备：TLS + 加密 + 隐私政策
- 无 → 必备：TLS + 输入校验

### 第 4 步 · 失败代价 —— 决定韧性深度
- 问：「一个错误请求 / 一次宕机会带来什么后果？」
- 一次错误 = 直接经济损失 → 必备：幂等 + 重试 + 熔断 + 事务
- 一次错误 = 用户流失 → 必备：降级 + 灰度 + 监控
- 一次错误 = 内部损失 → 必备：基本重试 + 日志

### 第 5 步 · 多人协作 —— 决定边界
- 问：「多少用户/角色？多租户？跨团队使用？」
- 多角色 → 必备：鉴权 + 授权 + 审计
- 多租户 → 必备：租户隔离 + 数据隔离 + 限流（防滥用）
- 跨团队 → 必备：API 版本 + 文档 + 限流

### 第 6 步 · 外部集成 —— 决定耦合点
- 问：「调用几个外部服务？公网/内网？可控性？」
- ≥3 个外部 → 必备：熔断 + 超时 + 重试 + 监控调用链
- 外部是关键路径 → 必备：降级方案 + 多供应商备选
- 调用 AI → 必备：Prompt 版本 + 评测 + 成本告警 + 输出审核

### 额外 · AI 触发器（如果项目含 LLM/Agent）
- 触发：用 LLM → 必须配：Prompt 版本 + 评测集 + 成本监控
- 触发：LLM 输出给用户看 → 必须配：输出审核 + 幻觉治理
- 触发：用户输入进 Prompt → 必须配：Prompt 注入防护
- 触发：调用昂贵模型 → 必须配：Token 限流 + 模型路由

## 三、3 个代表性真实项目完整解剖（照着当模板）

> 选 3 个不同形态的代表性开源项目（高星、生产可用、文档全）验证零件清单。**Cal.com** = 企业级 SaaS、**Supabase** = BaaS 平台、**Dify** = AI 应用平台，分别代表「传统 Web」「数据+后端服务」「AI 平台」三种最常见客户形态。

### 解剖 1 · Cal.com（~33k stars）—— 企业级 SaaS 排程系统

> 选它原因：真实服务全球 30+ 万用户，多角色、多集成、多种部署形态，是「中小团队给企业做 SaaS」的最佳参考标本。

| 维度 | 零件 | Cal.com 实际选择 | 为什么 |
|---|---|---|---|
| 前端 | Next.js 14 + React + TypeScript | 统一前后端，SEO 友好 | 多端（web/embed/mobile-web） |
| API 层 | tRPC + REST + GraphQL | tRPC 内部类型安全，REST 开放第三方 | 既要 DX 也要生态 |
| 数据层 | Prisma + PostgreSQL | 单库 + 多 schema | 业务复杂但仍是单体优先 |
| 缓存 | Redis (Upstash) | session + rate limit | 多 region 部署 |
| 鉴权 | NextAuth.js + 自研 SSO | 多 provider | 企业客户要 SAML/OIDC |
| 授权 | RBAC (Team/Org/Member) | 多租户 | 企业版核心 |
| 搜索 | Postgres FTS + Algolia（可选） | 大部分场景 FTS 够 | 成本考虑 |
| 实时 | WebSocket (Socket.IO) | booking 状态同步 | 多端同步需求 |
| 异步任务 | Inngest (event-driven) | retry/delay/cron | 不自建队列 |
| 邮件/通知 | Resend + 自研模板 | 可观测 + 高到达率 | 邮件是关键路径 |
| 集成 | 100+ Calendar/Video/Payment | 抽象 Provider 层 | 核心业务 |
| 部署 | Vercel + Docker self-host | 双形态 | 满足不同客户 |
| 监控 | Datadog + Sentry | APM + 错误聚合 | 标品组合 |
| CI/CD | GitHub Actions + Turborepo | monorepo 加速 | 标准 |
| 测试 | Playwright (E2E) + Vitest | 端到端覆盖 | 业务流验证 |
| 安全 | Vanta/SOC2 启动中 | 合规驱动 | 企业客户要 SOC2 |

**🔍 关键洞察**：
- 传统 SaaS 必备零件全有：鉴权、授权、审计、限流、缓存、监控、CI/CD、灰度（通过 Vercel preview）
- **没有熔断/降级/混沌**：单体 + 强依赖，主要靠 Vercel 平台保证——**反面教材：单点依赖外部服务**
- **没用 K8s**：用 Vercel 替代，表明「K8s 不是必须的」，但「配置管理 + 环境隔离」是必须的
- 来源：github.com/calcom/cal.com；cal.com/docs/developing/open-source-contribution/contributors-guide

### 解剖 2 · Supabase（~75k stars）—— 开源 BaaS（Firebase 替代）

> 选它原因：多组件协同的典范，把 PostgreSQL 生态拆成 8+ 个产品，每个产品都是独立零件。

| 组件/零件 | 作用 | 关键技术选型 |
|---|---|---|
| Postgres 主库 | 主存储 + RLS 鉴权 | 单库，配合 pgcrypto/CRDT/向量 |
| GoTrue | 认证服务 | Go，JWT，OAuth/SAML/Magic Link |
| PostgREST | 自动生成 REST API | 直接读 Postgres schema |
| Realtime | WebSocket 订阅 | Elixir Phoenix Channels |
| Storage | S3 兼容对象存储 | Go + S3/R2/Backblaze |
| Edge Functions | Deno serverless | 全球分布 |
| Studio | 管理 UI | Next.js |
| pgvector | 向量检索 | Postgres 扩展 |
| Logflare | 日志聚合 | ClickHouse + Cloudflare |
| Kong / 自研网关 | API 路由 + 限流 | 多租户 |
| CI/CD | GitHub Actions + Turborepo | monorepo |
| IaC | Terraform（生产） | 多 region 部署 |
| 灾备 | WAL-G + S3 增量备份 + PITR | RPO 5min |

**🔍 关键洞察**：
- 零件全部自研或精心选型，每个产品都有清晰边界
- 多语言共存（Go/Elixir/TypeScript）——「为每个零件挑最合适的工具」，不是「全栈统一」
- 强可观测：自研 Logflare，因为卖 BaaS 可观测是卖点
- 强合规：SOC2 + HIPAA + GDPR——做 BaaS 必须有
- 来源：github.com/supabase/supabase；supabase.com/docs/guides/auth/architecture

### 解剖 3 · Dify（~95k stars）—— AI/LLM 应用平台

> 选它原因：当下最热的 LLM 应用平台，把 AI 特有零件呈现得最完整，是做 AI 落地最有参考价值的项目。

| 维度 | 零件 | 选择 |
|---|---|---|
| 后端 | Python + Flask + Celery | 成熟 AI 生态 |
| 前端 | Next.js + TypeScript | 全栈友好 |
| 数据库 | PostgreSQL + Redis + Weaviate/Qdrant | OLTP + 缓存 + 向量 |
| LLM 抽象 | 自研 LLM Factory（统一 API） | 30+ 模型可换 |
| Prompt 编排 | 可视化 DAG | 节点化、版本化 |
| 工作流 | DAG 执行引擎 | 类 Airflow |
| RAG | 文档解析→分块→embedding→检索→rerank→生成 | 全链路可观测 |
| 评测 | 内置 Eval + 人工标注 | 关键卖点 |
| 鉴权 | 自研 RBAC + 工作空间 | 多租户 |
| 部署 | Docker Compose + Helm | 自托管友好 |
| 监控 | OpenTelemetry + Prometheus | 标准化 |
| Prompt 版本 | 内置 | AI 必备 |
| 输出审核 | 内置 Guardrails | 安全 |
| 成本 | 模型 token 消耗看板 | AI 必备 |
| 插件 | 工具调用 + 自定义工具 | Agent 能力 |

**🔍 关键洞察**：
- AI 特有零件齐：Prompt 版本、Eval、Guardrails、成本看板、模型路由——这正是维度 6 的实证
- RAG 全链路：解析→分块→embedding→检索→rerank→生成，每一步都可替换
- 多租户 + 工作空间：AI 平台必备，否则企业不敢用
- 来源：github.com/langgenius/dify；docs.dify.ai

## 四、跨项目对比与发现

**业界共识（任何生产项目都必备）**：
1. 鉴权、授权、审计、CI/CD、健康检查是**任何生产项目都必备**
2. 监控 + 告警 + 结构化日志是**默认配置**，没有项目例外
3. 环境隔离 + 配置管理 + 密钥管理是**底线**，缺一不可

**容易忽略（中小企业常缺，但很关键）**：
1. **灰度发布**只有 Cal.com（靠 Vercel preview）和 Dify（自托管环境隔离）做到——中小企业项目常缺这个，但很关键
2. **混沌工程** 3 个项目都没有——这是头部大厂的事，中小企业可暂缓，但要列入路线图
3. **AI 项目对 RAG 全链路的可替换性要求很高**，这是和传统项目最大的不同
4. **Dify 把「Prompt 版本」当一等公民**，传统 SaaS 项目很少把「配置」做到这个深度，值得借鉴
