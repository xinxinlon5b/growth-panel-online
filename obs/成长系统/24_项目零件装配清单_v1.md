# 24 项目零件装配清单（怎么知道这个项目该装哪些零件）

> 创建: 2026-09-09 | 更新: v1.0 | 用途: 拿到一个项目，用 6 个问题推导出「必须装哪些零件」，而不是靠感觉/靠别人提醒
> 一句话: 软件行业把「什么系统要什么保障」总结成了可推导的规则——问 6 个问题，答案就是零件清单。

---

## 〇、30 秒看懂

「回滚、幂等、重试、熔断、审计……」这些不是装饰品，是**按需装配的零件**。判断要不要装它，别问「这个词酷不酷」，问 **6 个问题**，答案自动映射到零件。

| 问题 | 它决定什么 |
|---|---|
| ① 系统挂了损失多大？ | 可靠性/灾备深度 |
| ② 峰值并发多少？ | 性能/横向能力 |
| ③ 数据里有什么？ | 安全/合规深度 |
| ④ 一次错误代价多大？ | 幂等/事务/熔断 |
| ⑤ 多少用户/角色？ | 权限/审计/隔离 |
| ⑥ 调几个外部服务？ | 熔断/超时/降级 |

---

## 一、六步推导法（照单问，答案即清单）

### 第 1 步 · 业务关键性 → 决定底线深度
- 问「系统挂了，业务损失是什么？」（零/小/大/灾难）
- 灾难级 → 灾备 + 混沌 + 24x7 on-call + SLO
- 大 → 备份 + 监控告警 + 回滚方案 + 健康检查
- 小 → 健康检查 + 基本日志 + 备份
- 零 → demo 级，可酌情

### 第 2 步 · 并发与规模 → 决定横向能力
- 问「峰值并发？峰值/均值比？数据量？增长？」
- QPS>1000 或数据>1TB → 缓存 + 读写分离 + 分库分表 + 压测
- 增长不可预测 → 自动伸缩
- 长尾量大 → CDN + 队列削峰

### 第 3 步 · 数据敏感 → 决定安全深度
- 问「数据里有什么？PII/支付/健康/商业机密？」
- 极敏感（金融/医疗/政府）→ 加密存储 + 加密传输 + 审计 + 脱敏 + 合规
- 敏感 → TLS + 加密 + 审计 + 密钥管理
- PII → TLS + 加密 + 隐私政策
- 无 → TLS + 输入校验

### 第 4 步 · 失败代价 → 决定韧性深度
- 问「一个错误请求/一次宕机带来什么？」
- 直接经济损失 → 幂等 + 重试 + 熔断 + 事务
- 用户流失 → 降级 + 灰度 + 监控
- 内部损失 → 基本重试 + 日志

### 第 5 步 · 多人协作 → 决定边界
- 问「多少用户/角色？多租户？跨团队？」
- 多角色 → 鉴权 + 授权 + 审计
- 多租户 → 租户隔离 + 数据隔离 + 限流
- 跨团队 → API 版本 + 文档 + 限流

### 第 6 步 · 外部集成 → 决定耦合点
- 问「调用几个外部服务？公网/内网？可控性？」
- ≥3 个外部 → 熔断 + 超时 + 重试 + 监控调用链
- 外部是关键路径 → 降级方案 + 多供应商备选
- 调用 AI → Prompt 版本 + 评测 + 成本告警 + 输出审核

### 额外 · AI 触发器（项目含 LLM/Agent 时必加）
- 用 LLM → Prompt 版本 + 评测集 + 成本监控
- LLM 输出给用户看 → 输出审核 + 幻觉治理
- 用户输入进 Prompt → Prompt 注入防护
- 调用昂贵模型 → Token 限流 + 模型路由

## 二、零件全集速查（9 大维度，每个零件「解决什么 + 触发信号」）

| 维度 | 零件 | 触发信号（什么时候必须有它） |
|---|---|---|
| 可靠性 | 重试 | 调外部/网络可能临时失败 |
| 可靠性 | 超时 | 下游可能慢/挂 |
| 可靠性 | 熔断 | 下游故障会连带拖垮我们 |
| 可靠性 | 幂等 | 重复提交会产生重复结果（支付/写库） |
| 可靠性 | 限流 | 会被刷/被滥用/成本敏感 |
| 可靠性 | 降级 | 挂了也要能部分服务 |
| 可靠性 | 回滚 | 有状态变更，错了要能撤销 |
| 可靠性 | 队列削峰 | 突发流量 > 处理能力 |
| 可靠性 | 缓存 | 读多写少/热数据 |
| 可靠性 | 备份 | 数据丢了会死 |
| 安全 | 鉴权 | 有登录/身份区分 |
| 安全 | 授权 | 有角色/权限不同 |
| 安全 | 审计日志 | 有金钱/隐私/多人操作 |
| 安全 | 密钥管理 | 有 API key/密码/证书 |
| 安全 | 数据脱敏 | 有 PII/隐私数据展示 |
| 安全 | 防注入 | 用户输入进系统 |
| 安全 | CSRF/Origin 校验 | 有浏览器写操作 |
| 可观测 | 日志 | 任何系统（调试/排障） |
| 可观测 | 指标 | 要监控健康/性能 |
| 可观测 | 告警 | 挂了要有人知道 |
| 可观测 | 健康检查 | 有部署/容器/负载均衡 |
| 数据 | 事务 | 多步写要原子 |
| 数据 | 校验 | 有外部输入 |
| 数据 | 迁移 | 数据模型会变 |
| 数据 | 主数据管理 | 多系统共用一套业务实体 |
| 部署运维 | CI/CD | 要频繁发版 |
| 部署运维 | 环境隔离 | 开发/测试/生产混一起会出事 |
| 部署运维 | 灰度发布 | 大版本/高风险变更 |
| 部署运维 | 配置管理 | 环境不同配置不同 |
| AI 特有 | 评测集 | 模型输出质量要可验证 |
| AI 特有 | 幻觉治理 | 输出给用户/客户看 |
| AI 特有 | Prompt 版本 | Prompt 会迭代/回滚 |
| AI 特有 | Token 成本 | 调用模型要花钱 |
| AI 特有 | Agent 权限白名单 | Agent 能调外部工具 |

> 完整 90+ 零件带触发条件：见 `21_系统零件判定与网页进化路径_双agent调研.md` A 卷

## 三、装配顺序（零件不是一起装的，按项目生命周期）

| 阶段 | 装什么 | 为什么现在装 |
|---|---|---|
| 骨架期（第一天） | 日志 + 配置管理 + 密钥管理 + 输入校验 | 地基，没有后面都难补 |
| 业务期（核心逻辑） | 事务 + 幂等 + 校验 | 跟着业务写才不返工 |
| 集成期（接外部） | 超时 + 重试 + 熔断 + 降级 | 依赖多了才需要 |
| 上线前 | 回滚 + 备份 + 健康检查 + 监控告警 + 审计 | 上线即生产，出事要有退路 |
| 增长期 | 缓存 + 限流 + 队列 + 灰度 + CI/CD | 用户多了/版本快了 |
| AI 系统 | 评测集 + Prompt 版本 + 幻觉治理 + Token 成本 | Agent 不可信，要护栏 |

## 四、真实项目解剖（3 个样板）

| 项目 | 类型 | 关键零件（为什么） |
|---|---|---|
| Cal.com | 开源日程 SaaS | 多租户隔离 + OAuth 鉴权 + Webhook 重试 + 数据库迁移 + 可观测（多用户/多集成） |
| Supabase | BaaS 平台 | 行级安全(RLS) + JWT 鉴权 + 实时订阅 + 备份恢复 + 审计（多租户数据库/安全敏感） |
| Dify | LLM 应用平台 | 评测集 + Prompt 版本管理 + 模型路由/成本 + Agent 工具白名单 + 审计日志（LLM 应用/AI 特有全配） |

**启发**: 每个真实项目都是按「它是谁、给谁用、接什么」推导出零件的——没有两个项目零件完全一样，但推导方法一样。

---

## 五、怎么用这张清单（工作流）

1. 接到项目 → 用六步推导法问客户/团队（10 分钟）
2. 得到零件清单 → 对着「零件全集」勾出该装的
3. 按「装配顺序」排进开发计划
4. 每完成一个零件 → 回到网页 09 关卡地图对应关卡打勾
5. 复盘时 → 哪个零件没装导致事故，回填反模式
