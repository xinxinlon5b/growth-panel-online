## 怎么用这张图（30秒上手）

1. 接了一个项目 → 先看你在**哪个大阶段**（1-7）
2. 每个阶段有**必过的关卡**（gate）→ 过了才能进下一阶段
3. 关卡旁标的 `[卡名]` 是库里对应的方法论卡，点进去看深度内容
4. 每个关卡都问自己："这关的关键点我做了吗？" 没做 = 后面必然返工/不稳定

## 全景：7 大阶段 × 每关关键点

### 阶段 1：接客户 / 需求澄清
> 目标：搞清楚"他到底要解决什么问题"，不急着讲技术
> FDE 视角：阶段1「找对问题」

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 1.1 需求诊断 | 客户说"我要AI客服"→ 真问题是"客服成本高/响应慢/流失"？用小白问题问出真需求 | `M-FDE-001 第一性原理`、`requirement-clarifier` |
| 1.2 范围界定 | 做什么/不做什么 白纸黑字；防止范围膨胀 | `POC-001 POC与MVP验证` |
| 1.3 报价与档位 | 启航包/工作站/近企业 三档报价；按结果付费也是选项 | `决策卡 STARTER-001/ENTERPRISE-001/RESULT-001` |
| 1.4 合规初判 | 客户行业有无监管（医疗/金融/跨境）；数据能不能出域 | `COMP-001 合规与法律` |

**这阶段最常见的坑**：不诊断就开干 → 做出来不是客户要的（你亲历的教训，需求1阶段没补）

---

### 阶段 2：技术选型 / 框架设计
> 目标：一开始就把框架做对，别等 MVP 跑通发现不稳
> FDE 视角：阶段1-2 衔接（数据审计）

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 2.1 数据摸底 | 客户数据在哪/多脏/能不能用（Medallion: raw→clean→ready） | FDE 书的"阶段0 数据审计" |
| 2.2 架构选型 | 自研 vs 开源 vs 云服务 vs 供应商；用「能不能跑通核心链路/长期成本/可控性/依赖风险」四维评估 | `B技术选型评估` |
| 2.3 存储选型 | 关系型/文档/向量 按数据模型选，不一刀切 | `H数据库选型` |
| 2.4 AI 能力选型 | 用哪个模型/要不要 RAG/多 Agent 还是单 Agent | `K AI Gateway`、`K多Agent编排` |
| 2.5 架构决策记录 | 为什么选这个方案 写下来（ADR），团队可追溯 | `AR-001 架构决策` |

**关键**：这一阶段是"框架从第一天就对"的兑现处。设计时想清楚 3 个月后要不要重构，而不是 3 周后

---

### 阶段 3：MVP / 试点
> 目标：最小投入证明"这条路能通/客户愿意用"
> FDE 视角：阶段2「赢得客户」（试点）

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 3.1 最小闭环 | 只做核心链路（输入→AI→输出→反馈），砍掉装饰 | `POC-001` |
| 3.2 幂等设计 | 同一个操作重复执行 = 只生效一次（用户连点/重试/重复回调 不重复扣费不重复发） | `C幂等 Idempotency` |
| 3.3 密钥管理 | API Key/密码不写死代码，集中托管+轮换 | `E密钥管理` |
| 3.4 数据脱敏 | PII 分级：无PII直接进/有PII脱敏后进/凭据绝不出 | `E PII分级与脱敏` |
| 3.5 试点验收 | 定成功标准（如准确率/时效/用户愿用），跑通才算过 | `EVAL-001 效果评估` |

**坑**：MVP 也要有幂等/密钥/脱敏，不是"先跑通再说"——你亲历的"MVP 很容易跑通但极不稳定"，多数就是跳过了 3.2/3.3/3.4

---

### 阶段 4：交付部署 / 上线
> 目标：让客户真正用起来，不是演示完就结束
> FDE 视角：阶段3「激活部署」

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 4.1 可观测性 | 日志+指标+追踪 三件套，出问题能定位 | `F可观测性` |
| 4.2 重试与熔断 | 临时故障自动重试（有退避）；下游挂了主动短路不雪崩 | `C重试 Retry`、`C熔断` |
| 4.3 限流与防滥用 | 单位时间用量设上限，防刷防薅 | `C限流` |
| 4.4 审计日志 | 谁/何时/对什么/做了什么/结果 不可篡改记录（合规+追责） | `E审计日志` |
| 4.5 灰度发布 | 新版本小流量放量，出事能回滚 | `F灰度发布 Canary` |
| 4.6 备份与回滚 | 定期快照+灾难恢复；发版可快速回上一版 | `F备份恢复`、`F应用回滚`、`I数据回滚` |

**坑**：直接全量上线没灰度 → 出问题影响所有用户；没审计 → 出事无法追责（客户要求合规时直接卡死）

---

### 阶段 5：质量保障 / 持续稳定
> FDE 视角：横切 FDE 阶段3-5（可观测/评测/迭代——质量不是某一段的事，是全程的底线）
> 目标：上线后长期稳定，出问题快速发现修复
> 对应需求2（审计 SOP）

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 5.1 测试体系 | 单元/契约/E2E 三层；测了才算数（禁假绿） | `J单元测试`、`J契约测试`、`JE2E测试` |
| 5.2 AI 质量评估 | RAG 召回率/忠实度；幻觉护栏；模型版本可回滚 | `KRAG质量评估`、`K幻觉与安全护栏`、`K模型版本与回滚` |
| 5.3 审计找 bug | 三审流水线：dsh结构 → OpenClaw安全 → Hermes总审；每次落报告 | `01_审核标准`、`a1四关清单` |
| 5.4 成本可观测 | Token 花费/API 调用量 实时可见，不失控 | `KToken成本可观测` |

**坑**：自测全绿 ≠ 真没问题（负向测试要做）；测试收集失败 ≠ 测试存在

---

### 阶段 6：运营 / 续约 / 客户成功
> 目标：客户持续用、持续付费、愿意转介绍
> FDE 视角：阶段4「守住续约」

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 6.1 使用监控 | 客户真的在用吗？活跃度/调用量/卡在哪 | `EVAL-002 高级效果评估` |
| 6.2 价值证明 | 帮客户省了多少/赚了多少，用数据说话（续约谈判的底气） | `决策卡 RESULT-001` |
| 6.3 客户成功机制 | 定期回访/新需求挖掘/培训，不是交付完消失 | `CJ-001 客户旅程` |

---

### 阶段 7：复盘沉淀 / 规模化
> 目标：每个项目都长经验，下一个不重踩坑；从1个客户复制到多个
> FDE 视角：阶段5-6「扩收/规模化」

| 关卡 | 关键点 | 对应卡/工具 |
|------|--------|------------|
| 7.1 项目复盘 | 结果/过程/坑归类/沉淀 四问；每次做完复盘10分钟 | `07_项目复盘清单` |
| 7.2 经验回填 | 坑 → 复盘区；成功 → 方法论"我们的实战"栏；不散在会话里 | `复盘区/` |
| 7.3 反模式沉淀 | 把踩过的坑变成"下次一眼看出问题"的清单 | `06_接客户前自问清单` |
| 7.4 产品化复制 | 把一个项目做成可复用的模板/决策卡，接下一个客户直接用 | `决策卡库` |
