# Part A · Q1：交付载体全景

## A.0 全文立场（先说清，再展开）

企业 AI 应用的"交付载体"按控制权 / 部署位置 / 用户触达方式，**业界已收敛到 7 种主流形态**。这 7 种不是互相替代关系，而是**沿两条正交轴展开**：
- 轴 1（谁持有代码运行权）：**我们持有 ↔ 客户持有**（多租户共享 ↔ 单租户专属）
- 轴 2（用户在什么环境里使用）：**浏览器 SaaS ↔ 系统进程 ↔ 浏览器内插件 ↔ 系统原生客户端 ↔ 第三方应用内嵌**

把这两条轴的格子填上，就得到下面 7 种主流形态。*判断：这两条轴是从 HP/Herdoku/Meta-Intelligence 等多家资料交叉抽取得到的，并非任何单一框架的官方表述*。

来源（综合）：
- https://www.hp.com/us-en/shop/tech-takes/ai-services-business-guide —— HP AI 服务模型盘点（SaaS/PaaS/Custom）
- https://www.meta-intelligence.tech/insight-cto-ai-agent-architecture —— Meta-Intelligence CTO 决策指南（自建/SaaS/混合）
- https://www.linkedin.com/pulse/saas-doomed-how-ai-agents-could-redefine-enterprise-ajay-pancholi-9lrie —— LinkedIn SaaS vs Agent 对比
- https://mgrowtech.com/ai-platform-as-a-service-simplifying-enterprise-adoption —— AI PaaS / SaaS / On-Premise 成本对比

## A.1 七种主流交付载体形态

### A.1.1 形态① 托管 SaaS / 多租户云服务

**一句话定义**：服务商拥有并运维一套云上应用，多个客户共享同一份代码与同一套基础设施，按订阅/用量付费。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  Web / Mobile / API 客户端（按品牌计费）       │
├──────────────────────────────────────────────┤
│  网关层：AuthN/AuthZ、限流、租户路由          │
├──────────────────────────────────────────────┤
│  应用层：业务服务 + AI 编排（按租户隔离上下文） │
├──────────────────────────────────────────────┤
│  数据层：共池 DB + 行级/列级租户隔离           │
├──────────────────────────────────────────────┤
│  模型层：调用公有 LLM API 或自托管推理集群     │
├──────────────────────────────────────────────┤
│  基础设施：公有云（AWS/Azure/阿里云/腾讯云）   │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：上线最快（数日）、运维摊薄、持续迭代天然支持
- ❌ **劣势**：定制能力有限、数据出域、租户数据混池带来合规风险
- 💰 **成本结构**：订阅费 + 按量 API。来源 mGrowTech 数据：AI SaaS 年费 30k–100k USD；AI PaaS 30k–300k USD；On-Premise 初次 500k–1M USD
- 🔒 **数据安全**：依赖服务商 SOC2/ISO27001；公有云区域要明确
- 🔧 **更新维护**：服务商全包，零运维

**代表案例 / 开源**：ChatGPT Team/Enterprise、Notion AI、飞书智能伙伴、销售 Salesforce Einstein、阿里通义/字节豆包的企业版、Coze 商业版。

**适合**：中小企业 / 通用知识工作 / 标准 SaaS 流程嵌入 / 数据合规要求不严 / 想"先用起来再说"。

**为什么**：客户不需要懂模型，订阅即用；服务商把通用能力做到 80 分以下几乎不可能失败。

---

### A.1.2 形态② 容器化私有部署（Docker Compose / K8s）

**一句话定义**：服务商把整套应用打成镜像，由客户在自己的服务器/私有云上运行，单租户专属。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  客户端（与 SaaS 一致，但域名指向客户内部）    │
├──────────────────────────────────────────────┤
│  反向代理（Nginx/Traefik）+ Ingress            │
├──────────────────────────────────────────────┤
│  业务容器：API / Worker / RAG / Agent          │
├──────────────────────────────────────────────┤
│  数据容器：PostgreSQL / Vector DB / Redis      │
├──────────────────────────────────────────────┤
│  模型层：可选 - 调用外部 API 或本地 vLLM/Ollama│
├──────────────────────────────────────────────┤
│  基础设施：客户机房 / 私有云（K8s 集群/VM）     │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：数据不出域、可深度定制、一次部署长期可控
- ❌ **劣势**：客户要承担运维、升级要重新打镜像 + 灰度
- 💰 **成本结构**：一次性买断（容器授权 + 实施费）+ 年度维护（约开发成本 15–25%，来源 HP）
- 🔒 **数据安全**：天然合规友好，数据 100% 在客户网内
- 🔧 **更新维护**：双方共担；服务商发版 → 客户 IT 升级

**代表案例 / 开源**：Dify（开源 LLM 平台，star 99k+）、FastGPT、Qdrant、AnythingLLM、Open WebUI + Ollama、ChatGLM/DeepSeek 的本地一体机（联想/浪潮）。来源 https://developer.volcengine.com/articles/7587307778956673043 与 https://blog.csdn.net/m0_65555479/article/details/149026527

**适合**：金融/医疗/政府/制造业（核心业务）、数据敏感行业、有 IT 运维团队的中型企业。

**为什么**：当合规明确要求"数据不出网"，或客户业务流程重度定制到 SaaS 模板撑不住时，私有部署是唯一选项。

---

### A.1.3 形态③ 客户端本地部署（桌面 / 终端 App）

**一句话定义**：应用直接装在客户员工个人电脑或工位机上，数据与推理都在本机。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  GUI（Tauri / Electron / 原生）                │
├──────────────────────────────────────────────┤
│  本地业务逻辑（Rust/Node/Python）             │
├──────────────────────────────────────────────┤
│  本地数据（SQLite / LanceDB / 文件）           │
├──────────────────────────────────────────────┤
│  本地推理运行时（llama.cpp / Ollama / Core ML）│
├──────────────────────────────────────────────┤
│  操作系统（macOS / Windows / Linux）           │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：离线可用、隐私最强（数据不出本机）、不依赖云
- ❌ **劣势**：性能受本机硬件限制、跨设备同步难、升级要全客户端推送
- 💰 **成本结构**：许可证 + 一次性集成；硬件成本由客户承担
- 🔒 **数据安全**：天然最强（端侧本地）
- 🔧 **更新维护**：难。需要 OTA + 多端一致性管理

**代表案例 / 开源**：LM Studio、GPT4All、ChatBox、Ollama Desktop、本地笔记 AI 助手（思源/Logseq）、各类 Mac 上的 AI 菜单栏小工具。

**适合**：律师/医生个人助手、调研/咨询行业、需要脱网工作的现场岗位、对云有强不信任的客户。

**为什么**：当数据出本机即违反保密义务、或工作场景在无网环境（出海/工厂/差旅），只能走本地。

### A.1.4 形态④ 智能体 + 网页（Agent + Web App 混合）

**一句话定义**：把"智能体编排层"做成核心，把"Web 界面"做成用户触点，二者解耦、可独立升级。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  Web UI（聊天/审批/看板/Side Panel）           │
├──────────────────────────────────────────────┤
│  LLM 编排层：LangChain / Dify / Coze / AutoGen │
├──────────────────────────────────────────────┤
│  工具/插件层：MCP 协议、Function Calling 工具  │
├──────────────────────────────────────────────┤
│  知识层：RAG 检索（向量库 + 文档库）           │
├──────────────────────────────────────────────┤
│  后端业务 API（被 Agent 当作工具调用）         │
├──────────────────────────────────────────────┤
│  模型推理：公有 API 或自托管（vLLM/SGLang）   │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：能跑复杂多步任务（Agent）、UI 不必长成传统 CRUD、低代码搭流程
- ❌ **劣势**：智能体幻觉/越权风险（OWASP LLM06 过度自主）、调试链路复杂
- 💰 **成本结构**：平台月费 + 按 token 计费 + 调用链监控
- 🔒 **数据安全**：取决于部署位置，可 SaaS 也可私有
- 🔧 **更新维护**：编排层迭代很快，需要持续跟进

**代表案例 / 开源**：
- 低代码：Coze（字节）、Dify（开源 ~99k star）、FastGPT
- 代码框架：LangChain（~108k star）、LlamaIndex（~42k star）、Semantic Kernel（微软企业级）
- 多 Agent：AutoGen（微软，~45k star）、CrewAI（~32k star）
- 协议：MCP（Model Context Protocol，Anthropic 推）、A2A（Agent-to-Agent）

来源 https://developer.volcengine.com/articles/7587307778956673043 与 https://m.toutiao.com/a7566812299286118962/

**适合**：需要"流程自动化 + AI 决策"的场景（RAG 问答、客服分派、报告生成、Agent 工具调用）；是 2025 年中小企业 AI 落地最主流的形态。

**为什么**：单纯 SaaS 太死、纯私有部署太重，Agent+Web 折中：用平台搭骨架，用 Agent 解决流程长尾。

### A.1.5 形态⑤ 嵌入式 / API 形态（BYO-LLM / 仅卖能力）

**一句话定义**：不交付完整应用，只交付**模型能力 API、Prompt 库、向量索引、Agent SDK**，由客户嵌入到他们已有的系统里。

**架构分层（典型）**：
```
客户自有应用
    │
    ├─→ 调用 我们提供的 API（按 token / 请求数）
    │      ├─ Embedding 端点
    │      ├─ Completion 端点
    │      ├─ RAG 查询端点
    │      └─ Agent 工作流端点
    │
    └─→ 数据与状态留在客户侧（按合同隔离）
```

**特点对照**：
- ✅ **优势**：与客户系统耦合最深、复用客户已有 UI / 权限 / 数据
- ❌ **劣势**：看不到终端用户、变现依赖客户调用量、议价能力弱
- 💰 **成本结构**：按调用量计费（典型 $0.001–$0.06 / 1k tokens，看模型）
- 🔒 **数据安全**：双方约定，常见做法是 prompt 不留存、日志脱敏
- 🔧 **更新维护**：纯接口对接，升级对客户透明

**代表案例 / 开源**：OpenAI API、Anthropic API、Mistral API、阿里百炼、火山方舟；以及 vLLM / SGLang / TGI 这类自托管推理框架作为我们卖给客户的"推理 API"。来源 https://docs.clore.ai/guides/comparisons/llm-serving-comparison

**适合**：有研发能力的客户做集成、SaaS 厂商做 AI 增强、模型层中间商。

**为什么**：当客户已经有完整产品，我们只补一块能力（"AI 模块"），没必要整套交付。

### A.1.6 形态⑥ 浏览器扩展 / 插件（Manifest V3）

**一句话定义**：以 Chrome / Edge / Firefox 扩展形式存在，注入到客户日常浏览的网页（飞书/企微/Salesforce/邮箱），在用户当前页面提供 AI 辅助。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  Browser Tab（客户在用的网页）                 │
│    └─ Content Script：注入 UI / 抓取 DOM      │
├──────────────────────────────────────────────┤
│  Background Service Worker（MV3 强制）       │
│    ├─ 跨标签页消息路由（chrome.tabs）         │
│    ├─ 状态/会话管理（chrome.storage）         │
│    └─ 代理到外部 API                           │
├──────────────────────────────────────────────┤
│  权限范围：最小化（activeTab/scripting/storage）│
├──────────────────────────────────────────────┤
│  后端 API（MCP 服务器 / SaaS 后端）            │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：零迁移成本、"就在用户工作流里"、单页玻璃效应强（来源：dev.to/kiran_ravi Manifest V3 文章）
- ❌ **劣势**：受 MV3 限制（不能持久 background pages）、跨站权限收紧、企业内网部署要走 Group Policy / 私有商店
- 💰 **成本结构**：开发费 + 上架费 + 企业 GPO 部署费
- 🔒 **数据安全**：扩展本身是攻击面，需要沙箱、最小权限、来源审计
- 🔧 **更新维护**：通过 Chrome Web Store / 微软 Edge Add-ons / 企业策略下发

**代表案例 / 开源**：阿里 page-agent（已包成 MV3 扩展，参考 meshworld 文章）、各种 AI 客服 Copilot、LinkedIn 销售自动化、Notion Web Clipper 类 AI 版。

**适合**：客服/销售/HR 在 SaaS 里需要边操作边让 AI 帮忙（写作、改邮件、抓数据）的"嵌入工作流"场景。

**为什么**：用户无需切换工作流 → 采用率最高；但要做企业分发，需要解决 MV3 限制与跨浏览器兼容。

### A.1.7 形态⑦ 智能硬件 / 一体机 / 行业终端

**一句话定义**：把 AI 应用 + 模型 + 必要算力全部打包进一台物理设备（工控机 / 一体机 / 行业终端），部署到客户物理场景。

**架构分层（典型）**：
```
┌──────────────────────────────────────────────┐
│  行业外设：摄像头/麦克风/工控 PLC/医疗仪器    │
├──────────────────────────────────────────────┤
│  边缘推理：本地 GPU / NPU（昇腾/寒武纪/Orin） │
├──────────────────────────────────────────────┤
│  嵌入式应用：Qt / Web (内嵌 Chromium)         │
├──────────────────────────────────────────────┤
│  本地向量库 + 小模型（量化到 INT4）            │
├──────────────────────────────────────────────┤
│  可选联网模块（4G/Wi-Fi）同步状态             │
└──────────────────────────────────────────────┘
```

**特点对照**：
- ✅ **优势**：开箱即用、断网可用、硬件绑定形成差异化壁垒
- ❌ **劣势**：成本高、迭代慢、备件库存压力大
- 💰 **成本结构**：硬件 BOM + 软件授权 + 现场实施
- 🔒 **数据安全**：最强（数据不上网）
- 🔧 **更新维护**：远程 OTA + 现场工程师

**代表案例 / 开源**：联想/浪潮的 DeepSeek 一体机、Salesforce AI 摄像头、NVIDIA Jetson 边缘 AI 盒子、商汤/旷视的边缘盒子。

**适合**：工厂车间（质检/AGV）、医院（影像辅助）、零售门店（智能货柜）、政府/军工（涉密场景）。

**为什么**：当"延迟 < 100ms 必须本地"或"物理位置决定了必须硬件化"，这是唯一选择。

## A.2 七种载体一张总图

| # | 载体形态 | 控制权 | 数据位置 | 上线速度 | 定制深度 | 合规友好度 | 单位客户成本 | 典型客户 |
|---|---|---|---|---|---|---|---|---|
| ① | 托管 SaaS | 我们 | 公有云 | 日 | 低 | 低-中 | 低 | 中小企业/通用 |
| ② | 容器化私有部署 | 客户 | 客户私有云 | 周-月 | 高 | 高 | 中-高 | 金融/医疗/制造 |
| ③ | 客户端本地部署 | 客户 | 个人电脑 | 天 | 中 | 极高 | 中 | 个人专家/律师/调研 |
| ④ | Agent + Web | 我们或客户 | 视部署 | 周 | 中-高 | 中-高 | 中 | 中小企业（首选） |
| ⑤ | 嵌入式 API | 我们 | 客户系统 | 天 | 取决于客户 | 取决于合同 | 低-中 | 已有 IT 的客户 |
| ⑥ | 浏览器扩展 | 我们或客户 | 浏览器 + 云 | 周 | 中 | 中 | 低 | 客服/销售/HR |
| ⑦ | 智能硬件 | 客户 | 设备本地 | 月+ | 高 | 极高 | 高 | 工厂/医疗/政府 |

> 表格说明：成本一列是相对量级，不是绝对报价；同一形态在不同规模客户下差异巨大。

## A.3 选型决策树（可直接拍板）

```
Q1: 客户愿意把数据放在公有云吗？
    ├── 不愿意（合规/强敏感）
    │   ├── Q1a: 业务必须在现场设备上跑吗（延迟/断网）？
    │   │   ├── 是 → ⑦ 智能硬件 / 一体机
    │   │   └── 否 → Q1b: 客户有 IT 运维团队吗？
    │   │       ├── 有 → ② 容器化私有部署
    │   │       └── 没有 → ③ 客户端本地部署（员工个人设备级）
    │   └──
    └── 愿意
        ├── Q2: 客户有现成系统需要 AI 增强吗？
        │   ├── 有 + 有研发 → ⑤ 嵌入式 API / SDK
        │   ├── 有 + 没有研发 → ⑥ 浏览器扩展（注入到客户现有 SaaS）
        │   └── 没有 / 想做新业务
        │       ├── Q3: 业务是"流程长尾"（多步推理/工具调用）吗？
        │       │   ├── 是 → ④ Agent + Web（首选 2025 中小企业）
        │       │   └── 否（流程标准化、CRUD）→ ① 托管 SaaS
        │       └──
        └──
```

### A.3.1 速查表（条件 → 载体）

| 条件组合 | 推荐载体 | 关键理由 |
|---|---|---|
| 数据敏感 + 有 IT + 重流程 | ② 容器化私有部署 | 合规 + 长期可控 |
| 数据敏感 + 无 IT + 个人使用 | ③ 客户端本地部署 | 端侧隐私最强 |
| 数据敏感 + 必须现场跑 | ⑦ 智能硬件 | 离线 + 低延迟 |
| 数据可上云 + 想最早上线 | ① 托管 SaaS | 标准流程、订阅即用 |
| 数据可上云 + 流程长尾/多步推理 | ④ Agent + Web | 2025 事实主流 |
| 客户已有系统 + 有研发 | ⑤ 嵌入式 API | 卖能力不卖应用 |
| 客户用 SaaS 办公 + 想提效 | ⑥ 浏览器扩展 | 零迁移、最快采用 |
| 不确定 / 想先验证 | ④ Agent + Web（MVP 优先） | 上可接 SaaS，下可沉私有 |

## A.4 我们业务的借鉴（按档位适配）

> 我们的客户是**中小企业**，档位 STARTER（¥3-8k）→ AR（增长型，¥8-30k）→ ENTERPRISE（¥80-300k）。MIGRATE 是迁移改造另算。

| 档位 | 默认推荐载体 | 报价里怎么体现 | 备选升级路径 |
|---|---|---|---|
| **STARTER ¥3-8k** | ④ Agent + Web（云上）+ Coze/Dify | 软件订阅年费 + 实施一次性 | 试用 1 个月后可转 ① SaaS 月付 |
| **增长型 AR ¥8-30k** | ④ Agent + Web（云上）+ 私有知识库 RAG | 实施费 + 第一年订阅 + 持续运营费 | 数据敏感时下沉 ② 容器化 |
| **ENTERPRISE ¥80-300k** | ② 容器化私有部署 + ④ Agent + Web 内核 | 一次性部署 + 实施 + 现场运维 | 核心业务可能叠 ⑦ 一体机 |
| **MIGRATE（迁移）** | 视现有形态 → ② 或 ④ 或 ⑤ | 迁移咨询 + 灰度切换 + 双轨期支持 | 视客户遗留系统决定 |
| **加购 / 共生** | ⑥ 浏览器扩展（员工提效）+ ⑤ API（系统集成） | 即插即用扩展授权 + API 调用包 | 独立计费，不影响主载体 |

### A.4.1 报价里"怎么体现"的展开说明

**STARTER（¥3-8k）**：
- 单点场景：小红书文案助手 / 内部知识问答 / 销售跟进生成
- 默认载体：Agent + Web（Coze 商业版或 Dify 云版均可）
- 报价结构：¥3k 实施 + ¥5k/年 订阅
- 客户买的不是"一套软件"，是"一个能用的 AI 工作流 + 持续迭代"
- *判断*：STARTER 不推荐容器化部署，运维成本压不下来

**AR / 增长型（¥8-30k）**：
- 多场景串联：知识库 + 工单分派 + 数据看板
- 默认载体：Dify/Coze 自托管版（云上）+ RAG 知识库
- 报价结构：¥15k 实施 + ¥10k/年 维护 + ¥5k/年模型费
- 客户买的是"业务流改造 + 数据资产沉淀"
- *判断*：AR 阶段要开始交付**质量门禁报告**（评测集 + 红队测试），不能只交付"能跑"

**ENTERPRISE（¥80-300k）**：
- 核心业务嵌入：风控、客服、生产排程、ERP/CRM 增强
- 默认载体：容器化私有部署 + 我们交付的 Agent 内核 + 客户 IT 共维
- 报价结构：¥150k 一次性（含部署、集成、3 个月陪跑）+ ¥100k/年 运维 + ¥50k/年 升级
- 客户买的是"可控 + 合规 + 长期资产"
- *判断*：ENTERPRISE 必须配套 OWASP LLM Top 10 + 关卡门禁（Gate Review）+ SLA

### A.4.2 跨档位共用的"加购"项

1. **数据治理加购**：把客户数据接入 + 标注 + 评测，做成"金标数据集 v1"
2. **红队评测加购**：按 OWASP LLM Top 10 跑对抗测试，输出"风险清单 + 修复建议"
3. **运营陪跑加购**：上线后 3-6 个月驻场或线上陪跑，按"产出效果（GMV/节省工时/采纳率）"结算
4. **迁移加购**：帮客户把已有 SaaS/老系统迁到新载体，按数据量 + 系统数计费

## B.2 工程全流程 MECE 12 主阶段（Layer 2，横向时间轴）

按时间先后拆 12 个阶段，每个阶段给：输入、核心活动、产出物、检查点（Gate）、常见坑、对应的零件。

### 阶段 1 · 需求澄清（Discover）

- **输入**：客户愿景 / 痛点描述 / 现有流程
- **核心活动**：现场访谈、流程观察、问题清单、价值假设、ROI 估算
- **产出物**：需求澄清文档（含「做不做」判断）、用户故事池 v0、成功指标 KPI v0
- **检查点（Gate 1）**：业务方签字 + 价值假设可证伪
- **常见坑**：把"老板想要 AI"当需求；忽略隐性流程（实际跑的不是写下来的）
- **零件**：访谈模板、流程鱼骨图、价值假设画布
- **关联**：DDD 的 Event Storming（领域事件抽取）

### 阶段 2 · 方案设计（Design）

- **输入**：需求澄清文档、KPI
- **核心活动**：技术选型、架构图、风险登记、依赖评估
- **产出物**：技术方案 v1、架构图、ADR（Architecture Decision Record）、风险登记册
- **检查点（Gate 2）**：方案评审通过、关键 ADR 记录在案
- **常见坑**：过早选型；忽略模型上下文窗口/推理成本
- **零件**：C4 图、ADR 模板、技术雷达（已用/试用/评估/避免）
- **关联**：DDD 限界上下文划分、12-Factor 第 I–III 条（代码库/依赖/配置）

### 阶段 3 · 架构选型 + 载体决策（Architect）

- **输入**：技术方案 v1、数据敏感度、合规要求
- **核心活动**：选载体（参考 Part A）、画部署图、确定数据流、确定模型来源
- **产出物**：载体决策书（★ Part A 的产出）、部署图、数据流图、模型来源清单
- **检查点（Gate 3）**：载体决策签字、合规预审
- **常见坑**：选了"政治正确"的载体而不是"业务合理"的载体
- **零件**：A.3 决策树、合规清单
- **关联**：Part A 全景；OWASP LLM01/06 的边界设计

### 阶段 4 · 数据准备（Data）

- **输入**：客户数据源、数据字典、隐私分级
- **核心活动**：数据接入、清洗、标注、划分（金标准）、向量索引
- **产出物**：数据集 v1（金标 + 训练 + 验证 + 测试）、数据卡（Data Card）、向量库 v1
- **检查点（Gate 4）**：数据质量报告 + 隐私合规审查
- **常见坑**：训练/测试数据泄漏；PII 未脱敏；分布偏差未识别
- **零件**：DVC/LakeFS、数据标注工具、Great Expectations
- **关联**：CRISP-ML(Q) 的 Data Preparation；OWASP LLM02/04/08

### 阶段 5 · 评估体系搭建（Eval）

- **输入**：KPI v0、数据集 v1
- **核心活动**：定义评测维度（准确性/相关性/安全/时延/成本）、建评测集、建基线
- **产出物**：评测集 v1、评测脚本、基线报告、Model Card 模板
- **检查点（Gate 5）**：评测维度 ≥ 5 项、基线分数记录
- **常见坑**：评测集太"干净"（脱离真实分布）；只用单维度
- **零件**：评测框架（Promptfoo / Garak / 自建）、人评界面
- **关联**：MLOps Level 0→1；OWASP LLM09（错误信息）

### 阶段 6 · 开发实现（Build）

- **输入**：架构图、API 契约、Prompt 草稿
- **核心活动**：编码、Prompt 工程、工具/插件开发、RAG 流水线、Agent 工作流
- **产出物**：可运行 MVP、单元测试、Prompt 版本库、API 契约
- **检查点（持续集成）**：CI 跑通（lint + 单测 + 集成测试）
- **常见坑**：Prompt 与代码混在一起没有版本；硬编码 secret
- **零件**：Git、Pre-commit、CI（GitHub Actions）、LangSmith/LangFuse 观测
- **关联**：12-Factor 第 IV–VIII 条；OWASP LLM03/05/06

### 阶段 7 · 测试（Test）

- **输入**：MVP、评测集、需求文档
- **核心活动**：功能测试、安全测试、性能测试、模型评测、红队测试
- **产出物**：测试报告、红队报告、性能基线、缺陷清单
- **检查点（Gate 6）**：通过 = 所有 critical bug 关闭 + 评测分数 ≥ 基线 + 红队无 P0
- **常见坑**：模型行为测试靠"看一眼"；不测对抗输入
- **零件**：单元/集成/E2E 框架、Promptfoo、Garak（LLM 安全）、k6/Locust（性能）
- **关联**：OWASP LLM Top 10 全量；MLOps Level 2

### 阶段 8 · 部署上线（Deploy）

- **输入**：通过测试的版本、运维 Runbook
- **核心活动**：环境准备、灰度发布、回滚预案、监控接入、变更审批
- **产出物**：生产环境 v1、Runbook、监控仪表盘、变更记录
- **检查点（Gate 7）**：上线 GO/NO-GO 决策（4 票制：技术/QA/产品/运维）
- **常见坑**：没有回滚路径；监控盲区；首次发布直接 100% 流量
- **零件**：CI/CD、IaC（Terraform/Pulumi）、蓝绿/金丝雀、Feature Flag
- **关联**：12-Factor 第 IX–XI 条（可处置/开发生产对等/日志）

### 阶段 9 · 验收交付（Accept）

- **输入**：上线版本、验收清单
- **核心活动**：UAT、用户培训、文档交付、资产移交
- **产出物**：验收报告、用户手册、运维手册、培训记录、源码/镜像 + 凭据清单
- **检查点（Gate 8）**：客户方签字 + 资产完整移交
- **常见坑**：文档与代码脱节；凭据未轮换
- **零件**：验收清单模板、文档生成（Docusaurus/MkDocs）、凭据管理（Vault）
- **关联**：12-Factor 第 XII 条（管理进程）

### 阶段 10 · 运维监控（Operate）

- **输入**：生产环境
- **核心活动**：值班、SLA 监控、事件响应、变更、容量规划
- **产出物**：值班记录、SLA 报告、事件复盘、变更单
- **检查点（持续）**：SLA 达成率 ≥ 99%（按合同）
- **常见坑**：只监控 up/down，不监控 token 成本/质量漂移
- **零件**：Prometheus/Grafana、ELK/Loki、Sentry、PagerDuty、LLM 专用监控（LangFuse/Helicone）
- **关联**：MLOps Level 3–4；OWASP LLM10（资源消耗）

### 阶段 11 · 迭代优化（Iterate）

- **输入**：运维数据、用户反馈、评测结果
- **核心活动**：A/B 测试、漂移检测、模型/Agent 升级、RAG 优化、Prompt 迭代
- **产出物**：迭代 Roadmap、实验报告、新版本上线
- **检查点（持续）**：每迭代一次 Gate Review
- **常见坑**：只看用户量不看质量；实验没对照
- **零件**：A/B 平台、特征存储、MLflow、AB 实验记录
- **关联**：MLOps Level 4；CRISP-ML(Q) 的 Monitoring → Model Development 闭环

### 阶段 12 · 退役下线（Retire）

- **输入**：业务下线决策、合规要求
- **核心活动**：数据归档、模型下线、用户通知、依赖解耦
- **产出物**：退役报告、数据归档、模型下架记录、合规证明
- **检查点（Gate 9）**：数据/模型/凭据 100% 清理 + 客户签字
- **常见坑**：只关服务不停数据；老数据继续产生成本
- **零件**：数据保留策略、删除脚本、合规审计
- **关联**：GDPR / 个保法"被遗忘权"

## B.3 角色 × 产出物 × 质量门禁（Layer 1，纵向质量纵切）

> 这是把每个阶段都"竖着切一刀"看到的：谁在做、产出什么、什么时候算过关。

### B.3.1 七大角色

| **运维/SRE** | 部署、监控、值班 | 8, 10, 12 |

| 产出物 | 模板要求 | 阶段 |
|---|---|---|

| ADR 架构决策记录 | 背景/选项/决定/后果 | 2 |

### B.3.3 质量门禁（Gate）—— 9 个不可跳过的关卡

| Gate | 触发时机 | 必含条款（Must-Meet） | 裁决人 |
|---|---|---|---|
| G1 需求门 | 阶段 1 末 | 价值假设可证伪、KPI 可量化、客户签字 | 业务方 + PM |
| G2 方案门 | 阶段 2 末 | ADR 记录、C4 图、技术风险登记 | 架构师 + 技术负责人 |
| G3 载体门 | 阶段 3 末 | 决策树路径明确、合规预审通过 | 架构师 + 合规 |
| G4 数据门 | 阶段 4 末 | 数据卡、PII 脱敏、训练测试无泄漏 | 数据负责人 + 合规 |
| G5 评测门 | 阶段 5 末 | 评测集 ≥ 5 维度、基线分数记录 | AI 负责人 |
| G6 测试门 | 阶段 7 末 | critical bug = 0、评测分数 ≥ 基线、红队无 P0 | QA + 安全 |
| G7 上线门 | 阶段 8 末 | 回滚预案就绪、监控告警就绪、变更审批 | 4 票：技术/QA/产品/运维 |
| G8 验收门 | 阶段 9 末 | UAT 通过、文档齐全、资产移交清单 | 客户 + PM |
| G9 退役门 | 阶段 12 末 | 数据/模型/凭据清理 + 合规证明 | 合规 + 客户 |

> *判断*：这套 9 Gate 是把 Phase-Gate（来源 sinra.dev、geeksforgeeks）原则落到 AI 程序的工程实际。每个 Gate 都是 Go / Conditional-Go / No-Go 三档，而不是 Yes/No。

## B.4 全景地图设计（Layer 3，横向 × 纵向合并）

### B.4.1 地图设计原则（如何做到 MECE）

| 原则 | 怎么落地 |
|---|---|
| **互不重叠** | 横向 12 阶段在时间上严格不重叠；纵向 3 维度（角色/产出物/门禁）在每阶段都有定义 |
| **合起来穷尽** | 横向覆盖 0→N→退役全周期；纵向覆盖"谁做/做什么/何时通过" |
| **可缩放** | 阶段可以折叠（如 MVP 项目只跑到 Gate 7 就交付），门禁可以收紧（如 STARTER 档位只跑 G1/G3/G6/G7） |
| **可比较** | 不同项目 / 不同档位都能映射到同一张地图，差异只在"跑到第几个 Gate" |

### B.4.2 拼接参考（业界成熟模型怎么落到地图里）

| 模型 | 在全景地图里的位置 |
|---|---|
| **SDLC**（Plan/Design/Implement/Test/Deploy/Maintain, 来源 AWS） | 横向 1-10 阶段的主体骨架 |

| **NIST AI RMF / MITRE ATLAS** | 阶段 3-7 的合规与红队框架 |

### B.4.4 AI 程序特有的纵向覆盖（不漏 AI 特有步骤）

普通软件工程的 12 阶段够用，但 AI 程序要再叠三层"AI 特有"切片（普通软件也包含这些，但 AI 更突出）：

| AI 特有切片 | 贯穿阶段 | 关键产出物 |
|---|---|---|
| **数据 / 评测** | 4, 5, 7, 11 | Data Card / Model Card / 评测集 / 漂移报告 |
| **模型 / Agent 安全** | 3, 6, 7, 10 | OWASP LLM Top 10 红队报告 + 安全 Runbook |
| **采用 / 价值闭环** | 1, 9, 10, 11 | KPI 仪表盘 + ROI 报告 + 用户采纳率 |

> *判断*：把"采用 / 价值闭环"单独提出来是 AI 项目区别于普通软件的关键——很多 AI 项目技术上上线了，但用户不用，等于没上。

## B.5 MECE 自检（为什么 12 阶段是 MECE）

| 检查 | 结论 |
|---|---|
| 时间上是否重叠 | ❌ 不重叠（每个阶段有明确输入→输出） |
| 时间上是否有遗漏 | ❌ 无遗漏（覆盖 0→1→N→退役全周期） |
| 角色是否互相补齐 | ❌ 7 角色覆盖业务/技术/数据/安全/合规 |
| 产出物是否分层清晰 | ❌ 每阶段产出物模板独立 |
| 门禁是否覆盖关键决策点 | ❌ 9 Gate 对应"该不该继续花钱" |
| AI 特有步骤是否被吞掉 | ❌ 数据/评测、安全、价值闭环三层纵向切片补齐 |
| 普通软件工程的实践是否被吞掉 | ❌ SDLC + 12-Factor + DDD 已合并进来 |

# 附录：3 个网页还缺的盲区（可超出 A/B）

> Hermes 队长让我额外指出 3 个我没在 A/B 覆盖到、但对网页很有价值的盲区。这些是 *判断*，不是公开资料的"事实"。

### 盲区 1 · "需求 → 方案"自动推导引擎

**现状**：网页有「场景向导」「自由拼装」是"选组合"型，但缺"输入项目基础信息→自动产出架构方案+载体+零件清单+理由"的分析引擎。

**为什么缺**：这是个**真正的"知识工作台"**区别于"备忘录"的关键。现在的网页让人点选，但不让它推理。

**怎么补**：
1. 给客户的项目输入表单（行业/规模/数据敏感度/合规/团队/预算）
2. 表单提交后自动跑 Part A 决策树 → 产出"建议载体 + 理由 + 风险表"
3. 再跑 Part B 全景 → 产出"项目 Roadmap + 必要零件清单 + 关键 Gate 清单"
4. 输出可以是 Markdown / Notion 卡片 / PDF 报告三种形态

**可参考**：
- LangChain / Dify 的 "Solution Builder" 形态
- Vercel "Build your stack" 推荐器
- 12-Factor 衍生出的"Stack Decision Graph"

### 盲区 2 · 真实项目"解剖室"

**现状**：网页有「客户项目复盘」「真实案例库」但是叙述型的。缺"打开一个项目，看清所有零件"的解剖视图。

**为什么缺**：知道"有回滚/幂等/熔断"和看到"这个项目怎么把回滚/幂等/熔断配出来"完全是两回事。

**怎么补**：
1. 选 2-3 个 GitHub 高星企业 AI 项目（如 Dify / FastGPT / Open WebUI / AnythingLLM / LibreChat）
2. 做"剖面图"：
   - 部署架构图（容器/服务/数据流）
   - 关键零件清单（auth/ratelimit/retry/observability/secrets/queue）
   - 每个零件的代码位置（文件/函数）
   - 选这个零件的理由（架构决策记录）
3. 把剖面图按 Part A 七种载体分类，做成"参考骨架"
4. 我们自己接客户时直接拿来当模板

### 盲区 3 · ROI / 价值闭环仪表盘（AI 项目专属）

**现状**：网页有 15 数据体系 / 09 关卡地图，但都是"过程指标"。缺"AI 项目到底帮客户省了多少/赚了多少"的"结果指标"展示。

**为什么缺**：客户买单的是结果，不是"上线了"。如果网页能展示"我们做过的 AI 项目平均 3 个月回本、6 个月 ROI 200%"，获客效率会上一个数量级。

**怎么补**：
1. 给每个客户项目建"价值仪表盘"：
   - 输入：项目目标（如"降低客服 30% 工时"）
   - 过程指标：上线时间、采纳率、活跃用户
   - 结果指标：实际节省工时/GMV 增量/错误率下降
2. 仪表盘数据脱敏后回流到网页"案例库"标签
3. 同时建"反例库"——项目做砸了的也要记（更稀缺）
4. 把 ROI 计算公式做成可复用模板（每个新项目直接套）
