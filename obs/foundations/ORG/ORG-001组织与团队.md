# ORG-001 组织与团队

> ID: ORG-001 | 创建: 2026-09-02 | 状态: ⭐ 正式（v1）
> 起草原模型: minimax/MiniMax-M3 | 任务来源: Hermes M3 队长派单
> 与 FDE-001 关系：FDE 讲「FDE 这个角色的能力栈」，ORG-001 讲「FDE 与其他角色如何组成团队」

## 这个子领域在解决什么问题（一句话）

组织解决的是「人多了之后怎么不互相拖累」——从单兵到小团队到跨职能团队，每次跨越都要重新设计决策权、沟通路径、交接标准，否则效率与人数成反比。

## 核心问题清单

1. **从 1 人到 2 人到 5 人到 20 人，每一跨的关键变化是什么？**
2. **什么时候该招人？什么时候该工具化？** 招人前先问「这件事能不能用脚本完成」
3. **「小团队」和「跨职能团队」的本质区别？** 前者共担目标，后者各有专业但目标耦合
4. **远程异步 vs 现场同步的边界？** GitLab 异步优先 vs Palantir 现场驻场
5. **角色定义不清的代价？** 同一件事两个人都以为对方在做 = 谁都没做
6. **SOP 在团队演化中的角色？** 单兵不需要 SOP，2 人以上就需要 SOP
7. **「客户机部署」作为组织能力是什么？** 不是「远程装机」，是「客户能自助的产品 + 交付方一键接管的能力」
8. **演化过程中的反模式？** 招人过快 / 单一职责 / 拒绝工具化 / 不写 SOP

## 标杆答案

### 来自 GitLab Remote Manifesto（GitLab 是全球最大全远程公司，3000+ 员工）：

> 「**Results not hours**：员工在哪里工作、什么时候工作不重要，重要的是结果。」

> 「**Async-first**：默认所有沟通走异步（文档、Issue、MRC），避免不必要的同步会议。」

> 「**Written culture**：所有重要决策必须写下来（手写笔记不算，必须是公开可访问的文档）。口头承诺 = 不存在。」

> 「**No blame culture**：错误是学习机会，不是追责理由。但必须诚实记录 + 公开复盘。」

> 「**Blameless post-mortems**：故障复盘的唯一规则是对事不对人。一旦复盘与绩效挂钩，人们就会开始修饰失败——而修饰过的失败，毫无教学价值。」——这与 xdash FDE 书第 7 章的「无罪化复盘」完全一致

**理解**：GitLab 的 Remote Manifesto 把远程协作的隐性约束显性化——结果导向 + 异步优先 + 书面文化 + 无责复盘。这套体系对个人项目（如中俄轻舟）和小团队（如 NIFTY + 大辉 M5）同样适用，不只对大公司。

### 来自 Spotify 团队拓扑模型（Squads / Tribes / Chapters / Guilds，2012 年公开）：

> 「**Squad（小队）** —— 一个跨职能小组，负责一个产品/服务的完整生命周期。Squad 是 Spotify 组织的基本单位。」

> 「**Tribe（部落）** —— 多个 Squad 组成，共同服务一个业务领域。Tribes 之间松耦合。」

> 「**Chapter（专业线）** —— 跨 Squad 的同一专业角色集合（如所有 FDE、所有数据科学家）。Chapter 用于专业能力建设和经验共享。」

> 「**Guild（公会）** —— 横切所有 Tribe 的兴趣社区（如所有用 Python 的工程师）。Guild 是轻量级、兴趣驱动。」

> 「**关键约束**：每个 Squad 必须能**独立交付价值**——无需其他 Squad 配合就能上线一个功能。这要求 Squad 内必须包含产品、设计、工程、测试等所有角色。」

**理解**：Spotify 模型解决了「规模化团队 vs 创业团队速度」的矛盾——保持小 Squad 的速度（5-8 人），通过 Tribe / Chapter / Guild 实现规模化协作。对个人项目和小团队的启示：**先做 Squad，再考虑 Tribe**。

### 来自 用户演化路径（我们的真实路径 2026-05 → 2026-09）：

```
单兵阶段（5 月前）→ 小团队 1+1（9 月，大辉 M5）→ 客户机 M1（9 月）+ 远程安装 SOP
```

**关键转折点**：
- **单兵 → 1+1**：能力上限触发「必须有人帮忙」——中俄轻舟跨境选品 + NIFTY 客户机部署同时进行，单兵扛不住
- **1+1 → 跨职能（客户机 + SOP）**：交付能力产品化——不再「交付方懂客户」而是「产品自己懂客户」

**理解**：个人 AI 项目的团队演化不是「公司化」，而是「能力产品化」。M1（测试机）不是「新员工」，是「让客户能自助的产品 + 一键远程接管的能力」。这是「小作坊」到「产品化交付」的关键跨越。

### 来自 xdash FDE 书 第 1 章（双角色模型）：

> 「部署战略师（内部代号'回声'）负责读懂客户的使命、各相关方和采纳路径，前线部署工程师（内部代号'三角洲'）负责技术实现。两人一组，一个诊断，一个建造，缺一不可。」——Palantir 官方分工

> 「FDE 不光要把部署做成功，还背着'让产品变得更成熟'的指标——现场学回来的东西，必须反哺平台。」

**理解**：FDE 的「双角色」是「跨职能小队」的最小版本——读懂业务 + 动手建造。Spotify Squad 的核心思想（独立交付价值）在 Palantir 这里演化成「Echo + Delta」双人组。

### 来自 xdash FDE 书 第 7 章「轮岗培养计划」：

> 「你没法靠招聘建出真正的 FDE 组织，只能养出来。——Vinoo Ganesh（Palantir 轮岗培养计划设计者）」

> 「250 多名工程师经轮岗进入真实部署，校友如今散在 OpenAI、xAI、Anduril 等公司。」

> 「培养的方法则是轮岗：把工程师成批送进真实客户部署，先当用户，再当建造者。」

**理解**：组织能力建设最反直觉的真相——**人才不能招，只能培养**。轮岗 = 「让员工先体验客户，再回来造产品」。这是「内部人才市场」的最佳实践。

### 来自 xdash FDE 书 第 7 章「三级复制杠杆」（与 ORG 强相关）：

> 「一级杠杆：知识复制（打法手册、检查清单）—— 新人上手周期，从一年压到三个月。」
> 「二级杠杆：组件复制（工具与代码）—— 下一支团队的起点不再是零。」
> 「三级杠杆：产品复制（平台能力）—— 从此这个需求，不再需要任何工程师到场。」

**理解**：组织规模化 = 知识 / 组件 / 平台 三层资产化。单兵团队没有这三层；小团队开始沉淀第一层；跨职能团队必须三层齐备。这与 Spotify Squad「独立交付价值」形成镜像。

### 来自 阿尔泰 客户获客 SOP v0.2（13 个 D1 模块 = 组织能力的载体）：

## 我们的实战

### 单兵阶段：1 人搞定全栈（阿尔泰初期，5 月前）

**特征**：
- 1 人 = 需求 + 设计 + 开发 + 测试 + 部署 + 运维 + 销售 + 客服
- 决策时间 = 0（想到就做）
- 沟通成本 = 0（不用解释）
- 能力上限 = 单兵能力上限

**典型一天**（回忆性描述）：
- 早上看客户反馈 → 中午改 bug → 下午写新功能 → 晚上和客户开会
- 决策快但「想到什么做什么」，没有 PRD、没有代码评审、没有测试流程
- 关键风险：**单点失败**——这个人病了/累垮了 = 项目停摆

**单兵阶段的纪律**：
- **写下来**——想到就做的后果是「忘了为什么这么做」。所有决策必须写到 Obsidian / Notion
- **备份**——单兵 = 数据无备份 = 一场硬盘故障 = 项目死
- **工具化**——任何第二次做的动作必须变成脚本/模板
- **不接超出能力上限的项目**——单兵的天花板决定能做什么

**单兵阶段的反模式**：
- 招人过早（招来了不知道干什么）
- 追求完美（单兵做完美 = 永远做不完）
- 拒绝工具化（每次手动 = 永远没时间做下一件事）

### 小团队阶段：王昕 + 大辉 M5（NIFTY 实战）

**特征**：
- 2 人 = 1+1 互补：王昕（AI/产品）+ 大辉 M5（客户机部署/运维）
- 决策时间 = 「两人同意后」才能做
- 沟通成本 = 「关键决策需要开会」
- 能力上限 = 两人互补后的上限

**关键事件**：
- 大辉 M5（Tailscale 100.109.143.55）拿到 NIFTY 交付包
- 离线 12+ 天未实测（暴露：单点客户验证的脆弱性）
- 远程看桌面 30 分钟签约（暴露：远程协同需要 SOP）

**小团队阶段的纪律**：
- **SOP 化**——所有「第一个人做过的事」必须写 SOP，让第二个人能重复
- **角色清晰**——谁负责什么、谁不负责什么，必须明确（否则两人各做一半 = 都不完整）
- **沟通频率**——每天 15 分钟站会足够（异步为主，同步只用于紧急决策）
- **决策权划分**——「两个人都能拍板」= 永远吵架，必须明确「A 领域 A 拍板，B 领域 B 拍板」

**小团队阶段的反模式**：
- 两个人做同一件事（重复劳动 = 浪费）
- 一人主导全部决策（另一个人 = 工具人，留不住）
- 没有 SOP（第二个人离职 = 项目停摆）

### 跨职能阶段：客户机 M1 + 远程安装 SOP（NIFTY + 阿尔泰 的目标态）

**特征**：
- 「团队」不只 = 人 = 人 + 客户机 + SOP + 自动化脚本
- M1 测试机 = 「不是人，但能承担 QA / 回归测试 / 简单部署」
- 远程安装 SOP = 「不是人，但能让客户自助装机」
- 决策权 = 人拍板 + 机器执行 + SOP 标准化

**关键能力**：
- 「一键远程装机」remote_install_sop.sh——客户机故障时，交付方远程重新部署，不需要客户懂技术
- 「修复工具 App」GUI——客户自己能诊断 + 修复（不依赖交付方）
- 「自愈 watchdog」hermes-crash-guard——机器自动处理 9 类常见故障
- 「103 项回归 + delivery 门禁」——代码改动自动化检查

**跨职能阶段的纪律**：
- **能自动化的事绝不用人**——人 = 贵 + 慢 + 易错；机器 = 便宜 + 快 + 一致
- **SOP 是组织能力的载体**——人离职了，SOP 还在；新人来了，SOP 让ta 快速上手
- **决策权下放**——越下层的执行决策，机器越能做；越上层的战略决策，人越要做
- **「团队」包括客户**——客户不是「被服务的对象」，是「协作团队的一员」（FDE-002 第 4 阶段「内部支持者」）

**跨职能阶段的反模式**：
- 招人解决所有问题（应该自动化 + SOP 优先）
- 拒绝工具化（「我的工作不可替代」心态）
- 不写 SOP（「我的经验都在脑子里」心态——人一走 = 项目停）

## 反模式（不该怎么做）

1. **垂直管理（层层汇报）** —— 信息传递链长 = 失真 = 决策慢；扁平化 + 自组织更高效
2. **单一职责（each person does one thing）** —— 每个人只懂自己的一小块 = 无法独立交付价值（Squad 反例）
3. **拒绝工具化（「我的工作不可替代」）** —— AI 时代最大的反模式；能用脚本做的事不用人做
4. **不写 SOP（「经验都在脑子里」）** —— 人走了 = 项目停；SOP 是组织能力的唯一载体
5. **招人过快（招来了不知道干什么）** —— 招人是最后手段，先自动化、再 SOP、最后才招人
6. **角色定义模糊（同一件事两个人都以为对方在做）** —— 谁都没做 = 项目停摆；必须明确 RACI（谁负责、谁批准、谁咨询、谁通知）
7. **追求「公司化」（HR、财务、行政全套）** —— 个人项目 / 小团队不需要「公司架构」，需要「产品化交付」
8. **「沟通」代替「文档」** —— 口头承诺 = 不存在；所有重要决策必须写到公开可访问的文档
9. **(扩展) 把「忙碌」当「产出」** —— 团队成员都忙 = 可能都在做错事；忙 ≠ 价值
10. **(扩展) 工具崇拜（「用 Notion 就好」「用 Slack 就好」）** —— 工具是手段不是目的；先想清楚要解决什么问题，再选工具

## 与其他子领域的关系

- **依赖：FDE-001（角色定义）** —— ORG-001 是 FDE-001 的「团队版」

- **顺序**：单兵 → 小团队 → 跨职能，每一阶段都是前阶段能力成熟后的自然演化
- **冲突**：与「招人解决所有问题」「沟通解决所有问题」的简单思维冲突
- **替代**：无；组织能力是底层能力，不可外包
