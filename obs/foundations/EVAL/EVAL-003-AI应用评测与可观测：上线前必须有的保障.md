## 是什么(用大白话讲)

所谓「AI 应用评测与可观测」,就是**把传统软件工程里那套「测试 + 日志 + 监控」搬进 AI 项目**,但要换一套思路。传统软件是确定性输出(代码怎么写就怎么跑),AI 应用是概率性输出(同一个 prompt,温度参数一改结果就飘);所以传统测试够用,AI 项目要再加三件事:

1. **评测集**(Evaluation Suite)——一组「标准问 + 标准答」,每次改 prompt、改模型、改参数就跑一遍,看分数。相当于 AI 项目的「单元测试 + 回归测试」。
2. **红队 / 漏洞扫描**(Red Team)——故意用「恶意 prompt / 边界输入」去戳你的 AI,看会不会泄露隐私、编造事实、绕过限制。OpenAI 和 Anthropic 都在用。
3. **可观测**(Observability)——AI 在生产环境里每一推理跑了多少 token、调了什么工具、卡在哪步、为什么失败,都要看得见摸得着。出问题时能像查传统日志一样,逐 token 逐调用回放。

队长 20:11 那段话已经讲明白了:**AI 要像软件一样被工程化管理——测试集、版本、可观测、回滚,缺一不可**。这是「企业 AI 落地 vs 玩具 demo」的分水岭。

---

## 什么时候需要

不是所有 AI 项目都要从头搞这一套。看清楚什么时候「必须上」、什么时候「先别上」:

**必须有的(上线前就应到位)**:
- AI 输出会进入客户决策链路(像 NIFTY 出图要进客户店铺、阿尔泰触达要进客户邮箱 / Telegram)
- 任何 prompt / 模型版本调整会影响真实业务结果
- AI 涉及个人数据 / 商业数据 / 钱(医疗、跨境、法律、获客、推荐)
- 多轮对话或多 agent 协作(中间链路一断,后果难追溯)

**可以缓一缓(但别忘)**:
- 内部工具 / 个人 demo / 一次性脚本
- 输出仅供人眼审核、不进外部链路(如内部文案脑暴)

**触发建立评测集的明确信号**(任意一个):
- 改了 prompt,客户说「感觉效果不一样了」——要量化它
- 模型升级(GPT-4 → GPT-4o,Claude 3.5 → 4)前——必须留基线
- 出过一次事故(幻觉、错发、未触达)——必须补回归用例防复发

## 怎么做(三件套)

下面这三件工具就是队长点名的那批开源方案,**都是真实项目,真有 GitHub star(分别为 ★2.4w / ★2.7w / ★1.6w),不是空话**。建议组合使用,不挑食。

### 评测集 + 红队: promptfoo

**做什么**:测 prompt、agent、RAG 的效果;同时能做红队/渗透测试/漏洞扫描(protection against prompt injection, PII leakage, jailbreak 这一类)。
**特点**:OpenAI 和 Anthropic 都在自己评估流程里用它;配置是声明式的 YAML 配置文件,跑在命令行里;可以和 CI/CD 集成(每次发版自动跑评测)。
**适合我们**:NIFTY 图片生成、阿尔泰触达 prompt 改版前后的效果对比。
**最小动作**(参考素材「怎么做」+ 工程节奏):
1. 维护一份黄金集 YAML(场景 + 期望关键词/格式/红线)
2. 跑 `promptfoo eval` 看分数,改 prompt 再跑,对比
3. 接 CI:发版前自动跑,红灯阻止发版
4. 红队用例单独一组,扫描幻觉 + 拒绝类风险

### 实验追踪 + 版本与回滚: mlflow

**做什么**:实验追踪(每次推理记下模型版本 / prompt 版本 / 参数 / 评分)、模型注册表、版本回滚,主打「AI 应用的工程化管理」。
**特点**:开源 AI 工程平台,可以 debug、evaluate、monitor、optimize,统一管 prompt/数据/模型/token 成本;模型注册表 = 出问题时秒级回滚。
**适合我们**:NIFTY / 阿尔泰所有 prompt 改版都必须落 mlflow,否则「我之前那个 prompt 怎么写的?」永远找不到。
**最小动作**:
1. 每次推理写入 mlflow:prompt 文本、模型、参数、评分、积分成本
2. UI 里对比两次改版的指标差异
3. 出事故时按 mlflow run id 回滚 prompt 版本

### 可观测(Trace + Dashboard): RagaAI-Catalyst

**做什么**:Python SDK,管 agent / LLM / tool 的调用追踪;多 agent 场景调试;自带 dashboard(时间线 + 执行图)。
**特点**:把「这一轮推理经过了哪些步骤、每步多少 token、哪步失败了」画成时间线——复杂 agent 链路排查必备。
**适合我们**:NIFTY 出图链路(抠图 → AI 生成 → 质检 → 入库 4 步)一旦中断,5 分钟定位哪步;阿尔泰多平台触达(Telegram / VK / WhatsApp)一旦发送失败,能区分是平台限速还是 prompt 被拒。
**最小动作**:
1. 接入 SDK,每轮推理包一层 trace
2. dashboard 自托管,慢调用 / 错调用置顶
3. 慢调用 / 高失败率触发预警

## 不该怎么做(反模式)

这部分结合素材反模式 + 现有 EVAL-001 第「反模式」章节综合整理,都是踩过的坑:

1. **只收藏不研读**——学习池素材原文警告:GitHub star 高 ≠ 你会用了,要点开 README + 真跑一遍。
2. **不对照自己项目生搬硬套**——promptfoo 是评测,RagaAI 是可观测,mlflow 是实验追踪/版本,职能不同;别拿一个当万能。
3. **只靠感觉上线**——「改完 prompt 我自己看着挺好」≠「客户用着挺好」。没有评测集,你都不知道改好改坏。
4. **mock 验收假动作**——NIFTY 踩过的坑:`accept_test.sh` 默认走 mock,改完 prompt 当场发版,结果生产翻车。模拟通过 ≠ 真调 AI 通过。
5. **评估数据不归档**——不存 prompt 版本 + 评分,「当时改完效果挺好」下次谁都说不清,等于没评。
6. **评估过拟合到黄金集**——只反复跑同一批题 = 模型「背答案」。要保留「惊喜集」(黄金集外的真实样本)交叉验证。EVAL-001 已记录此坑。
7. **没有消耗预算意识**——任何接外部 API 的评估,都默认走低成本路径;真调用必须显式 `-full` 并打印积分警告。NIFTY 116 积分教训。
8. **可观测等于打日志**——不是 `print()` 一行就算可观测。要 trace_id、要时间线、要能跳到具体请求;RagaAI 这种时间线 + 执行图正是为这事设计。
9. **评估系统不评估系统本身**——元评估:评测集什么时候更新的?CI 上次跑分多少?dashboard 是否还在采?(hermes-crash-guard 第 9 项就是这个理念。)

## 我们的实战映射

下面映射全部基于现有 EVAL-001 已记录的 NIFTY / 阿尔泰实战,**不新增未发生的事**;每条标出可直接参照的现有素材,便于三审核对。

### 映射一:NIFTY 图片生成(纳福)

**现状**(已发生,EVAL-001 / NIF-001 记录):
- 已有一套「103 项回归 + 4 项 e2e + 真烧积分 `--full`」验收链
- 已有「防幻觉质检」(GVLM 3.1 对比 pass/fail/review 三态,专治「凭空加金属件/丢链」)
- 已有「真烧积分」成本核算(14 积分/张 + 2 积分/质检)

**本卡建议补的三件**(上线前必须):
| 动作 | 用哪个工具 | 关联 EVAL/NIF 已有素材 |
|---|---|---|
| 建图片 prompt 黄金集(20~50 张商品图 + 标准风格/构图/红线) | promptfoo | EVAL-001 「黄金集怎么建」章节 |
| 每次 prompt 改版自动跑黄金集评分 | promptfoo + CI | EVAL-001 「评估系统可演化」教训 |
| 主动跑幻觉红队(凭空加件、丢件、产品变形) | promptfoo vulnerability scanning | NIF-001 「保真工程 + 防幻觉质检」 |
| prompt / 采样参数 / 积分成本 落 mlflow,版本可回滚 | mlflow | 队长补注「每次推理能定位到模型版本」 |
| 抠图→AI→质检→入库四步链路 trace,失败可定位 | RagaAI-Catalyst | NIF-001 「四步流程」现有描述 |

**预期收益(大白话)**:原来「改 prompt 好不好」靠人眼感觉 → 改成「跑黄金集 1 分钟出分数」;原来「生产翻车」靠复盘 → 改成「CI 上次跑分 + 当前生产 trace 对比」。

### 映射二:阿尔泰触达(获客系统)

**现状**(已发生,EVAL-001 + ALT-001 决策卡记录):
- 已有「每日筛查报告」(线索 / 评分 / 触达 / 回复 / 漏斗)
- 已有「7 天回访」(评分阈值、触达频率、账号健康)
- 已有「触达率 / 账号健康 / 线索质量」指标定义

**本卡建议补的三件**:
| 动作 | 用哪个工具 | 关联素材 |
|---|---|---|
| 不同触达 prompt × 不同客户分群的接受率评测集 | promptfoo | ALT-001 客户分群思路 + EVAL-001 业务指标哲学 |
| prompt 版本 + 平台风控状态(e.g. VK 风控变化)落 mlflow | mlflow | 队长补注「出问题能回滚」 |
| Telegram / VK / WhatsApp 多平台发送 trace + 失败原因归类 | RagaAI-Catalyst | 队长补注「上线后怎么知道它好不好」 |

**特别注意**:阿尔泰触达涉及**平台风控**,每次 prompt 改版都可能被某平台风控识别为骚扰,RagaAI 的 trace 能区分「平台拒收」「限速」「真未发送」,这三条混在一起就完全没法调试。

### 共通交付物(任何 AI 项目)

按这三件套落实后,任何 AI 项目都会产出**三件共性资产**(也是 EVAL-001 一直强调的):
1. **黄金集**(`eval/golden.yaml` 或类似)——上线准入证
2. **版本档案**(`mlflow` runs / experiments)——可回滚的事故追溯
3. **trace dashboard**(`ragaai` / 兼容 OpenTelemetry 的替代品)——生产环境的「飞机黑匣子」

## 验收问题（入库后用 5 问检验是否真的有用）

1. 什么时候"必须上"评测/可观测？（答得出：AI 输出进客户决策链路 / 改 prompt 影响业务 / 涉及数据或钱）
2. 三件套各管什么？（promptfoo=评测集+红队；mlflow=实验追踪+版本回滚；RagaAI=线上可观测）
3. 评测集（黄金集）要多大才够？（答得出：不用追求大，覆盖主要场景 + 红线即可起步，随事故补回归用例）
4. 要不要"元评估"（用 LLM 评 LLM）？（答得出：promptfoo 可配 LLM 评委，但要有基准样本防评委漂移）
5. 出事故时的回滚流程？（答得出：mlflow 里按 run id 找回上一版 prompt，重跑评测集确认恢复）
