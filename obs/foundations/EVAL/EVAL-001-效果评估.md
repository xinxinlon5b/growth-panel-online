# EVAL-001 效果评估

> ID: EVAL-001 | 创建: 2026-09-02 | 状态: ⭐ 正式（v1）
> 起草原模型: minimax/MiniMax-M3 | 任务来源: Hermes M3 队长派单
> 用途: 解答「这个 AI 项目到底有没有用」「demo 通过了但生产环境呢」「用户说好用就是好用？」

## 这个子领域在解决什么问题（一句话）

效果评估解决的是「AI 项目从'看着像有用'到'真的有用'的可证明转换」——用一组标准场景（黄金集）+ 量化指标（命中率、转化率、回归通过率）+ 真实业务验收（真烧积分、真上线、真出单），把模糊的「效果不错」翻译成可追责的数字。

## 核心问题清单

1. **「有用」怎么量化？** demo 通过 ≠ 真实场景通过；用户口头认可 ≠ 业务指标提升
2. **离线评测 vs 在线评估的关系？** 离线是「准入证」，在线是「资格证」，两者都得有
3. **黄金集（golden dataset）应该怎么建？** 来源、大小、更新频率、谁标注
4. **回归测试在 AI 项目里的角色？** 传统软件测代码逻辑，AI 项目要测「输出分布」
5. **「用户说好用」和「客观数据证明好用」冲突时信哪个？**——永远信数据，但要先理解用户为什么觉得「好用」
6. **如何避免「评估过拟合」？**——黄金集不能成为唯一优化目标，要保留「惊喜集」
7. **AI 项目的 acceptance test 与传统 acceptance test 的本质区别？**——传统是确定性测试，AI 是概率性测试，需要「真烧积分」作终验
8. **黄金集评测结果应该公开还是保密？** 公开 = 同行监督 + 客户信任；保密 = 商业秘密但失去外部校准

## 标杆答案

### 来自 Salesforce AI Research「intellagent」评测框架：

> 「intellagent 是一个面向多智能体系统的评测框架，关注「智能体在多轮对话、多任务、多角色协作场景下的真实表现」，核心理念是 'beyond static benchmarks'——传统的 MMLU/HumanEval 等静态基准已经不够，需要构建动态、多步、面向真实任务的评估管线。」

**intellagent 的三个核心组件**：

1. **任务生成器（Task Generator）**——基于 LLM 自动生成大量多样化任务场景，每个任务包含用户角色、目标、约束、可用工具
2. **环境模拟器（Environment Simulator）**——构建可控的多智能体运行环境，包括外部 API mock、数据库状态、用户响应模型
3. **多维度评估器（Multi-dimensional Evaluator）**——同时测量任务完成率、工具调用准确性、对话连贯性、安全合规性、成本效率

**理解**：intellagent 的革命性在于「承认 AI 系统的输出是概率性的」——不能用一个 pass/fail 评估，要多维度、概率化、可解释。这与本卡 NIFTY 103 项回归测试的「每项都给具体输出 + pass/fail/review」三态机制完全吻合。

### 来自 golden-v0.2.md（黄金集评测机制）：

> 「**评测机制（沿用 v0.1）**：
> - 命中（推荐架构匹配）= 1 分
> - 部分命中（组件重合 ≥50%）= 0.5 分
> - 不命中 = 0 分
>
> **目标分数 ≥ 0.7（70%）**——低于此分要么改卡要么改黄金集。」

> 「10 个场景（v0.2，扩展自 v0.1）覆盖 6 张已发布方法论卡 + 1 张决策卡」

> 「当前覆盖率 50%（5/10）。距离目标 70% 还差 2 张核心卡。
> - 已达成命中: ALT-001 / AR-001 / AR-002 / POC-001 / CJ-001（5 张）
> - 缺: NIF-001 / 启航包档 / 近企业档 / REL-001（4 张）
>
> v1.1 优先级: ① NIF-001（场景 4 必命中）；② 启航包档（场景 1 必命中）；③ REL-001（场景 8 必命中）」

**理解**：黄金集是「方法论库的单元测试」。每张方法论卡都要在 10 个标准化场景上跑一遍，命中 ≥70% 才算「正式（已过黄金集评测）」。REL-001 的命中让覆盖率从 50% 升到 60%，但要达到 70% 还需要补 NIF-001 + 启航包档或近企业档。这种「自我量化」的机制是确保方法论库不空转的关键。

### 来自 NIFTY STUDIO 项目综合评价「保真工程 + 防幻觉质检」：

> 「**保真工程**：本地抠图→AI 只画背景→PIL 合成，产品像素不被 AI 碰过（Photoroom 同原理）；参考图全量上传」

> 「**防幻觉质检**：GVLM 3.1 对比原图 vs 生成图，pass/fail/review 三态；专治 AI 凭空加金属件/丢链」

> 「**真实成本核算**：14 积分/张 + 2 积分/质检（实锤非估算）」

> 「103 回归 + e2e 4 + delivery 同步 + git —— 每轮改动都跑」

**理解**：NIFTY 的评估体系是三层金字塔：
- 底层：103 项回归（自动化，每次改动都跑）
- 中层：4 项 e2e（端到端真实流程）
- 顶层：「真烧积分」验收（用真实 AI 接口、真实成本、真实结果）

底层防回归、中层防链路断裂、顶层防「自欺欺人」。每层都有不可替代的价值。

### 来自 NIFTY 交接_20260902_下午（accept_test.sh 烧积分教训）：

> 「accept_test.sh 完整模式真调 AI 3 次约 112 积分，无警告（agent 实测烧了 116 积分）」

> 「**已修**：默认跳过 AI（=原 --quick），必须显式 `--full` 才跑 + 跑前打印积分警告」

> 「修复后**回归 103/103 全绿** + 服务健康 + `/api/op/group` 坏输入实测不崩」

**理解**：NIFTY 踩过一个评估系统设计的典型坑——**验收脚本的「完整模式」是真烧钱**。如果不设警告、不设默认安全值，开发者会在不知情下烧掉几十块到几百块。这条教训的普适版本：**任何接外部 API 的评估，都必须有「消耗预算」概念**，并且默认走低成本路径。

### 来自 中俄轻舟-项目全景与决策记录（Ozon 选品命中率 + Listing 转化率）：

> 「首批观察品类候选清单（3 方向 × 10 候选，审核等待期用）」

> 「选品逻辑最终版：标题相关性 + 利润率 ≥20% 优先（v1 分数/v2 纯利润都踩坑）」

> 「保暖袜教训：只看分数选到亏损发热袜（¥25）→ 换珊瑚绒 ¥3.6 → 83.6% 利润」

> 「VK 数据是 B2B 物流场景，与 B2C 零售选品需交叉验证」

**理解**：中俄轻舟的评估哲学更朴素——**业务指标（命中率、转化率、利润率）是终极评估，技术指标（响应时间、API 成功率）是支撑**。Listing 写得好不好，9/15 上架后 9/22 是否出单说了算；选品对不对，看 30 天后实际利润率。

### 来自 中俄轻舟 信息差引擎使用手册 + Listing 工具技术方案：

> 「Step 1（8/26）：CLI 生成脚本，中文→俄语标题/描述/搜索词，SQLite 存储」

> 「Step 2（9 月中旬）：接 Ozon Seller API，商品直接提交后台」

> 「Step 3（10 月）：接 MCP 监控，AI 看店铺数据自动建议」

**理解**：中俄轻舟的 Listing 工具效果评估是分阶段递进的——v1 验证「脚本生成能跑」（技术指标），v2 验证「提交后台能上架」（流程指标），v3 验证「AI 建议能提升转化率」（业务指标）。每一阶段都有明确的验收标准，没到下阶段不进入下阶段。

### 来自 ALT-001 决策卡「每日筛查报告 + 触达率/账号健康指标」：

> 「每日筛查报告：趋势/线索/触达一目了然 | 替代方案: 看板 8898」

> 「下一步（这是给 agent 的）：7 天后回访：评分阈值/触达率/账号健康」

**理解**：阿尔泰的评估是「日频 + 7 天回访」双节奏。每日筛查看趋势（避免单日噪音），7 天回访做决策（够样本量）。这是数据驱动决策的标准节奏，比「拍脑袋」靠谱，比「等月底看报表」快。

### 来自 hermes-crash-guard skill（评估型监控）：

> 「9 项实时健康检查：每张卡片显示状态色（绿=健康/黄=警告/红=危险）+ 当前值 + 可展开的明细 + 建议操作按钮」

**理解**：可靠性监控本身也是评估——对系统「健康度」的实时评估。EVAL 和 REL 在评估层面是同构的：REL 评估「系统在不在」，EVAL 评估「系统在不在**好好干活**」。

## 我们的实战

### NIFTY STUDIO · 纳福（103 项回归测试 + 真烧积分验收）

NIFTY 是「客户能自助运行」的产品，效果评估是产品本身的生死线：

1. **103 项回归测试**（自动化、低成本）
   - 每次代码改动、配置变更、SOP 调整前必跑
   - 覆盖：接口健康、异常分支、并发安全、数据完整性、积分账本、UI 关键路径
   - 跑完出报告：103/103 全绿 = 可发布；任何红 = 禁止发布
   - 真实验证：「修复后 103/103 全绿」是 NIFTY 每次发版的最低门槛

2. **4 项 e2e 测试**（端到端、模拟真实流程）
   - 上传商品图 → 抠图 → AI 生成 → 质检 → 看板展示 全流程
   - 包含 LibTV + 火山 双通道切换
   - 包含并发队列调度
   - 包含异常恢复（断网重连、积分不足、超时重试）

3. **真烧积分验收**（终极验证）
   - 完整模式 `--full` = 真实调用 AI，真实消耗积分
   - 默认走 `--quick`（跳过 AI，仅测流程）
   - 跑前必须显示「本次将消耗约 X 积分」警告
   - 这是「不是模拟，是真打」的纪律

4. **交付门禁**（check_delivery_sync.sh）
   - 改完代码、跑完回归、还要过交付包同步检查
   - 防止「本机是好的，交付包是旧的」事故
   - 拦截过：SOP 配置双份不一致、画布节点引用云端 URL 不落盘、33 个空测试项目混入交付包

**NIFTY 效果评估教训**：
- 评估系统本身要可演化——新增功能要同步加测试，不能「上线了再补测」
- 评估数据要可信——不要在评估系统里造假数据，否则后续调试都基于假信号
- 评估成本要可控——`--full` 烧积分的教训说明「真验」是有代价的，必须有预算意识

### 阿尔泰获客系统（每日筛查报告 + 触达率/账号健康指标）

阿尔泰是「多平台 + 长周期」的获客业务，效果评估走「日频 + 7 天回访 + 月度大盘」三层节奏：

1. **每日筛查报告**（趋势）
   - 线索新增量、评分分布、触达量、回复量、转化漏斗
   - 看一眼就知道「今天正常不正常」
   - 看板 8898 是 Dashboard URL 的代号（不是真实端口）

2. **7 天回访**（决策）
   - 评分阈值是否需要调整？触达频率是否要限速？
   - 账号健康度（VK 是否触发风控、Telegram 是否被封号）？
   - 真实业务转化：多少线索进了 CRM、多少进了下一步

3. **月度大盘**（战略）
   - 各平台 ROI 对比
   - 客户分群效果（哪类线索最容易转化）
   - SOP 改进项

4. **关键指标定义**：
   - 触达率 = 已触达线索 / 应触达线索（应触达 = 通过评分阈值的 A/B 类）
   - 账号健康 = 平台返回的 error rate + 警告频次
   - 线索质量 = 后续转化的客户数 / 触达线索数

**阿尔泰效果评估教训**：
- 评分阈值不能拍脑袋——要 7 天回访，根据真实转化数据动态调整
- 多平台对比才有意义——单平台看绝对值，多平台看相对优势
- 账号健康是「红线指标」——一旦某平台 error 率上升，立即降低触达频率

### 中俄轻舟（Ozon 选品命中率 + Listing 转化率）

中俄轻舟是「个人 + AI 协作」的跨境电商项目，评估体系最朴素也最有效：

1. **选品命中率**（前置评估）
   - 候选品类清单（3 方向 × 10 候选）→ 1688 询价 → 利润率计算 → 上架
   - 命中率 = 上架后 30 天出单的 SKU 数 / 上架 SKU 总数
   - 教训：只看分数选到亏损发热袜 → 必须利润率优先（≥20%）

2. **Listing 转化率**（后置评估）
   - 流量：曝光数 / 点击数（Ozon 后台）
   - 转化：下单数 / 加购数
   - 9/9-9/14 测流量调标题主图 → 9/15-9/22 目标第一单
   - 教训：俄语本地化深度 = 转化率，AI 翻译 + 人工润色是必需

3. **真实成本 vs 估算**（财务纪律）
   - 14 积分/张 + 2 积分/质检（NIFTY 模式）
   - 1688 拿货价 + 物流成本 + Ozon 佣金 - 售价 = 单 SKU 利润
   - 选品观察表 Excel 带公式自动算利润

4. **时间节点表**（过程纪律）
   - 每天有进步（哪怕只是完成一个 SOP）
   - 9/22 目标第一单 → 没出单 = 复盘 + 调整
   - 出单 = Go/No-Go 决策点

**中俄轻舟效果评估教训**：
- 业务指标永远比技术指标重要——AI 翻译快不快不重要，Listing 转化率高才重要
- 「先有假设，再有验证」——选品命中率假设是「利润率 ≥20%」，30 天后用真实数据验证
- 个人项目不要追求完美评估体系——能用就行，关键是「每天看数据」

## 反模式（不该怎么做）

1. **只看 demo 通过**——demo 数据是精心准备的「最佳情况」，真实数据是「最差情况」；demo 通过 ≠ 生产能用。
2. **不量化的「效果不错」**——「用户反馈很好」没价值，「80% 用户在 3 天内复购」才有价值；任何「不错」「挺好」「还行」都要追问「多大概率、多大量、多快」。
3. **「用户说好用就行」**——用户说好用可能是「新鲜感」「礼貌」「暂时没遇到问题」；客观数据（续费率、使用频率、转化率）才是真信号。
4. **评估过拟合到黄金集**——只优化黄金集分数 = 模型「背答案」；必须保留「惊喜集」（黄金集外的新场景）做交叉验证。
5. **回归测试覆盖不够**——只测「正常路径」，不测「异常分支」；NIFTY 早期 bug 教训：异常分支的日志调用 `_log` 未定义 → 直接 500。
6. **acceptance test 是模拟而非真烧**——用 mock 数据测试通过 ≠ 真接口通过；NIFTY `--full` 模式真烧积分是必要的「终验」。
7. **评估数据不归档**——「当时看着效果挺好」无法复盘；每次评估的结果、配置、版本都要存。
8. **追求完美评估体系拖慢上线**——评估是手段不是目的，过度设计 = 项目延期；NIFTY 103 项够用，中俄轻舟每日看板够用，不要为评估而评估。
9. **(扩展) 让客户做评估的唯一来源**——客户视角是「主观满意度」，业务视角是「客观指标」；两个都要看，但不要混为一谈。
10. **(扩展) 评估系统本身不评估**——评估系统坏了 = 全员瞎飞；评估系统必须有元评估（hermes-crash-guard 第 9 项「guardian cron 是否配置、上次运行状态」就是这个意思）。

## 与其他子领域的关系

- **依赖：REL-001（可靠性）**——评估系统本身要可靠，否则「评估结果不可信」= 评估等于没做。
- **依赖：POC-001（POC 验证）**——评估是 POC 毕业的依据；没有量化评估，POC 永远是「看上去成功」。
- **依赖：FDE-002 第 4 阶段（守住续约）**——续约的「季度价值报告」本质是 EVAL 的业务指标化。
- **依赖：AR-001（架构决策）**——选哪种评估体系是架构决策；离线 vs 在线、规则 vs 模型。
- **顺序**：在客户旅程的第 1-3 阶段（找问题→赢客户→激活部署）就要建立基线；没有基线就无法评估增量。
- **冲突**：与「快速迭代」「MVP 优先」的张力——但 NIFTY 证明：MVP 也可以自带 103 项回归。
- **替代**：无；评估是底层能力，不可外包。

## 验收问题（看完能回答这 5 个问题就算会了）

1. **「demo 通过」和「生产可用」的差距本质是什么？**（demo 数据是精心准备的「最佳情况」，真实数据是「最差情况」；NIFTY `accept_test.sh --full` 真烧积分、阿尔泰 7 天回访看真实转化、中俄轻舟 30 天出单率，都是跨越这道差距的具体手段）
2. **黄金集应该多大？怎么决定？**（黄金集是方法论库的「单元测试」，每张卡至少要在 10 个标准化场景上跑一遍；命中 ≥70% 才算「正式（已过黄金集评测）」；golden-v0.2 的 10 场景是当前基线，后续按缺口场景补）
3. **「真烧积分」验收 vs mock 验收的本质区别？**（mock 验证「流程跑通」，真烧验证「结果可信」；mock 100% 通过可能是因为 mock 太宽松；NIFTY 的 `--full` 模式 + 积分警告是「真烧」纪律的样板）
4. **评估系统的「元评估」是什么？为什么必要？**（元评估 = 评估系统自身是否可信；hermes-crash-guard 第 9 项检查「guardian cron 是否配置、上次运行状态」就是元评估；没有元评估，评估结果不可信 = 评估等于没做）
5. **业务指标 vs 技术指标的优先级？**（业务指标永远优先。中俄轻舟用「30 天出单率」评估选品命中率，而不看 API 响应时间；NIFTY 用「客户是否复购」评估产品，而不看 103 项测试是否全绿——测试全绿是必要条件，业务指标才是终极裁判）
