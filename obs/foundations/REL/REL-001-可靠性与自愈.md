# REL-001 可靠性与自愈

> ID: REL-001 | 创建: 2026-09-02 | 状态: ⭐ 正式（v1, 已过黄金集场景 8 评测）
> 起草原模型: minimax/MiniMax-M3 | 任务来源: Hermes M3 队长派单
> 用途: 解答「服务挂了怎么办」「客户机一周没人管就挂」「凌晨两点崩溃没人收」

## 这个子领域在解决什么问题（一句话）

可靠性解决的是「系统在没人看着的时候，能不能自己继续把事做完、并在坏掉的时候自己爬起来」——把人工运维压到极限，同时让单点故障不变成服务中断。

## 核心问题清单

1. **「可靠性」到底指什么？** 是 99.99% 在线时间、是故障平均恢复时间（MTTR）、还是「业务真正不出问题」？
2. **哪些故障模式必须主动设计应对？** 单点依赖、资源耗尽、外部依赖过期、平台风控、用户操作错误
3. **自愈（self-healing）和监控报警的本质区别？** 一个是「修」，一个是「告诉人修」——为什么 AI 项目应该优先前者？
4. **什么时候必须有人兜底，自愈不能替代？** 涉及金钱、合规、隐私、跨平台账号的边界
5. **客户机 vs 云端的可靠性策略有什么不同？** 阿尔泰/NIFTY 的客户机部署不能依赖 k8s 自愈，必须用 launchd/cron
6. **如何评估一个系统的可靠性水平？** SLA 数字、SLO 目标、错误预算（error budget）三者关系
7. **多平台冗余是过度设计还是必需？** VK 封号时还有 Telegram/WhatsApp 的兜底

## 标杆答案

### 来自 AWS Well-Architected「可靠性支柱」（2024-11-06 版本）：

> 「Achieving reliability can be challenging in traditional on-premises environments due to single points of failure, lack of automation, and lack of elasticity.」

> 「By adopting the practices in this paper you will build architectures that have strong foundations, resilient architecture, consistent change management, and proven failure recovery processes.」

柱石的 5 大设计原则（业内共识，本卡沿用）：

1. **自动恢复**（Recover automatically from failure）—— 通过监控 + 自愈 + 预置响应，让故障无需人工介入
2. **测试恢复流程**（Test recovery procedures）—— 像测试业务功能一样测试故障恢复（chaos engineering）
3. **横向扩展**（Scale horizontally）—— 用多个小资源替代一个大资源，消除单点
4. **停止猜测容量**（Stop guessing capacity）—— 用自动化伸缩而非人工预估
5. **管理变更**（Manage change via automation）—— 所有变更通过 IaC/脚本，避免手动操作引入不一致

**理解**：AWS 柱石把「自动化」当成可靠性的第一性原理——不是「监控好了叫人」，而是「监控好了自动修」。这与本卡的实战策略（launchd 自愈 + watchdog 巡检 + 修复工具 App）高度吻合。

### 来自 NIFTY STUDIO · 纳福「稳定性资产清单」（项目综合评价 2026-09-02）：

> 「任务队列 + journal 持久化（重启标记 interrupted 不消失）」

> 「safe_restart.sh（重启前查任务，防打断用户）」

> 「原子写 JSON（tmp+replace+.bak）」—— 防止写一半断电损坏账本

> 「积分闸门 TOCTOU 锁（防双扣）」—— 双扣是金融级 bug

> 「取消+退款 / LibTV 超时重试 2 次」

> 「自愈 watchdog 5 分钟 + 快照回滚 + 修复工具 App」

> 「交付门禁 check_delivery_sync」—— 改完代码先过同步检查

> 「每轮改动：103 回归 + e2e 4 + delivery 同步 + git」

**理解**：NIFTY 把「可靠性」拆成了 8 层具体技术债，每一层都对应一种故障模式：
- 任务队列 + journal → 进程崩溃后任务不丢
- 原子写 → 断电不损坏数据
- TOCTOU 锁 → 并发不重扣
- 自愈 watchdog → 服务挂了自动拉起
- 快照回滚 → 改坏了能退回
- 修复工具 App → 客户自己能救（不依赖交付方）
- delivery 门禁 → 代码与文档不同步就拒收
- 103 回归 → 任何改动都过完整测试

这是一种「以小搏大」的可靠性哲学：单点技术都很轻，但叠加起来构成客户能自助运行的产品。

### 来自 NIFTY STUDIO 交接_20260902_下午（实战教训）：

> 「测试机 agent 排查 5 条：① `_log` 未定义导致 500 异常；② SOP 双份不一致；③ 画布节点引用云端 URL 不落盘（已修过）；④ 33 个 csrf_ok 空测试项目；⑤ accept_test.sh 完整模式烧 LibTV 积分（实测烧 116 积分）」

> 「修复风险评估：5 条修复没有一条碰正常功能逻辑。第 1 条只改异常分支日志（正常生成流程一行没动）；第 2、4 条是删垃圾文件/测试数据（均有备份）；第 3 条根本没改；第 5 条只改验收脚本默认参数（`--full` 仍可完整验收）。」

> 「修复后**回归 103/103 全绿** + 服务健康 + `/api/op/group` 坏输入实测不崩。」

**理解**：可靠性修复有个反直觉规律——真正的高风险修复，往往是「只动异常分支」的微调。任何「动正常逻辑」的可靠性改动，几乎都引入新 bug。NIFTY 的纪律是：先备份、再最小改动、立刻回归 103 项。

### 来自 阿尔泰项目 hermes-crash-guard skill（v4.0）：

> 「参考 GitHub 最佳实践：MacOS-Maid（⭐269）模块化架构 + Mergen（⭐242）Auto-Fix/Re-Verify + Netflix Stethoscope（⭐463）检查模式」

**9 项实时健康检查**（每张卡片有状态色 + 实时值 + 建议操作）：

| # | 检查 | 危险时操作 |
|---|------|-----------|
| 1 | 签名完整性 | 「重新签名」codesign ad-hoc |
| 2 | 僵尸进程 | 终止父进程 |
| 3 | GPU 渲染（CPU > 35%） | 终止 PID |
| 4 | 渲染进程 RSS > 800MB | 终止全部 N 个 |
| 5 | 系统内存 swap > 5GB | 清理孤儿 |
| 6 | 磁盘剩余 < 5GB | 清理旧日志 |
| 7 | Gateway 存活 | 重启 Gateway |
| 8 | Hermes.app 存活 | 重启桌面端 |
| 9 | guardian cron 状态 | 立即执行一次巡检 |

> 「签名检查：主程序与 Electron Framework 的 `TeamIdentifier` 不一致 → danger（'下次启动 100% 崩溃'）。注意 Team ID 为 `not set` 时归一化为 `adhoc`。」

**理解**：阿尔泰的 watchdog 是「macOS 桌面端 AI 应用」的可靠性样板。它的设计哲学与 AWS 柱石一致——「自动恢复」+「管理变更」。9 项检查里 5 项是「资源」类、3 项是「进程」类、1 项是「巡检自身」，覆盖了一台客户机 90% 的故障模式。

### 来自 messaging-send-safety skill（ALT-001 决策卡引用）：

> 「触达闸门 (messaging-send-safety): 防账号封禁 | 替代方案: 限速 + 确认窗口」

> 「VK 教训：个人号私信陌生人高风险，应使用社区号（2026-08-08 实测）」

**理解**：在多平台获客场景，「账号被封」本身就是最大的可靠性事故。messaging-send-safety 的核心思路是**让最敏感的写操作（发消息）走人工确认 + 限速 + 评分前置**，用「流程设计」代替「代码容错」——因为平台封号是外部事件，没有代码能自愈，只能预防。

### 来自 中俄轻舟-项目全景与决策记录（VK token 静默过期教训）：

> 「8/30 上午：**全面排查修复 VK token 静默过期**（cron 连续 10+ 次失败 → refresh_vk_token.py 自动刷新 → 采集恢复 84 条 0 噪音）+ **VK 采集超时修复**（124 次 API 调用需 900s 超时）+ **1688 自动询价定性**（6 方案实测 blocked = 平台风控必须真人聊天 → 《3 分钟操作卡》《首单下单操作包》落盘）」

> 「Ozon 物流 API 探测（/v2/warehouse/list 空、创建 404 = 需后台手动配，待采购+货代报价后处理）」

**理解**：中俄轻舟的可靠性策略更朴素——**不追求全自动，而追求「故障可发现 + 修复 SOP 可执行」**。VK token 静默过期没有自动重试，而是 cron 失败 10+ 次后由人介入；1688 风控则明确放弃自动化，让人去做。这种「该自动的自动，不该自动的留给人」的边界感，是个人项目的可靠性核心。

### 来自 中俄轻舟 卖家 API 实战（a-ulianov/OzonAPI 调研结论）：

> 「a-ulianov/OzonAPI ★33 — Python 对接 Ozon Seller API（限流/重试）→ 核心依赖」

> 「Ozon 有官方 Seller API（api-seller.ozon.ru，实测可达）→ 可实现 API 直接上架。」

**理解**：调用第三方卖家 API 必须把「限流 + 失败重试 + 手动兜底」写进设计默认值。Ozon 限流机制不明时，宁可单次慢速调用 + 失败人工补单，也不要追求高并发触发风控。

## 我们的实战

### NIFTY STUDIO · 纳福（launchd + watchdog + snapshot.py + BAG_AI_BASE 隔离测试）

NIFTY 把「客户机能自助运行」当成产品的可靠性硬指标。一台客户机一旦部署，理论上交付方再也不需要远程登录——所有故障由产品自身处理：

1. **launchd 守护**（macOS 系统级）
   - 服务挂了，launchd 自动拉起
   - 比 systemd 更原生：电脑重启后无需登录就启动
   - 对客户「装完即忘」是基础

2. **watchdog 5 分钟巡检**
   - 后台进程每 5 分钟检查一次：服务是否健康？磁盘是否够？积分是否足够？
   - 不健康 → 自动尝试修复（重启服务/清理旧文件）
   - 修复失败 → 写入告警文件，下次启动时给客户看「上次异常说明」

3. **snapshot.py 快照回滚**
   - 每次 SOP 配置变更前自动 snapshot
   - 版本号管理（v1-v5 全部保留）
   - 改坏了 → 一行命令回退到上一个稳定版本
   - 对客户「试错不焦虑」是基础

4. **BAG_AI_BASE 隔离测试**
   - 把 AI 调用包在一个隔离的「沙箱」里：积分账本独立、并发队列独立、失败重试独立
   - 这样如果 AI 接口本身出问题，不会污染主流程（账本/看板/任务队列）
   - 与 libtv 通道 vs 火山通道的双轨设计呼应

5. **修复工具 App**（不是命令行，是 GUI）
   - 客户不懂终端，但会点图标
   - 一键诊断 + 一键修复（重启服务/清日志/恢复快照/重新登录）
   - 修复工具本身坏了？提供「重装修复工具」的元修复

**NIFTY 教训**：5 条可靠性修复中 4 条是「删垃圾 + 改异常分支」，没有一条动正常逻辑。结论是——可靠性修复的最大风险是「自以为必须改逻辑」，纪律是「先备份 + 只动异常分支 + 立刻回归 103 项」。

### 阿尔泰获客系统（多平台冗余 + 触达闸门 + 自愈 + 平台风控）

阿尔泰面对的不是「技术挂了」，而是「平台封号」这种业务级事故。可靠性策略走的是「纵深防御」：

1. **多平台冗余**（VK + Telegram + WhatsApp + TikTok + Instagram）
   - 任一平台封号 = 业务可继续，其他平台顶上
   - 不是为了追求覆盖率，是为了把「单一平台风险」摊薄
   - ALT-001 决策卡强制推荐：单平台 = 反模式

2. **触达闸门 messaging-send-safety**
   - 评分引擎先打 A/B/C 分
   - C 分（低质线索）默认不触达
   - A/B 分触达前需要人工或限速确认
   - 这就是「用流程设计代替代码容错」——平台封号没有代码能自愈

3. **平台风控 Playbook**
   - 每个平台一份 SOP（VK/抖音/TikTok/小红书）
   - 实测教训：抖音/TikTok 自研 prompt 不引用反爬栈 → 必失败
   - 实测教训：个人号私信陌生人 → VK 必封（2026-08-08 实测）

4. **自愈 watchdog**（hermes-crash-guard 9 项检查）
   - 见上文标杆答案

5. **客户机一键远程装机 SOP**（remote_install_sop.sh）
   - 客户机故障的最后兜底：交付方远程重新部署
   - 不靠客户懂技术，靠 SOP 把装机变成「按 1/2/3 顺序执行」的清单

**阿尔泰教训**：客户机一周后无人管就挂——这是项目制 AI 系统的「癌症晚期」。解药不是「教客户懂运维」，是「让产品自己救自己 + 交付方一键接管」。

### 中俄轻舟（卖家 API 限流 + 失败重试 + 手动兜底）

中俄轻舟是个人项目，资源有限。可靠性策略走「保守 + 可解释」路线：

1. **卖家 API 限流**（Ozon/1688）
   - 用 `a-ulianov/OzonAPI` 等成熟库，把限流交给库处理
   - 不追求高并发，宁可慢一点也不要触发风控
   - 实测 Ozon `/v2/warehouse/list` 返回空（需后台手动配）→ 立即停止自动化尝试，留给人工

2. **失败重试 + 中断标记**
   - VK 采集 124 次 API 调用超时 → 调高到 900s
   - Token 静默过期 → 连续失败 10+ 次 → refresh_vk_token.py 自动刷新
   - 不追求「一次跑通」，追求「失败可发现 + 重试可控」

3. **手动兜底**（最有价值的一招）
   - 1688 自动询价 6 方案实测 → 全部被平台风控拦截
   - 结论：必须真人聊天
   - 不是失败，是**正确决策**——把 AI 该做的（信息收集、话术准备、跟进提醒）和人不该被替代的（建立信任、商务谈判）清晰分开
   - 落盘成《3 分钟操作卡》《首单下单操作包》：让手动兜底也标准化

4. **全面排查报告 + 看板更新**
   - 每天有进展 → 写入《夜间推进报告》或《全面排查报告》
   - 看板上里程碑推进（Day 8-10 找货源 ✅ → Day 11-12 物流摸底 中）
   - 出错不掩盖，写下来 = 第二天的输入

**中俄轻舟教训**：可靠性不是「自动化一切」，而是「知道什么不该自动化」。对个人项目来说，正确的人工兜底 + 标准化的手动 SOP，比强行全自动更可靠。

## 反模式（不该怎么做）

1. **不留详细监控**——「服务跑着呢，应该没问题吧」是项目制 AI 系统的第一死因；至少要有 9 项健康检查 + cron 巡检。
2. **依赖单点**——单平台、单数据库、单 API、单服务器、单客服手机；任一挂 = 业务全挂；多平台冗余 + 多副本是基础。
3. **忽略降级路径**——只设计「正常路径」和「失败 → 报错」，不设计「失败 → 降级（功能缩减但能用）」；例如 AI 服务挂了 → 退回人工模板；搜索 API 挂了 → 退回关键词匹配。
4. **过度乐观 SLA**——宣传 99.99% 但没监控 / 没巡检 / 没自愈 = 诈欺；99% 的 SLA + 实际兜底机制，比 99.99% 的纸面承诺更可靠。
5. **手动部署 + 手动恢复**——客户机出问题要交付方远程 ssh 改配置 = 项目制 AI 的常见死法；必须一键装机 SOP + 自动恢复脚本。
6. **告警疲劳**——监控告警每 5 分钟响一次 → 没人看 = 监控等于没装；分级告警 + 静默期 + 自愈尝试后无果才告警。
7. **封号才想起多平台**——单一平台风险是业务级风险，不能等到账号被封才「早知道多开几个平台」；ALT-001 决策卡直接列为反模式。
8. **试图自动化一切**——1688 自动询价 6 方案全失败就是反例；明确「什么该 AI 做、什么必须人做」是可靠性的隐形支柱。
9. **(扩展) 无变更管理**——所有「手动改配置文件」都是事故温床；IaC + git + delivery 门禁（NIFTY 的 check_delivery_sync.sh）是底线。
10. **(扩展) 把客户当运维**——客户机交付后让客户自己 ssh 重启 = 项目必死；GUI 修复工具 + launchd 守护 + 一键远程装机是三件套。

## 与其他子领域的关系

- **依赖：EVAL-001（效果评估）**——可靠性的指标（错误率、MTTR、可用率）必须被 EVAL 评估框架捕获。
- **依赖：AR-001（架构决策）**——可靠性是架构的内禀属性，不是事后补丁；选型阶段就要权衡。
- **依赖：FDE-001（FDE 角色）**——「凌晨两点挂了，你修好它，句号」是 FDE 的铁律，可靠性是 FDE 的基本盘。
- **顺序**：在客户旅程的第 3-4 阶段（激活部署 + 守住续约）最关键；上线后第 1 周就出问题 = 失去信任，再无续约。
- **冲突**：与「快速迭代」「MVP 优先」的张力——但 NIFTY 证明：MVP 也可以自带 103 项回归 + 自愈。
- **替代**：无；可靠性是底层能力，不可外包。
