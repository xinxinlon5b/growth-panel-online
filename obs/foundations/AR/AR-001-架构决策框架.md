## 这个子领域在解决什么问题（一句话）

新项目第一周应该按什么顺序做什么架构决策，避免「想到哪做到哪」——把零散的技术选型（模型、数据库、部署形态、风控、计费、可观测）收束成一份「可以照着做」的决策清单 + 一份「可以回去查」的回溯日志。

## 核心问题清单（10 个，按决策先后顺序）

1. **业务目标决定什么架构模式？**（SaaS 多租户 vs 桌面工具单租户 vs 嵌入式插件——错配会让 80% 的后续决策都别扭）
2. **部署形态决定运维复杂度？**（本地单机 vs Docker 容器 vs 云函数——决定了安装/升级/回滚/监控整套心智模型）
3. **模型通道怎么选？**（自托管开源 / 云 API 按量 / 中间商包月——决定了计费、限流、退款、风控一整套）
4. **状态如何持久化？**（本地 JSON + 原子写 / SQLite / Postgres——决定了并发、可观测、灾备一整套）
5. **付费/积分账本怎么记？**（云端账本 / 本地账本 / 双账本——决定了脱敏交付、双通道费用聚合、退款链路）
6. **路径/数据安全怎么做？**（路径穿越防护 / CSRF / API Key 本地化——决定了客户多账号共享 Mac 时的安全边界）
7. **后台任务怎么调度？**（同步请求 / 队列 + worker / 任务 journal 持久化——决定了重启恢复、取消、并发上限）
8. **可观测性怎么埋？**（前端轮询 / 后台日志 / 任务阶段进度——决定了客户能不能"信任系统在干活"）
9. **配置与提示词怎么管？**（代码硬编码 / 配置文件 / 版本化 SOP——决定了能不能不改代码调效果）
10. **风控/边界/拒绝规则怎么写？**（每日上限 / 红线 / 终止信号——决定了平台账号不被封、被投诉时能体面收尾）

## 标杆答案（每条都标引来源 + 对应到本地代码实证）

### 1. AWS Well-Architected 五大支柱（来源: aws.amazon.com/cn/architecture/well-architected/）

> AWS 把"好的架构"拆成 5 个相互制衡的支柱，每个支柱都给了 Design Principles、Lens、Best Practices 三层递进。这套框架之所以值得背，不是因为 AWS 正确，而是因为它强迫你在 5 个维度都做一次"防御性思考"——单点最优不等于全局最优。

#### 1.1 卓越运营（Operational Excellence）

> 原文原则: "Perform operations as code, make frequent, small, reversible changes, refine procedures frequently, anticipate failure, learn from all operational failures."

**本地代码实证: NIFTY STUDIO 把所有运维动作写成 launchd plist + 脚本**
- `install.sh` 第 122-156 行：6.1/6.2/6.3 三个 plist 落地——主服务、自愈 watchdog（每 5 分钟）、快照（每小时）。可逆（小变更）+ 自动化（launchctl load/unload）。
- `install.sh` 第 18-22 行：装包时启 `progress_server.py` 占 8896 端口，把 7 步安装的「当前步/百分比/标题/描述」实时暴露给前端网页——这是"运行时让客户看见系统在干活"的可观测性，与 Well-Architected 的"Anticipate failure"一脉相承。
- NIFTY `server.py` 第 528-551 行 `_journal_restore()`：启动时把中断任务标 `interrupted` 而非 `not_found`——这是"频繁小步回滚"的具体实现，事故后不用追问"任务哪去了"。
- NIFTY `server.py` 第 3401-3461 行 `_cleanup_orphan_outputs()`：每 6 小时扫 outputs/，清掉 >24h 的临时文件与未被引用的孤儿图。防磁盘无限增长，这是 Learn From Failure 的具象化。

#### 1.2 安全（Security）

> 原文原则: "Implement a strong identity foundation, apply principle of least privilege, protect data in transit and at rest, keep people away from data, prepare for security events."

**本地代码实证: NIFTY 做了 6 层防御**
- **L1 路径穿越防护**：`_safe_path()` 第 110-155 行——resolve() 后必须 `is_relative_to(OUTPUTS/UPLOADS)` 才放行。第 138-143 行的"裸文件名分支"必须再次校验 is_relative_to，否则 `outputs/foo/../../server.py` 可逃逸白名单（dsh 第 5 轮 HIGH-1 修复）。
- **L2 隐藏文件拒绝**：第 119-121 行 `if any(seg.startswith('.') and seg not in ('.', '..') for seg in ...): return None`——防 outputs/.env 被前端当图片路径拉走。
- **L3 CSRF**：第 459-470 行 `_csrf_guard()` 拒绝所有非本机 Origin 的写请求，且 scheme 必须是 http（防 https 来源伪造）。
- **L4 API Key 本地化**：第 26-30 行 VOLC_CONFIG 注释明示"只存本机 models/volc_config.json（不进交付包），chmod 600"。
- **L5 管理员密码哈希**：第 222-240 行 SHA-256 + 随机盐，旧明文自动迁移到哈希格式。
- **L6 上传类型白名单 + 像素上限**：第 2012 行限定 13 种图片扩展名；第 2036-2038 行 >8000 像素拒绝。
- **V1 隐患（事后发现的）**：本地工具对客户共享 Mac 的防护仍弱——共享场景下任何登录用户都能读 `/uploads/<path:fname>`（第 2063-2070 行只校验 Host 不校验登录用户），应在 v1.1 加 OS 用户隔离或管理员 token 强校验。

#### 1.3 可靠性（Reliability）

> 原文原则: "Automatically recover from failure, test recovery procedures, scale horizontally, stop guessing capacity, manage change via automation."

**本地代码实证: NIFTY 的多层故障恢复**
- **原子写防并发损坏**：第 782 行 `tmp = PROJECTS_DB.with_suffix(f".json.tmp.{uuidlib.uuid4().hex[:8]}")` 后 `os.replace`——唯一临时文件名 + replace，根治固定 `.tmp` 的并发竞态（dsh P1-2 修复）。
- **损坏恢复兜底**：第 763-776 行 `load_projects()` 检测到 JSON 解析失败，先尝试 `.bak`，再备份为 `.corrupt_<ts>`，最后才返回空。**不静默丢数据**。
- **任务取消语义**：第 723-740 行 cancel 接口只改 `cancelled=True`，worker 在执行函数内/云端调用前自检——已扣费的会自动退（`LEDGER.add("一键组图取消退款", -cost_total, ...)` 第 3390 行）。
- **排队超时与僵尸任务**：第 685-690 行 queued 任务 15 分钟未开始 → 自动 error；第 694-700 行 running 超过 30 分钟 → error。这条 30 分钟阈值是为 bg_image 7 张参考图实测 11.5 分钟倒推出来的（S7 修复注释明示）。
- **V2 隐患**：没有跨进程锁（仅线程锁 `_tasks_lock`/`_admin_state_lock`/`_projects_lock`/`_journal_file_lock`/`_volc_state_lock`），如未来切到 gunicorn 多 worker，会出现账本双写——应在切多 worker 前先做进程级文件锁。

#### 1.4 性能效率（Performance Efficiency）

> 原文原则: "Democratize advanced technologies, go global in minutes, use serverless architectures, experiment more often, consider mechanical sympathy."

**本地代码实证: NIFTY 在单机资源约束下做"机械同情"**
- **异步任务池**：第 503 行 `_task_pool = _Queue(maxsize=2)` 与 2 个 worker 匹配——大于 worker 数会积压排队，前端提示"满 2"实际能排 4，导致任务堆到 worker 处理慢时全卡死。**队列容量必须 = worker 数**。
- **登录态缓存**：第 830-890 行 `_auth_status_cache`——LibTV CLI 冷启动 3-5s，前端每次刷新都调会爆。60s 缓存 + 探测失败时 cache=None 强制下次重探测（防负缓存长期卡 False）。
- **HEIC 转码**：第 2041-2056 行——iPhone 传图主路径 HEIC 在 pillow-heif 注册后立即转 PNG，下游 rembg/PIL 不再挂。转码失败不再静默保留原文件（2026-09-02 修复），明确报错。
- **小策略**：所有提示词模板用 `_fmt_prompt()` 第 190-198 行的 `.replace()` 而非 `format()`——format 遇 `{product}` 缺失会 KeyError 崩 worker，replace 留原文不阻塞。

#### 1.5 成本优化（Cost Optimization）

> 原文原则: "Implement cloud financial management, adopt a consumption model, measure overall efficiency, stop spending on undifferentiated heavy lifting, analyze and attribute expenditure."

**本地代码实证: NIFTY 的双通道计费**
- **双通道架构**：LibTV（包月，给"积分"感）+ 火山方舟 API Key（按量，给"用多少付多少"感）。第 834-890 行 `auth_status` 任一可用即 AI 可用——客户不会因为某个通道挂了整个工具停摆。
- **费用聚合**：第 1538-1614 行 `/api/stats` 把 LibTV 积分成本 + 火山估算费用（从 `note` 解析"X元估算"）分开聚合——客户看见自己花了多少，运营审计有抓手。
- **退款路径**：第 3317-3318 行 + 3375-3376 行——云端失败 → 自动退 cost_total 里已扣的 14 积分；第 3390 行——取消任务时整单退款。**不退费的工具没人敢用**。
- **本地资源零云依赖**：白底合成、抠图走本地 rembg/basicsr（不烧云积分）；HEIC 转码、HEIF 验证全部本地；只有 AI 生成才上云。**先把免费能力用满，再让云端做它擅长的事**。

### 2. ADR 模式（来源: Michael Nygard 原文 "Documenting Architecture Decisions"，2011）

> Nygard 把 ADR 提炼为 4 段式：标题/状态/上下文/决策/后果。后来社区补充第 5 段「替代方案」（Considered Alternatives）——这不是装饰，是给未来"为什么没选 X"留路标。

#### 2.1 4 段式结构（带本地代码 ADR 示例）

```
# ADR-001: NIFTY STUDIO 采用双通道计费模型（LibTV 包月 + 火山按量）

> 状态: 2026-08-31 Accepted | 决策人: 队长 + AI 协作 | 影响范围: 全部客户

## 上下文（Context）
客户群分两类：① 有持续出图需求、希望"包月不心疼"的电商小白；
② 偶尔用、不想开月费的尝鲜用户。单一通道要么逼小白买月卡（门槛高），
要么逼尝鲜用户走 API（门槛更高）。客户退货率会爆炸。

## 决策（Decision）
- 默认主通道 = LibTV（CLI 包月，积分感强，0 学习成本）
- 备选通道 = 火山方舟 API Key（按量付费，先进少数尝鲜用户）
- 任一通道登录成功 → 工具全部能力可用（不绑死）
- 费用分开记账：`ledger.entry.op = "火山[xxx]"` 时 credits=0 + note 记估算费用

## 后果（Consequences）
- ✅ 客户覆盖面扩大（小白 + 尝鲜）
- ✅ 通道故障时另一通道顶住
- ❌ 双通道都要测试（开发/QA 成本 ×2）
- ❌ 客户认知成本："为什么两个都要登录？"
- ❌ 双费用聚合的 UI 必须做得直观，否则客户搞不清自己花了多少

## 替代方案（Considered Alternatives）
- ❶ 仅 LibTV：放弃尝鲜用户，营收上限被锁死
- ❷ 仅火山：要求所有客户自购 API Key，小白 0 转化
- ❸ 三通道（再加 Midjourney/Replicate）：维护成本不可控，先双通道跑通再说
```

#### 2.2 何时记录决策

> "The earliest moment to write an ADR is when you realize a decision needs to be made but you don't have enough context yet to make it well. Capture the question, not the answer."

**本团队的事后判定标准**（适用于 v1 走完开始回填 ADR 时）：
- 决策涉及 ≥2 个备选方案（不是单选就别记）
- 决策被 ≥2 次重复讨论过（说明它不是一次性 trivia）
- 决策影响 ≥3 个月后的代码路径（一次性修复不留档）
- 决策对客户可见（计费/性能/安全这类更要记）

#### 2.3 如何回溯（4 个具体动作）

1. **ADR 文件夹按 ID 编号**：`docs/adr/0001-use-postgres.md`、`0002-...md`，不按主题分类（主题分类会随项目长大崩）
2. **状态字段必填**：Proposed / Accepted / Deprecated / Superseded by ADR-XXXX（superseded 必须指明替代者）
3. **Git 提交信息包含 ADR ID**：`git commit -m "fix: 火山双通道登出标记 (refs ADR-001)"`——这样 `git log --grep ADR-001` 能拉出全部相关代码改动
4. **每季度 5 分钟扫描**：扫一遍 Accepted 列表，看有没有"事实已变但 ADR 还没标 Deprecated"的——及时标 Superseded 避免误导新人

### 3. RAG 架构模式（来源: NIRDiamant/RAG_Techniques）

> RAG_Techniques 把 RAG 演进分三代：Naive → Advanced → Modular。三代不是替代关系，是叠加关系——Modular RAG 里仍然可以保留 Naive 的 retrieve-then-read 流程作为某个模块。

#### 3.1 Naive RAG（"喂啥吐啥"）

> "Index chunks, retrieve top-k, prompt LLM with chunks as context, return answer."

**适用场景**：FAQ 机器人、内部知识库（一问一答，不追问）。
**本地映射**：中俄轻舟的《俄语关键词库》《俄罗斯消费者行为速览》《Ozon Listing 生成器》就是 Naive RAG 的极简版——关键词/事实/模板作为 static context 进 prompt，不实时检索。
**失败模式**：知识库过时（关键词半年前对，现在错）、chunk 切碎导致语义断裂。

#### 3.2 Advanced RAG（"前后处理"）

> "Pre-retrieval: query rewriting, HyDE, step-back prompting. Post-retrieval: re-ranking, compression, citation injection."

**本地映射**：阿尔泰的精聊引擎——AI 筛选阶段用 `vk_ai_filter_batch.py`（DeepSeek 批量 8 条/次打分），本质是 post-retrieval re-ranking：原始 362 条线索 → DeepSeek 判定 intent + reason + template → 只把 high intent 进 `vk_contact_queue.jsonl` 私信队列。
**实战经验**：批量打分比单条打分省 60%+ token 成本（一次性包 8 条 vs 8 次请求），且更稳定（批次内互相对比减少分数漂移）。

#### 3.3 Modular RAG（"乐高拼装"）

> "Routing, scheduling, fusion, memory, metacognitive modules. Each module is independently swappable."

**本地映射**：NIFTY 的 `_do_group()` 一键组图流水线——白底生成（本地）+ 三视角换背景（云端）+ 多角度组图（云端）+ 防幻觉质检（云端 GVLM）= 4 个独立模块，可任意组合、可跳过、可重排。
**实战经验**：模块化的代价是配置复杂度（DEFAULT_SOP 31 行 JSON 定义 7 个步骤 + 8 个模式），所以 v1.0 加了 SOP 版本管理 + 回滚（`_snapshot_sop_version` 第 355-406 行）——没有回滚能力的可配置化是定时炸弹。

### 4. AI 系统部署模式（来源: calmrocks/ai-engineer-notebooks FDE 实战 notebook）

> calmrocks 把 AI 系统部署拆成 7 步流水线：prompt → RAG → evaluation → agent → adaptation → serving → observability。每步是一个独立的"必须答对"问题，跨步才会出错。

#### 4.1 prompt（提示词）

> "Prompts are code. Version them. Test them. Diff them like any other artifact."

**本地实证**：NIFTY 第 299-322 行 `DEFAULT_SOP["prompt_template"]` + 8 个模式的 prompt 模板，全部存在 `models/sop_config.json`（不进代码库），通过 SOP 版本管理可回滚。**单点配置 + 多版本索引 + 自动 diff** = 把 prompt 当一等公民。

#### 4.2 RAG（检索增强生成）

> "Bad retrieval + great LLM = bad answer. Great retrieval + bad LLM = salvageable answer."

**本地实证**：NIFTY angle 多角度生成用 `{{Image 1}}` / `{{Image N}}` 显式引用参考图——reference 是"硬 RAG"，比纯文本检索更可控。

#### 4.3 evaluation（效果评估）

> "If you can't measure it, you can't improve it."

**本地实证**：NIFTY `_do_group()` 第 3360-3371 行——换背景生成后调 `detect_hallucination()`（GVLM 3.1 Flash）对参考图做防幻觉质检，2 积分/次扣在 ledger 里。**每次 AI 生成都自动带质检，不是"做了就好"而是"做了且验证了"**。

#### 4.4 agent（智能体）

> "Agents are prompts + tools + memory + control flow. The control flow is where 90% of bugs hide."

**本地实证**：中俄轻舟的 AI 协作 5 角色定义（情报员/翻译官/自动化工程师/分析师/记录员）——每个角色一个 prompt 模板 + 一个工具集 + 一个记忆范围，比"造一个万能 agent"更容易出活。

#### 4.5 adaptation（自适应）

> "Models drift. Data drifts. Users drift. Your system must drift too."

**本地实证**：NIFTY `_volc_logged_out` 内存标记 + `logged_out` 持久化标记——支持"已登出但文件存在"的中间态，未来加"按月自动重登"也只需扩这个状态机，不动核心代码。

#### 4.6 serving（服务化）

> "From localhost demo to production is 10× the work. Plan for it on day 1."

**本地实证**：NIFTY `app.run(host="127.0.0.1", port=8901, threaded=True)`——刻意绑定 127.0.0.1（不让外网直接访问），第 3496 行 `threaded=True` 是 Werkzeug 单线程死锁后必须开的（HI-01 修复注释明示：一个慢请求会阻塞全站所有 API）。
**V3 隐患**：未来要开 0.0.0.0 必须先解决：① API Key 加密存储；② 管理员鉴权覆盖全部写接口；③ 上传限速防刷；④ 操作日志外发。**这 4 件事不做完就开 0.0.0.0 = 裸奔**。

#### 4.7 observability（可观测性）

> "Logs are for you. Metrics are for your users. Traces are for your future self."

**本地实证**：
- 日志：`unified_responder.log`（阿尔泰）记录每条 AI 回复的输入/输出/rule_chain/状态。
- 指标：`/api/stats` 7d/30d/180d/365d 按天聚合 gen/cost/ops 分布——客户在前端看见自己"用了多少"。
- 追踪：NIFTY 任务阶段的 `update_task_stage()` 第 665-676 行——前端能看见"上传图片 30s / AI 生成中 95s / 下载结果 12s / 质检中 20s"四段进度，每段都能算 ETA（`expected - elapsed` 第 701-710 行）。

## 关键纪律（跨框架提炼）

### D1: 决策先于代码

> ADR 必须在写代码前至少写"Context + 决策草案"——不是为了合规，是为了让自己在写代码前发现"我其实还没想清楚"。

### D2: 失败模式优先

> 写 ADR 时"后果"段先写失败模式（"如果错了会怎样"），再写成功收益——悲观预期比乐观估计更能指导后续排期。

### D3: 替代方案不是装饰

> Considered Alternatives 段是给"半年后的自己"留的——半年后有人问"为什么不用 X？"时能直接贴 ADR 链接，而不是翻历史 commit。

### D4: 5 支柱必须全过

> 任何架构决策都要用 AWS 5 支柱自检一遍——性能最优但成本爆表 = 不通过；安全满分但客户用不动 = 不通过。**5 个支柱有 1 个不及格就回去重做**。

### D5: 7 步流水线必须全跑通

> calmrocks 的 prompt → RAG → eval → agent → adaptation → serving → observability，缺任何一步就上线 = 给自己埋雷。

### ADR 4 段式模板 → 我们 16 个 ADR 的真实例子

**完整对照清单**（按 ID 排序）：

- **ADR-ALT-001** Chrome CDP 9222 作为统一平台账号载体——Context：6 平台账号体系各自独立 + 不能用官方 SDK/headless；Decision：独立 Chrome Profile + CDP 调私有 API；Consequences：✅ 一次扫码 6 平台受益 / ❌ token ~24h 失效硬痛点；Alternatives：❶ 各平台官方 API 限流严 ❷ headless 被检测 ❸ 6 个独立 Profile 操作成本 ×6。
- **ADR-ALT-002** AI 筛选与触达分层——Context：362 条/天误判 → 触发反垃圾 → 整批账号被封；Decision：采集 → 筛选 → 待联系队列 → 触达 4 步解耦；Consequences：✅ 任一环节挂掉不连累下游 / ❌ 增加 1 层 JSONL 落盘；Alternatives：❶ 采集同步 AI（采集挂 = 全部丢） ❷ 不过规则直接 AI 回复（Korobochki 案已经吃过亏）。
- **ADR-ALT-003** 5 平台风控等级 + 1+1+1 跟进节奏——Context：6 平台账号资产价值不等（VK 8 个月 vs TikTok 新号）；Decision：分平台每日上限表 + 90-150 秒随机间隔；Consequences：✅ 6 个月 0 账号被封 / ❌ 转化速度被牺牲；Alternatives：❶ 不分平台统一上限 ❷ 完全照搬跨境同行（3 天全封）。
- **ADR-ALT-004** 统一响应器（被动模式）——Context：客户主动来消息需 24h 有人回；Decision：cron 每 5 分钟 + 只检测未读 + `[[TRANSFER]]` 转人工；Consequences：✅ 24h 自动响应 / ❌ OUR_MSG_MARKS 关键词列表要持续维护；Alternatives：❶ 7×24 人盯（不可行） ❷ 不做（转化率低）。
- **ADR-ALT-005** CodeBuddy 云看板——Context：客户是老板不是技术人员，需扫码看进度；Decision：腾讯 CodeBuddy CN + 一键脚本打包上传；Consequences：✅ 任何电脑扫码可看 / ❌ 链接每次重启变；Alternatives：❶ 让客户一直开 Mac ❷ AWS/阿里云（预算门槛高） ❸ NAS（客户没有）。
- **ADR-NIFTY-001** 单文件 server.py 3500 行「先跑通后拆分」——Context：v1.0 目标 30 天内让小白跑起来；Decision：所有逻辑塞 server.py + 5 个外部模块；Consequences：✅ 13 天交付 13 轮迭代 / ❌ 架构债沉重；Alternatives：❶ 严格按模块拆分（晚 2-4 周） ❷ Flask Blueprint ❸ 微服务（单机撑不住）。
- **ADR-NIFTY-002** 双通道计费（LibTV 包月 + 火山按量）——Context：客户分两类（电商小白 vs 尝鲜用户）；Decision：主通道 LibTV + 备选火山 + 任一可用即全部能力开；Consequences：✅ 客户覆盖面扩大 / ❌ 双通道测试成本 ×2；Alternatives：❶ 仅 LibTV ❷ 仅火山 ❸ 三通道（先双通道跑通）。

- **ADR-ZRQZ-003** 缝隙打法——Context：跨境老手拼供应链/价格，王昕两个都不占；Decision：深度俄语本地化 + 快速小批量 + 跨平台情报；Consequences：✅ 6-12 个月窗口期要跑通 / ❌ 缝隙窗口期可能很短；Alternatives：❶ 拼供应链 ❷ 拼价格 ❸ 拼广告。
- **ADR-ZRQZ-004** AI 协作 5 角色——Context：一人完成全流程不可能什么都精；Decision：情报员/翻译官/自动化工程师/分析师/记录员 5 个独立 prompt 模板；Consequences：✅ 提示词可沉淀可复用 / ❌ 5 角色切换有上下文开销；Alternatives：❶ 单个万能 agent ❷ 完全人工 ❸ 雇人（预算 ≤3000 雇不起）。
- **ADR-ZRQZ-005** 资金/进度/AI 工具 3 道红线——Context：跨境 90% 新手死在囤货；Decision：不囤/不借钱/不 All-in + 预算 ≤3000；Consequences：✅ 心态稳 + 决策快 / ❌ 没有规模效应；Alternatives：❶ 孤注一掷 ❷ 找投资 ❸ 全职 All-in。
- **ADR-ZRQZ-006** 失败兜底——Context：30 天可能成功也可能失败；Decision：Go（30-50 SKU） / No-Go（转服务商零风险） + 红线触发立即停；Consequences：✅ 失败不是终局 / ❌ 30 天可能太短；Alternatives：❶ 无限试 ❷ 全职创业 ❸ 完全放弃。

> **16 个 ADR 的共性规律**：每个 ADR 的 Consequences 段都同时有 ✅ 和 ❌（诚实记录双面性），Alternatives 段至少列 2 个未选方案（给未来「为什么不选 X」留路标）。**这就是 ADR 比「决策记录」强的本质——它承认「做错也有理由」，而不是粉饰太平**。
