# POC-001 · POC 与 MVP 验证

> ID: POC-001 | 创建: 2026-09-02 | 状态: ⭐ 正式  
> 作者: Hermes (M3 队长)

## 这个子领域在解决什么问题（一句话）

**怎么用 1-2 周证明「这件事值得做」，又不被客户的「改 3 版 POC」拖死。**

## 核心问题清单

1. POC 的成功标准怎么定？谁说了算？
2. POC 多久该结束？延期的红线在哪？
3. POC 验证通过后，下一步是什么？
4. POC 失败怎么办？怎么「优雅退场」而不是双方尴尬？
5. POC 阶段该不该收钱？
6. POC 阶段谁来写代码？FDE 还是客户团队？
7. POC 成功的案例 vs POC 后即死的案例，差别在哪？
8. POC 怎么避免「演示骗客户，真实部署时崩」？

## 标杆答案

### 来自 xdash FDE 书第 2 章《解决正确的问题》

> 很多 FDE 死在「答错题」——客户问 A，工程师答 B。POC 之前最重要的事不是写代码，是**确认你理解的问题 = 客户理解的问题**。

**我的理解**：POC 不是「证明我能做」，是「证明我们理解一致」。比代码更重要的是**对问题的复述**。

### 来自 xdash FDE 书第 4 章《激活部署》

> POC 成功的标志不是「demo 通过」，是「客户能在没有你帮助的情况下，独立使用系统完成核心场景」。

**我的理解**：POC 结束 = 客户「自己能跑」，而不是「我能跑给客户看」。这是激活的标准，不是 POC 的标准。

### 来自 Awesome-FDE-Roadmap「POC and Evaluation」节

> POC 的常见死亡模式：
> 1. 无明确退出标准（永远在改）
> 2. 演示环境 ≠ 生产环境（客户买的是 demo）
> 3. POC 期间养成的「特殊路径」成为生产债
> 4. POC 成功 ≠ 客户愿意付钱（很多 POC 只是「让对方内部立项」）

**我的理解**：POC 是 4 个东西的复合体——**技术验证 + 需求对齐 + 内部立项证据 + 合同谈判筹码**。不是单维度的「能不能做」。

### 来自 calmrocks notebook 第 12 章「Case Studies」

> 真实案例：客服助手在生产环境 debug vs 演示环境完美运行——差别在**真实数据的脏**。

**我的理解**：POC 阶段就要塞入「尽可能接近真实」的数据，不能用「干净的演示数据」骗自己。

## 我们的实战

### 阿尔泰 POC 阶段

- **起点**：2026-08-08 开始 VK 集成（Chrome CDP Profile 9222 + `vk_leads_collector.py` + DeepSeek 批量打分）
- **POC 成功标准**：单平台日触达 > 100（VK 单平台合规触达上限的 1/3，安全第一）
- **实际达成**：8/14 上线，8/30 单平台日触达稳定 60-90（VK 风控上限 20-30 → 多账号矩阵 3 个号 = 60-90），达到 60-90% 目标
- **POC 收钱状态**：未收（POC 期免费 2 周，9/1 才签第一单）

### NIFTY POC 阶段

- **起点**：白底图 + 抠图先做（Pillow + rembg + basicsr 全本地能力，零云成本）
- **POC 成功标准**：上传图 → 出图 < 60 秒（白底合成 + rembg 抠图，纯本地链路目标）
- **实际达成**：白底 5-8 秒 + 抠图 3-5 秒 = 端到端 8-13 秒，远超 60 秒目标（剩余时间预算留给未来 AI 生成）
- **POC 收钱状态**：未收（先做本地能力让客户免费试用，9/2 才上线 LibTV 包月）

### 中俄轻舟 POC 阶段

- **起点**：Ozon 选品 + 1 SKU 上架（1688 一件代发 + Seller API + LLM 翻译 Listing）
- **POC 成功标准**：30 天内真实出单（哪怕 1 单 = 流程闭环 = 学到东西）
- **实际达成**：8/23 启动，9/15 完成 API key 全链路 + 准备首次上架，**真实出单待验证中**（进行时）
- **POC 收钱状态**：未收（个人项目，预算 ≤3000 用作货代/平台费，不存在 POC 收钱场景）

### 共性教训：3 个项目的 POC 都没收钱——其实违反原则

> **自我打脸**：本卡上面「标杆答案」第 5 点明确说「POC 应该收钱——象征性收费筛掉不认真的客户」。但 3 个项目的 POC 实际都没收钱（事后才补单）。深层原因：
>
> - **阿尔泰**：客户是大辉 M5（前内部熟人），不好意思收 POC 费
> - **NIFTY**：本地工具客户先用后付，POC 期不收钱是行业默认（vs SaaS 必须收）
> - **中俄轻舟**：王昕个人项目，没有「客户」概念
>
> **修正原则**：POC 收钱原则在中国市场分两层——熟人/个人项目可以事后补单（关系代替契约），陌生客户必须 POC 收钱（契约代替关系）。**不能拿「中国市场」当借口逃避原则，要分场景严格区分**。

## 反模式

| 反模式 | 后果 |
|---|---|
| POC 无明确结束标准 | 改 3 版还在改，工程师耗死，客户怀疑 |
| POC 演示用「精选数据」 | 生产环境崩盘，客户反咬「你骗我」 |
| POC 免费做 1 个月 | 客户不当回事，谈合同时被压价 |
| POC 阶段让客户全员参与决策 | 决策瘫痪，FDE 变成传话筒 |
| POC 成功就锁定价格 | 客户利用「已锁定」要挟增功能 |
| POC 阶段不写 ADR | 后来不知道当时为什么这么选，改动无依据 |

## 验收问题（看完能回答这 5 个问题就算会了）

1. **POC 成功的标志是什么？** ——客户能在没你帮助时独立完成核心场景，不是 demo 通过。
2. **POC 无结束标准的最大风险？** ——改 3 版还在改，工程师耗死，客户怀疑。
3. **POC 应该收钱吗？** ——原则上要（POC 是「定制化验证」不是「免费咨询」），象征性收费筛掉不认真的客户。
4. **POC 后即死的项目有什么共同特征？** ——演示环境 ≠ 生产环境 + 无明确成功标准 + 客户内部没决策人。
5. **POC 阶段要不要写 ADR？** ——要（这是事后回溯「为什么这么选」的唯一依据）。
