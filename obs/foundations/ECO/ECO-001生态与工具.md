# ECO-001 生态与工具

> 一句话：AI 项目用什么模型 / 框架 / 部署 / 监控——按"稳定 + 便宜 + 可控"三原则选型，避免被单一供应商绑架。

---

## 5-10 个核心问题清单

1. **模型选型**：主力模型是闭源旗舰（GPT/Claude）还是开源自托管（DeepSeek/MiniMax）？按量 vs 包月？
2. **框架选型**：LangChain / LlamaIndex / AutoGen / CrewAI 哪个匹配团队能力与场景？
3. **部署形态**：客户机是 macOS / Linux / Windows？单进程（launchd）还是容器（docker/k8s）？
4. **监控体系**：日志 / 指标 / 告警三件套是否齐全？是否自动巡检（cron + watchdog）？
5. **备份策略**：数据多久备份一次？本地 + 异地双备？
6. **供应商锁定**：核心能力是否押在 1 家 SaaS？能否 48 小时内迁移？
7. **成本曲线**：按量计费是否有失控风险？月度预算上限如何设？
8. **升级路径**：框架/模型升级是否影响线上？灰度策略是什么？
9. **可观测性**：能否从一个 trace ID 还原整条调用链？
10. **离线能力**：网络中断时本地能否继续工作至少 1 小时？

---

## 标杆答案（来源标引）

### 1. 模型：MiniMax M3 包月 vs DeepSeek 按量 vs Kimi K3
- **MiniMax M3 包月**：固定成本、调用不限次数、适合稳定主力推理（"牛马"角色）。
- **DeepSeek 按量**：高峰弹性、复杂推理首选（"队长"角色），需设月度预算硬上限。
- **Kimi K3（用户偏好）**：禁按量计费，避免月底天价账单，长上下文场景做轻量补充。
- 组合拳：**M3 牛马 + DeepSeek 队长 + K3 禁按量**，按场景路由。

### 2. 框架：LangChain / LlamaIndex / AutoGen / CrewAI
- **LangChain**：通用编排、工具调用成熟，社区最大，文档齐。
- **LlamaIndex**：RAG 场景首选，索引/检索能力专精。
- **AutoGen**：多 Agent 对话/协作场景，研究与原型首选。
- **CrewAI**：角色化任务编排，适合"虚拟团队"业务流程。
- 选型原则：**先跑通再抽象**，不要 5 人小团队上 AutoGen 玩多智能体。

### 3. 部署：launchd / docker / k8s
- **macOS 客户机**：launchd（开机自启 + 自动重启 + 日志统一）首选，单文件 plist 易维护。
- **Linux 服务器**：systemd unit 或 docker compose。
- **k8s**：仅团队 ≥ 10 人 + 多副本 + 多区域时才考虑，5 人以下纯属过度工程。
- 容器化原则：**能单进程就别上 docker，能单 docker 别上 compose，能 compose 别上 k8s**。

### 4. 监控：Hermes cron + watchdog + Baidu 网盘备份
- **Hermes**：定时任务调度（每日备份 / 对账 / 巡检）。
- **watchdog**：进程异常退出自动拉起，配合 launchd KeepAlive。
- **Baidu 网盘备份**：本地快照加密后异步上传，离线物理介质兜底。
- 告警三通道：邮件 + 微信 + Telegram，避免单点通知失灵。

## 我们的实战（必填）

### 阿尔泰：DeepSeek 队长 + M3 牛马 + K3 禁按量
- **DeepSeek**：复杂决策（内容生成、脚本编排）按量调用，预算硬上限 ¥3000/月。
- **M3 包月**：常规客服问答、模板回复、批量文本处理主力。
- **K3 仅包月**：长上下文文档分析做补充，绝不开按量。
- 路由规则在 `model-router.ts` 集中管理，按任务类型 + token 预算自动分流。

### NIFTY：launchd 自愈 + watchdog + snapshot
- NIFTY 主进程由 macOS launchd 托管（`com.nifty.agent.plist`），KeepAlive 自动拉起。
- 外层 watchdog 脚本每 5 分钟 `pgrep` 检测，进程僵死则强制 kill + 重启。
- 每日凌晨 3 点 snapshot：SQLite 备份 + 配置归档，加密后上传 Baidu 网盘。
- 半年零人工重启，验证 launchd 自愈有效性。

### 中俄轻舟：Ozon Seller API + 1688 一件代发
- **Ozon Seller API**：订单、库存、价格三接口轮询，失败走指数退避 + 队列重试。
- **1688 一件代发**：通过开放平台下单，库存自动同步至 Ozon。
- 工具栈：Python + requests + APScheduler + SQLite + launchd，全栈单机能跑。
- 监控：每日对账（订单 / 库存 / 资金）三方对不齐自动告警。

## 7 个反模式

1. **盲目追新模型**：每出一个新模型就切换，生产环境跟着 Beta 跑。
2. **强依赖云端 SaaS**：核心能力全部押在 OpenAI/Anthropic，无 fallback。
3. **单一监控指标**：只盯 QPS 不盯错误率，事故来了才发现。
4. **过度工程化**：5 人小团队直接上 k8s + Istrio，3 个月都在配基础设施。
5. **按量无上限**：Kimi/Claude 按量不设预算，月底天价账单。
6. **无备份验证**：每天备份但从不恢复演练，真出事发现备份损坏。
7. **框架锁死**：深度耦合 LangChain 1.0 API，升级一次重写半年。

---

## 5 个验收问题

1. 模型路由是否有"主力 + 备用 + 降级"三档且已演练切换？
2. 客户机部署是单进程（launchd/systemd）还是过度容器化（k8s）？
3. 监控是否覆盖日志 / 指标 / 告警三件套且至少 2 个通知通道？
4. 数据备份是否本地 + 异地双备且 ≥ 1 次恢复演练？
5. 单一供应商（云 / 模型 / 框架）下线时能否 48 小时内迁移？
