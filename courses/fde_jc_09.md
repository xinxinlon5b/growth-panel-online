# 上篇 · 书籍内容

## 引子：从“会回答”到“能交付”

大模型进入业务现场后，最先暴露的不是不会写文章，而是很难独立把一件事做完。它能生成方案、总结会议、写代码，却需要人在中间不断确认下一步、资料位置、系统调用和结果质量。人类仍是操作者，模型只是强大的工具。

Agent 产品解决的是“人类不断盯梢”的成本。理想状态下，用户只提出目标，Agent 就能理解任务、拆分计划、调用工具、读取记忆、执行动作，并根据结果反思修正，直到交付可用结果。关键不是美化聊天窗口，而是把“目标—行动—反馈—再行动”变成可控工作系统。

产品经理必须回答三个问题：什么任务值得交给 Agent；模型、记忆、工具如何组合；如何让一次惊艳演示变成稳定、可收费、可持续交付的业务能力。

## 主线：Agent 的技术演进与产品判断

1. **观察风口演进。** AutoGPT 让 Agent 进入公众视野；Devin 将“AI 程序员”推到聚光灯下；更通用的产品开始处理简历、调研和办公任务。人们期待 AI 从回答问题升级为独立完成任务。
2. **识别大模型缺口。** 模型推理时不会自动改变；对话记忆受上下文限制；不能直接与外部系统交互；复杂开放任务仍有能力边界。
3. **明确协作等级。** Copilot 阶段，人类和 AI 工作量大致相当；Agent 阶段，AI 完成绝大部分工作，人类设定目标、提供约束、处理例外并验收。
4. **理解产品组成。** 大模型作为决策中枢，配合规划、记忆、工具调用、执行和反思，补足场景关键缺陷。
5. **从演示走向工作流。** 自然语言先形成初版，再由专业人员细化、测试、做权限和数据治理。Demo 能跑不等于企业系统可靠。
6. **翻译成业务价值。** 围绕任务完成率、人工介入率、交付周期、错误代价和复用范围设计，而不是只比较模型参数或聊天效果。

## 逐点精读一：为什么 Agent 持续成为热点

### 风口不是凭空出现的

Agent 并非大模型时代才有。IBM 深蓝在 1997 年战胜国际象棋大师，AlphaGo 战胜围棋世界冠军，AlphaStar 在《星际争霸2》中击败职业选手，OpenAI Five 也曾在《Dota 2》中战胜顶尖玩家。这些系统的共同点是：在明确环境和规则中，较少依赖人类，独立采取行动并取得结果。

大模型时代的变化，是降低构建通用智能体的门槛。AutoGPT 以命令行展示自动拆解和执行任务；Devin 将自己定位为类似“一个人的软件工程师”，采用接近人力服务的定价逻辑；通用 Agent 又把任务扩展到简历处理、资料整理和办公工作。产品价值不在模型能不能说，而在能不能把事情推进到结果。

### 区分演示、能力与交付

Devin 的早期宣传引发巨大期待，后来又遭到外界对演示的逐帧分析和质疑。这说明酷炫演示不能证明稳定生产能力。评估 Agent 至少要看四层：

- **展示层：** 是否隐藏人工操作、预设条件或失败案例。
- **能力层：** 相同输入能否重复完成，遇到不确定性是否暴露并处理。
- **流程层：** 是否访问真实数据、调用真实工具、保存上下文并遵守权限。
- **业务层：** 结果是否被采用，是否减少时间和人力，能否沉淀为交付资产。

不能只问“能不能做”，还要问“边界是什么”“失败损失多大”“谁来接管”。可信度来自可观测、可回滚、可验收。

## 逐点精读二：补上大模型落地的四个缺口

### 缺口一：推理不会自动训练

大模型训练完成后，每次运行通常是独立推理。它不会因答错而自动修改参数。继续训练、微调和强化学习都需要数据、算力、工程和评估投入，成本较高。

产品不能简单承诺“长期自我变聪明”。应区分两种学习：模型能力升级依赖版本迭代；产品经验积累则保存用户偏好、任务记录、成功案例、规则和反馈，让下一次执行更贴近用户。前者是训练问题，后者是记忆、检索和工作流问题。

### 缺口二：上下文不等于长期记忆

模型看似记得对话，是因为历史消息被放进提示词。上下文窗口有限，历史越长成本越高，最终会达到上限。把全部聊天记录塞入上下文，不是可靠的长期记忆。

应区分三种记忆：短期记忆保存当前任务步骤、变量和临时判断；长期记忆保存稳定偏好、组织知识和历史结论；任务记忆保存某次交付的输入、过程、产物和验收结果。记忆还要支持检索、更新、删除和追溯，否则会带来过期信息、隐私泄露和错误引用。

### 缺口三：模型不会天然操作外部世界

模型本质是预测下一个 Token。没有工具接口时，它主要只能聊天。查实时信息、订票、查库存、创建工单、更新 CRM、计算指标和运行代码，都需要外部系统提供工具，并定义参数、权限、返回值和异常处理。

工具调用不是接一个按钮。产品经理要规定工具能做什么、不能做什么，哪些参数必填，是否允许写操作，失败返回什么，是否需要二次确认，如何记录审计日志。搜索、日历、计算器、代码解释器、数据库和业务系统都是 Agent 的手脚，但权限和风险必须治理。

### 缺口四：复杂任务仍有边界

推理模型在数学、编程等答案相对明确的领域进步明显，但复杂开放任务仍会遗漏、误判、产生幻觉。传统 Agent 在单一规则环境中可超越人类；大模型 Agent 更通用、更易迁移，却不等于在所有复杂任务上稳定超过人类。

产品目标不应是“完全替代人”，而应是“在明确边界内独立完成高频任务，在高风险节点交给人处理”。任务可分为低风险自动执行、抽样复核和必须人工审批三类。

## 逐点精读三：从 Copilot 到 Agent

Copilot 是副驾驶：AI 提供建议、草稿和局部操作，人类持续判断和推进。Agent 把工作重心交给 AI：人类说明目标和约束，Agent 自主计划和执行，人类只在关键节点介入。

这带来三项设计变化。第一，交互单位从一个问题变成一个任务，输入包含目标、背景、约束、输出格式、权限和截止条件。第二，界面从聊天记录变成任务面板，展示状态、计划、工具调用、产物、风险和待审批事项。第三，评价从单轮回答质量变成端到端完成质量，关注完成情况、耗时、修改次数、资源使用和可复盘性。

自动化提高后，必须补上暂停、撤销、重试、转人工和审批机制；否则一次不可逆错误就会摧毁信任。

## 逐点精读四：传统 Agent 与大模型 Agent

传统 Agent 针对封闭领域训练，效果极好，甚至击败世界冠军，但成本高、扩展性弱，能下围棋的系统不能自然迁移到另一款游戏。

大模型 Agent 的优势是通用和可扩展。一个通用模型通过提示词、工具和知识库，可承担翻译、编程、分析和客服等角色。基础模型训练投入很高，但能力能迁移到多种任务，个人和小团队也可构造产品，应用试错成本下降。

这不是“新技术一定更好”。封闭、规则清晰、追求极致性能的任务，专用系统仍有优势；目标多变、知识密集、需要自然语言协作的任务，大模型 Agent 更有潜力。选型应看规则稳定性、答案可验证性、工具数量、容错要求、数据敏感度和迁移需求。

## 逐点精读五：典型产品如何做成体验

### 教育：口语教练

口语教练的核心不是陪聊，而是闭环：设定场景、语音对话、分析表达、评分反馈，再进入下一轮。它可持续工作，不需要真人审核每次回复，决策和反馈主要由 AI 完成。

关注点包括语音识别准确度、评分透明度、反馈可执行性、难度适配和持续练习意愿。教育 Agent 的价值是持续扮演教练、评估者和陪练者。

### 情感陪伴：角色、人设与长期关系

AI 陪伴产品提供多个角色，每个角色有稳定人设、故事背景和表达风格。用户与其互动的不是通用接口，而是持续一致的角色。角色记忆、情绪回应和内容边界决定关系是否可信。

长期记忆是核心体验，但必须可控。用户应知道系统记住了什么并能修改、删除。产品还要处理依赖、误导、隐私和敏感内容风险。

### AI 教学：完整教学过程

AI 教师将课程讲解、练习布置、答疑和反馈串成连续流程。价值不在一次问答，而在有目标、有进度、有反馈的学习任务系统。

### Agent 编程：先做 Demo，再工程化

Agent 编程产品能根据一句需求创建网站、生成前端代码并补充管理后台。不懂代码的产品经理也能得到可运行 Demo。典型流程是：产品经理用自然语言构建框架和原型，确认方向后由程序员下载代码，进行架构调整、细节打磨、测试、部署和维护。

这划清了“原型自动化”与“生产系统工程化”的边界。Agent 适合验证需求、展示交互和争取资源；完整系统仍需数据模型、鉴权、异常处理、性能、安全、维护和上线流程。Demo 可运行，不能替代工程验收。

## 逐点精读六：Agent 架构检查清单

一个 Agent 可抽象为七层：

1. **目标层：** 任务是什么，完成条件是什么。
2. **模型层：** 模型选择、推理需求、成本、速度和稳定性。
3. **规划层：** 能否拆分步骤，是否支持动态调整。
4. **知识与记忆层：** 哪些来自知识库，哪些来自本次任务，如何追溯和更新。
5. **工具层：** 搜索、计算、代码、数据库和业务系统如何调用，权限如何划分。
6. **执行反馈层：** 如何判断结果，失败如何重试、降级或转人工。
7. **治理交互层：** 如何查看进度、审批、回滚，并形成日志和指标。

产品经理应同时看任务成功率、过程可控性、结果可验证性、单位任务成本和规模化交付能力。七层架构与五类指标对齐，Agent 才能从 Demo 变成产品。

## 结论与金句

Agent 让 AI 从生成内容进入完成任务：以大模型为中枢，用规划弥补一步到位的不足，用记忆弥补上下文限制，用工具连接外部世界，用反思反馈提高完成质量。

**金句一：Agent 的价值不在于会聊天，而在于能否把任务推进到可验收的结果。**

**金句二：上下文是临时工作台，记忆才是可管理的长期资产。**

**金句三：演示能证明可能性，稳定交付才能证明产品价值。**

**金句四：大模型降低了构建 Agent 的门槛，却没有取消工程、权限和责任。**

# 下篇 · 方法论精华

## 一张速查表

| 判断问题 | 关注维度 | 设计动作 | 验收指标 |
|---|---|---|---|
| 任务适合吗 | 高频、重复、可验证 | 定义目标和边界 | 端到端完成率 |
| 模型够用吗 | 能力、速度、成本、稳定性 | 模型路由和降级 | 单任务成本、时延 |
| 需要规划吗 | 多步骤、存在依赖 | 计划、执行、修订 | 计划成功率 |
| 需要记忆吗 | 跨会话偏好、历史、组织知识 | 区分三类记忆 | 召回准确率、过期率 |
| 需要工具吗 | 查询、计算、写入系统 | 定义契约、权限、日志 | 调用成功率 |
| 如何控风险 | 错误代价、数据敏感、可逆性 | 审批、抽检、回滚 | 高风险拦截率 |
| 如何规模化 | 模板、知识、连接器复用 | 沉淀交付包和评估集 | 周期、复用率 |

## 通用原则

**原则一：先选任务，再选模型。** 先问是否值得自动化、结果能否验收、失败是否可承受，模型选择服务任务。

**原则二：目标必须可验收。** 将“做好客户分析”拆成数据范围、分析维度、格式、引用要求和决策用途。

**原则三：自动化与风险反向匹配。** 可撤销草稿可自动化；对外发送、费用、权限和客户承诺需审批审计。

**原则四：记忆必须可治理。** 记住什么、为何记住、何时更新、谁能查看、如何删除，都应明确。

**原则五：工具优先于复杂提示词。** 需要实时数据或写入系统时，应先设计稳定接口，再规定调用时机和约束。

**原则六：失败是流程的一部分。** 让失败可发现、可解释、可恢复，每一步都有状态、证据和替代路径。

**原则七：先做闭环，再扩展能力。** 先稳定完成一个场景，再增加工具、角色和模型。

## 可复用模式

### 模式一：目标—计划—执行—验收
将目标转为任务清单，逐项调用工具，按验收条件检查结果，适合研究、报告、交付和运营。

### 模式二：检索—生成—引用
先从知识库检索证据，再生成答案并保留来源，适合企业问答、交付手册和 8895 知识库。

### 模式三：草稿—审批—正式动作
Agent 先生成邮件、报价、方案或工单，人审批后才执行外部动作，适合销售和客户沟通。

### 模式四：低风险自动化—高风险转人工
分为自动完成、抽样复核和强制人工三档，根据敏感度、不可逆性和客户影响动态分流。

### 模式五：重试—降级—接管
工具失败时有限重试，仍失败则切换工具或输出中间产物，超过风险阈值转人工，并携带上下文和失败原因。

### 模式六：交付资产化
每次交付沉淀场景模板、提示词、知识切片、工具连接器、验收集和故障案例，下一次组合资产并补齐客户差异。

# 借鉴篇 · 我们能借鉴的点

结合王昕的企业 AI 客户交付、FDE、获客系统和 8895 知识库，重点是把 Agent 底层方法转成业务系统。

1. **建立交付任务 Agent。** 场景：签约到上线的需求澄清、资料收集和实施推进。做法：结构化客户目标、现状、系统清单、权限、里程碑和验收标准；自动生成计划、提醒待办、汇总纪要；权限变更、数据迁移和上线由 FDE 审批。
2. **拆解 FDE 诊断流程。** 场景：首次访谈和问题定位。做法：预置行业问题树，Agent 追问业务流程、数据来源、角色权限和成功指标，形成诊断报告；FDE 校正关键判断。
3. **建设 8895 检索—引用—反馈闭环。** 场景：交付人员、销售和客户查知识。做法：按产品、行业、版本、客户类型和有效期切分；回答附来源版本；“需修正”进入修订队列，保证可追溯。
4. **建立客户任务记忆。** 场景：长期项目跨周、跨角色协作。做法：保存目标、确认事实、未决问题、历史方案、接口状态和验收记录，区分事实与推断，并按客户和角色隔离敏感信息。
5. **将获客系统升级为线索推进 Agent。** 场景：官网、活动、内容和转介绍线索。做法：读取来源和企业画像，判断业务问题，生成沟通草稿和会议议程；销售确认前不自动承诺价格、周期和能力边界。
6. **建立“问题—方案—证据”三联单。** 场景：售前方案和客户复盘。做法：记录原始问题、影响、方案、知识来源、结果和反馈；Agent 生成初稿，FDE 确认事实，避免夸大偶然成功。
7. **用 Agent 编程验证内部工具。** 场景：交付看板、满意度问卷、客户后台和线索 Demo。做法：自然语言生成原型，方向确认后由工程补齐鉴权、校验、日志、测试、部署和备份；区分 Demo 与生产验收。
8. **设置交付风险分级。** 场景：生成报告、修改知识、调用客户系统。做法：摘要和内部草稿自动执行；写知识和改配置复核；删除数据、改权限、对外发信和触发费用强制审批并留审计。
9. **沉淀 FDE 失败案例库。** 场景：答错、工具失败和客户异议。做法：记录输入、判断、错误节点、人工修正、结果和预防规则，转成评估题集，测试引用、拒答和转人工能力。
10. **用任务指标衡量价值。** 场景：交付和获客运营。做法：追踪完成率、一次通过率、人工介入率、交付时长、单任务成本、知识复用率、线索转会议率和满意度；聊天量上涨不等于价值上涨。
11. **形成场景包商业交付。** 场景：复制 FDE 服务。做法：场景包包含目标模板、访谈树、知识结构、连接器、提示词、审批节点、验收集、培训和运维说明，销售的是能跑起来的工作系统。
12. **明确人机服务边界。** 场景：客户对交付结果负责。做法：合同、方案和界面说明能力边界、确认节点和数据保存规则；FDE 处理例外和最终沟通，透明比夸大“全自动”更能建立信任。
13. **用反馈反哺路线。** 场景：多客户共性需求与个性需求冲突。做法：Agent 汇总去重，按影响、价值、成本、风险和复用潜力用 RICE 或四象限评估，区分定制要求与平台能力。
14. **以最小闭环启动试点。** 场景：新客户首次试点。做法：先选资料足、结果可验证、失败可回滚的任务，如交付问答、会议纪要转待办或方案初稿；跑通目标、知识、工具、审批和指标后再扩展。

## 收束：产品化的最后一公里

Agent 时代，AI 产品经理设计的是完整任务链：用户为何提出目标，Agent 如何计划，知识从哪里来，工具怎样执行，结果如何验收，失败谁接管，经验如何沉淀，价值如何收费。

对王昕业务，最值得借鉴的不是追逐每个新模型，而是组织客户交付中重复出现的判断、资料、动作和反馈。FDE 负责复杂问题和关键关系，Agent 负责检索、整理、推进和记录，8895 知识库让经验可复用，获客系统把客户问题带入同一条数据链。这样，Agent 才会成为企业 AI 服务的执行层与学习层。
