# 上篇 · 书籍内容

## 引子：为什么需要 RAG

大模型有两个绕不开的硬伤：**幻觉** 和 **知识更新不及时**。幻觉是大模型在不知道答案时一本正经地胡说；知识更新不及时是大模型的训练数据有截止日，截止日之后发生的事情它就答不上来。这两个还不是最致命的，**最致命的是它答不了企业私域问题**。客服话术、产品规格、合同条款、内部制度……这些不会出现在公共互联网里，更不会拿去训练大模型。所以即便大模型再强，也无法被直接用在企业的核心业务场景里。

要解决「让大模型回答它没学过的私域知识」这件事，方法有两条路：微调（Fine-tuning）和 RAG（Retrieval-Augmented Generation，检索增强生成）。微调是把知识灌进模型的「脑子」里，RAG 是把知识放在模型旁边，让它「翻书答题」。这两条路不是谁好谁坏，是场景不同。UP 主给出了一个判断标准：**长期不变的知识（法律条文、金融规则、企业内部固定制度）适合微调；频繁更新的知识（产品手册、客服话术、政策法规、行业资讯）适合 RAG**。

RAG 的核心概念一句话就能说清：**「给我一个上下文，我可以回答你整个世界。」** 在用户提问的时候，先从知识库里检索出相关的参考资料，把参考资料和原问题一起塞给大模型，让它「参照资料」作答。这样一来：

- 大模型不必记住所有私域知识，只需要具备「读懂参考资料 + 整合输出」的能力；
- 知识一旦更新，只需要更新知识库，不必重训模型；
- 每一句回答都能溯源到原文，可解释性强；
- 解决私域问答 + 解决幻觉 + 解决时效，三件事一石三鸟。

RAG 最容易落地的三个场景是 **AI 客服**、**政策查询**、**AI 搜索**。客服和政策查询的本质是把 FAQ 和文档喂给模型；AI 搜索则是把「联网检索 + 参考资料汇总」的过程包装成 RAG。三者覆盖了企业 AI 落地的 80% 场景。

## 主线：RAG 全流程

RAG 全流程分为两条主线：**离线建库**（红色，事先一次性准备好）和 **在线问答**（蓝色，每次用户提问时执行）。

```
【离线建库】
文档 → 切分器 → 知识块 → Embedding 模型 → 向量 → 向量数据库

【在线问答】
用户问题 → Embedding 模型 → 问题向量
                              ↓
              向量数据库检索 → Top-K 参考文档
                              ↓
        提示词模板（问题 + 参考文档） → 大模型 → 答案
```

RAG 三个字母对应三个阶段：**R**etrieval（检索）、**A**ugmented（增强）、**G**eneration（生成）。中间被省略的部分就是「检索增强」的全过程。

按 UP 主的话讲：**学会只需要一周，上线需要一年**。学会是因为流程就那么几步，框架成熟、代码现成；上线难是因为「可选参数太多、工程细节太碎」，每一步都有一堆旋钮要拧。下面把这几步拆开讲。

## 逐点精读

### 一、知识收集

第一步永远是先把数据准备好。要考虑三件事：

1. **存哪里**：PDF？数据库？Word？不同格式的解析难度不一样。PDF 是公认的硬骨头，因为 PDF 存的是图片版式，要先 OCR 再解析表格与正文，比 Markdown/纯文本难得多。还要考虑是否有图片、视频、表格等非纯文本内容——一旦涉及，就得多模态模型介入。
2. **怎么清洗**：UP 主给了一个非常务实的建议——**别过度清洗**。大模型的容错性其实很高，建设 RAG 时只要做「粗洗」就够了，过度精细的清洗只会拖慢上线进度、让团队陷在预处理里出不来。
3. **跟着场景收**：做产品客服就只收产品相关知识，不要把公司规章制度一股脑塞进来。知识库的「边界」要严格对齐业务场景的「边界」。

### 二、文档切分（Chunking）

为什么要切？因为大模型有上下文窗口限制（一次性吃不下整本书），同时**整本书丢进去检索效率极低、Token 消耗极大**。RAG 要从知识库里挑出最相关的几段，所以必须先切小。

切分有个永恒的取舍：

- **切太大**：一个块里混了三四个语义（公司介绍 + 地址 + 产品），检索时匹配不准；
- **切太小**：一个块里只有半句话，生成时缺上下文，答案不完整。

UP 主介绍了四种切分方法，效果上后者通常更好，但「更好」是概率意义上的，不绝对：

1. **按固定大小切**：按字数或 Token 数固定切片。最简单，但效果最差，句子可能被腰斩。
2. **按标点切**：按换行符、句号等切分。能保证一个句子不会被切开，比方法 1 略好。
3. **按文档结构切**：按标题、章节切分。隐含假设是「同一章节讲同一件事」，对结构化文档效果最好（特别适合带章节的电子书、研究报告）。
4. **按语义切**：先按句子切（因为单句往往只表达一个语义），再用语义相似度把相邻相似的句子合并到一起。既保证语义独立、又保证语义完整，理论上最好，但实现成本也最高。

**还有一个隐藏要点**：如果数据本身是「问一答一」的 FAQ 形式（客服常见问题库），甚至不需要切分，一问一答天然就是一个完整的语义块。

### 三、向量化（Embedding）

为什么要把文字变成向量？因为**计算机只认数字，不认文字**。所有「让计算机读懂文字」的努力，本质都是把文字转成数字序列。

UP 主梳理了文字向量化的演化史：

1. **One-Hot 独热编码（0/1 表示）**：建一个大词表，每个词在词表里出现就标 1、不出现就标 0。问题是向量维度等于词表大小（动辄上万），而且「两个词有多相似」完全看不出来。
2. **词频表示（不去重的 One-Hot）**：在 0/1 的基础上，加上「出现了几次」。比 1 好一点，但仍没解决维度灾难和语义丢失。
3. **TF-IDF**：用词频 × 逆文档频率给每个词算权重，比前两个聪明，但仍然是「词袋模型」，理解不了「苹果和水果是同类」这种语义关系。
4. **稠密向量（Dense Embedding，神经网络时代）**：用神经网络把一段文字压缩成 512/1024/2048 维的向量，**几乎每一个维度都有数值**。语义相近的文本，向量距离也近；语义无关的，距离就远。

稠密向量的最大优势是 **它能理解语义关系**：

- 「想你了」和「想你」意思相近 → 向量距离近；
- 「中国不能没有山东，就像西方不能没有耶路撒冷」→ 模型能自动把「山东」和「耶路撒冷」做对比；
- 问「天空中飞行的天鸟如何保证它能平稳下来」，虽然没出现「飞机」二字，向量检索也能找到飞机相关的文档。

**实战要点**：

- 不用自己训练 Embedding 模型，直接用 Hugging Face、MTEB 排行榜上现成的开源模型即可；
- 维度不是固定的，根据模型不同可能是 512、1024 或 2048；
- 一旦选定模型，向量维度就锁定了，后续整个向量数据库的 Schema 都得跟着走。

### 四、向量数据库

向量数据库做三件事：**存向量、做相似度检索、支撑业务调用**。常见的有 Milvus、Pinecone、Chroma、Qdrant 等。选型时关注：数据规模、检索延迟、是否支持元数据过滤、运维成本。

值得注意的是：**前面所有步骤（切分、向量化、存储）其实都没用到「对话大模型」的能力**——只有最后一步「生成答案」才用到。前面那一长串其实是一个独立的「检索系统」，这就是为什么 RAG 项目可以分阶段交付、可以小步快跑。

### 五、检索（Retrieval）

检索有两大类方法：

**方法 A：相似度检索（向量语义检索）**

把用户问题也变成向量，到向量数据库里找最近的 K 个向量。常用的相似度度量有：

- **余弦相似度**：看两个向量的「方向夹角」，夹角越小越相似；
- **欧氏距离**：看两个向量的「直线距离」，距离越近越相似。

优点：能理解深层语义、能挖掘用户真实意图。
缺点：黑盒、不可控、对专业术语 / 编号类查询不友好。

**方法 B：关键词检索（倒排索引）**

先建一张「关键词 → 文档」的反向索引表。用户提问后，抽取关键词，倒查索引表，召回包含关键词的文档。

优点：精准、可控、对于「第 X 章第 Y 条」「产品编号 XXX」这种结构化查询极其高效。
缺点：完全不理解语义，碰上同义词、近义词就抓瞎。

**实战上两种通常要组合使用**（这就是后面要讲的「多路召回」）。

### 六、生成（Generation）

检索拿到 Top-K 参考文档后，进入生成阶段。这一步做两件事：

1. **构造提示词（Prompt）**：把用户原始问题 + 参考文档拼成一个 Prompt 模板，塞给大模型。常见模板还会附加「如果你不知道就回答『不知道』」之类的指令，减少幻觉。
2. **选大模型**：要考虑开源还是闭源。

| 维度 | 开源 | 闭源（API） |
|---|---|---|
| 安全隐私 | 高，本地部署 | 低，数据需出网 |
| 算力要求 | 高，需要 GPU 集群 | 低，按调用付费 |
| 维护成本 | 高，自行运维 | 几乎为零 |
| 模型能力 | 取决于具体模型（DeepSeek 等开源模型已超过部分闭源） | 通常较强 |

UP 主的建议：**ToB 场景优先考虑开源/本地部署，ToC/小团队优先考虑闭源 API**。

## 10 个 RAG 优化技巧

RAG 上线难，难在「工程细节」。UP 主把 10 个常见优化技巧分成三大块：**5 个检索优化 + 3 个生成优化 + 2 个提示词优化**。

### 检索侧优化（5 个）

#### 1. 摘要检索（Small-to-Big 之一）

切分时把块切大一点，用大模型对每个块生成一份**摘要**存入向量库。检索时用摘要匹配，匹配成功后把**原块**返回给生成阶段。
- 摘要语义更精炼 → 检索更准；
- 原块信息更完整 → 生成更全。

#### 2. 子问题检索（Small-to-Big 之二）

对每个知识块用大模型生成「可能命中这块的几个典型问题」，把这些问题向量入库存起来。用户提问时，先检索问题，命中后返回对应的原块。
- 一块内容可能同时回答「产品 A 是什么」「产品 B 是什么」等多个问题，子问题索引让每个角度都能被召回。

#### 3. 句子窗口检索（Small-to-Big 之三）

把块切到最小粒度（一个句子或一段话），检索时先精准定位到这句话，再把它的「前后 N 句」拼接成完整窗口送给生成阶段。
- 检索时细（精准），生成时宽（完整），两全其美。

> ⚠️ 这三种 Small-to-Big 方法都依赖大模型介入，**效果好不好完全取决于大模型本身的能力**。如果大模型性能一般，可能反而不如原始方案。

#### 4. 多路召回

同一个问题同时跑多种检索方式（关键词 + 向量语义 + 其他），把多条召回结果合并去重，按某种打分机制选 Top-K。

合并打分有两种经典算法：

- **倒数排名融合（RRF）**：每个文档在每个召回通道里有个排名，排第 1 得 1 分、排第 2 得 0.5 分、加权求和。但 RRF 对「第一名」加权过重（一旦拿到第一就直接无敌），需要加平滑指数才能让稳定发挥者胜出。
- **加权求和**：对每条召回通道人工设定权重（比如关键词 0.3、向量 0.7），按权重加总。

多路召回的好处是「不把鸡蛋放在一个篮子里」，能显著提升召回质量。

#### 5. Rerank 模型

多路召回到的文档可能多达几十条，直接全部喂给大模型会爆 Token、还会引入噪音。**Rerank 模型就是一个「二次精选」**：它接收「问题 + 文档」对，给出相关性分数，把最相关的几条挑出来再送给大模型。

为什么不一开始就上 Rerank？**因为 Rerank 模型很贵**。它要对每一条候选都算一次分数，几百上千条文档跑下来慢且贵。多路召回先粗筛、把候选压到几十条，再交给 Rerank 精筛，是性价比最高的做法。

Rerank 也有现成模型（BGE-Reranker、Cohere Rerank 等），不用自己训练。

### 生成侧优化（3 个）

#### 6. 葫芦娃找爷爷模式（顺序喂入）

把检索到的 N 个知识块**一个一个**按顺序喂给大模型，每喂一个就让大模型判断「这是不是最终答案」。是 → 结束；否 → 喂下一个、继续问。遍历完所有块还没出答案，就把最后一个当答案。

优点：能用上所有块，避免上下文窗口溢出。
缺点：调用大模型 N 次，成本极高。**适合块数 ≤ 5 的轻量场景**。

#### 7. 分块打包模式（分 piece 喂入）

把 N 个知识块**分成若干组**，每组打包喂一次大模型，每组同样问一次「这是不是最终答案」。

优点：节省调用次数（假设 9 块分 3 组，只调 3 次大模型而不是 9 次）。
缺点：组与组之间可能存在信息割裂。
**比葫芦娃模式更实用，是大多数项目的默认选择。**

#### 8. 链式压缩模式（前一次输出当下一次输入）

把检索到的块分成几组，**第一组喂给大模型得到中间结果**，把中间结果当作第二组的「前置上下文」再喂给大模型……以此类推。理论上能产生递进式深度推理，但**前一步错了后面全错，调试极难**。UP 主的建议：**了解即可，慎用。**

### 提示词侧优化（2 个）

#### 9. 提问改写（Query Rewrite）

用户的提问五花八门，不能直接拿去检索。三种典型场景：

- **指代消解**：用户先问「吕布战力最高」，再问「他哪年生的」——必须把「他」替换成「吕布」才能正确检索。
- **复杂问题拆解**：用户问「目前值得购买的股票是哪一支」，太复杂，要拆成「哪些行业值得买 → A 股票基本面怎么样 → 当前估值是否合理」三步走。
- **口语转标准**：把「你们发什么快递」改写成「物流方式 / 快递公司」。

改写可以基于规则（正则替换、关键词映射），也可以基于大模型（让 LLM 改写后送检索）。

#### 10. 合理利用元数据

元数据是「对文档的描述」，比如文档类型、作者、发布日期、章节号。**它不是文档正文**。四类典型用法：

1. **检索前过滤**：用「文档类型=科幻」直接过滤掉无关文档；用「发布日期 ≥ 某时间」过滤掉旧版本。
2. **检索中加权**：把权威来源加权高（专家 0.8 vs 学生 0.2）；把可信度低的来源加权低（防止恶意回答污染）。
3. **检索后排序**：把关键文档往前排，让大模型「优先看见」。
4. **生成时增强体验**：把来源 URL、标题、发布时间拼到答案尾部，让用户能溯源（AI 搜索的标准做法）。

## RAG 评估

没有评估就没有优化方向。RAG 评估分三大块，**最关键的是「检索阶段」**——从头向量到参考文档出来这一段链路直接决定了答案质量。

### 三大评估维度

#### 1. 准确率（最终答案对不对）

这是最直观的指标——给一批「问题 + 标准答案」，让 RAG 跑一遍，对比输出的最终答案和标准答案，给出准确率或人工打分。

#### 2. 忠实度（Faithfulness）

大模型生成的内容**是否忠实于提供的参考资料**。哪怕答案「碰巧对了」，但如果模型没看参考文档自己胡诌，依然判错——因为它没有按你给的内部资料作答。这条对企业内部 RAG 尤其重要（内部资料可能与外部常识相悖）。

#### 3. 召回率 / 精准率 / F1（检索阶段）

- **召回率（Recall）= 检索到的相关文档数 / 所有相关文档总数**：所有应该被找到的相关块，RAG 找回了几成？
- **精准率（Precision）= 检索到的相关文档数 / 检索到的总文档数**：RAG 找回来的东西里，有多少是真的相关的？
- **F1 = 召回率和精准率的调和平均**：综合考量两者。

召回率与精准率天然对立：召回率拉满（把全部文档都返回）→ 精准率骤降。要在两者之间找平衡点，用 F1 调优。

### 两种评估方式

**人工评估**：准备测试集（问题 + 标准答案 + 评分标准），人工逐一比对。成本高但**准确率最高，是上线前的最后一关**。前期可以用大模型生成测试样本、降低人力投入，但**人工「一对一核对」这个环节不能省**。

**模型自动评估**：

- 用一个更强大的「裁判模型」（如 GPT-4）给 RAG 答案打分；
- 把标准答案和 RAG 答案做文本相似度对比（余弦相似度、BLEU 等），相似度越高分越高。

**辅助工具**：LangSmith、RAGAS、LlamaIndex 自带评估模块等，可一键跑完整流程、可视化每个环节的指标。

## 项目经理视角：上线 RAG 项目的 6 个灵魂拷问

UP 主最后一课以「项目经理视角」收尾，把 RAG 从技术问题拉回工程管理问题。**项目启动前必须先回答这 6 个问题：**

1. **项目可行性**：这个 RAG 项目真的能做成吗？评估复杂度、开发周期、人力成本、预期收益。如果自己都判断不了大模型能不能做这件事，就别立项。
2. **用户与场景**：给谁用？内部员工还是外部客户？单轮问答还是多轮对话？每个组合对技术选型要求都不一样，必须**事先钉死**。
3. **知识库边界**：包含哪些知识？存在哪个媒介（PDF / 数据库 / 内网 Wiki）？企业内部有没有可用的大模型（如果不能连外网 API，就必须先解决「本地大模型」的问题，没有这个前提项目做不了）？
4. **准确度要求**：甲方要求准确率 80% 还是 95%？要求不同，工程量和方案差异巨大，**必须事前和甲方对齐**。
5. **项目周期与预算**：评估周期、算力预算、Token 成本。
6. **验收标准**：什么算「做完了」？答案准确率、响应时延、并发能力都要写进验收条款。

UP 主还反复强调一条：**先把 demo 跑通，再逐步迭代优化**。不要妄想一次做到完美——先把整体框架搭起来，每个环节能跑通、能给老板看到进度，再一点一点把单点能力打深。这是从「学会一周」过渡到「上线一年」的关键心态。

### RAG vs 微调：项目层面的对比

| 维度 | RAG | 微调 |
|---|---|---|
| 技术难度 | 低，框架成熟、组件现成 | 高，需要算法 + 算力 + 数据 |
| 回答质量 | 中，受检索质量影响 | 高，知识内化在模型里 |
| 投入成本 | 低 | 高（GPU + 训练时长） |
| 响应速度 | 较慢（要先检索） | 较快（直接生成） |
| 知识更新 | 极快，更新知识库即可 | 慢，需要重新训练 |
| 可解释性 | 强，每条答案都能溯源 | 弱，无法溯源 |
| 适用场景 | 频繁更新的知识、ToB 长尾问答 | 稳定不变的知识、领域专用 |

UP 主的总结很到位：**两者不是谁替代谁，而是各管一摊**。能离线内化的、稳定的、跨场景通用的知识用微调；会变的、私域的、需要溯源的知识用 RAG。

### RAG 的三个发展阶段

1. **基础 RAG（Naive RAG）**：文件载入 → 文本切分 → 向量化 → 知识检索 → 提示词构造 → 大模型生成。这就是前面讲的最简单闭环。
2. **进阶 RAG（Advanced RAG）**：在基础 RAG 之上引入 Rerank 模型、查询改写、多路召回等优化。本章讲的 10 个技巧大部分属于这一层。
3. **模块化 RAG（Modular RAG）**：把检索、生成、改写、压缩、路由等环节**像乐高积木一样拆出来**，不同场景自由组合。目前还没有标准实现，但这是行业演进方向。

## 结论 / 金句

- **「给我一个上下文，我可以回答你整个世界。」** —— RAG 的核心定义。
- **大模型的硬伤不是「不聪明」，是「不知道私域知识 + 答得没依据」。** —— RAG 同时解决这两个问题。
- **RAG 不是算法问题，是工程问题。** —— 流程简单，参数爆炸。每一个环节都有 5~10 个可调旋钮。
- **「学会只需要一周，上线需要一年。」** —— 这是 RAG 工程化最真实的体感。
- **检索阶段是 RAG 质量的天花板。** —— 大模型再强，喂它错的资料也只能输出错的答案。检索优化永远排在第一位。
- **小型项目 RAG 优先，大型企业合规要求严格再考虑微调。** —— 不是技术高低之分，是 ROI 之分。
- **没有评估就没有优化方向。** —— 上线前必须有一个人工评估的「最后一关」。
- **先跑通 demo，再逐步迭代。** —— 这是项目经理视角的金科玉律。

# 下篇 · 方法论精华

## 一张速查表

| 阶段 | 关键决策 | 推荐方案 | 常见坑 |
|---|---|---|---|
| 数据收集 | 存哪、清洗多细 | 只粗洗、跟着场景收 | 过度清洗拖死项目、边界不清导致噪音 |
| 文档切分 | 切多大、怎么切 | 句子窗口 / 语义切分 | 块太大切不准、太小答不全 |
| 向量化 | 用哪个 Embedding | HuggingFace 榜单选型 | 频繁换模型导致向量库 Schema 重做 |
| 存储 | 向量数据库选型 | Milvus / Chroma / Pinecone | 用传统数据库扛向量检索 |
| 检索 | 单一 vs 多路 | 关键词 + 向量多路召回 | 只用一种导致召回不全 |
| 选 Top-K | 喂几条给大模型 | 3~5 条 | 太少答不全、太多浪费 Token |
| 生成 | 开源 vs 闭源 | ToB 本地 / ToC API | 用弱模型做生成 |
| 评估 | 怎么知道好坏 | 准确率 + 忠实度 + 检索指标 | 没有评估就上线 |

## 通用原则

1. **私域知识 → RAG，稳定知识 → 微调**。能离线内化的不依赖实时检索。
2. **检索质量决定 RAG 上限**。大模型再聪明也救不了错的检索。
3. **多路召回 + Rerank 是性价比最高的优化组合**。一个提召回、一个提精度，配合使用天花板高。
4. **元数据是被低估的优化杠杆**。成本几乎为零、收益巨大。
5. **先粗洗后精洗，先 demo 后完美**。过度工程化是 RAG 项目失败的首因。
6. **人工评估不能省**。模型自评只是辅助，上线前必须有真实人工抽检。
7. **提问改写成本低、收益高**。指代消解和复杂拆解是两个高 ROI 方向。
8. **答案可溯源是 RAG 的差异化优势**。微调做不了这件事，要用足。

## 可复用模式

### 模式 1：Small-to-Big（检索细、生成宽）

- 检索时用小粒度（句子级、摘要级）保证精准；
- 生成时把原块或上下文窗口喂给大模型，保证完整。

适用于：高精度要求的专业领域问答。

### 模式 2：检索 - 精排 - 生成三段式

- 第一段：多路召回 → 候选 N 条；
- 第二段：Rerank 精筛 → Top-K（3~5）；
- 第三段：大模型基于 Top-K 生成。

适用于：所有中等复杂度以上的 RAG 项目。

### 模式 3：FAQ 优先 + 自由问答兜底

- 把高频 FAQ 单独建一张「一问一答」索引，匹配则直接返回答案；
- 没匹配上才走完整 RAG 链路。

适用于：客服、政策问答等高频重复场景。

### 模式 4：元数据驱动的多租户 RAG

- 在向量库里给每条数据打「租户 ID / 文档类型 / 权限标签」；
- 检索时先按元数据过滤，再做语义匹配。

适用于：多业务线、多权限隔离的 ToB 场景。

### 模式 5：分块打包生成（最实用的生成模式）

- 检索到的 N 个块分成 3~5 组；
- 每组独立问大模型「这是不是最终答案」，是则结束；
- 全都不是则合并所有组的回答再问一次。

适用于：知识块数量多、不确定最终答案在哪块的场景。

# 借鉴篇 · 我们能借鉴的点

> 王昕业务背景：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库。

## 1. 把 8895 知识库按 RAG 思维重塑

**对应业务**：8895 知识库（客服 / 销售 / 行业案例 / 产品手册四类内容混在一起）。

**怎么做**：

- **分库管理**：按业务场景把 8895 拆成 4 个独立向量库（客服库 / 产品库 / 行业案例库 / 销售话术库），每库只装该场景的内容，**严守「知识库边界 = 业务场景边界」**。
- **元数据打标**：每条数据打上「部门归属 / 文档类型 / 更新时间 / 适用产品线」四个标签，为后续多租户和权限隔离打基础。
- **粗洗为主**：8895 文档量大、来源杂，UP 主说的「粗洗就够」原则特别适用——先把所有文档一次性进库，**让 RAG 先跑起来**，再回头清理噪音。

## 2. 给获客系统加一个「AI 政策解读助手」

**对应业务**：获客系统的客户常问政策、合规、行业趋势，这些是高频但又变来变去的知识——**典型的 RAG 场景**。

**怎么做**：

- 把监管文件、行业报告、合规指南单独建一个「政策向量库」，每月增量更新；
- 用 **摘要检索**（Small-to-Big 之一）：每份政策生成 200 字摘要向量入索引，匹配后返回原文段落；
- 配合 **元数据过滤**：按「文件类型=监管」「生效日期≥某时间」先过滤，再做语义匹配，避免把过期版本召回给客户。

## 3. FDE 交付流程里内置「RAG 可行性评估」6 问

**对应业务**：FDE 在客户现场要做的是**判断「这个需求该不该用 RAG 解决」**，而不是一上来就搭系统。

**怎么做**：把 UP 主讲的「项目经理 6 问」做成 FDE 立项前的标准问卷：

1. 用户与场景是什么？客服 / 销售 / 内部知识？
2. 知识库边界在哪？数据存在哪里？
3. 是否有可用的大模型（本地或云端）？
4. 准确率要求是多少？80% 还是 95%？
5. 知识更新频率？周更、月更、年更？
6. 验收标准（准确率、时延、并发）写进合同了吗？

把这 6 问的答案记入项目档案，**让 RAG 交付从「凭感觉」变成「凭数据」**。

## 4. 用「多路召回 + Rerank」做企业级知识问答底座

**对应业务**：FDE 在中大型企业交付时，单一检索方式普遍召回率不够。

**怎么做**：

- 同时跑 **关键词检索**（适合产品编号、法规条款）和 **向量语义检索**（适合口语化提问）；
- 用 **RRF 算法**（倒数排名融合 + 平滑指数）合并打分，把稳定的「全能选手」排在前面；
- 候选前 20 条过 **BGE-Reranker** 精筛，最终只送 Top-3 给大模型；
- 这一套三段式是 UP 主认可的「性价比最优组合」，直接抄进 FDE 标准方案。

## 5. 把「提问改写」做成对话系统的标配模块

**对应业务**：客户现场用户提问方式千奇百怪，「他」「这个」「那个」「上一条」满天飞。

**怎么做**：

- 每个 RAG 项目上线前先开发一个 **Query Rewrite 模块**：用大模型把用户问题改写成自包含、可检索的标准化表述；
- 重点实现三个能力：**指代消解**（把「他」替换成具体人名 / 产品名）、**复杂拆解**（把多跳问题拆成单跳）、**口语转标准**（把「你们发什么快递」转成「物流配送方式」）；
- 改写后的 query 同步入检索日志，为后续的 FAQ 挖掘提供数据。

## 6. 上线前必跑「准确率 + 忠实度 + 召回率」三大评估

**对应业务**：FDE 在客户现场被问「这套系统到底能不能用」时，必须拿出数字。

**怎么做**：

- 准备 50~100 条 **测试集**（问题 + 标准答案 + 标准参考文档），这是 UP 主强调的「上线前最后一关」；
- 三个指标必须都看：
  - **准确率**：最终答案对不对（人工核 + 裁判模型打分双轨）；
  - **忠实度**：答案是不是按参考文档答的（防止模型「凭常识胡诌」而碰巧答对）；
  - **召回率**：该找到的参考文档找回了多少（决定 RAG 上限的关键指标）；
- 指标不达标的环节**先优化再上线**，不要把「先上线再调」当借口。

## 7. 用「分块打包生成」替代「全量塞给大模型」

**对应业务**：8895 知识库数据量大，检索后经常召回 8~15 条参考文档，全部塞进 Prompt 会爆 Token。

**怎么做**：

- 召回超过 6 条时，**强制启用分块打包**：3 条一组喂给大模型，每组问「这是不是最终答案」，3 组都不是再合并回答；
- 这一招来自 UP 主讲的「分 piece 模式」，**比葫芦娃模式调用次数少、比链式模式调试容易**，是 8895 这类大体量知识库的默认选择；
- 同时监控 Token 消耗，把单次 RAG 调用的平均 Token 数纳入运维看板。

## 8. 给客户讲 RAG 与微调的「场景化决策树」

**对应业务**：客户经常问「为什么不用微调而用 RAG」「我们该不该上微调」——这是 FDE 的高频问题。

**怎么做**：

- 制作一张**决策图**，背下来就能用：
  - 知识 1 年内基本不变 + 预算充足 + 合规要求严 → **微调**；
  - 知识高频更新 + 需要溯源 + 预算有限 → **RAG**；
  - 两者并存（核心稳定知识微调 + 长尾更新知识 RAG）→ **混合架构**；
- 引用 UP 主给的类比：「微调是把知识记进脑子里，RAG 是考试现场翻课本」——这句话讲给客户听，对方秒懂。

## 9. 把「可解释性」当成 RAG 项目的差异化卖点

**对应业务**：客户对 AI 的最大顾虑是「它说 A 对，我怎么知道真的对」。

**怎么做**：

- 所有 RAG 交付项目**默认带答案溯源**：每条答案尾部自动拼接「参考资料编号 + 原文片段 + 来源 URL」；
- 利用 UP 主讲的「元数据排序」技巧，把可信度高的来源（官方文档、权威机构）加权排前面；
- 在客户培训中重点演示「点开答案看原文」这个动作，把「AI 黑盒」标签撕掉。

## 10. 用 LangSmith / RAGAS 做交付级 RAG 评估基线

**对应业务**：FDE 项目验收时客户要求看「评估报告」，手工跑 100 条样本太低效。

**怎么做**：

- 把 LangSmith 或 RAGAS 作为标准评估工具集成进交付包；
- 每次 RAG 系统配置变更后自动跑一遍评估基线，输出准确率 / 忠实度 / 召回率三项指标的趋势图；
- 把这份「带数字的趋势图」作为 FDE 交付文档的一部分，**让客户看到 RAG 系统是在持续变好的**，而不是一锤子买卖。
