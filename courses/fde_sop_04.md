## 一、设计四步（阶段 3 · 把需求变成蓝图）

### 第 1 步 · 画原型（一张图顶十页文档）

**做什么**：画出产品长什么样，先对齐「大家想的是不是同一个东西」。

**怎么做（分两档）**：
1. **低保真原型**：画框框图（哪里是输入框、哪里是按钮、点完出现什么）。目的是「对齐流程」，不是「好看」。
2. **高保真原型**：加上颜色、真实文字、能点。目的是「给开发/客户看最终效果」。

**小白例子**：AI 客服产品，先画低保真——「用户输入问题 → 显示 AI 回答 → 不满意可点『转人工』」。对齐这个流程，再谈细节。

**侧重点**：**原型是用来「对齐」的，不是用来「炫技」的**。别一上来画高保真（浪费），先低保真把流程对齐。

### 第 2 步 · 设计提示词（会说话才能干活）

**做什么**：设计「让模型听懂、按你的要求回答」的指令。

**怎么做（提示词的基本结构）**：
1. **角色**：你是谁（「你是中俄电商客服」）。
2. **任务**：做什么（「回答用户关于物流/退款的常见问题」）。
3. **约束**：不做什么（「只回答知识库里的内容，不知道就说不知道」）。
4. **格式**：怎么输出（「简洁、用简体中文、分点」）。
5. **例子**（可选）：给 1-2 个标准问答示范（`Few-shot`）。

**小白例子**（给客服 AI 的系统提示词）：
> 你是「中俄跨境物流客服」。只回答用户关于时效、运费、清关、退款的问题。**只答知识库里有的内容，不知道就回「这个我需要查一下，稍后人工回复您」**。用简体中文，语气友好，回答不超过 50 字。

**侧重点**：**提示词 = 角色 + 任务 + 约束 + 格式**。最容易漏的是「约束」（不做什么），没约束 AI 就会乱说。

### 第 3 步 · 设计 RAG（让 AI 接上私有知识）

**做什么**：让 AI 能答「公司内部/业务知识」，而不是只会通用知识。

**怎么做（RAG 四步流程）**：
1. **切块**（`Chunking`）：把文档切成小段。
2. **向量化**（`Embedding`）：把每段变成「意思坐标」。
3. **检索**：用户提问 → 找最相关的几段（必要时 `重排`）。
4. **生成**：把「问题 + 检索到的段落」一起给模型，让它照原文回答。

**小白例子**：把「物流时效表」「退款政策」切成小块、向量化存进向量库。用户问「到莫斯科几天」→ 检索到「时效表」那一块 → 模型照原文答「7-10 天」，不编造。

**侧重点**：**RAG 的命门是检索质量**——切块大小、向量化质量、要不要重排，直接决定答得准不准。**RAG 是工程问题，不是换个模型能解决的。**

### 第 4 步 · 设计 Agent 架构（复杂任务怎么编排）

**做什么**：如果产品不是「一问一答」，而是「多步骤任务」，就要设计 Agent。

**怎么做（选型判断）**：
- **简单线性流程** → 用 `LangChain`（把模型/工具串成一条链）。
- **复杂有分支/循环/状态** → 用 `LangGraph`（画成流程图，能分支、回退、记忆状态）。
- **判断标准**：流程会不会「根据结果走不同分支」？会 → 用图。

**小白例子**：客服「识别意图 → 查单 → 查不到转人工」，有分支（查到/查不到），用 `LangGraph` 画流程图更清晰。

**侧重点**：**别过度设计**——一句话问答不需要 Agent，多步骤有分支才需要。上来就上复杂架构，MVP 都做不完。

## 二、开发实现（阶段 4 · 把蓝图变成能跑的）

### 核心：Agent 的三个「为什么」

搭 Agent 时，先理解三个核心机制（第二册第 6 章）：

1. **`ReAct`（推理+行动）**：让 AI「想一步 → 做一个动作 → 看结果 → 再想」。这是 Agent 能「自己找答案」的底层逻辑。
   - 小白例子：问「哪款手机卖最好」→ AI 先想「得查销量」→ 调搜索 → 看到数据 → 再组织答案。

2. **记忆（`Memory`）**：让 AI 记住之前说过的话、做过的事。
   - 小白例子：客服记住「这客户上周问过退款」，这次接着聊不用重说。

3. **工具调用（`Tool Use`）**：让 AI 能调用外部函数/API 做真事。
   - 小白例子：AI 理解「帮我查订单 123」→ 调用查单函数 → 返回结果。

### 开发顺序（别跳步）

1. **先 MVP**：只做核心流程能跑通（比如「提问 → 检索 → 回答」），不做登录/多用户/高级功能。
2. **再测试**：每加一个功能，先手动测一遍，别攒到最后一起测。
3. **再迭代**：跑通了再往上加（记忆、多 Agent、工具调用）。

**侧重点**：
- **RAG 是工程问题**（检索质量是命门），不是「换个更强的模型」。
- **Agent 是编排问题**（规划 + 记忆 + 工具），不是「模型越牛越好」。
- **先 MVP，再迭代**——别一上来求全，结果啥都没跑通。

### 常见的 3 个坑

1. **一上来追求「全自动 Agent」**：结果不可控、不可预测。正确做法是先「半自动」（AI 建议 + 人确认），跑稳了再放权。
2. **不写测试就上线**：后面修 bug 修到死。正确做法是「边写边测」。
3. **提示词没写约束**：AI 乱说、泄露不该说的。正确做法是提示词里写死「不做什么」。

## 三、这一章的小结（一张卡带走）

```
设计（把需求变成蓝图）
  ① 画原型   → 低保真对齐流程，别炫技
  ② 设计提示词 → 角色+任务+约束+格式（约束别漏）
  ③ 设计 RAG  → 切块→向量化→检索→生成（命门=检索质量）
  ④ 设计 Agent → 简单用链(LangChain)，复杂有分支用图(LangGraph)

开发（把蓝图变成能跑的）
  ① 先 MVP   → 核心流程能跑通
  ② 再测试   → 边写边测
  ③ 再迭代   → 跑稳了再加记忆/工具/多Agent

核心理解：ReAct(想一步做一步) + 记忆 + 工具调用 = Agent 三件套
```

> 记住：**RAG 是工程问题、Agent 是编排问题、提示词是母语**。这三句话理解了，开发阶段就不会被「换更强模型」这种话术带偏。
