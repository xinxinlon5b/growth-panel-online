# 上篇 · 书籍内容

## 引子 · 为什么是 LangGraph

AI 应用的开发范式正在从「链（Chain）」走向「图（Graph）」。这不是凭空造出来的概念，而是在复杂场景中被一步步逼出来的方向。

链的黄金时代有三个优势：纯线性流水线，菜谱式顺序执行，执行路径一眼看懂；成熟组件生态，模型接入、工具调用、结果解析都有现成封装；快速验证成本低，脑子里一个点子五分钟就能跑 Demo。这套范式在简单任务上效率极高，但一旦进入复杂 Agent 场景，四大局限立刻显形：

1. **无法回溯**：单向执行，一步错则污染后续推理，没有自我修正能力；
2. **无原生状态管理**：只能把上一步输出传给下一步，复杂上下文全靠自己手动传、易丢失；
3. **无法动态分支**：只能线性顺序走，写 Prompt 引导模型选择路线不稳定、像黑盒；
4. **没有结构化记忆**：多轮对话历史得自己手动拼 Prompt，前后一致性难保证。

链的能力边界决定它撑不起复杂决策，而图结构天生适合复杂决策。它由三大要素构成：**节点（Node）**——最小执行单元，每个节点负责一件具体的事；**边（Edge）**——节点之间的流转逻辑，可以是直线也可以是带决策的跳转；**状态（State）**——全图共享的公共笔记本，所有节点都能读写、全程同步。

LangGraph 在图结构之上沉淀出三大工程价值：把黑盒 Prompt 决策变成白盒代码（可视化、可测试、可追踪、可监控）；统一的 State 抽象大幅降低多轮对话、工具调用、记忆管理的开发成本；自带断点续跑、人工介入、流式输出，是真正面向生产的工程底座。

## 逐点精读

### 一、核心三要素：State / Node / Edge

**State（状态）**是整个图的灵魂、全局共享的数据盒子，每个节点执行一次就更新一次。设计上有三大基石：

- **类型化**：用 TypedDict 或 Pydantic 把字段和类型定死，IDE 能补全提示，写错当场报错；
- **Reducer（归约器）**：给每个字段单独定义合并规则——消息列表追加、配置项深层合并、计数字段累加——数据扭转的控制权更细；
- **Immutability（不可变）**：每跑一步不修改原状态，而是深拷贝一份全量快照，支持断点存档、任意一步回溯。

State 设计直接决定 Agent 系统的天花板，编码前多花 10 分钟设计好，后面就能少花 10 小时调试。

**Node（节点）**是图的肌肉，最小执行单元，本质是纯函数或类方法。原则是「节点不存状态、数据全在 State 流转」。最易踩的坑是「上帝节点」——把调模型、选工具、解析结果全塞进一个函数，改一处就千丝万缕。正确做法是**单一职责**：调模型一个节点、选工具一个节点、解析结果一个节点，节点之间不直接调用、全部靠 State 传输，单测、好定位、可复用。

**Edge（边）**是图的神经，负责节点连接与流转方向。任何图都必须有 `START` 和 `END` 两个边界节点，否则执行链断成不了闭环。

**Conditional Edge（条件边）**是图的大脑，本质是一个**路由函数**——输入当前 State、输出下一节点名称字符串，把数据状态和执行路径打通，是 Agent 智能的核心来源。三种经典模式覆盖 90% 场景：

- **分支模式（IF/ELSE 二选一）**：判断要不要调工具，是则进工具节点、否则直接给答案；
- **循环模式（B 环自修正）**：跑完一轮判断是否达标，没达标回去再来一遍、达标则结束，类似「写—检查—修改—提交」；
- **路由模式（智能分发）**：识别用户意图（查资料/写代码/算数学题），动态分发到对应处理节点，支持一对多、多对多。

### 二、StateGraph 完整工作流：定义 → 编译 → 执行

**第一步 定义 State**——按场景复杂度分三档：

| 档位 | 方式 | 适用 |
|---|---|---|
| 基础版 | Python 原生 TypedDict | 固定小场景 |
| 标准版 | Pydantic BaseModel | 绝大多数正式项目（自带校验、默认值、文档） |
| 进阶版 | 带 Reducer | 多轮对话等需精准控制更新的复杂场景 |

设计原则：字段名语义化（message、user_input、tools、result，不要 data/info）；State 不是垃圾桶，只存节点间共享的内容；嵌套不超过两层；Reducer 策略编码前定好。

**第二步 写节点函数**——结构三段式：输入接收完整当前 State（**只读原则**，不要在原 State 上改）、处理调用模型/工具/数据清洗逻辑、输出返回字典且**只返回这次要更新的字段**（系统自动增量合并）。每个节点只管自己那一点变化，依赖解耦。

**第三步 加边**——三种常用边：

- **普通边** `add_edge(A, B)`：A 跑完铁定到 B，无判断、纯线性；
- **起点边** `add_edge(START, A)`：定义流程入口，每张图只有一个；
- **条件边** `add_conditional_edges(A, router)`：A 跑完调路由函数 R，动态决定下一节点；返回 `END` 字符串即终止。

路由函数三大纪律：严格纯函数（只读 state、无副作用）、只返回节点名字符串、所有分支必覆盖（尤其 END 终止分支，否则死循环）。

**第四步 编译**——调用 `compile()` 方法做三件事：

1. **拓扑校验**：检查死循环、孤立节点、走不通的死路，问题扼杀在运行前；
2. **构建最优执行计划**：提前算好节点顺序与分支逻辑，运行时免解析、性能更好；
3. **绑定 Checkpointer**：配置持久化存储，运行自动存快照、业务代码零感知。

**第五步 执行**——两种模式：

- **`invoke` 全量执行**：调用一次从头跑到尾，返回最终 State，最常用、适合 API 接口；
- **`stream` 流式执行**：跑一步输出一步，可抓 token 级事件，适合长流程监控与前端实时展示。

完整生命周期五步：初始化（生成首份 State 快照）→ 节点执行（从 START 出发挨个跑）→ 边路由（普通边直跳、条件边调路由）→ 快照保存（每步自动存 Checkpoint）→ 执行终结（走到 END 汇总返回）。

### 三、记忆与持久化：从 Demo 到生产的关键一跃

没有持久化的 Agent 有三大致命痛点：对话接不上（每次全新绘画、历史清零）、一出错全白干（崩了就从头来）、无法人工插手（运行黑盒、关键节点没人把关）。形象比喻：没有持久化的 Agent 就是没有硬盘的电脑，每次开机都是新的。

**三大核心价值**：真正多轮对话（全量历史上下文）、容错与恢复（断点续跑、不丢已完成步骤）、人机协作（关键节点暂停等人确认）。

**MemorySaver**——基于内存的 Checkpoint 实现，开箱即用、一行代码启用、读写零延迟，但进程一停数据全丢，**只能用于开发调试与短生命周期 Demo，绝对不能上生产**。

**Checkpoint 机制三概念**：

- **快照（Snapshot）**：每完成一个节点生成一份完整 State 数据，相当于游戏里的即时存档；
- **线程（Thread）**：一次独立的 Agent 会话，每个线程有自己的历史状态、互相隔离，如不同存档位；
- **检查点（Checkpoint）**：某个线程某步骤的快照 + 元数据（当前节点、时间戳、版本号），是回滚与中断恢复的定位依据。

**存储后端三级可选**：

| 级别 | 后端 | 适用 |
|---|---|---|
| 开发级 | MemorySaver | 本地开发、单测、功能验证 |
| 入门级 | SqliteSaver | 轻量演示、个人工具、小型业务 |
| 生产级 | PostgreSQL / Redis | 高并发、集群部署、自动备份 |

**上层接口完全统一**，从 MemorySaver 切到 PostgreSQL 核心业务代码一行不用改。

**断点续跑三层能力**：

1. 自动存快照（每步系统自动存、业务代码零侵入）；
2. 失败能恢复（指定 thread_id 重调，自动找最近成功 Checkpoint 接着跑，前面结果不丢）；
3. 时间旅行（任意历史快照可回退，调试查问题利器）。

落地业务场景：长流程容错（几十分钟任务崩了从断点续，省时间算力）、异步任务处理（提交后离开、下次回来看进度）、A/B 测试（同一 Checkpoint 并行跑不同策略对比结果）。

**人在回路（HITL）两种实现**：

- **Interrupt 节点（中断节点）**：关键操作前自动暂停并保存状态，等人工输入确认再执行，适合核心决策、敏感操作确认、关键信息校验；
- **edit_state（编辑状态）**：允许人工直接改 State 数据（补信息/纠错）后手动触发继续运行，适合结果跑偏需微调。

实际项目一般两种结合用，既有关键节点自动暂停确认，也支持随时介入改状态、回退重来。

### 四、高级模式：子图 / 并行 / 工具调用 / Agent 架构

**子图（Subgraph）**——把一整张图封装成一个节点塞到更大的图里，本质就是软件工程讲了几十年的「模块化、封装、复用」。三大典型场景：复杂系统拆解（几十上百节点拆成独立模块，维护成本指数级下降）、团队协作开发（不同团队各管一块、各自独立测试、最后拼图）、核心能力复用（搜索、总结封装成标准化子图，多项目复用）。没做子图的 Agent 系统就像不写函数的代码，规模一大就彻底没法维护。

**分支并行（Branch Parallelism）**——上游跑完后同时派生出多条独立执行分支，所有分支同时启动并发处理。和条件边的区别：条件边是**分流**（几条路互斥、一次走一条、串行），并行是**复制**（所有路径同时启动、服务底层资源调度）。核心价值：把服务器多核算力用满、串行等待变并行处理，I/O 密集且无依赖任务耗时直接砍半。

三大常用场景：多元信息解锁（同时去百度/知乎/维基搜索同一话题汇总）、多模型对比测试（同时发 GPT/Claude/通义千问做 A/B）、独立任务并行处理（总结/关键词提取/翻译互不依赖的可同时启动）。

**三大注意事项**：分支逻辑必须独立（无数据依赖，否则死锁）、终点必须汇合（否则数据散乱无法统一处理）、要权衡资源与成本（并行吃算力/内存/API 额度，资源有限时开太多反而因竞争变慢）。

**Tool Calling（工具调用）**——大模型本身只能生成文本，工具调用给它接上手脚，能调用外部 API、数据库、专业软件。一个完整流程四步：用户提问 → LLM 决策（要不要调、调哪个、参数怎么填，决定 Agent 能力上限）→ 工具执行（发 HTTP、查数据库、跑代码）→ LLM 总结（把原始数据整理成自然语言回答）。没有工具调用的 Agent 就是会空谈的嘴炮，有工具调用才是真正落地的智能执行者。

四大设计原则：工具职责单一（一个工具做好一件事，名字直白如 `query_weather`）；参数清晰明确（每个入参名字/类型/详细描述，不写 data/info）；错误处理完善（超时、服务挂要有重试和友好错误，不能一个工具失败整个流程断掉）；结果格式统一（按 JSON 结构化输出，大模型易理解、后续编排好处理）。

**Agent 三大架构范式**：

| 范式 | 核心 | 优势 | 劣势 | 适合场景 |
|---|---|---|---|---|
| **ReAct** | 推理+行动形成闭环，想一步做一步看反馈再想下一步 | 机制简单、应变强、实现成本低 | 缺乏全局视角、步骤多易走偏、易陷无效循环 | 探索性任务、简单问答、开放性试错 |
| **Reflection** | 执行→复盘→改进，先自己挑错再迭代 | 自我修正、错误率低、逻辑严谨、像人思考 | Token 消耗大、响应慢、成本高 | 写代码、写文案、专业报告（质量优先） |
| **Plan-and-Execute** | 先拆解全局列步骤清单，再按计划顺序执行 | 全局规划、结构清晰、能撑多步骤长流程 | 初期规划错则全偏、灵活性差、调整成本高 | 工业流程控制、复杂数据分析（结构化稳定任务） |

**LangGraph 为何适合做 Agent 架构**：天然支持各种范式（ReAct 的条件边循环、Reflection 的反思节点、Plan-and-Execute 的子图拆解都能原生实现）；状态管理完善（思考轨迹、工具结果、中间变量全收敛在 State，行为可追溯）；可组合性极强（子图/并行/工具调用像搭积木，从单节点 Agent 演变为复杂多分支协作无需换框架）。

### 五、入门案例：100 行代码跑通问答机器人

**环境铁律（区分专业与玩玩的分水岭）**：

- **环境彻底隔离**：每个项目单独开虚拟环境（如 Python 3.13 venv），各项目互不污染；
- **版本精确锁死**：依赖写进 `requirements.txt` 或 `pyproject.toml`，开发/测试/生产三套环境同版本；
- **API Key 安全**：`.env` 文件 + `.gitignore` 忽略，绝不写死在代码里——写死等于银行卡密码写在卡背面。

**为什么用 OpenAI SDK 调阿里百炼/通义千问**：OpenAI 接口格式已成行业事实标准（Type-C 充电口比喻），阿里、字节、DeepSeek 全都兼容。换模型只需改 `base_url` 和 `api_key`，业务代码一行不动——模型与业务解耦。

**完整四步流程**（LangGraph 套路不变，复杂的从来不是套路、只是节点多了几个、边花哨一点）：

1. **定义 State**（TypedDict，两个字段：`user_input` 用户问题、`response` AI 回答）；
2. **写节点函数**（`chat_node`：从 State 拿 `user_input` → 调模型 → 把 `response` 写回 State 并返回）；
3. **构建图**（`StateGraph(State)` 实例化 → `add_node` 注册 `chat_node` → `add_edge(START, chat_node)` → `add_edge(chat_node, END)` → `compile()` 编译）；
4. **运行**（`graph.invoke({"user_input": "简单介绍一下 LangGraph"})`，一次跑完返回结果）。

模型初始化四要素：`model` 名称（如 `qwen3-max`）、`api_key`（从环境变量 `os.getenv` 读取）、`base_url`（厂商提供）、`temperature`（0.7 是通用问答的常用中间值——严谨与发散之间）。`if __name__ == "__main__"` 是 Python 标准写法，确保文件被直接运行才执行测试代码。

## 结论 · 金句

1. **从链到图，是 AI 技术发展的必然方向；LangGraph 是这条路上目前最好用的工程实践载体**——它把行业最佳实践沉淀成标准化编程模型，为复杂 AI 系统提供完整工程化支撑。
2. **State 是图的灵魂，Node 是图的肌肉，普通 Edge 是图的神经，Conditional Edge 是图的大脑**——几个简单规则就能组合出无限可能性，这就是图模型的核心威力。
3. **没有持久化的 Agent 是没有硬盘的电脑**——多轮对话、容错恢复、人机协作三大价值缺一不可，这才是从 Demo 到生产的关键一跃。
4. **真正的生产级 Agent 不是 AI 取代人，而是 AI 辅助人**——人把关方向和风险，AI 负责落地和执行。
5. **没有最好的架构，只有最适合的架构**——根据真实业务场景在灵活性、质量、成本之间做平衡，才是架构师的水平。

# 下篇 · 方法论精华

## 一张速查表

| 模块 | 核心概念 | 关键 API/机制 | 适用边界 |
|---|---|---|---|
| **State 设计** | TypedDict/Pydantic + Reducer + Immutability | `Annotated[list, add_messages]` 控制合并 | 字段名语义化、嵌套≤2 层、Reducer 提前定 |
| **Node 编写** | 单一职责、纯函数、只读 State、返回增量字段 | `def node(state) -> dict` | 不存状态、不调其他节点、不写上帝函数 |
| **普通 Edge** | 固定方向线性连接 | `graph.add_edge(A, B)` | 无条件跳转、A 必跑完到 B |
| **起点边** | 流程入口唯一 | `graph.add_edge(START, A)` | 每图一个、定义逻辑源头 |
| **条件 Edge** | 路由函数 + 三模式（分支/循环/路由） | `graph.add_conditional_edges(A, router_fn)` | router 纯函数、返回节点名字符串、覆盖 END |
| **编译** | 拓扑校验 + 执行计划 + 绑定存储 | `graph.compile(checkpointer=...)` | 上线前必做、配 Checkpointer 后业务零感知 |
| **执行** | invoke 全量 / stream 流式 / stream_events token 级 | `graph.invoke(state)` / `graph.stream(state)` | API 走 invoke；前端实时展示走 stream |
| **持久化** | MemorySaver / SqliteSaver / Postgres | `MemorySaver()` 实例化传入 compile | 开发 MemorySaver、生产 Postgres、别用 MemorySaver 上生产 |
| **Checkpoint** | Snapshot + Thread + Checkpoint | `thread_id` 定位会话 | 断点续跑、A/B 测试、时间旅行都靠它 |
| **人在回路** | Interrupt 节点 + edit_state | `interrupt_before=["node"]` | 核心决策/敏感操作前暂停；edit_state 适合结果跑偏微调 |
| **子图** | 图封装成节点、模块化复用 | `subgraph.compile()` 嵌入父图 | 复杂系统拆解、团队协作、能力复用 |
| **分支并行** | 多分支同时启动、终点汇合 | `Send` API 或并行节点 | 分支独立无依赖、I/O 密集任务、按算力成本权衡 |
| **Tool Calling** | LLM 决策 + 工具执行四流程 | `bind_tools([...])` 注册工具 | 单一职责、参数清晰、错误处理完善、结果结构化 |
| **Agent 范式** | ReAct / Reflection / Plan-and-Execute | 组合条件边/反思节点/子图实现 | 探索试错→ReAct；质量优先→Reflection；结构稳定长流程→P&E |

## 通用原则

1. **State 先行**——构思图的第一件事是想 State 怎么设计，节点协作全由 State 结构决定。
2. **节点单一职责**——调模型、选工具、解析结果各一个节点，单测、可复用、好定位。
3. **路由函数只指路不下场干活**——纯函数、返回字符串、覆盖所有分支（含 END）。
4. **编译必做**——拓扑校验纠错、构建执行计划提性能、绑定 Checkpointer 让业务零感知。
5. **State 只存共享数据、节点内部用临时变量**——State 不是垃圾桶，节点不是仓库。
6. **持久化分级别选后端**——开发 MemorySaver、单机 Sqlite、生产 Postgres，接口统一可热切。
7. **断点续跑 + 人在回路是生产标配**——长任务靠 Checkpoint 容错，关键决策靠 Interrupt 把关。
8. **工具调用四步：问→决策→执行→总结**——LM 是大脑、工具是手脚，决策一步决定 Agent 上限。
9. **Agent 范式按场景选**——没有最好只有最合适，灵活性/质量/成本的三角平衡。
10. **代码前先固化环境**——venv 隔离 + requirements 锁版 + .env 配 Key，是专业与业余的分水岭。

## 可复用模式

**模式一：标准单节点问答机器人**（入门模板）
```
定义 State(2 字段) → 写 chat_node（读 input→写 response）→ 图 START→chat_node→END
→ compile → invoke
```
适用：单轮对话、无工具、无记忆，30 行代码内搞定。

**模式二：循环自修正 Agent**（Reflection 范式）
```
START → 生成节点 → 检查节点（条件边判断是否达标）→ [达标] END / [不达标] 回到生成节点
```
适用：写代码、写文案、专业报告等质量优先任务。

**模式三：多分支并行信息汇总**（并行模板）
```
START → 分发节点 → 并行调用 3 个搜索/模型节点 → 汇合节点（合并结果）→ END
```
适用：多元信息查询、多模型 A/B、独立子任务批处理。

**模式四：HITL 审批流**（人在回路模板）
```
START → 自动处理节点 → 关键决策节点（Interrupt 暂停）→ 人工确认 → END
```
适用：花钱、改权限、访问敏感数据等高危操作必经审批。

**模式五：子图嵌套的多 Agent 协作**（Plan-and-Execute 范式）
```
父图：START → 规划节点（拆任务）→ 派发到 N 个子图（各管一块）→ 汇合节点 → END
```
适用：复杂任务多步骤、团队分块开发、能力复用。

# 借鉴篇 · 我们能借鉴的点

结合王昕业务——**企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库**，逐条列出可落地动作：

### 1. 客户交付场景 · 用 StateGraph 改造现有「线性 LLM 调用」
**场景**：当前给客户做 AI 助手多为单次 invoke，无状态、无工具、无记忆。
**怎么做**：把 State 设计成 `customer_id` + `user_input` + `response` + `history`，节点拆分为「意图识别 → 工具调用（查订单/查知识库）→ 总结回复」三段，条件边路由分发。客户体验从「一问一答」升级为「连贯多轮 + 真干活」。

### 2. FDE 现场交付 · 用 MemorySaver + Checkpoint 做 Demo 容错
**场景**：客户现场演示常因网络、Token 限额、模型超时崩掉，重来一遍体验差。
**怎么做**：每个客户 Demo 接 MemorySaver（开发环境）或 SqliteSaver（本地），出现异常 `thread_id` 不变直接重 invoke，从最近 Checkpoint 续跑。哪怕断网五分钟，回来接着演示不翻车。

### 3. 获客系统 · 用 Stream 流式 + Interrupt 做「智能留资机器人」
**场景**：官网/B 站留资机器人需在关键节点（要联系方式）前暂停等人确认，避免过早索取吓跑用户。
**怎么做**：配置 `interrupt_before=["collect_contact_node"]`，让 AI 先聊需求、聊到关键时机才暂停等人输入手机号，体验自然、合规友好。配上 Stream 实时打字机效果，留资率可期提升。

### 4. 8895 知识库 · 用子图封装「检索 + 重排 + 生成」为标准化模块
**场景**：知识库问答在多个客户项目里反复实现，复制粘贴改配置。
**怎么做**：把「Query 改写 → 向量检索 → BM25 重排 → LLM 生成」封装成一个 Subgraph，输出统一接口（`{context, answer, sources}`）。新客户接入只需配知识库 ID 和切到对应 Checkpointer，半天完成接入，效率提升数倍。

### 5. 企业 AI 客户交付 · 用 Tool Calling 四原则做工具注册规范
**场景**：客户系统对接的外部 API（ERP/CRM/OA）五花八门，工具命名不规范导致 LLM 调用错乱。
**怎么做**：内部制定工具注册规范——单一职责命名（`erp_query_order` 而非 `data_api`）、参数类型+描述齐全（参考 Pydantic schema）、错误返回统一 JSON 结构（含 `code`/`msg`/`data`）、超时重试内置。规范化的工具层是 Agent 稳定性的地基。

### 6. FDE 交付物 · 用 ReAct + Reflection 双范式组合做质量优先任务
**场景**：合同审核、报告生成等客户场景对准确度要求极高，单 ReAct 容易出错。
**怎么做**：ReAct 范式拉数据、Reflection 范式做复核——「生成初版 → 自检 → 标注可疑点 → 修订」。多花 30% token 但错误率显著下降，对外可宣称「双校验机制」，是 FDE 的差异化卖点。

### 7. 获客系统 · 用分支并行做「多渠道同时触达」任务编排
**场景**：一个客户线索需要同时查企查查、查工商信息、查社交媒体画像。
**怎么做**：上游分发节点派生出三个并行分支（各查一个数据源），汇合节点合并画像结果。从串行 30 秒变并行 12 秒以下，销售跟单节奏紧跟线索热度。

### 8. 8895 知识库 · 用 Checkpoint 时间旅行做「答案对比审计」
**场景**：客户经常质疑「为什么这次答案和上次不一样」，难以解释。
**怎么做**：保留每次回答的 Checkpoint 元数据（模型版本、温度、检索源），出问题时一键回放指定版本对照。审计能力 = 客户信任度。

### 9. 企业 AI 客户交付 · 用 Pydantic + Reducer 做客户对话 State 设计标准
**场景**：每个客户项目都要现想 State 字段，标准不统一。
**怎么做**：内部沉淀一套 `EnterpriseAgentState` 模板（`messages: Annotated[list, add_messages]` + `user_profile` + `tool_results` + `confidence_score`），新项目复用 80%，只改业务专属字段。这是 FDE 的工程效率护城河。

### 10. FDE 客户培训 · 用「四步套路」做交付方法论
**场景**：客户开发常问「LangGraph 怎么上手」，没有标准化交付节奏。
**怎么做**：把 LangGraph 的「定义 State → 写 Node → 加 Edge → 编译执行」固化成客户培训四步法，无论多复杂的 Agent 都按这四步讲，配合一个能跑通的 100 行 Demo 做锚点。让客户团队复制这套方法自行扩展。

### 11. 获客系统 · 用 LangGraph 范式对比表做客户架构咨询话术
**场景**：客户问「我的场景该用 ReAct 还是 Plan-and-Execute」，FDE 难快速回答。
**怎么做**：把三种 Agent 范式对比表（优势/劣势/适用场景）做成客户咨询辅助卡片，结合客户业务特征（探索性 vs 结构化、实时性 vs 质量优先）30 秒内给出建议。从「卖产品」升级为「卖架构判断力」。

### 12. 8895 知识库 · 用持久化分级做「环境隔离」交付标准
**场景**：客户本地知识库 Demo 和生产部署常因环境差异翻车。
**怎么做**：交付时按场景配 Checkpointer——本地 Demo 用 MemorySaver、PoC 用 SqliteSaver、生产部署用 Postgres。配套交付 `requirements.txt` 锁版、`docker-compose.yml` 一键起服务。让客户的开发/测试/生产三套环境同版本。
