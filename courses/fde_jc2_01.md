# 上篇 · 书籍内容

## 引子：这套知识要解决什么问题

很多人第一次接触大模型，会在两个极端之间摇摆：一边把它想成无所不能的“数字员工”，另一边又认为自己不会写代码，就无法参与 AI 产品。两种理解都不准确。

AI 产品经理和 FDE（Forward Deployed Engineer，前线部署工程师）的核心，不是把自己训练成算法工程师，而是能把企业模糊的愿望翻译成可落地的产品方案：用户究竟遇到了什么问题？这个问题是否值得付费解决？大模型能否胜任？需要什么数据、工具和人工审核？交付后用什么指标判断有效？

因此，本章不追求背诵网络结构的每个公式，而是建立一条从“业务问题”通向“模型应用”的认知链。学完之后，应当能够看懂一次企业 AI 交付的基本过程：识别场景，选择模型，设计提示词，准备知识库，编排 Agent，接入工具，设置评测与安全边界，再根据真实反馈迭代。

## 主线：从产品价值到智能执行

这套知识可以压缩成八个连续环节：

1. **先找真问题**：从用户和业务流程出发，确认痛点而不是追逐新功能。
2. **再做能力判断**：知道模型擅长语言理解、生成、抽取、分类和多模态处理，也知道它不是可靠的计算器、事实数据库或物理执行器。
3. **把模型接进产品**：模型像发动机，应用还需要界面、后端、数据库、网关、权限和业务规则。
4. **把需求说清楚**：通过提示词提供任务、背景、输入、示例、格式和约束。
5. **把企业知识找回来**：用 RAG 从知识库检索相关片段，再交给模型作答，减少“看似合理但不正确”的幻觉。
6. **把复杂任务拆开执行**：用 Agent 的记忆、规划、工具调用和反馈闭环完成多步骤工作。
7. **把经验封装成 Skills**：把稳定、重复、可验证的 SOP 做成可加载、可复用的能力模块。
8. **用结果而非演示验收**：围绕准确率、响应时间、成本、完成率、人工接管率和安全事件持续评估。

这条主线也解释了为什么 FDE 需要跨界能力：既要理解业务，又要理解模型边界；既要和客户沟通，又要能把方案拆成数据、提示词、接口和流程；既要交付一次，还要把交付沉淀为下一次可以复用的资产。

## 逐点精读

### 一、AI 产品经理的第一课：AI 是手段，产品价值是目的

产品不是一个漂亮的界面，也不等于堆上一个聊天框。产品可以是实物、软件或服务，它存在的理由是解决某类用户问题并创造可感知的价值。对 AI 产品来说，AI 只是实现价值的一种新能力，不能因为“用了大模型”就自动成为好产品。

分析价值时，可以从四层看：

- **核心价值**：产品最根本要完成什么。例如客服系统的核心价值是准确回答并解决问题，而不是展示一个会聊天的头像。
- **实体价值**：用户实际接触到的界面、交互和输出形式。它决定产品是否易用，但不能掩盖核心能力不足。
- **延伸价值**：围绕核心任务增加的提醒、统计、推荐、协作等能力，必须建立在真实场景上，不能为了“智能”强行增加。
- **心理价值**：用户获得的信任感、确定感和控制感。企业尤其在意这一层，因为错误回答可能带来投诉、损失或合规风险。

AI 产品经理每天要完成的工作，通常包括需求与场景定义、模型能力判断、方案和交互设计、提示词设计、研发协作、数据准备、效果评测、迭代以及成本和风险控制。传统产品能力仍然重要：需求调研、用户流程、PRD、原型、项目管理和沟通都不能少；新增的是模型、数据、评测、安全和成本意识。

**怎么用。**访谈客户时不要只记录“想做一个智能助手”，而应追问：谁在什么时刻遇到什么任务？现在由谁完成？每周发生多少次？错误的代价是什么？客户愿意用预算换取什么结果？如果只是“行业里都有，所以我们也要有”，它更像愿望，不一定是真需求。

**常见坑。**把功能数量当价值；把客户提出的方案直接当需求；只展示一次成功演示就承诺稳定上线；只讨论模型能力，不讨论知识来源、权限、人工兜底和责任归属。

### 二、模型、应用与工作流：先分清发动机和汽车

大语言模型（Large Language Model，LLM）是经过大规模数据训练、拥有大量参数、通常基于 Transformer 架构的模型。它本身不是完整的企业应用。一个可用的 AI 产品还需要前端或对话入口、后端服务、模型接口、数据库、缓存、网关、日志、权限和业务系统连接。

可以把模型比作汽车发动机：它决定了核心动力，但有发动机还不等于有汽车。一个应用也可以根据任务选择不同模型；同一个模型也可以被客服、写作、分析等多种应用调用。这个边界对产品经理非常重要，因为方案失败时，问题可能不在模型，而在检索、数据、提示词、工具接口或权限配置。

一次普通对话的链路大致是：用户在应用中输入问题，应用把请求发给后端，后端整理上下文、权限和提示词，再调用模型；模型生成结果返回后端，后端可能做格式校验、敏感信息过滤和业务处理，最后由应用呈现给用户。产品设计时要把这条链路画出来，明确每一步输入什么、输出什么、失败怎么办。

**怎么用。**在 PRD 中分别列出“模型负责的事”和“程序负责的事”。模型负责理解语言、抽取信息、生成草稿、选择工具；程序负责身份认证、订单查询、金额计算、状态写入、权限校验和可追溯日志。凡是涉及确定性数据和高风险动作，都不应只依赖模型自由生成。

**常见坑。**把模型回答当成数据库查询；认为换一个更大的模型就能解决所有问题；忽略模型服务的延迟、调用费用、上下文限制和数据出境要求；没有设计失败、超时和人工接管路径。

### 三、模型为什么能回答：下一个 Token 的概率生成

大模型的一个有效直觉是“超大规模的下一 Token 预测器”。Token 是模型处理文本的基本单位，可能是一个汉字、一个词、英文的一部分或标点，不是固定长度的“字”或“词”。输入的文字、图片说明、文档内容和用户问题，在模型处理层面都要转成可计算的表示。

当我们输入“今天天气真”，模型并不是像人一样先查天气，也不是调用一个传统程序直接“理解”了现实，而是根据上下文计算候选 Token 的概率，再选择或采样下一个 Token；新 Token 加入上下文后，再预测下一个，如此循环生成结果。所谓“聪明”，很大程度上来自训练数据的广度、模型参数的规模、训练算法、算力和生成策略，而不是每次都在进行可靠的事实检索。

这带来三个产品层面的认识：

1. **输出是概率性的**：同一个问题可能得到不同措辞，甚至偶尔出错，不能把一次回答当成绝对保证。
2. **输入输出都消耗 Token**：上下文越长，成本和延迟通常越高；上下文窗口是 Token 的上限，不等于汉字数。长对话还可能稀释早期规则和关键信息。
3. **参数不是知识条目数**：参数可以理解为模型在训练中学到并保存的海量权重。参数更多不等于对每个企业事实都知道，企业私有信息仍需通过知识库或系统接口提供。

**怎么用。**做方案评估时同时问三个问题：模型能否理解任务？模型是否拥有所需事实？结果是否需要确定性计算或系统操作？第一问适合用模型，第二问可用 RAG 或业务数据，第三问应交给函数、数据库或代码执行器。

**常见坑。**把流畅当准确；把模型的自信语气当证据；用模型做库存、金额、日期等关键计算却不做程序校验；把完整历史对话无限拼接，导致超出上下文、成本失控或早期约束失效。

### 四、模型怎样被训练：预训练、监督微调与人类反馈

模型的训练可以理解成逐层塑形的过程。

第一步是**数据采集与清洗**。数据可能来自公开文本、网页、论坛、新闻和其他可用来源，也可能来自企业内部授权数据。采集后要去重、清理格式、过滤低质量内容，并区分无标注文本和带标签数据。企业项目不能把“能拿到的数据”直接等同于“能合法使用的数据”，还要考虑版权、隐私和授权范围。

第二步是**预训练**。模型在大量无标注文本上学习语言规律、知识关联和表达模式，形成通用的基础能力。预训练后的模型可能知识广，但不一定懂得按人的意图回答；它甚至会接续文本，却没有真正完成任务。

第三步是**监督微调（SFT）**。人类准备问题—正确答案、指令—示范结果等高质量样本，教模型遵循任务、使用合适格式并给出更符合预期的回答。这一步像老师批改作业，把“会续写”塑造成“会按要求办事”。

第四步是**基于人类反馈的强化学习（RLHF）**。让模型生成多个答案，由人类按质量、帮助性和安全性排序，使用这些偏好训练评价模型，再据此优化原模型，使输出更符合人类偏好和安全规则。今天的实际训练还会使用其他对齐方法，但产品经理记住这条逻辑即可：模型的能力、行为方式和价值边界，分别受到数据、训练目标和反馈标准影响。

**怎么用。**当客户说“模型不听话”，先判断是知识缺失、指令未遵循、数据质量差，还是安全策略导致拒答，再决定使用提示词、RAG、微调、规则或人工审核。不要一遇到错误就直接要求微调。

**常见坑。**用少量脏数据微调，导致模型遗忘通用能力；把企业内部偏见原样喂给模型；没有保留评测集，无法判断迭代到底变好还是变坏；只关注正常样本，不测试越权、诱导、敏感和极端输入。

### 五、Transformer 与提示词：产品经理需要理解到哪一层

Transformer 是当前主流大模型的重要底层架构。对产品岗位而言，掌握信息流比背公式更有用：输入先被切分为 Token，Token 被转换成向量表示，再加入位置信息；注意力机制让模型在处理当前内容时关注上下文中更相关的部分；多层网络反复变换表示，最后通过输出层给出下一个 Token 的概率。

注意力机制可以用一个产品化比喻理解：同一句话中，不是所有词对当前任务都同样重要，模型需要动态判断哪些上下文值得重点参考。它也解释了为什么输入结构、顺序、示例和上下文质量会影响输出。至于残差连接、归一化、多头注意力等细节，算法工程师需要深入，产品经理至少知道它们属于模型内部机制，不应把应用层问题误判为“加一个按钮就能解决”。

**提示词工程**研究的是两件事：精准表达和高效引导。精准表达是消除歧义，让模型知道对象、任务、边界和交付标准；高效引导是为模型提供合理的处理路径，减少它在众多可能方案中随机发散。

一个可迁移的提示词结构是：**角色/能力边界 + 任务指令 + 背景上下文 + 输入数据 + 示例 + 输出格式 + 约束与校验**。例如，不要只写“写一份手表上市方案”，而应说明目标用户、产品卖点、渠道、市场阶段、篇幅、语气和必须覆盖的栏目。对“苹果”这类有歧义的词，要明确是苹果公司、某款 iPhone，还是水果。

常用技巧包括：

- **简洁且具体**：去掉无关修辞，明确对象和成功标准。
- **少样本示例**：当格式难以用语言描述时，给出一两个输入—输出样例，让模型模仿结构。
- **角色分配**：让模型以测试工程师、法务审阅员或面向普通人的讲解者视角工作，本质是限定思考方向，不是给模型授予真实资质。
- **限定格式、长度和风格**：要求 Markdown、JSON、表格或固定字段，方便后续程序解析；但要配合格式校验，不能只靠文字约定。
- **分步处理复杂任务**：把“先抽取事实、再分类、再生成结论、最后检查遗漏”写清楚。对于复杂任务，要求可验证的中间产物比单纯要求“认真思考”更稳妥。

在 LangChain 中，这类结构通常会被写成 PromptTemplate 或 ChatPromptTemplate，再与模型和输出解析器组成链。下面是示意代码，重点是接口关系，不绑定某个版本：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是企业客服分析助手，只依据给定资料回答"),
    ("human", "资料：{context}\n问题：{question}\n请用固定字段输出")
])
chain = prompt | llm | StrOutputParser()
result = chain.invoke({"context": context, "question": question})
```

这里的关键不是代码长短，而是把变量、模型、输出解析和调用入口分开：提示词可版本管理，模型可替换，结果可被程序继续处理。

**常见坑。**提示词过长却没有层次；把互相冲突的要求同时写入；要求 JSON 却不校验 JSON；把角色设定当作权限；让模型直接输出未经审核的法律、医疗或财务结论。

### 六、RAG：让模型先查企业知识，再组织答案

RAG（Retrieval-Augmented Generation，检索增强生成）不是某个单独的模型，而是一种工程方案：先从外部资料中检索与问题相关的内容，再把检索结果连同问题交给模型生成答案。它解决的是模型不知道企业私有事实、知识更新不及时以及回答缺乏依据的问题。

以企业智能客服为例，不能直接把“保修期多久”丢给通用模型，因为模型可能会用公共语料中的常见说法猜一个答案。正确流程是：先把产品手册、服务政策、FAQ 等资料切成片段；用 embedding 模型把每个片段转换成向量；向量与原文、文档标题、版本和权限一起存入向量数据库。用户提问时，再把问题向量化，在数据库中召回语义相近的片段，经过重排选出最相关的少量内容，最后将问题和片段放入提示词中回答。

这里有四个重要概念：

- **分片**：按标题、段落、语义边界切分，而不是机械地把每个固定字符截断。片段太大，检索不精准；太小，信息不完整。
- **Embedding**：用嵌入模型把文本映射为向量，使语义相近的内容在向量空间更接近。向量不能直接还原原文，所以必须把原文和向量一并保存。
- **向量数据库**：负责存储向量及其元数据，并通过余弦相似度、欧氏距离或点积等方式进行近似检索。具体选哪一种，要结合模型和数据验证。
- **召回与重排**：先用成本较低的检索召回一批候选，再用更精细的重排模型挑出少量片段。候选太少可能漏掉答案，候选太多则会稀释关键证据并增加上下文成本。

示意代码可以这样表达这一流程：

```python
retriever = vector_store.as_retriever(search_kwargs={"k": 10})
candidates = retriever.invoke(question)
top_docs = reranker.rank(question, candidates)[:3]
context = "\n".join(doc.page_content for doc in top_docs)
answer = chain.invoke({"context": context, "question": question})
```

在真实项目中，还应补充来源引用、文档版本、权限过滤、空结果处理和“资料不足时明确说不知道”的规则。LangChain 可以把文档加载、切分、Embedding、向量库和检索链串起来，但它不是准确性的保证；准确性取决于资料质量、切分策略、召回效果、提示词和评测集。

**常见坑。**把整本手册塞进提示词；只存向量不存原文；不区分旧版和最新版政策；检索到了内容却没有把它放进最终提示词；检索失败时仍要求模型自由作答；忽略不同用户的权限，导致知识越权。

### 七、Agent：从一次生成走向感知、规划与行动

Agent（智能体）可以理解为一个能够感知环境、自主规划、调用工具并完成任务的软件系统。一个实用的抽象公式是：**Agent = 大模型 + 记忆 + 规划 + 工具/行动**。大模型像“大脑”，但真正让系统接近“能办事”的，是外部工具、状态管理、执行器和反馈机制。

它与传统软件的区别，不是界面看起来更智能，而是传统软件要求用户严格按菜单和步骤操作；Agent 可以接收相对自然的目标，由模型拆解任务、选择工具、观察结果，再决定下一步。例如“找出下周去深圳的低价机票”，系统可能先确认日期，再调用日期工具和机票 API，比较结果，最后给出方案或请求确认。

Agent 的四个组件可这样理解：

1. **感知**：接收用户请求、文件、网页、系统状态和工具返回值。
2. **记忆**：短期记忆是当前上下文窗口中的对话；长期记忆是经过筛选、结构化并存入数据库的用户偏好、历史事实或经验。长期记忆不等于把所有聊天永久堆进去，而要有写入、更新、删除和权限机制。
3. **规划**：将目标拆成步骤，判断先做什么、失败后怎么办。常见的 ReAct 思路是循环执行“思考—行动—观察”，但生产环境应把可执行动作结构化并加上边界。
4. **行动**：根据模型生成的结构化工具调用，真正调用 API、数据库、代码解释器、邮件、日历或业务系统，并把执行结果反馈给模型。

工具调用的关键是函数契约：工具名称、参数类型、必填字段、返回格式、错误码和权限范围都要明确。模型可以决定“调用哪个工具”，但程序负责验证参数、执行函数和记录审计。图表也往往不是模型直接画出来的，而是模型生成绘图代码，由代码执行环境完成计算和渲染。

LangGraph 适合把这种有状态、可循环、可分支的流程显式编排。示意上，可以建立 `retrieve`、`draft`、`verify`、`human_review` 四个节点，把共享状态放在 State 中，用条件边判断“证据是否充分”“是否需要人工确认”，再循环到重试或结束。与 LangChain 的线性链相比，LangGraph 更强调节点、状态、条件路由和持久化。产品经理不必亲自实现图，但要能画出节点、状态、转移条件和终止条件。

Agent 必须有停止规则：任务完成就结束，达到最大步骤数也要结束；网络超时、工具失败、参数不全时要重试或转人工，不能无限循环。高风险动作还必须二次确认、幂等执行和最小权限。

**常见坑。**把 Agent 当成“更会聊天的机器人”；没有明确终止条件；让模型直接操作生产数据库；工具返回自然语言而非结构化结果；短期上下文过长导致遗忘；把未经验证的长期记忆再次当作事实；只测成功路径，不测超时、重复执行和权限拒绝。

### 八、Skills：把 SOP 变成可加载的数字资产

Skills 可以理解为面向 Agent 的能力插件或数字化 SOP。它不是把所有规则永久塞进一个超级提示词，而是把一个边界清晰、可复用、可组合的任务封装起来，按需加载。典型的 Skill 目录可以包含：

- `SKILL.md`：名称、描述、触发条件和主要执行流程，是模型理解能力的入口。
- `scripts/`：真正执行计算、转换、抓取或校验的代码。
- `references/`：需要时再加载的长手册、规范和示例。
- `assets/`：模板、图片或其他资源。

这体现了“渐进式披露”：先加载所有 Skill 的简短元数据，让模型判断哪个能力相关；命中后再读取对应的 `SKILL.md`；只有流程需要时才加载参考文档和脚本结果。这样既节省 Token，也减少无关规则相互干扰。

一个好的 Skill 要写清触发条件、输入参数、执行步骤、依赖环境、错误处理和固定输出格式。比如“单元测试报告分析”可以规定：读取报告文件，统计总数和通过率，归纳失败用例，定位可能原因，输出固定 JSON；统计和解析由脚本完成，模型负责解释与归纳。

Skills 的核心不是“写一段很长的提示词”，而是把提示、代码、资料、测试和版本管理放在一起。它应当一次编写、多次复用，也可以由多个 Skill 组合完成复杂任务。生产环境要对外部 Skill 做人工代码审计，在容器或沙箱中运行，遵循最小权限，并记录每次调用。

**怎么用。**从历史记录中找出高频、重复、规则稳定且能验收的操作，优先封装为 Skill；给每个 Skill 设清晰的输入输出和单元测试；把通用能力与企业私有资料分离，用版本控制管理升级。

**常见坑。**描述含糊，模型无法正确触发；把大量代码直接写进 `SKILL.md`；没有声明依赖库和运行环境；输出格式不稳定，无法进入下一步自动化；直接安装外部 Skill 而不审计代码和权限。

## 结论 / 金句

- AI 产品的起点不是模型，而是值得解决、有人愿意付费的问题。
- 模型是应用的核心引擎，但不是产品的全部；模型、数据、工具和流程共同决定交付结果。
- 大模型擅长基于上下文生成语言，不等于天然知道事实、能够可靠计算或可以直接操作现实世界。
- 提示词负责把需求说清，RAG 负责把知识找回，Agent 负责把任务做完，Skills 负责把做法沉淀下来。
- 让模型自由发挥适合探索，让程序负责确定性和安全性；真正可交付的系统一定是人机协作，而不是模型单打独斗。
- FDE 的作品不是一次漂亮演示，而是一条在真实业务中跑通、可评测、可复用、可迭代的工作流。

## 一张速查表

| 对象 | 它解决什么问题 | 适合放在哪里 | 关键检查 |
|---|---|---|---|
| 产品价值 | 判断做什么是否值得 | 需求发现与立项 | 是否是真痛点，谁愿意付费 |
| LLM | 理解与生成语言 | 对话、抽取、改写、分类、草稿 | 能力边界、随机性、成本、延迟 |

| Embedding | 把语义变成向量 | 知识库建库与查询 | 分片、模型、维度、版本 |
| 向量数据库 | 存储并检索语义相近内容 | RAG 的检索层 | 权限、相似度、召回数量 |
| 重排 | 从候选中挑最相关内容 | RAG 的精排层 | 相关性、上下文长度、延迟 |
| RAG | 给模型补充外部知识 | 企业客服、制度问答、知识助手 | 引用、版本、空检索、幻觉 |
| Agent | 完成多步骤任务 | 查询、分析、审批、自动化 | 状态、工具、重试、终止 |
| Skills | 复用稳定 SOP | Agent 能力扩展 | 触发、依赖、测试、权限 |
| 评测 | 判断是否真的变好 | 上线前后与每次迭代 | 质量、成本、速度、风险 |

## 通用原则

**原则一：先定义成功，再选择技术。**把“更智能”改成可观察指标，例如回答命中率、一次解决率、人工接管率、平均响应时间、单次成本和高风险错误数。没有验收标准，技术讨论容易变成模型型号比较。

**原则二：确定性工作交给确定性系统。**金额、库存、日期、权限、状态变更和计算，应由数据库、函数或代码完成；模型负责理解自然语言、生成参数和解释结果。模型输出必须经过类型校验和业务校验。

**原则三：知识与指令分离。**提示词写稳定规则，RAG 提供会更新的事实，业务系统提供实时状态，Skill 封装重复流程。把所有内容混成一段超级提示词，会导致维护、更新和权限管理困难。

**原则四：检索不是越多越好。**先保证召回不漏，再通过重排和元数据过滤减少噪声；对没有证据的问题，让系统明确说明资料不足，而不是强行回答。

**原则五：自动化必须可回退。**每个工具调用都应有超时、重试次数、最大步骤数、幂等策略、人工确认点和审计记录。高风险动作默认“建议而不执行”，由人确认后再落地。

**原则六：把一次交付做成资产。**保留需求访谈、数据清单、提示词版本、评测集、错误样本、成本数据、上线复盘和可复用 Skill。这样下一次交付不是重新试错，而是组合已有模块。

## 可复用模式

### 模式一：场景—能力—证据—动作
先写清业务场景，再判断模型能做什么，接着寻找证据来源，最后决定是否调用工具或交给人工。适用于客服、销售、运营和内部助手，能避免“模型先行”。

### 模式二：召回十份，重排少量，带证据回答
RAG 可采用“粗召回 + 精重排 + 受控生成”的三级结构。候选数量按实验设置，不把课堂示例中的数量当成固定标准；最终上下文要少而相关，并尽量附带文档名称、版本和出处。

### 模式三：草稿—校验—发布
模型先生成草稿，规则或第二个模型进行格式、事实和敏感性校验，必要时进入人工审核，再写回系统或发布。适合报告、邮件、营销文案和知识回答。

### 模式四：计划—执行—观察—修正
对于长任务，先形成可追踪计划，再逐步调用工具；每步记录输入、输出和状态，失败时根据错误类型修正参数或转人工。适合研究报告、数据分析和跨系统流程。

### 模式五：高频操作 Skill 化
从历史日志统计高频操作，筛选规则稳定、输入明确、结果可测试的任务；先做一个小 Skill，补齐脚本、参考资料、测试样例和权限，再逐步组合成更大的工作流。

# 借鉴篇 · 我们能借鉴的点

以下动作结合王昕的企业 AI 客户交付、FDE、获客系统和 8895 知识库业务，重点不是照搬课堂案例，而是把方法转成可执行的业务资产。

1. **建立企业 AI 交付的“痛点准入表”。**  
   对应场景：企业客户首次咨询、售前诊断。  
   怎么做：每个需求记录使用角色、发生频率、当前人工流程、错误成本、数据来源、愿付费对象和成功指标。只有能说明“谁因为什么问题损失了什么，并愿意用预算解决”的需求，才进入方案评估；“想要一个 AI 助手”只能作为待澄清线索。

2. **把 FDE 交付流程固定成六步工作流。**  
   对应场景：从售前到上线的客户交付。  
   怎么做：统一为“访谈场景—判断模型—盘点数据—设计提示/RAG/工具—小范围试跑—评测复盘”。每一步产出一页文档，明确负责人、输入、输出和下一步准入条件，避免客户需求直接跳到开发。

3. **为每类客户建立模型能力边界卡。**  
   对应场景：企业方案选型与客户预期管理。  
   怎么做：按对话、文档抽取、分类、代码、图像、实时查询和自动执行列出“可做、需辅助、不可直接承诺”三档。遇到金额、合同生效、库存和权限等任务，明确必须通过 API 或人工确认，销售和交付使用同一份卡片。

4. **把 8895 知识库改造成可追溯的 RAG 资产。**  
   对应场景：企业制度、产品手册、客户服务资料的问答交付。  
   怎么做：为文档增加来源、部门、版本、生效日期、失效日期和权限标签；按标题和语义切片，保存原文与 embedding 的对应关系；上线前用真实问题集测试召回和答案，并要求引用出处。资料过期时优先下架或重建索引，而不是只改提示词。

5. **在获客系统中采用“内容生成 + 人工审核 + CRM 回写”。**  
   对应场景：行业报告、客户画像、线索跟进和销售邮件。  
   怎么做：用提示词约束受众、事实范围、语气和固定字段，模型先生成初稿；由人工核验行业事实和客户信息，再把结构化结果写入 CRM。涉及企业名称、预算和联系方式时，禁止模型自行猜测，缺失字段必须标记待补充。

6. **把获客流程设计成可评测的 Agent，而不是自动群发机器人。**  
   对应场景：线索收集、网页信息整理、预约和销售辅助。  
   怎么做：拆成“读取线索—去重—判断行业—生成个性化草稿—人工确认—发送—记录结果”节点；对发送、改写客户资料等外部动作设置确认门；记录每个节点的耗时、失败原因、转人工率和有效回复率，先在低风险环节自动化。

7. **从高频交付动作中沉淀 Skills。**  
   对应场景：重复性的测试报告、会议纪要、知识整理和客户周报。  
   怎么做：统计历史项目中重复出现的操作，优先选择输入明确、流程稳定、输出可验收的任务；按 `SKILL.md`、`scripts/`、`references/`、`assets/` 组织文件，规定触发条件、依赖、错误处理和固定输出。先在内部使用并做单元测试，再交给客户环境。

8. **为每个交付项目建立最小评测集。**  
   对应场景：RAG、客服、获客和 Agent 上线验收。  
   怎么做：收集真实问题、标准答案、可接受变体、禁止回答样本和越权样本；每次修改模型、提示词、切片或 Skill 都自动重跑。除了答案质量，还记录响应时间、Token 成本、工具成功率、人工接管率和安全事件。

9. **建立“短期上下文 + 长期记忆”的分层策略。**  
   对应场景：8895 知识库中的客户项目协作与持续服务。  
   怎么做：当前任务只保留必要对话，较早内容压缩成结构化摘要；稳定事实、客户偏好和已确认决策经过人工或规则筛选后写入长期库；为记忆设置来源、时间、置信度、更新和删除机制，避免把模型猜测当成客户事实。

10. **把安全与权限写进交付清单，而不是上线前补丁。**  
    对应场景：企业客户部署、外部 Skill、Agent 工具调用。  
    怎么做：外部代码先人工审计，再在容器或沙箱中运行；按最小权限开放文件、网络和系统操作；对邮件发送、数据删除、合同提交等动作实行二次确认；保留调用日志、版本号和回滚方案。这样既能展示 AI 的效率，也能让客户敢于把它放进真实流程。

11. **把每次交付复盘成“问题—原因—修复—验证”记录。**  
    对应场景：FDE 项目迭代和团队知识传承。  
    怎么做：错误不要只改一句提示词，而要判断根因属于数据缺失、切片错误、检索噪声、模型能力、工具参数、权限还是流程设计；记录修复动作和评测结果。可复用的修复方案再转为模板、规则或 Skill，逐步降低后续项目的交付成本。

12. **用作品集证明“真实跑通过”，而不是只展示概念。**  
    对应场景：个人获客、FDE 能力展示和客户提案。  
    怎么做：围绕一个真实工作流展示前后对比、流程图、输入输出、评测集、失败案例、成本和安全边界。哪怕只是自动生成日报、分析评论或整理测试报告，只要能稳定运行、可解释、可复盘，就比堆砌模型名词更能证明交付能力。
