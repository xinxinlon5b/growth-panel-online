# 上篇 · 书籍内容（原文结构化精读）

## 引子：Demo 和生产系统是两回事

Demo 里模型能拆任务、能调工具、发现自己出错还能改——看着已经很接近一个能干活的同事。可真接进企业系统，要回答的问题立刻换成另一批：

- 它用的**业务口径**对不对？
- 会不会调到**不该调的工具**？
- 算错了，**谁来拦**？
- 疑似任务到底**花多少钱**？
- 量大了，还**跑不跑得动**？

这几个问题有个共同点：**换一个更强的现成模型基本都解决不了**。它们不是模型能力问题，是系统设计问题。

> **核心洞察**：Agent 真正落地，靠的不是让模型更自由，而是把模型放进一套**受控的行动系统**。

## 架构主线：一条线看懂受控系统

```
用户问题
   ↓
Agent 理解与路由
   ↓
语义与上下文层
   ↓
受控编排
   ↓
确定性执行
   ↓
校验与审计 ——→ 答案 / 真实业务动作
```

权限、成本、实验（可观测）这三条预算，从头到尾压在整条链路上。
这条链路上有**五个最容易出事的位置**，就是本片的五道边界：**语义、执行、权限、验证、成本**。

## 第 1 章 · 语义边界 —— 能听懂 ≠ 懂业务

**问题**：用户问「这个月销售额为什么跌了」，模型每个字都认识，但它不知道：这家公司的销售额用哪个指标？统计窗口怎么定义？退款算不算扣除？

**证据（两组数字，口径不同但指向同一件事）**：
- 腾讯：Spider 2.0、BIRD 这类公开评测集上，表现最好的模型在理想条件下 SQL 生成准确率也只有 **七成左右**，碰上复杂查询明显下降；
- 阿里析言：客户反馈**直接生成 SQL 的开箱可用率约 6~7 成**。

**主要瓶颈不在 SQL 语法，而在语义映射**：选错表、选错指标、选错时间口径——语法完全通过、业务完全错，是最典型的失败方式。

### 解法 A：语义层方案（本片讲得最彻底的一家——Aloudata 类指标语义层）

不让模型直接碰数据库，中间插一层**指标语义层**：

| 角色 | 类比 | 职责 |
|---|---|---|
| 指标语义层 | 地图 | 描述指标、维度、公式、血缘和权限 |
| 大模型 | 导航 | 理解意图、规划下一步 |
| 查询引擎 | 行动 | 生成并执行确定的 SQL |

流程：自然语言 → 翻译成 **MQL（指标查询语言）**——一句「只讲业务、不讲存储」的查询：要哪个指标、按什么维度拆、加什么过滤、看哪段时间。至于这个指标落在哪张表、对哪个字段求和，由语义层里**预先定义好的计算逻辑**说了算，不用模型操心。权限检查在 MQL 执行前完成，再由引擎把 MQL **确定性编译成 SQL**。

> ⚠️ 注意那个「100%」要按原意理解：它指的是「在 MQL 已经正确的前提下，引擎可以 100% 把 MQL 转成对应 SQL」——**不代表**自然语言到 MQL 有 100% 准确率，更不代表最终结论一定对。
> 真正值钱的是这层拆分本身：**把「问题理解得对不对」和「SQL 生成得对不对」变成两个可以分别测试的阶段。**

### 解法 B：析言（瓴羊）路线
- 用 **Evidence 注入**业务术语和同义词；
- 用 **Date Resolver** 把「近一个月」这类模糊时间映射到企业预设定义；
- 再用一组 **SQL 探针 Agent** 实际查询数据、反推表和列的含义，生成 M-schema 半结构化描述。
- 诚实的数据：这些自动生成描述**端到端精度大约只有 DBA 手写的一半** → 自动化能省标注成本，但还替代不了高质量的人工语义。

### 解法 C：更前置的统一元数据（Apache Gravitino）
做 Agent 用数据之前的**前置条件**：统一元数据坐标、统一血缘、统一权限。没有这层，Agent 只能靠表名/文件名猜，也没法判断数据新不新鲜、动了会影响谁。

> **本章结论：Agent 的第一步不该是生成 SQL，而是先确认这个问题对应的业务语义是什么。**

## 第 2 章 · 执行边界 —— 能调用工具 ≠ 可以自由行动

**最有说服力的样本：eBay 客服支持系统**（本片讲得最透的一家）。

他们先把主流路线调研了一圈：RAG、固定工作流、自主 Agent、ReAct（边推理边行动）、Reflection（自我反思）、一路排到 Tree of Thought、蒙特卡洛树搜索（MCTS）这些在推理树上做搜索的方法。

**反直觉的结论**：搜索能力更强的方法，离线评测完成率确实可能更高，但代价是模型调用次数、路径长度、延迟一起涨。社区实测：跑完一次完整 Agent 路径评估可能消耗**几十到几百美元**；如果 Agent 要靠两千多次 MCTS、花五个小时才返回答案——对一个等着解决线上故障的人来说，评测分再高也没有可用性。

### eBay 的取舍：往回退
1. 一开始想让模型根据历史工单**自主生成计划** → 真实用户描述不规范、历史记录不完整、计划做不稳；
2. 最终改成：由**专家写好的标准作业流程库（SOP）**，Agent 负责「选哪条 SOP → 补参数 → 按步骤执行」；实在没有匹配的 SOP，才让模型动态补全；
3. 执行阶段**放弃树搜索**，改成**单路径贪心**（每步只选当前最好的工具往下走，不回退、不探索其他分支），再用**多次采样投票**提高稳定性。
4. 把整条链路拆成**八个环节**：意图识别 → 路由 → 重新路由 → 路由算法 → 智能规划（基于 SOP 的规划）→ 受控执行 → 可扩展性……

> **重新路由最容易被忽略，但很实用**：路由决定问题交给哪个 Agent 处理，而一次分派完全可能是错的——用户在多轮对话里换了话题，或 Agent 干到一半拿到新信息发现最初判断不对。重新路由 = 让系统识别上下文已切换，自动退回路由内部重新分派，而不是沿着错的方向一路做到底。

### 同样的取舍，各家的做法

| 厂商 | 做法 | 要点 |
|---|---|---|
| 腾讯 | 按阶段分支 | 数据准备阶段用 DFSDT（带回溯的决策树搜索）或预定义结构在节点内调工具；进入分析解释阶段才换带规划的 ReAct 去探索 |
| 百度 | 线上异常洞察 | 用 LangGraph 把「影响判断→特征定位→修复建议」编排成三阶段**显式状态图**，中间允许用户用自然语言纠正；对比过低代码工作流和角色扮演式多 Agent，选代码编排是因为**状态、节点和边界显式化** |
| 火山引擎 | Data Agent | 把 Plan 和 ReAct 分开：在昂贵的工具调用**之前**先把问题补全、把计划做出来；执行阶段保留根据观察调整的能力。**计划被显式产出这件事本身就有价值**——给人或规则留出了一道可以检查的关口 |

百度的延伸建议：当前异常、时间窗口、每个 Agent 的证据和置信度、分支、重试、超时和回退——**都值得做成代码里的状态对象，而不是留在提示词里**。

> **本章金句（作者最认的一句）：越接近真实的业务动作，流程越应该确定；越接近意图理解，模型才越可以灵活。**

## 第 3 章 · 权限边界 —— 能连接工具 ≠ 能治理工具

**背景**：MCP 常被说成「只解决连接」——这个说法已不准确。协议本身带了基于 **OAuth 的授权框架**，也能接企业统一身份管理，**接入和授权这一段是标准化了的**。但协议能力 ≠ 治理落地：最终用户身份怎么映射到数据权限、行列级控制、审批审计、运行沙箱、资源配额——还得企业系统真正去实现。

### 范本：腾讯太极的内部 MCP 架构
- 不把公共 MCP 生态直接开放给内部业务，而是**自建内部市场和受控运行环境**；
- 只允许使用企业内部 MCP 市场；依赖包从内部镜像取；
- **Server 跑在沙箱里**，限制网络、文件系统和资源；
- 注册和运行时保留软件包、访问 Token 等元数据；
- **协议适配只是很小一块**，难的是供应链安全、运行隔离、凭证代理、权限映射、版本兼容和审计。

### 风险点提醒
- **声明式 MCP 的盲区**：有方案让客户端只传自然语言、看不到 Schema——这确实有治理价值，但 **Schema 不可见 ≠ 安全**：如果服务端用的是一个统一的高权限账号，客户端看不见，反而会**掩盖越权**。
- **Elastic 把检索能力做成 MCP Server**，重点讲标准化和复用；但真上生产至少还要补齐：限制允许访问的索引和字段、把**最终用户身份传到查询层**、设置 TopK/超时/结果大小、对查询和返回做**审计、脱敏和注入防护**。如果 Agent 能任意指定索引和查询语句，标准协议只会把攻击面放大。
- **Aloudata 的做法最值得认同**：把权限判断放在 MQL 执行**之前**，越权的数据**根本不进模型上下文**——这比生成答案之后再脱敏可靠得多。

> **权限五问（可照着自查）**：① 身份透传了吗？② 行列与租户隔离了吗？③ 调用预算设了吗？④ 审批流有吗？⑤ 注入防护做了吗？
> **本章结论：协议帮你把接入和授权流程标准化了；业务权限、策略、审计和资源预算，还得企业自己建。**

## 第 4 章 · 验证边界 —— 能完成任务 ≠ 结果可信

**最危险的状态**：Agent 不是报错，而是给你一份**结构完整、语言流畅、口径完全错**的结果。

**一组必须记住的数字（腾讯）**：在 BFCL、τ-bench 这类基准上，大模型单次执行任务准确率能到 **七成**；但如果要求**同一个任务连续跑 8 次全对**，准确率会骤降到 **两到三成**。这个指标衡量的不是多步链路的误差累积，而是**一致性**——同一道题，这次做对了，下次未必还对。对「结果必须可复现」的数据分析场景，这个矛盾比平均准确率低更要命：**单次跑通，替代不了稳定跑通**。

### 应对一：分层验证（腾讯）
- 按步骤选不同模型；用验证 Agent 检查结果；
- 大结果先切片再做细粒度验证；
- 工具调用前后都保留参数校验（前置校验 + 结果校验）；
- 高风险任务用固定工作流兜底。

> ⚠️ 他们自己承认的局限：**验证 Agent 和执行 Agent 如果用相近的模型 + 相同的上下文，会共享同一批盲点。自检替代不了确定性验证。**

### 应对二：防幻觉四机制（百分点科技，做数据治理）
1. 企业标准文件和制度文档**先进知识库**，生成内容时优先检索既定知识；
2. 把温度这类生成参数压低（例：0.1）；
3. 每个子步骤的**输入输出都明确定义**（元数据读取→字段分析→规则推荐→等级汇总一步步排开），**消除工作流黑箱**；
4. 模型只负责**出初稿**，最终由**领域专家审核确认**。

> ⚠️ 两个清醒认知：
> - **低温度最容易被高估**——它只能降低输出波动，不能保证事实正确，替代不了规则校验和人工审核；
> - 「输入输出明确定义」的真正价值：**出错的时候分得清责任**——到底是数据的问题、检索的问题、模型的问题、还是规则的问题。
> - 他们给的人机分工：Agent 约八成、人工两成做审核调整（明确**不含**前期的 Agent 开发阶段）。

### 应对三：把最容易算错的拿走（Aloudata 归因引擎）
回到「这个月销售额为什么跌了」——要回答它得把下滑拆开：哪些地区/品类各自贡献多少跌幅（**归因**），每块占多大比例（**贡献度**）。他们的分工：

- **贡献度全部由算法引擎精确计算**；
- 模型只做三件事：判断用户问的是哪一类归因、组织分析流程、把结果写成报告；
- 高基数维度（如几百万个商品编号）模型根本装不下 → 先在引擎侧算完排序，**只把贡献最大的 200 来项**交给模型解释。

> ⚠️ **贡献度拆解 ≠ 因果**：华南贡献了六成跌幅，只说明这次下滑主要发生在华南，不能就此认定是华南出了问题——也可能是季节、渠道政策变了，或者那边的盘子本来就最大。

> **本章验收标准：不是「有没有回答」，而是「错误能不能被发现、被阻断、被回放」。**

## 第 5 章 · 成本边界 —— 能运行一次 ≠ 能规模化

一次用户请求背后可能是：多轮规划、多次检索、若干条 API、重排、重试和大模型调用。**模型单价低 ≠ 完成一个真实任务的成本低。**

### 四种有效的省钱做法

**① 按问题深浅分级**（Perplexity 的深度研究四级）：
- L1 一问一答，直接返回结果；
- L2 不光给答案，还能解释原因；
- L3 从多个角度探索、提出假设并逐一验证；
- L4 数据一有变化就自动识别异常、直接给解决方案，全程不用人插手。
- 现状：L4 完全自主动察还没实现；L3 已在不少场景跑出效果。
- 延伸洞察：**自主性涨一级，要验证的东西也跟着外扩**——从验答案对不对 → 验解释站不站得住 → 验假设和证据够不够 → 验这个问题值不值得系统主动提出来。**自主性涨一级，验证成本也涨一级，不该一味往高级别冲。**分级的实际作用 = 按复杂度分配研究深度，不让所有任务都走最重的流程。

**② 漏斗**（Elastic 检索链路）：先用便宜确定的召回缩小范围 → 中间做一次重排 → 最后才让昂贵的重排模型处理少量候选；相似度够高时，甚至可以完全不调大模型。

**③ 能力下沉到服务端**（声明式 MCP 案例）：引用的 PostgreSQL 评测里，准确率从 **58.5% 提到 80.08%**，客户端 Token 消耗降到约 **1/10**；代价是响应时间从约 **5.85 秒升到 12.87 秒**，且同样的改造在 MySQL 上增益很小。这几个数字得一起看：**Token 降 10 倍 ≠ 总成本降 10 倍**——省掉的是客户端反复传 Schema 的上下文开销，计算挪到了服务端，服务端要多跑一层模型，这正是响应时间涨上去的原因。

**④ 别让 Agent 自己扛计算**（阿里云）：把精确的大规模计算整个交给 **MaxCompute 这类执行底座**；模型负责理解和编排，平台负责规模化执行——**别让 Agent 把大表往上下文里搬**。

> **本章结论：要统计的是「每个成功任务的端到端成本」，而不是单次模型调用的价格。**

## 终章 · 放回同一张图 + 模型的尽头 + 五问清单

### 一句话答案
> **把概率性的理解和规划放在前端；把确定性的计算、业务规则和权限控制放在后端；中间用一层可观察、可回退的编排把两边连起来。**

### 五道边界的共同前提（重要）
以上所有约束，全都是在**模型不动**的情况下从外面加的：模型不稳就加校验，模型乱走就用 SOP 把路框住。这条路能把系统送上生产，但有个绕不过去的上限——回到那个数字：**同一个任务连跑 8 次只有两三成全对。外面的校验层能把错的拦下来，却没法让它下次做对。**要真正动这个数字，只能回到模型本身，让它在多步工具调用里学会哪一步该走、错了又错在哪——这就是 **Agentic RL**（PPO/GRPO、RLVR 等）在解决的问题（视频后半为课程引流，方法论部分此处略）。

### 五问评审清单（可直接拿去评审自己的 Agent 项目）
1. 它用的**业务语义从哪来**——是语义层/元数据，还是提示词里硬写的？
2. **哪些步骤允许模型自由推理，哪些必须固化成工作流或 SOP？**
3. **工具权限是不是继承了最终用户的身份**，而不是共用一个高权限账号？
4. **错误怎么被验证、被阻断、被回放？**
5. **有没有统计过每个成功任务的完整成本**，而不只是模型单价？

### 结尾金句
> Demo 之所以惊艳，是因为它把模型彻底放开了；生产之所以难，是因为你要一边放开、一边把每一步都收得住。
> 这批实践给人最深的印象，不是谁家的模型更强，而是**他们在每一处不确定的地方，都配了一道确定的设计兜着**。
> **一个成熟的 Agent，不是能做最多事情的那个，而是在明确的边界里、能稳定完成正确事情的那个。**

# 下篇 · 方法论精华（可迁移框架）

## 1. 一张架构主线（记住这条链）
`理解路由 → 语义上下文 → 受控编排 → 确定性执行 → 校验审计`，全程压着「权限 / 成本 / 可观测」三条预算。

## 2. 五道边界速查表

| # | 边界 | 一句话 | 核心证据 | 最彻底做法 | 判断标准 |
|---|---|---|---|---|---|
| 1 | 语义 | 能听懂≠懂业务 | SQL 开箱可用率仅 6-7 成；瓶颈在语义映射不在语法 | 指标语义层（地图/导航/行动分离） | 业务口径来自哪？ |
| 2 | 执行 | 能调工具≠自由行动 | 树搜索评测高但延迟成本爆炸；5 小时返回=不可用 | SOP 主 + 单路径贪心 + 多次采样投票 | 哪步可自由、哪步必须确定？ |
| 3 | 权限 | 能连工具≠能治理 | 协议标准化≠治理落地；Schema 不可见≠安全 | 内部市场+沙箱+身份透传+权限前置 | 继承最终用户身份吗？ |
| 4 | 验证 | 能完成任务≠结果可信 | 单次 70% 但连跑 8 次全对仅 2-3 成 | 分层验证 + 确定性校验 + 算数交给引擎 | 错误能被发现/阻断/回放吗？ |
| 5 | 成本 | 能跑一次≠能规模化 | 模型单价低≠任务成本低 | 分级/漏斗/下沉服务端/底座执行 | 算过端到端单任务成本吗？ |

## 3. 两条通用原则
- **确定性/灵活性分工律**：越靠近真实业务动作 → 越确定（SOP/工作流/状态对象）；越靠近意图理解 → 越灵活（模型自由）。中间用「可观察、可回退」的编排连接。
- **外部约束的极限律**：模型外的校验/SOP 能把错误**拦下来**，但改不了模型本身的**一致性上限**；要根治只能回到模型（Agentic RL / 评测驱动迭代）。

## 4. 三组可复用设计模式
1. **分层拆分**：把「理解对不对」和「执行对不对」拆成可分别测试的阶段（NL→MQL→SQL 同理）。
2. **前置闸门**：权限判断放执行前，越权数据根本不进上下文（比事后脱敏可靠）；校验放工具调用前后。
3. **状态外置**：把分支、重试、超时、回退、置信度做成代码里的状态对象，别留在提示词里。

# 借鉴篇 · 我们能借鉴的点（结合我们的业务）

## 借鉴 1：直接变成客户交付的「生产化体检工具」⭐最高价值
我们做企业 AI 落地 / 智能体交付（FDE 线），最怕客户以为「Demo 能跑 = 交付完成」。「五问评审清单」就是现成的**交付验收工具**——每个项目上线前拿这 5 问过一遍：
- 客户数据口径谁定义？（语义）→ 正好接我们的「数据盘点/口径对齐」服务；
- 哪些动作固化 SOP？（执行）→ 正好是我们给客户写标准操作流程的卖点；
- 权限是否继承最终用户身份？（权限）→ 对接我们的安全红线交付标准；
- 错误怎么被拦？（验证）→ 接「黄金集评测 / LLM-as-judge」体系；
- 端到端成本算过吗？（成本）→ 接包月订阅/模型选型的成本顾问话术。

**落地动作**：做成一张「Agent 生产化体检卡」，放进交付包（决策卡体系 + FDE 手册「激活部署」章）。

## 借鉴 2：给我们自己的获客 Agent 系统做一次自查
我们的获客线（线索采集→AI 评分→画像→话术触达）本身就是 Agent 系统，能直接套五问：
- **语义**：线索评分/画像的「业务口径」来自哪？话术引擎 customer_journey_engine.json 里硬写的规则 vs 结构化知识——哪些判断可能选错口径？
- **权限/合规**：VK 合规红线（禁群发陌生用户、token 1h 过期、3rps）正是「权限边界」的企业实践——我们已做对的继续守；用户 key 不共享高权限账号 ✅；
- **验证**：评分模型输出有没有「连续一致率」概念？同一线索两次评分结果稳不稳？
- **成本**：批量触达的端到端成本（API+代理+人工跟进）有没有按「成功触达/成交」算过，而不是只看单条消息成本？

## 借鉴 3：8895 成长系统方法论入库
- 新增决策卡候选：**「Agent 生产化五问」（评审清单卡）**、**「五道边界速查」**、**「确定性/灵活性分工律」**；
- 这条「视频→书籍内容」加工流水线本身也可以沉淀成 skill（如果这轮验证 OK）：B站视频 → yt-dlp 直连下载音频 → whisper 转写 → 结构化书章节 → 方法论/借鉴点三层加工。

## 借鉴 4：销售/咨询场景的「诊断式开场」
给潜在客户演示时，「五道边界」是很好的**需求制造框架**：问客户「你的 Agent 敢不敢让最终用户直接问？答错了谁来发现？越权了谁负责？跑一次真实任务多少钱？」——大部分企业的 Agent 项目都答不上来，这正好打开咨询/交付入口。

## 借鉴 5：内容创作弹药（短视频/公众号）
我们自己要做「7 天交付级智能体」内容——这个视频是现成选题参照：
- 「Demo 惊艳 vs 生产艰难」的反差开场 + 五道边界清单体，是很好的短视频结构；
- 视频里的数字（单次 70% vs 连续 8 次 2-3 成；SQL 开箱可用率 6-7 成；Token 1/10 但延迟翻倍）都是能直接引用的「硬核证据」。

## 借鉴 6：成本观对齐
「统计每个成功任务的端到端成本，而非模型单价」——和我们已有的成本纪律（包月订阅当牛马、DeepSeek 低谷时段跑、K3 禁按量）完全同构，可以写进给客户的成本方案话术。
