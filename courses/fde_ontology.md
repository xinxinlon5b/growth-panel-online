# 上篇 · 书籍内容（原文结构化精读）

## 第1章 先看一个"会说谎"的 Agent

视频从一个非常扎心的场景开场：老板让你做一个 Agent（智能体）。老板问："供应商 A 的评分是多少？"Agent 第一次回答 85 分；同样的问题，两分钟后再问，变成了 92 分。

问题出在哪？你可能已经把企业文档、企业数据一股脑全部打包丢给了这个 Agent——一个典型的 RAG（检索增强生成）式问答。但当初你没有让 Agent 真正"读得懂"：它不知道评分机制是什么、评分背后的业务需求是什么、衡量指标是什么。所以本质上，**它没有说谎，它只是真的不知道**——不知道供应商是谁、评分的价值维度是什么、评分算的是什么。

这就是 Ontology 要解决的问题。

### Ontology 是什么

Ontology，中文叫**本体**，说白了它是一种**知识地图（Knowledge Map）**。它不只是告诉 AI"企业有哪些数据"，更重要的是告诉 AI：

- 这些数据**之间有什么关系**；
- 这些数据需要**遵守什么样的规则**；
- 每个业务概念背后的**含义与衡量口径**。

它是企业在 AI 层面的**数字孪生（Digital Twin）**——让 AI 能读懂你企业的东西。有了这张地图，AI 才能从原来的"随机猜测"变成"有据可查"，它才能跟着你的业务流程走。

举个例子：你定义好"供应商"有名称、评分、地区；"材料"有存储条件和安全阈值；再定义供应商和材料之间的关系。这些东西写进知识图谱，就是 Ontology。有了这些结构化事实之后，你再去给老板交付那个 Agent，它就不是在猜了，而是在顺着这张地图做推理：**"这个材料缺货了"→ 会影响哪一条产品线 → 会影响哪一个客户的订单**——这些 Business Flow（业务流程推演）只有在 Ontology 构建好之后才能实现。

所以视频给出一个核心论断：**企业 AI 的前置条件，是先搭建好 Ontology。**

## 第2章 旧办法为什么走不通：白板知识工程之死

传统知识地图是怎么建的？知识工程师（Knowledge Engineer）和领域专家坐在一起，花几个月画白板、反复讨论、修改，把各种标准格式的定义艰难地写完。

但这套方式有几个很深刻的问题：

1. **慢**：好不容易建完，业务可能已经发生变化，整个过程又慢又滞后；
2. **没人维护**：搭建完之后，没有人愿意持续维护；
3. **结果是"死模型"**：大多数公司的知识管理系统最终变成死模型——它没有接入系统（没有介入企业的 ERP 等业务系统）；即使介入了，也解决不了**人才矛盾**（专家太贵、太少）和**速度矛盾**（业务变化太快）的问题。

LLM（大语言模型）出现之后，这件事有了解法，但**没那么简单**——LLM 想要构建 Ontology 还有四道坎：

**第一道坎：实体定义问题。** 你一开始不知道领域里有多少种类型。是 10 种还是 1000 种？连最开始的领域专家都说不准。

**第二道坎：幻觉问题。** LLM 本身会产生幻觉，可能创造出原始数据当中不存在的概念，然后把它幻觉想象出来的东西当成事实。

**第三道坎：颗粒度问题（最危险）。** 实体和实体之间关系的颗粒度很难控制：列得太宽（太粗），大家觉得没用、没人用；列得太细，又没有人能维护。实体之间的联系太笼统也不行。没有人能说清什么样的颗粒度更适合，这是一个很大的难题。

**第四道坎：交付与评估问题。** 你该告诉别人"怎么样的 Ontology 才算好"？没有人给你答案，也没有绝对的对错之分。怎么评估好坏、怎么判断建好的 Ontology 是否可用，同样是问题。

这四道坎，学术界和工业界发展出了**五种不同的应对流派（方法论）**。

## 第3章 五种构建流派：把 Ontology 从纸面落到代码

### 3.1 拆解法（Agentic Pipeline）——最可靠，但工程量最大

思路：把一个大任务**拆解成一个个小任务**，每一步选用最适合的工具：提取实体 → 提取关系 → 去重 → 归并验证 → 存储，一步一步来。

它最关键的设计是**验证闭环（Validation Loop）**：每一个新事实，都必须先通过**结构化检查**和**逻辑验证**，才能进入可信的知识图谱；通不过的只保留在日志里，绝不让它污染整个知识库/本体。就像做一道很复杂的菜——先洗、再切、再炒、再装盘。LLM 在这里只是辅助工具（帮你提取关系、抽取核心概念），而**业务规则的处理和验证，都要由业务专家来做**。

代表性案例：**法国电力公司 EDF** 用这套方法管理核电站的知识——第一层做结构化验证，第二层做逻辑验证，两层都通过，才算一个完整可信的核心本体。这也许是目前最可靠的方式，但它的工程量非常大。

### 3.2 聚类法（数据驱动自底向上）——让数据自己说话

思路：**先别定义有什么东西**，把任务交给数据，让数据自己说话。先把文档当中所有的"名字"（名词）都提取出来，再用聚类方法分组。

为什么用 AP 聚类（Affinity Propagation，亲和传播）而不是 k-means？因为 **k-means 要你事先告诉它一共有几类**，而我们的数据里事先并不知道有几类，所以要用**不需要指定聚类数量**的 AP 聚类。聚类完成之后，再让 LLM 给每一个 group 起名字。

视频提到 2025 年的一篇代表性论文（LM 驱动的无监督本体构建方法），流程是：输入文档 → 提取文档中的名词 → 用 Embedding 模型把名词向量化 → 对向量做 AP 聚类 → 用 LLM 命名 → 最后构建出本体层级。就像搭乐高积木：颜色相近的放在一起，再给每组贴标签，然后看各组之间怎么链接、有哪些动作。核心创新是**实例关系到本体关系的上升**：第一步从实例中提取关系，第二步把实例关系上升为本体关系，构建三元组——实体（Entity）、关系（Relationship）、另一个实体。

优点：**数据驱动**；因为是在解决一个个小任务，幻觉（出错率）也低一些。缺点：**聚类质量直接影响最终结果**。在开放域（比如用 Wikipedia 这类数据构建本体）中，输出颗粒度可能过细也可能过粗。适合场景：**探索全新的领域**——你不知道有哪些类型、哪些结构时，用这种方式比较好。

### 3.3 提纲两步法（中间产物可审查）——快速出 V0.1

思路：先让 LLM 从文档中提取概念清单，再把这些清单整理成有上下级的**层级结构**，最后生成一种标准格式（如 OWL/RDF 等本体标准格式）。就像写论文：先写提纲，再按提纲写章节。

关键优点：**中间产物是可以查看的**，可以由人工审查和调整——不是黑盒一把梭。最适合**快速输出 V0.1 版本**，用来验证我们对整个 Ontology 的想法。同类代表性工作（如 Ontology EKG 一类的论文方法）：通过这种方式快速提取文档中模块化的内容，然后生成标准的 Ontology 格式。

### 3.4 框架约束法（Schema 约束生成）——有行业标准时的最优解

思路：先引入一个**已有的成熟框架**作为约束。比如 **Wikidata**——全球最大的开放知识库，里面有几十亿个实体，类型、关系早已定义好。让 LLM 在这个框架内提取实体，而不是随意发明。

这样做可以**大大减少 LLM 的幻觉问题**，输出也天然符合大家的共识和合规要求。**如果你所处的行业本身有标准规范——比如金融、医疗、电力，本身就有标准 Schema（模式）**——这种方式最适合：用框架（Wikidata 或行业标准）约束 LLM 去提取 Ontology，少走弯路。

### 3.5 直给派（端到端 Prompt）——最快，也最危险

思路：通过端到端的 Prompt，用最简单也最危险的方式——设置一个 Prompt，让 LLM 直接从文本输出 Ontology，一个模型包揽所有工作。

优点：时间最快，适合你**想快速学习、理解一个 Ontology** 的场景，可以走很快。缺点：幻觉风险最高，输出质量最不稳定——Prompt 稍微改一下，结果可能就完全不同。视频提到：去年（2025）有一个通过 LLM 提取 Ontology 的挑战赛，大家发现只要 Prompt 稍作改动，整个 Ontology 结构就会变掉。这种对 Prompt 的极度敏感，决定了它**只适合原型验证**。

### 3.6 选型地图与两个反直觉教训

| 你的处境 | 推荐流派 |
|---|---|
| 快速试试看、探索一个全新的领域 | 聚类法 / 提纲两步法 |
| 已有行业标准或现成知识模型（金融/医疗/电力/Wikidata） | 框架约束法 |
| 要上生产系统 | **一定是拆解法** |
| 学习、理解一个 Ontology 长什么样 | 直给派（仅原型） |

**教训一：错误大多只发生在第一步——实体提取。** 类型标错、关系识别错、实体混在一起……这些错误会一路传导到后面，越积越多。所以宁可构建的第一步多花功夫，也不要到后期再返工。这跟我们做数据治理一模一样：先把数据治理好，后面的模型输出才能可靠。

**教训二（违反直觉）：构建 Ontology 并不是数据越多越好。** 视频引用的论文案例，用了不到 1000 个 token（极少量数据/样本）就搭建了一个很完整、很有效的知识图谱。关键不是数据量，而是**数据质量和约束是否合理**。

> 一句话总结：LLM 构建 Ontology，已经不是"能不能"的问题，而是"怎么建得更好"的问题。五种方法各有擅长与场景，根据场景选择合适的方法，去满足自己的需求。

## 第4章 落地细节：从一堆脏文件到一个 Ontology

万事开头难，最难的一步其实是**最开头的一步：怎么接入数据**。很多人直接给你讲最后的结果，跳过"一群脏数据是怎么一步一步变成一个 Ontology"的细节。视频用 **Palantir Foundry 官方文档里的航空公司场景**，把这条链路完整走了一遍。

### 4.1 三类原始数据

假如你有一个航空公司，手里的数据大概有三种形态：

1. **结构化数据（CSV / Database）**：例如航班表，一行代表一个航班，有出发时间、状态、飞机尾号等字段——最标准的结构化数据。
2. **半结构化数据（JSON）**：例如乘客预定数据，来自 OTA（在线票务平台）订票系统，每一份预定单里嵌套着乘客信息、多段行程等内容，结构复杂。
3. **非结构化数据（最糟糕）**：例如 PDF 扫描件、工程师手写的维修记录。

### 4.2 五段链路总览

这三类数据构成一个 Ontology 的完整链路，可以简单理解为**五个阶段**：

① 数据连接（把数据接进来）→ ② 分类存储 → ③ 清洗解析（签约/解析成标准表格）→ ④ 映射构建（构建成 Ontology 的对象）→ ⑤ 逻辑与动作（让本体"活"起来）。

### 4.3 阶段一：数据连接（Data Connection）——原封不动

Foundry 的第一个原则：**从原系统拉取数据的时候，不进行任何预处理，让所有的变化都在 Foundry 内部完成**。这样你就能从 Ontology 的任何一个数据点，追溯到最原始的源文件。在金融、医疗这些合规要求非常严格的行业，这是硬性要求。

Foundry 有 200 多种连接器（Connector），可以对接不同的数据源。拉取方式有两种：

- **Snapshot（快照）**：每次全量替换；
- **Append（追加）**：只增加新数据。

后面讲增量更新时，这个区别很重要。

### 4.4 阶段二：存储——DataSet 与 MediaSet

数据拉进来之后，存在 Foundry 的存储层，有两个核心概念：

- **DataSet（数据集）**：通用存储容器，可以存 CSV 表格、JSON 文件等。每次更新都有版本记录，像 Git 一样——被称为 **"Git for Data"**，任何历史版本都找得回来。
- **MediaSet（媒体集）**：面向媒体类、非结构化信息的通用存储容器，可以存图片、视频、音频、PDF。它在 DataSet 的基础上，额外提供了**对 AI/解析工作流的集成**——因为 PDF、音频这些内容，都需要单独通过 LLM、OCR 或其他模型做识别解析。

两者之间有一个关键设计叫 **Media Reference（媒体引用）**：可以在 DataSet 里引用 MediaSet 中的某个文件。比如你的维修记录，每一行有航班号、维修日期这些结构化字段，同时还有一列指向最原始的那份 PDF 扫描件——**这把结构化和非结构化数据连接了起来**。

### 4.5 阶段三：Pipeline Transform——最脏的部分

这是对数据做清洗、解析的部分，三类数据走的路线完全不同。

**路线一：结构化数据（最简单）。** 比如一份 200 万行的航班原始 CSV。Foundry 有一个 **Apply Schema（应用模式）按钮**：点完之后自动扫描整个 CSV 样本，识别哪些是文本、哪些是时间、哪些是数字，自动推断字段类型。之后你可以用 Foundry 的 **Pipeline Builder** 做过滤和去重，得到一张干净的 Clean Table（清洗表）。整个过程不用手写代码——它有自动推断 Schema 的逻辑。

**路线二：半结构化 JSON / XML。** 要做的事情是把嵌套结构"摊平"。比如客户预定文件：客户信息和多段行程嵌套在一起，一份订单可能包含两段行程。这里有一个关键操作叫 **Explode（炸开/展开）**：把嵌套的数组炸开、摊平成单独的行。这样一个 JSON 文件就变成了两张关系表——**乘客表**和**预定表**，再用一个**订单 ID** 把两张表关联起来。

**路线三：非结构化数据（维修报告 PDF 扫描件）。** 没有数字化的结构，必须让 AI 来处理，流程是：

1. PDF 转成 Markdown：**OCR + 多模态视觉理解**，让 AI"看"界面，输出 Markdown 格式的文本；如果只做文字处理，也可以用开源工具（如 Marker 一类的 PDF 转 Markdown 工具）；
2. 从 Markdown 中**解析业务字段**：比如航班号、维修日期、更换的部件、连接件等；
3. **人工复核校验**（最容易被跳过的一步）：判断格式是否正确、字段是否错位，需要人工参与；
4. 输出一张干净的 **Maintenance 表（维修结构化表）**：每一行保留一列指向原始 PDF，方便后续数据追溯。

### 4.6 阶段四：映射到 Ontology（Mapping）

前面花大量工作清洗、结构化数据，得到干净的表之后，还要把它映射到 Ontology。怎么做 Mapping？核心是一张对照表：

- 一张干净的表 → 对应一个 **Object Type（对象类型）**。例如航班 CSV 表对应一个对象类型；
- 表里的每一行 → 对应一个 **Object（对象）**，例如具体的某个航班；
- 表里的每一列 → 就是 **Property（属性）**，例如航班的出发时间、状态；
- 两张表之间有关联关系 → 用 **Link Type（链接类型）** 连起来，例如 Flight（航班）和 Aircraft（飞机尾号）的链接；
- 对对象的读写操作 → 定义为 **Action Type（动作类型）**，例如航班改签、更新状态。

视频强调：**Action Type 是 Ontology 的一个核心创新**。传统的数据工具只能"查"不能"改"，但 Palantir Ontology 可以让业务用户直接参与修改数据，并且把修改**写入独立的 Writeback Dataset（回写数据集）**，不会污染原始数据源——原始数据源始终保持干净。这正是它最开始做"数据原封不动"那个原则的价值。

### 4.7 阶段五：Logic 与 Action——让本体活起来

构建好 Object Type、Link Type、Action Type 之后，还需要两样东西才能把 Ontology 真正用起来：

**第一样：Logic（逻辑）。** 做逻辑推断和逻辑计算的，能自动推导新信息。例如一个航班延误多久——不需要人工录入，系统可以直接根据计划出发时间和实际起飞时间自动算出来；又例如每家公司平均延误了多久——可以跨航班聚合得到。

**第二样：Action（动作）。** 前面说过 Action Type 是 Ontology 的创新点。每个 Action 有四部分：

1. **参数（Parameters）**：需要哪些输入；
2. **规则（Rules）**：执行时做什么；
3. **前置条件（Preconditions）**：什么情况下才能执行；
4. **负责人（Approvers）**：由谁来审批、触发什么。

每一个修改都会写入独立的记录，不会覆盖原始数据——谁改了什么、什么时候改的，全程可审计。

## 第5章 上了生产之后的三个真问题

### 5.1 增量更新：三层配合，绝不每次全量重建

原始系统的数据每天都会变：新航班进来、乘客改签、维修记录更新……怎么同步？是不是每次都要全量更新、重新构建？**不至于。**

图书馆比喻：图书馆要新增 100 万本书，你不会把图书馆全部搬空，再把 2100 万本全部搬进去。全量搬运费时费力；而**增量更新**每周只处理新增的书，可以省下大量时间。

增量更新需要**三层的配合**：

1. **数据同步**：拉取新的数据（Append 方式）；
2. **Pipeline 处理**：只处理新增的行；
3. **Ontology 索引**：只更新发生变化的对象。

三者缺一不可。

### 5.2 坑一：数据是可变的

如果航班状态从"准点"变成"延误"，用 Append 模式同步时，就会出现新版本和旧版本同时存在的问题。这种问题需要在 Pipeline 里**去重，并且只保留最新的状态**。

### 5.3 坑二：人工修改与批量更新的时间差

用户通过 Ontology 界面点击"改签"时，修改**立刻生效**；而 Pipeline 的批量更新是**定时运行**的——两个数据来源之间有时间差（Gap）。Ontology 会把两个来源的数据合并，所以需要留意这个时间差。

### 5.4 宽表怎么办：一个 Object Type 只能对应一张表

现实中的数据不是几张简洁的小表。从 ERP 导出的往往是**大宽表**——把订单、客户、商品、物流全部放在一张表里的大宽表。

Foundry 有一条**硬性规则：一个 Object Type（一种实体类型）只能对应一张表**。所以宽表不能直接映射，必须在 Pipeline 里把它**拆解成几张聚焦的小表**——比如订单表、商品表、物流表——再把每张表映射到各自的 Object Type，最后用 Link 把它们链接起来。

Foundry Pipeline Builder 里的 AI 功能可以帮助你编写拆解代码，但**"究竟怎么拆、哪个字段属于哪个实体、哪些需要人来判断"——这些是 FDE 们最宝贵的时间投入所在**。

### 5.5 FDE 的价值时刻，与"产品化"之辩

为什么说 FDE（Forward Deployed Engineer，前向部署工程师）的价值大量体现在这里？因为他们需要**理解业务逻辑，替企业做出这些判断**：哪些实体需要构建、哪些不需要、宽表应该怎么拆。

有人会问：能不能把不同业务、不同行业的模型沉淀成模板，以后快速部署、一键安装？技术上也许能做出来，但**没有价值、没有动力**——因为 FDE 常驻咨询本身就是 Palantir 的商业模式，是绑定客户的核心资源。

为什么不沉淀模板？很多对象（供应链里的 shipment 物流、医疗业务里的 patient 患者、金融里的 account 账户）跨行业、跨企业，通用度非常高。但"你知道又怎样？你有产品又怎样？它不会成为你的护城河。"

**真正值钱的是什么？** 客户给你一张系统导出的、包含 200 张大宽表的数据包，你能告诉它"哪一列映射到哪一个 Entity（实体）"——**这一套 Mapping 规则，才是 FDE 在客户那里反复花时间做的事情**。所以产品化的方向不是一个静态的模板，而是沉淀"拆解与映射的判断方法"；对垂直行业的玩家来说，谁能先把这些领域的知识标准化，谁站在 Palantir 的生态当中，就有一个更结构性的优势。

视频最后的劝退与定位：**FDE 是一个不得不做的事**（脏活累活）。如果你已经有一个很不错的产品，不要去做 FDE。但这里不存在鄙视链——FDE 也在解决一个实际的问题，而且很多好的产品、好的思路，都是从先做一个 FDE 开始长出来的。

## 第6章 Ontology ≠ 一张好表：与普通数据库 Schema 的三大差异

有人觉得 Ontology 不就是在做数据处理吗？其实真正的差异是这三点：

1. **血缘追溯（Lineage）**：Ontology 中任何一个字段，都可以追溯到最开始原始文件当中的任何一行——尤其是金融、医疗这些行业。
2. **可以写回（Writeback）**：Palantir 的 Action Type 可以把产生的修改写进 Writeback Dataset，不污染原始数据。
3. **应用层可以直接消费**：不需要再写一套 API。AI 和应用可以直接操作 Ontology 里面的对象，一次操作就可以完成，基于这个 Ontology 进行各种业务决策和决策仿真。

正是这三点，让 Ontology 变成了一个 **AI Agent 的操作层（Operational Layer）**。

## 第7章 Agent 怎么操作 Ontology

在 Palantir 体系当中，**AI 不会直接访问底层数据，也不会自由地完整扫描 Ontology 的 Schema**。它是在 Page（页面）和授权的边界内，通过 Ontology 暴露出来的对象、关系、上下文函数、动作，来完成交互业务。

Ontology 可以理解为：**企业的数字孪生，一个语义接口**；而 Agent 是**通过自然语言去使用这些接口的操作员**——它相当于一个 Agent OS（智能体操作系统）。

很多人一听到 Ontology 就以为它是一个知识图谱或某种数据结构，但它其实是一个 **Operational Layer（操作层）**——坐在数据库、数据表、模型之上，把技术底层的语言翻译成业务语言。它分两种能力：

**能力一：描述世界（静态语义层）。** 例如 Shipment（物流单）、Order（订单）、Warehouse（仓库）、Customer（客户）这些 Object Type；Status（状态）、ETA（预计到达时间）这些属性；以及"Shipment 归属于哪个 Order、Order 又属于哪个 Customer"这些 Link（链接/关系）。这一层解决的是：**Agent 怎么知道企业内部有哪些东西、谁和谁关联**。

**能力二：改变世界（动态行为层）。** 分两大类：

- **Action（动作）**：例如 Update Shipment ETA（更新物流预计到达时间），以函数形式存在，可以动态更新运输到达时间；
- **Function（函数）**：实时计算一些东西，比如计算评分点、计算延误风险，或优化函数来做调度优化。

这一层解决的是：**Agent 如何从一个问答工具，变成真正帮我们执行业务、产生业务价值的工具**（比如做仿真决策）。

所以 Palantir Ontology + AI 的核心不是"给一张表换个名字叫本体"，而是把**名词（实体）、规则、关系、动作**，全部放进一个操作层里。

## 第8章 五层架构：Agent × Ontology 交互的完整骨架（全片核心）

Agent 和 Ontology 的交互可以分成**五层**来理解，越往后 Agent 的主动性越强，第五层贯穿始终。

### 8.1 第一层：Context Layer（上下文层）——系统自动备料

每次用户发消息时，系统会把相关的背景自动准备好。注意：是**自动准备好**，而不是等 AI 决定要不要查——这是确定性触发的，每一条消息都会自动执行，不需要 LLM 判断"要不要检索"。有三种准备方式：

**① Ontology Context（对象上下文）**：从对象类型里检索，可以绑定固定的对象。比如你在页面上选中了"华南仓"，Agent 就会自动拿到华南仓的相关信息——库存、整体面积、对应负责人，只要跟它相关的全部拿到。过程中也可以使用语义搜索：比如"华南仓最近有没有延误相关的投诉"，系统会自动对历史投诉做向量搜索，通过 Embedding 返回最相关的几条。

打个比方：就像**秘书在老板走进会议室之前，先把相关资料摆在桌上**。语义搜索相当于图书管理员听到你的问题后，主动从书架上抽出最相关的五本书放在你面前——你不用自己找书，直接翻更方便。

**② Document Context（文档上下文）**：从文档里捞内容。有两种模式：**全文模式**——把整份合同丢给 LLM；**片段模式**——只返回最相关的几个文档块。比如你问"合同 A13A 里关于延误赔偿的条款是什么"，系统会自动从三份合同里筛选最相关的段落返回，而不是把整份合同都丢进去。看起来跟语义检索类似，只是变成了文档形式，用的也是 Vector Embedding 搜索，返回片段式或文段式内容。

**③ Function-backed Context（函数支撑的上下文）**：前两种不够用时，你可以写一个 TypeScript 或 Python 函数做自定义搜索。比如"客户 360 视图"：同时拉取 CRM 记录、活跃订单、投诉工单，拼凑成一份综合情报交给 LLM。比方说：**秘书在老板开会之前，同时打电话给销售部、客户部、法务部，把各方信息归拢之后再交给你**。企业高频场景可以预设函数——客户相关的问题，不管问什么，所有关于客户的信息都会被写进一个函数；用户一问，系统就把客户信息调出来，喂给 LLM 作为上下文。

### 8.2 第二层：Query Layer（查询层）——Agent 自己决定查什么

Context 是系统自动准备的，Query Layer 则让 Agent **自己决定要查什么**：做过滤、聚合、检查，或者顺着关系链搜索、继续往下追。

这里有一个**关键区别：它查的是 Ontology 的语义对象和关系，不是自己去写 SQL**。它面对的是订单、承运商、仓库这些业务对象。有三种典型的查询模式：

**模式一：多条件过滤 + 聚合。** 比如"今天有哪些会延误？"Agent 先做一个 Filter 筛选，返回"有 7 个"。用户可能追问"哪些是 VIP 客户的？"它就会沿着 Ontology 的 Link，从 Shipment → Order → Customer，并且按照 Service Level = VIP 做筛选，再返回结果。就像老板开会时自己翻资料：先按地区筛订单，再追问哪些客户……资料都在桌上，具体筛哪些类型，老板自己决定。

**模式二：Link 遍历（顺着关系追溯归因）。** 比如有一个编号 8832 的订单，你问"延误在哪个环节出的问题"，它会沿着 Ontology 的网络结构和 Link 去追溯——这里有一个超参数，你可以设置它最多追溯多少层。比如从 Shipment 追溯到 Carrier（承运商），看到承运商的准点率只有 72%，再结合中转枢纽的拥堵情况，判断是"车辆故障加上枢纽拥堵"导致了延误，给出实际性的原因。就像**侦探顺着线索链追查：从案件到嫌疑人、从嫌疑人到同伙、从同伙到据点**，每一步都顺着关系一层一层往下查。

**模式三：分组聚合出运营概览。** 比如各仓库的积压情况，按区域 Group By 把数据聚合起来。管理层需要一张各区域的红绿灯看板，不需要看每一单的具体数字，只看汇总数字就能一眼判断。

### 8.3 一个容易搞混的关键区分：Retrieval Context vs Query Tool

视频专门强调：**Retrieval Context（检索上下文）和 Query Tool（查询工具）很容易搞混**，但必须分清：

- **必须让 Agent 知道的信息 → 放进 Retrieval Context**：比如当前仓库的信息、今天的 KPI、你的权限等级。每一轮对话都需要这些输入，所以只要 Agent 给出答案之前，系统都会把它作为 Context 交给 Agent。
- **可以让 Agent 自己探索、自己判断的 → 放进 Query Tool**：比如"帮我对比一下两个仓的情况""这个仓过去两三天的表现怎么样"——这些是临时提出的问题，没办法提前预置，就放在 Query 里。

放错了有什么后果？Context 里塞太多信息，会**浪费大量 Token**，这些噪音也会干扰模型（需要上下文处理能力很强的模型才能处理），成本随之上升；而 Query 配置得太窄，LLM 查不到想要的信息，它**又开始编**。

> **一条原子原则：确定性的内容走 Context，允许 Agent 探索的内容走 Query Layer。**

### 8.4 第三层：Logic Layer（逻辑层）——专业计算交给专业函数

查到对象、拿到相关信息之后，很多场景还需要调一个业务函数做专业计算。**为什么不让 LLM 自己验算？** 比如客户问"这个客户的风险分析等级是怎样的"——如果没有做对应的 Function，LLM 看起来会分析，但它算的并不是企业用户能接受的答案。

有了 Function 之后，Agent 才可以调用 **Calculate Delayed Risk（计算延误风险）** 之类的函数：函数会查证过去 90 天同路线的延误数据、读取承运商的准点评分、调用天气 API、查看目的地未来 24 小时有没有可能出现暴雨等恶劣天气、再叠加运营预测模型，最后输出一个**结构化结果**——而不是某个模型的原始数据。

这就是 Logic Layer 的作用：**LLM 的工作是理解你的意图、选择合适的函数、并用自然语言解释结果；业务规则和计算模型交给 Function，不要让 LLM 做专业判断。** 除了这类分析评估函数，还可以做推荐、做算法优化——比如运行最优分配方案，用户不需要懂运筹学，只要能看懂结果、能做决策就可以了。

### 8.5 第四层：Action Layer（动作层）——从问答助手到业务操作员

Action Layer 让 Agent 能够对 Ontology 进行变更。在这里，Agent 从一个问答助手变成了**业务操作员**。有两种场景：

**高風險操作 → 人工确认。** 系统会先生成一个 Action，执行前需要人工确认。比如更换承运商、签署合同、涉及成本的操作，会弹出提示："承运商 B 的单价比 A 高 12%，预计增加运费 300 元，但时效可以提升 10%"。你点击确认，系统才开始执行。

**低風險操作 → 自动触发。** 比如天气原因延误两小时，系统自动判断后直接更新 ETA（预计到达时间）、自动给客户发通知——低風險的操作不需要人工介入。

此外还有三个辅助工具：

1. **Update Application Variable（更新应用变量）**：让 Agent 能修改应用状态，比如你说"只看华东"，页面就能自动过滤；
2. **Comment（评论/触发）**：可以触发其他应用操作，比如在地图上标出五个延误的订单；
3. **Request Verification（请求确认）**：执行前向用户确认模糊的指令——比如"你指的是哪个订单？"。就像护士打针前多问一句"打左手还是打右手"，先确认一下。

### 8.6 第五层：Governance Layer（治理层）——重头戏，贯穿前四层

Governance Layer 不是单独的一步，而是**贯穿前面四层的约束机制**。

**角色不同，看到的世界完全不同。** 比如一个运营助手，调度员和区域经理登录后看到的东西完全不一样：调度员的 Context 只会注入三条线路的 Shipment——只能查这三条线路相关的东西；不能调用利用率查询函数；可以计算延误风险、可以自动更新 ETA，但**不能指派承运商**。而区域经理的 Context 直接注入整个华南区的概览，Query 可以查看所有线路和承运商的绩效，也可以查利润。这就是权限的分层。**就像同一栋楼：11 层的员工只有自己楼层的门禁卡，总经理有全楼的门禁卡。**

**防幻觉机制——企业 Agent 最看重的东西。** 用户问"今年总营收是多少"，普通 Agent 可能编一个数字告诉你（因为它没有数据基础）。Palantir 怎么做？**不是在一个 Prompt 里加一句"你不要编造数据"**，而是有好几层结构性约束：

1. 没有配置财务 Context——Agent 看不到相关数据，无法返回结果；
2. 没有 Financial Report 这个 Object Type——它检索不到；
3. 没有财务数据的权限——所以看不到；
4. 没有财务授权的函数——所以也算不了。

这些约束叠加之后，Agent 对"营收"这件事是**彻底不知情**的——它不是被告知"不能说"，而是**根本接触不到**。这是从结构层面解决问题。所以它最终给你的答案是："我没有全局访问公司财务数据的权限。"

同时，所有这些操作都会进入**审查日志**：谁在什么时候、让 Agent 做了什么、结果如何，全部可实现可追溯。

**这不是一个简单的技术问题，这是一个很大的工程问题。**

### 8.7 工具是怎么暴露给 Agent 的

两种模式：一种是**文本式工具调用（Prompt-based Tool Calling）**——把工具写成 Prompt 描述，所有模型都支持；第二种是**原生工具调用（Native Tool Calling / Function Calling）**——用模型原生的工具调用能力，并且可以一次并行调用多个工具。

一个容易误解的点：**Palantir 并不是把 Ontology 的整个 Schema 全塞进 System Prompt**，而是把当前 Page（页面）、当前用户授权范围内的那部分放进去。

## 第9章 一轮完整交互：把五层串起来

用一个例子把五层完整走一遍。用户问："帮我看华南仓有哪些订单有一些延误风险。"

**第一步（Context Layer，自动触发）**：作为系统级的确定性步骤，通过语义搜索返回 Top 10 最相关的 Shipment，输入给 LLM。LLM 不参与"是否触发"的决策。

**第二步（Query Layer）**：Agent 主动过滤"华南仓"，再追加延误条件，筛出 23 个结果；然后沿 Link 搜索 Order、Customer，读取相关的优先级和客户等级。

**第三步（Logic Layer）**：调用函数计算延误风险——在这 23 个结果里告诉你"5 个是高風險"，再调用建议方案函数给出处理建议。

**第四步**：LLM 生成回答，并问你"是否要执行"。

**第五步（Action Layer + Governance）**：你点击确认，系统分发给运营——创建一个异常的 Case（工单），执行之后 Ontology 自动更新结果。

这就是完整链路。

## 第10章 内部 Agent 与外部 Agent：Ontology MCP

前面讲的五层架构，主要描述的是 **Agent 与 Ontology 的交互（内部 Agent）**。外部 Agent 其实还接触两个机制，其中一个是 **Palantir 的 Ontology MCP（Model Context Protocol 服务）**：它面向外部业务 Agent，可以读取数据、执行 Action（写数据），但**不能修改 Object Type 的定义**——本体 Schema 是受控的。

但不管走哪条路，核心内容不变：**Agent 通过受治理的 Ontology 接口访问一切，但绝不通过 Ontology 直接碰底层数据。**

# 下篇 · 方法论精华（可迁移框架）

## 一、Ontology 建模五步流程（从业务到本体）

1. **定场景**：先锁定一个要交付的 Agent 场景（如"延误风险运营助手"），用场景反推需要哪些对象，而不是为了建模而建模；
2. **盘数据**：清点三类原始数据——结构化表、半结构化 JSON/XML、非结构化文档（PDF/图片/手写记录），并保留原始文件的完整血缘；
3. **清洗成干净表**：结构化自动推断 Schema；半结构化用 Explode 摊平嵌套并以业务 ID 关联；非结构化走"OCR/多模态 → Markdown → 字段解析 → 人工复核"，且每行保留原始文件引用；
4. **映射为本体**：干净表 → Object Type；行 → Object；列 → Property；表间关系 → Link Type；写操作 → Action Type；逻辑推导 → Logic/Function；
5. **上增量 + 上治理**：三层增量同步（数据同步 / Pipeline 只处理新增 / 本体只更新变化对象），权限与审计贯穿。

## 二、八条核心原则

1. **原样接入**：从原系统拉数不做预处理，一切变换在平台内完成——这是血缘可追溯的前提（金融/医疗是硬要求）；
2. **可写不污染**：业务修改写 Writeback Dataset，原始数据源永远干净；
3. **一实体一表**：宽表必须拆成聚焦小表再映射，一个 Object Type 只对应一张表；
4. **确定性走 Context，探索性走 Query**：每轮必需的放 Context（省 Token、防噪音），临时探索的放 Query（配太窄会诱发幻觉）；
5. **专业计算不交给 LLM**：风险、评分、调度走 Function；LLM 只做意图理解、函数选择与结果解释；
6. **高風險动作人工确认，低風險自动执行**；模糊指令先 Request Verification；
7. **防幻觉靠结构性隔离，不靠 Prompt 叮嘱**：无 Context + 无 Object Type + 无权限 + 无函数 = 彻底不知情；
8. **错误源头在第一层**：实体提取阶段多花功夫，宁可在第一步返工，不在后期返工。

## 三、四道坎检查清单（构建前自问）

- [ ] 实体类型全集是否已知？（未知 → 用聚类法探索，先别拍脑袋定类型）
- [ ] 如何防幻觉？（框架约束 / 验证闭环 / 结构性不可见，选一种以上）
- [ ] 颗粒度是否可控？（太宽没人用，太细没人维护——先出 V0.1 给人看再调）
- [ ] 好坏如何评估？（有没有结构化 + 逻辑两层验证？中间产物能不能人工审查？）

## 四、技术选型速查

| 场景 | 选型 |
|---|---|
| 上生产系统 | 拆解法（Pipeline + 验证闭环，专家守验证） |
| 全新领域探索 | 聚类法（名词提取 → Embedding → AP 聚类 → LLM 命名） |
| 快速验证想法 | 提纲两步法（概念清单 → 层级 → 标准格式，中间产物可审） |
| 有行业标准（金融/医疗/电力） | 框架约束法（Wikidata / 行业 Schema 内提取） |
| 学习理解一个本体 | 直给派（端到端 Prompt，仅限原型） |

## 五、五层架构速查卡（交付 Agent 时对照）

| 层 | 谁做主 | 解决什么 |
|---|---|---|
| Context Layer | 系统（确定性） | 每轮自动备料：对象上下文 / 文档上下文 / 函数上下文 |
| Query Layer | Agent | 过滤聚合、Link 遍历归因、分组运营概览（查语义对象，不写 SQL） |
| Logic Layer | 专业函数 | 延误风险、评分、调度优化等专业计算 |
| Action Layer | Agent + 审批 | 高風險人工确认，低風險自动执行，业务写回不污染原数据 |
| Governance Layer | 贯穿 | 权限分层、防幻觉结构性隔离、全程审计 |

# 借鉴篇 · 我们能借鉴的点（结合我们的业务）

我们做的是企业 AI 落地咨询与智能体交付，本质就是 FDE 式交付——给客户装智能体、跑业务、看结果。这个视频几乎是为我们量身定做的技术底稿，以下六点可以直接用：

## 1. 把"业务对象地图"做成所有项目的第一交付物

我们很多项目一上来就急着选模型、调 Prompt、灌文档。视频第一个耳光就是：**RAG 式"一股脑喂文档"必然得到会"说谎"的 Agent**——它不知道评分维度、衡量口径、对象间的关系。落地时我们应该把交付顺序改成：**先跟客户盘出"对象—关系—规则"三件套**（这个行业的 Object Type 有哪些、Property 是什么、谁 Link 谁、Action 有哪些），把对象地图作为项目第一里程碑，客户确认后才进入数据与模型工作。这张地图同时就是给客户看的"我们读懂了你的业务"的证据。

## 2. 客户知识结构化：决策卡之前先建"本体骨架"

我们的决策卡/黄金集体系沉淀的是"方法论卡片"，但客户现场的知识是散落在 200 张宽表、一堆 PDF 里的。借鉴视频的映射逻辑：**把客户的每一类原始数据（表/文档/工单）先摊平清洗成干净表，再映射到我们自己的对象体系**——客户(行业/规模/阶段) → 决策点 → 卡片 → 案例/证据，用 Link Type 把"这个客户的这个症状对应哪张卡"显式连接起来。这样检索 Agent 才能像视频里那样沿 Link 追溯（症状→模式→卡片→案例），而不是靠向量碰运气。

## 3. "防幻觉"必须在结构层做，不能靠 Prompt 叮嘱

视频最值钱的一课：普通 Agent 被问"总营收"会编数字，Palantir 的解法是**让它根本接触不到**——没有财务 Context、没有那个 Object Type、没有权限、没有函数。落到我们的交付：**给客户 Agent 的上下文、对象、函数、权限都要按角色裁剪**，客户问"你们这个方案报价为什么这么高"这类问题，如果 Agent 根本没有成本对象和报价函数，它就只能老实说"我没有权限/没有数据"，而不是现编。在交付验收清单里加一条：**挑 5 个 Agent 不该知道的问题，验证它结构性答不出，而不是靠提示词拦住**。

## 4. 五层架构 = 我们交付 Agent 的默认验收框架

我们给客户搭智能体时，常常只有一个"RAG + 工具调用"。可以升级为视频的五层结构并写进交付方案：

- **Context 层**：把客户每轮必用的信息（当前项目上下文、客户档案、KPI）做成确定性注入，不靠模型自觉——省 Token 还稳；
- **Query 层**：让 Agent 查我们的结构化知识库（对象+关系），禁止它自由发挥写 SQL；
- **Logic 层**：评分、诊断、报价测算全部封装成函数，LLM 只做意图理解和解释——这正好复用我们已有的算法/评分脚本；
- **Action 层**：凡是会改客户数据的操作（发消息、建工单、改状态）全部走"低風險自动/高風險确认"两级审批 + 写回审计日志；
- **Governance 层**：按客户角色（老板/运营/一线）裁剪可见范围，全程留痕。

这套结构可以直接变成我们售前方案书里的"平台架构图"，比讲 RAG 高级得多，也确实是正确做法。

## 5. 可复用的技术栈清单（现成组件就能搭）

视频里的关键机制，我们用现有工具都能落地：① **Media Reference 式血缘**：每份客户文档/录音处理后保留原始文件路径引用，保证任何结论可追溯回原始素材；② **确定性 Context 注入**：会话开场自动注入客户档案/项目对象，语义搜索用向量库兜底；③ **Function-backed Context**：把高频问题（客户 360 视图）写成预设函数一次拉全；④ **审计写回**：Agent 的所有写操作记录到独立日志表，不污染原始数据；⑤ **Ontology MCP 思路**：对外暴露只读 + 受控 Action 的接口（读数据可以、改 Schema 不行），防止客户乱接。

## 6. 商业模式提醒：静态模板不是护城河，Mapping 判断力才是

视频对"行业模板能不能一键复用"的回答很清醒：跨行业的对象（客户、订单、供应链）大家都懂，**模板本身不值钱，值钱的是"给你 200 张脏表，你能告诉客户哪列映射到哪个实体"的判断力**。这对我们的启发：

- 不要试图卖"通用行业包"，要卖**现场拆解与映射的工时与方法论**（这正是客户付不起也复制不了的部分）；
- 可以把积累沉淀成"拆解方法/映射规则/踩坑库"（怎么判断某列是属性还是独立实体、颗粒度怎么定），而不是静态模板；
- 对垂直行业客户（如医疗、制造、跨境物流），**先做领域知识标准化，就抢占了结构性优势**——这正是我们做中俄跨境、医疗、企业 AI 咨询时可以提前布局的护城河。

> 最后记住视频开头的判断：企业 AI 的前置条件不是更强的模型，而是先把企业的对象、关系、规则结构化——**先有地图，AI 才不会迷路，才不会说谎**。
