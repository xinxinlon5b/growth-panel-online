## 上篇 · 书籍内容

### 引子：PRD 与原型，到底解决什么问题

做 AI 产品的最后两步，是把前面所有的市场研究、用户调研、需求分析收敛成两份可交付物：**PRD（产品需求文档）**和**原型图**。

这两份交付物同时承担三个角色：
1. **团队对齐的载体**——研发、算法、数据、设计、测试，所有人都从同一份文档起步。
2. **跨期交付的契约**——PRD 写清楚验收标准，原型画清楚交互路径，前后两批人能凭文档接手。
3. **项目复盘的底稿**——上线后回头看当初是怎么决策的，文档就是原始证据。

这一章要解决的核心矛盾是——传统产品经理写 PRD 是「**把确定的功能描述清楚**」，AI 产品经理写 PRD 是「**把不确定的智能行为管理起来**」。同样，传统原型是「**标准操作手册**」，AI 产品经理的原型是「**智能交互脚手架**」。理解这一层差别，比掌握任何模板都重要。

---

### 一、PRD 的本质：把一个产品「从生到死」写在一份文档里

#### 1. 一句话定义

PRD（Product Requirements Document，产品需求文档）= 你**要交付的大作业**。读完整份文档，团队里任何人——开发、测试、设计、产品——都能独立判断「这个产品是什么、怎么做、什么算做完、做完之后怎么迭代」。

#### 2. PRD 应该装下什么

直播课里把 PRD 定位为「**总装车间**」：前面所有章节的产出物都收口在这里。具体来说，一份完整的 PRD 通常包含：

| 模块 | 来源章节 | 装什么 |
|---|---|---|
| 行业分析 | 第1章 | 行业趋势、市场机会、政策与算力 |
| 竞品分析 | 第1章 | 直接/间接/替代/潜在四层竞品 + 学/抄/避/差异化结论 |
| 用户调研 | 第1章 | 三视角发现、需求清单、抽样与结论 |
| 需求分析 | 第2章 | Kano 分类 + RICE 打分 + 优先级结论 |
| 需求池 | 第2章 | 已收口的需求条目与状态 |
| 主流程 | 本章 | 核心用户路径与异常分支 |
| 产品功能图 | 本章 | 功能架构 + 信息架构 + 交互设计 |
| 验收标准 | 本章 | 功能验收 + AI 性能指标验收 |
| 迭代计划 | 本章 | 版本节奏、回滚机制、再训练触发条件 |

#### 3. PRD 的核心价值：图文的信息密度

为什么必须落到文档，而不是靠视频/口头传达？直播里给了一个非常工程化的对比：

- **视频/口播**：颗粒度细，能具体到「这一步之后下一步怎么点」，但**信息密度低**——一个 30 分钟的会议讲清楚的事，写在文档里可能 5 分钟就读完了。
- **图文文档**：颗粒度粗一点，但**信息密度高**——同等信息量可以压缩到几页纸里，让 30 个开发在同一个时刻读到同一份内容。

更关键的是**异步对齐**——文档发出去，每个开发按自己的理解速度去读，读不懂来问，而不是你对着 30 个人讲 5 遍，5 个人听懂、5 个人半懂、20 个人其实没跟上。文档是把**一对多的同步沟通**降级成**一对一的异步沟通**，是项目组放大产能的最朴素工具。

#### 4. PRD 的协作模式

文档的协作模式也是定式的：
1. 先把整个框架（行业、竞品、用户、主流程、验收）发出去，让所有人有全局图。
2. 大家带着框架自学、自己读懂 70%。
3. 集中评审，对齐剩下的 30%。
4. 评审后不懂的来问，文档作者统一回复。
5. 文档更新版本，所有人按最新版执行。

这套「**发框架 → 自学 → 评审 → 答疑 → 迭代版本**」的节奏，几乎适合所有 AI 项目的协作场景。

### 二、AI 产品经理的 PRD：管理不确定性，而不是描述确定性

#### 1. 一个关键类比：大楼 vs 团队

直播课的学生「周同学」在分享时给了一个非常清晰的类比——这个类比是本章的核心：

- **传统产品经理**像是要**精确建造一栋功能确定的大楼**：设计图、施工图、验收标准都是确定性的，按图施工、按标验收。
- **AI 产品经理**像是要**组建一支持续学习的团队**：团队里有数据、有算法、有算力，团队要持续训练，目标是产出一个**具备持续学习能力的系统**，整个过程要**管理不确定性**。

这两个定位直接推导出了 PRD 的本质差别：传统 PRD 输出的是「功能清单」，AI 产品经理的 PRD 输出的是「**数据→模型的训练路径 + 不确定性管理方案**」。

#### 2. PRD 文档的扩展字段

直播课里给出了 AI 产品经理 PRD 应当包含的字段清单：

- **需求背景**：为什么做这件事，对应哪个业务场景。
- **页面设计**：人看到的界面长什么样。
- **接口设计**：系统之间怎么对话。
- **字段设计**：每个接口的字段含义、类型、是否必填、示例值。
- **业务流程**：用户走完一遍要做哪些步骤。
- **业务需求逻辑**：每一步背后的判断规则（这是传统 PRD 的重点）。
- **验收标准**：怎么算合格（这是 AI PRD 的最大变化点，下一节展开）。
- **后续迭代**：下一版怎么升级、回滚条件、再训练触发条件。

#### 3. AI PRD 与传统 PRD 最大的差别：验收标准

传统 PRD 的验收标准基本只看**业务指标**：订单量降低多少、效率提升多少、人工成本减少多少。

AI 产品经理的 PRD 验收标准必须**同时包含两类**：

| 指标类型 | 举例 | 评估方式 |
|---|---|---|
| 业务指标 | 工单分类准确率提升 / 客服人力节省 / 销售线索转化率提升 | AB 实验、上线前后对比 |
| 技术性能指标 | 模型识别准确率 / 召回率 / 幻觉率 / 推理 P99 延迟 / 单次调用成本 | 离线评测集 + 在线埋点 |

业务指标回答「**做出来有没有用**」，技术指标回答「**模型本身达不达标 + 还有多少优化空间**」。两类指标缺一个，PRD 都不算合格——只盯业务会埋下「业务指标涨了但模型已经飘了」的雷，只盯技术会埋下「指标全绿但业务没人用」的雷。

#### 4. 需求评审的相关方变化

传统 PRD 评审的相关方：产品、研发、测试、设计、运营。
AI PRD 评审必须**新增至少两类**：

- **数据工程 / 数据同学**：评审**数据可行性**——数据从哪来、有多少、标注成本多高、会不会漂移。
- **算法同学**：评审**模型可行性**——这个需求用基础模型做、RAG 做、还是微调做？成本与效果的天花板在哪？

更进一步，**安全 / 法务 / 合规**同学几乎一定要进评审，因为 AI 涉及数据合规与内容合规。

### 三、PRD 的写作流程

直播课里给了一个非常简洁的四步流程，可以作为任何 PRD 的写作脚手架：

1. **问题定义**：用一句话说清楚要解决的问题。要避免「提升用户体验」「优化流程」这种空话——一定要落到具体的「谁、在什么场景、遇到什么问题、希望用什么方式解决」。
2. **需求描述**：把上面的问题翻译成具体的需求条目。需求条目要可验收、可独立交付。
3. **字段 / 流程 / 验收标准填充**：把每条需求翻译成可设计、可开发、可测试的细节。
4. **评审与迭代**：拉上相关方（数据、算法、合规、研发、测试、设计）评审，评审后回到第 1 步循环。

### 四、原型的本质：交互骨架，而不是界面截图

#### 1. 传统 PM 的原型 vs AI 产品经理的原型

直播课里给了第二个非常关键的类比——**汉堡菜谱 vs 顶尖大厨**：

- **传统产品经理的原型**：像一份**汉堡菜谱**——把原材料一步步写清楚，每一步做什么、放多少料、什么火候。产品按菜谱做出来，结果是确定的、可预测的。
- **AI 产品经理的原型**：像给一个**顶尖创意大厨**布置任务——客人带了一部分食材过来（**数据输入**），大厨基于食材给出 A、B、C 三道建议菜系（**多个概率性输出**），并解释为什么这么搭配（**可解释性**）。客人根据大厨的建议再反馈（**多轮交互**），不满意就换食材再试，满意就下单（**闭环收敛**）。如果全程做不出来，还有**转人工兜底**（**失败兜底方案**）。

这个类比拆出了 AI 原型的四个关键属性：

| 属性 | 含义 | 设计要求 |
|---|---|---|
| 多概率结果 | 模型不会只给一个答案 | 界面要给多个候选 + 置信度 |
| 可解释性 | 用户要知道为什么这么答 | 每个答案要附推理依据 / 引用来源 |
| 多轮交互 | 用户会追问、修正、补充 | 设计对话状态机、上下文记忆 |
| 失败兜底 | 总有解决不了的 | 转人工 / 兜底话术 / 降级方案 |

传统原型只关心「点这个按钮会跳到哪」，AI 原型必须同时关心「**这个回答是哪条路径走出来的、用户怎么追问、追问错了怎么挽回**」。

#### 2. 一个完整例子：AI 智能问询

直播课里周同学举了一个非常具体的例子——企业内部 AI 智能问询，覆盖三类问题：

- **财务政策咨询**：员工问「差旅住宿费上限多少」「探亲假怎么报销」。
- **提单流程咨询**：员工问「我这个场景该怎么提单」。
- **报销单进度咨询**：员工问「我上周提的报销单现在到哪一步了、什么时候打款」。

这三类问题对应三种不同的交互模式：

- 第 1 类**纯知识问答**：可以用 RAG + 政策文档直接答。
- 第 2 类**多步骤引导**：模型要把员工的场景拆解、判断走哪条流程、一步步引导。
- 第 3 类**对接业务系统**：模型要查用户的报销单 ID、再去 ERP 系统查状态、再把状态翻译成人话。

对应的原型上必须同时设计三种入口、三种交互方式、三种失败兜底（知识没命中怎么办、引导卡住了怎么办、ERP 调不通怎么办）。这就是 AI 原型比传统原型复杂的地方——**一个 AI 入口背后往往挂着一组异构后端**，原型的设计必须把这层异构性反映出来。

---

### 五、不同端口的原型：外部端 + AI 端是两套语言

#### 1. 三种端口的差异

直播课明确把 AI 产品的端口分成：
- **外部端口**：小程序、App、H5——这些是给最终用户用的，画原型的工具是 Figma、墨刀、Axure。
- **AI 端**：智能问答、Agent 工作流——这些是用**扣子、Dify、n8n**等智能体平台搭出来的，本质是一张**节点 + 流程图**，而不是传统的界面设计稿。
- **接口层**：MCP 协议、A2A 协议、API——这些是机器与机器之间的对话协议，原型上要画出**谁调用谁、传什么字段、返回什么字段**。

外部端口用 UI 原型工具，AI 端用智能体平台，接口层用接口文档——三套语言，不要混为一谈。

#### 2. AI 端的原型：用智能体平台搭

AI 端的原型不是「画图」，而是「**搭工作流**」。具体步骤：

1. 在扣子 / Dify / n8n 里新建一个工作流。
2. 把用户输入 → 意图识别 → 知识检索 → 模型推理 → 输出解析 → 兜底回复串成一条流程。
3. 每个节点配置输入输出字段、模型选择、提示词。
4. 跑一遍，截图或导出流程图，作为原型交付物。

这样做原型的优点是「**原型即实现**」——搭出来的工作流几乎可以直接上线，而传统 UI 原型还要经过研发重新实现一遍。

#### 3. 接口层：MCP、A2A 与 API

直播课里特别提到了几类协议与平台，AI 产品经理至少要知道：

- **MCP 协议**：Model Context Protocol，让模型与外部工具/数据源对话的协议。AI 产品经理要知道有哪些 MCP 服务可用、怎么挂到自己的 Agent 上。
- **A2A 协议**：Agent to Agent，智能体之间互相调用的协议。
- **API 调用**：每个大模型都有自己的 API（ModelScope、Hugging Face、各大模型官网），AI 产品经理要知道**怎么获取 API key、怎么写调用代码、怎么计费**。
- **开源社区**：GitHub 上有大量现成的智能体插件、工作流模板，AI 产品经理要会搜索、会读 README、会装到自己的项目里。

#### 4. Cursor 与「不用写代码也能做原型」

直播课最后特别提到一点——**AI 产品经理不一定非要会写代码**，但要会**用 Cursor 这类 AI 编程工具和 AI 对话，让 AI 帮自己写代码、做原型**。

具体来说：你可以不会敲 Python，但你可以通过对话让 Cursor 帮你写一个能跑的脚本；你可以不会搭后端，但你可以和 AI 对话让它帮你搭一个最小可用的 Demo；后期课程里也会带大家实操一次「一行代码不写，做出一个能用的程序」。

这件事的战略意义在于：**AI 产品经理能不能跑通最小闭环，决定了 Ta 在团队里的不可替代性**。别人还在等你画原型、研发排期，你已经把 Demo 跑通给老板演示了——这就是 AI 时代产品经理的核心竞争力之一。

---

### 六、AI 产品经理的「多看一层」在 PRD 与原型上的体现

回到全书反复强调的「AI 产品经理多看一层」——**算法、算力、数据**三件套，在 PRD 与原型环节落地为：

| 维度 | PRD 上的体现 | 原型上的体现 |
|---|---|---|
| 算法 | 写清楚模型选型决策（基础模型 / RAG / 微调）与理由 | 画清楚「数据 → 模型 → 输出」的推理链路 |
| 算力 | 写清楚单次调用成本、QPS 预估、总预算 | 原型上标注哪些交互会触发推理、成本量级 |
| 数据 | 写清楚数据来源、标注规则、漂移监测方案 | 原型上画出数据从哪来、怎么回流、怎么再训练 |

这三件套是 AI 产品经理 PRD 比传统 PRD 多出来的硬核内容。**会写这三块的 AI 产品经理，在招聘市场上的薪资会比只会写业务流程的产品经理高一截**——这是直播里反复强调的观点。

---

### 结论 / 金句

> PRD 的本质：把一个产品「从生到死」写在一份文档里，让 30 个开发在同一个时刻读到同一份内容。

> 传统 PRD 是「描述确定性功能」，AI 产品经理的 PRD 是「管理不确定性 + 训练持续学习系统」。

> AI PRD 的验收标准必须同时包含**业务指标**与**技术性能指标**——缺一个都不算合格。

> 传统原型是「标准操作手册」，AI 产品经理的原型是「智能交互脚手架」——必须同时设计**多概率结果、可解释性、多轮交互、失败兜底**四个属性。

> AI 产品的端口是三套语言：**外部端口用 UI 工具、AI 端用智能体平台、接口层用协议与 API**——不要混为一谈。

> AI 产品经理的护城河：**会写算法 / 算力 / 数据三件套的 PRD** + **会用 Cursor 让 AI 帮自己做原型**。

### 通用原则（脱 UP 主，可迁移）

1. **PRD 是异步对齐工具，不是同步沟通替代品**——文档把「一对多同步」降级为「一对一异步」，是项目产能放大的最朴素杠杆。
2. **发框架 → 自学 → 评审 → 答疑 → 迭代版本**——这套节奏适合所有 AI 项目的协作。
3. **AI PRD 必须双验收**——业务指标 + 技术性能指标，缺一不可。
4. **AI 原型四属性**——多概率结果、可解释性、多轮交互、失败兜底。任何 AI 交互设计都过一遍这四属性。
5. **三端口不要混**——外部端口、AI 端、接口层是三套语言与三套工具，不要试图用一套工具画完。
6. **AI 端原型即实现**——用扣子 / Dify / n8n 搭出来的工作流，几乎可以直接上线，省掉研发重写一遍。
7. **产品经理也要会跑最小闭环**——Cursor 等 AI 编程工具让 PM 可以不写代码就做出能跑的 Demo，这是 AI 时代 PM 的护城河。
8. **算法 / 算力 / 数据三件套入 PRD**——AI 产品经理比传统 PM 多看的那一截，最终都体现在文档的字里行间。

### 可复用模式

- **PRD 总装模板**：行业分析 → 竞品分析 → 用户调研 → 需求分析 → 需求池 → 主流程 → 功能图 → 验收标准 → 迭代计划。每节挂上「AI 产品经理多看什么」。
- **双验收指标卡**：每条 AI 需求都配套一张卡，左边业务指标、右边技术指标，中间对齐模型版本与 AB 流量。
- **AI 原型四属性 checklist**：多概率 / 可解释 / 多轮 / 兜底，每条交互都过一遍。
- **三端口原型交付包**：外部端口用 Figma 截图、AI 端用扣子/Dify 工作流截图 + 导出的流程图、接口层用接口文档 + MCP 服务清单。
- **最小闭环 Demo 法**：PM 用 Cursor 与 AI 对话，2 小时内跑通一个能演示的最小 Demo，作为需求评审的预演。
- **评审相关方 checklist**：产品 / 研发 / 测试 / 设计 + **数据 / 算法 / 合规**——AI 项目必须把后三者加上。
- **PRD 版本号规范**：v0.1 草稿 / v0.5 评审版 / v1.0 上线版 / v1.x 迭代版，让所有人按最新版执行。
- **汉堡菜谱 vs 顶尖大厨类比**：在评审会上用这个类比解释「为什么 AI PRD 不能只描述确定性功能」，比讲十页 PPT 更有效。

## 借鉴篇 · 我们能借鉴的点

> 对应业务：王昕团队做**企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库**，以下每条都标注对应场景与可落地动作。

### 1. 用「PRD 总装模板」沉淀客户交付的标准交付物
**对应业务场景**：FDE 在客户现场交付 AI 项目，目前的交付物可能散落在不同文档里，客户看到的不是一份「从生到死」的总装文档。
**怎么做**：把 PRD 总装模板（行业分析 → 竞品分析 → 用户调研 → 需求池 → 主流程 → 功能图 → 双验收 → 迭代）做成 FDE 团队的标准交付模板，每个客户项目交付时都按这个结构出文档。重点加挂「AI 产品经理多看一层」的算法 / 算力 / 数据三件套，让客户高层一眼看出团队懂行。

### 2. 用「双验收指标卡」做客户 AI 项目的 AB 实验设计
**对应业务场景**：客户上线 AI 功能后，业务方与技术方经常互相甩锅——业务方说「效果不明显」，技术方说「指标都达标了」。
**怎么做**：每条 AI 需求交付时，配套一张「双验收指标卡」——左边业务指标（订单量 / 人力节省 / 转化率）、右边技术指标（准确率 / 召回率 / 幻觉率 / 延迟 / 单次成本），中间对齐模型版本号与 AB 流量划分。卡上明确写「业务指标涨但技术指标漂移」「技术指标绿但业务没人用」两类失败的处理预案，把责任边界写在交付物里。

### 3. 用「AI 原型四属性」做客户智能问答 Demo 的体验审查
**对应业务场景**：FDE 给客户做的智能问答 / 智能 Agent 原型，经常在客户现场被「这个回答为什么是这样」「我能追问吗」「答错了怎么办」三个问题卡住。
**怎么做**：建立 AI 原型四属性 checklist——**多概率结果**（是否给候选 + 置信度）、**可解释性**（是否附推理依据 / 引用来源）、**多轮交互**（是否能追问 / 修正 / 补充）、**失败兜底**（是否转人工 / 兜底话术 / 降级方案）。任何 Demo 上客户现场前过一遍这四属性，缺一项就补。

### 4. 用「三端口原型交付包」做 AI 项目交付物的标准化
**对应业务场景**：FDE 交付的 AI 项目常常包含小程序端 / App端 + 后台 Agent 工作流 + 多个 API 接口，三种端口的原型散落在不同工具里，客户看不懂。
**怎么做**：建立三端口交付包规范——**外部端口**用 Figma 截图（带交互标注）、**AI 端**用扣子 / Dify / n8n 工作流截图 + 导出的流程图、**接口层**用接口文档 + MCP 服务清单 + 协议说明。三套交付物打包成一个 ZIP 或一个飞书文件夹，统一命名规范，让客户任何角色都能找到自己要看的那份。

### 5. 用「汉堡菜谱 vs 顶尖大厨类比」做客户高层沟通
**对应业务场景**：客户高层（特别是传统行业老板）经常不理解「为什么 AI 项目不能像传统软件一样按需求交付、按图施工」，导致期望管理失败。
**怎么做**：在与客户高层首次沟通或评审会上，用「汉堡菜谱 vs 顶尖大厨」的类比解释 AI 产品的本质——汉堡菜谱是传统 PRD，结果确定；顶尖大厨是 AI 智能体，结果多概率、需要食材（数据）、需要试菜（迭代）、需要兜底（转人工）。一个类比胜过十页 PPT，能让客户高层 30 秒内对齐预期。

### 6. 用「Cursor 原型法」训练 FDE 的最小闭环能力
**对应业务场景**：FDE 在客户现场经常需要快速做一个能跑的 Demo 给客户演示，但目前可能受限于「不会写代码」或「研发排不上」。
**怎么做**：把「Cursor 原型法」纳入 FDE 团队的培训——用 Cursor 与 AI 对话，让 AI 帮自己写脚本、搭 Demo、跑通最小闭环。培训目标是「2 小时内 FDE 不用研发就能跑通一个能演示的最小 Demo」。这是 FDE 在客户现场赢得信任的核武器。

### 7. 用「评审相关方扩展」做客户 AI 项目的需求评审室配置
**对应业务场景**：FDE 在客户现场组织需求评审时，常常只有业务方 + 研发，缺少数据 / 算法 / 合规的同学在场，导致评审通过但落地翻车。
**怎么做**：建立客户 AI 项目评审室的标准化配置清单——产品 / 业务方 / 研发 / 测试 / 设计 + **数据工程 / 算法 / 合规**。在评审邀请邮件模板里把这三类后置角色写进必邀名单，并提前与客户沟通「这三类角色必须到场，否则评审不闭环」。这是降低交付翻车率的最朴素动作。

### 8. 用「算法 / 算力 / 数据三件套入 PRD」建立 FDE 的专业护城河
**对应业务场景**：市面上的 FDE / 解决方案工程师很多，但真正能把算法选型、算力成本、数据可行性写进 PRD 的不多——这是王昕团队可以建立的专业护城河。
**怎么做**：把「算法选型决策表 / 算力成本估算表 / 数据可行性评估表」三张表做成 FDE 团队的标配 PRD 附件。每次客户 AI 项目立项，**算法选型**写清楚「为什么用基础模型 / RAG / 微调」、**算力成本**写清楚「单次调用成本 / 月度预算 / QPS 上限」，**数据可行性**写清楚「数据从哪来 / 标注成本 / 漂移监测」。三张表一摆，客户能感受到「这帮人真懂」，竞品模仿不来。

### 9. 用「发框架 → 自学 → 评审 → 答疑 → 迭代版本」做 8895 知识库的内容协作
**对应业务场景**：8895 知识库的内容建设如果用「编辑写完就发」的方式，团队其他成员无法异步对齐，贡献度也起不来。
**怎么做**：把直播里讲的协作节奏套用到知识库——**发框架**（先出一份知识库的整体目录与每节模板）→ **自学**（团队成员按目录认领、补充）→ **评审**（月度/双周评审会过一遍新增内容）→ **答疑**（评论区 + 群答疑）→ **迭代版本**（每月底发 v1.x 版本号，让所有人按最新版阅读）。

### 10. 用「PRD 版本号规范」做获客系统的客户沟通节奏
**对应业务场景**：获客系统在跟进客户时，常常因为「方案改了好几版、客户还在看老版本、销售自己都搞不清现在到哪一版」导致沟通混乱。
**怎么做**：把 PRD 版本号规范（v0.1 草稿 / v0.5 评审版 / v1.0 上线版 / v1.x 迭代版）借用到客户方案上——每次方案修改都升级版本号 + 在邮件/群里同步「客户现在应该看 v1.x」。配合获客系统的 CRM 字段，把客户当前看的方案版本号写到客户档案里，销售换班也能直接接手。
