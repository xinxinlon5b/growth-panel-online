# 上篇 · 书籍内容

## 引子：复盘和项目管理，为什么在 AI 产品里被彻底改写

传统软件项目里，上线即终点，复盘只是给流程画句号，项目管理也只需要把范围、时间、质量、风险、人这几件事盯紧。

AI 项目不是这样。**上线不是终点，而是运营的起点。** 模型会在真实流量里持续漂移，效果会因为数据分布变化、Prompt 调整、用户结构变化随时劣化。复盘不再是季度一次的仪式，而是持续运转的工程动作；项目管理也不再是按甘特图排里程碑，而是在巨大的技术不确定性和探索性里通过**三方会诊**，找到一条可以落地、可以确定的交付路径。

UP 主的洞察是：**复盘告诉你过去哪里做错了，项目管理告诉你未来怎么不再犯同样的错**。分开讲等于把 AI 产品的「反思」与「执行」割裂；放在一起讲，正好构成 AI 产品从「能跑」到「能跑好」的完整闭环。

这套方法要解决的核心问题是：**AI 产品经理如何在不确定性极高的项目里，把每一次复盘变成系统级调优的引擎，把每一次项目管理变成三方协同的剧本？**

---

## 主线：方法流程

UP 主把复盘和项目管理拆成两条平行主线，再让它们在「系统级调优」处合流：

```
复盘主线
  1. 复盘定位     →  从「项目成败」升级到「复杂系统视角」
  2. 复盘焦点     →  模型性能 / 人机交付效果 / 业务影响（三层）
  3. 技术归因     →  数据 → 模型 → 服务的完整链路
  4. 迭代计划     →  算法 + 数据 + 工程三位一体系统调优
  5. 复盘节奏     →  实时监控 + 快速响应
  6. 复盘协作     →  业务 + 产品 + 技术三方联合会诊

项目管理主线
  1. 范围管理     →  从「功能清单」到「能力达标标准」
  2. 时间管理     →  里程碑 + 柔性延期
  3. 风险管理     →  传统风险 + 数据 / 算法新增风险
  4. 干系人管理   →  传统四方 + 算法 + 工程 + 跨语言翻译
  5. 质量管理     →  业务目标 + 模型质量 + 完整链路可靠性
  6. 成功交付     →  上线是运营起点 + 用户反馈飞轮

合流点：每一次项目管理过程中的关键节点，都是下一次复盘的素材；
       每一次复盘的产出，又回流到项目管理的下一阶段。
```

把这两条主线合并后看，UP 主真正传递的是一个底层判断：**AI 产品经理的工作，不是「交付一个功能」，而是「持续运营一个会变化的系统」**。复盘管「过去为什么变差」，项目管理管「未来怎么控制变化」。两者合起来才是 AI 产品的完整生命周期方法。

## 逐点精读

### 第一部分：复盘——从「找 Bug」到「调系统」

#### 1.1 复盘的根本目标：传统 vs AI

| 维度 | 传统产品复盘 | AI 产品复盘 |
|---|---|---|
| 复盘视角 | 单一项目 / 单一功能 | 复杂系统（数据 + 模型 + 服务） |
| 复盘对象 | 迭代目标 vs 结果 | 模型表现 + 人机交付效果 + 业务影响 |
| 问题归因 | 需求 / 设计 / 开发责任清晰 | 数据 / 算法 / 算力都可能，需链路排查 |
| 迭代产出 | 优化项归入下一版本 | 算法微调 / 数据重标注 / 系统调优 |
| 节奏 | 季度 / 月度复盘 | 实时监控 + 快速响应 |
| 协作模式 | 产品主导，业务 + 技术辅助 | 三方联合会诊 |

传统复盘模式：定迭代目标 → 看结果 → 比对 → 找问题与原因 → 定义优化项 → 归入下一版本 → 明确负责人 / 截止时间。这套打法在确定性世界里够用。

AI 产品复盘要换思路：**AI 模型本身具有一定的不确定性**，因此要持续监控和测试，测试出来的问题要建立系统性归因框架。复盘核心目标围绕三件事——**AI 系统目前表现如何、为什么会这样、有什么方式可以让它更好**。

#### 1.2 复盘的三个焦点：从 AI 的角度重新分层

UP 主给出的三层框架，AI 产品复盘焦点从「AI 的角度」分成三层：

1. **模型性能（技术层）**：准确率、召回率、F1、幻觉率、响应延迟、Token 消耗。偏技术，AI PM 必须能看懂、能拉齐对话。
2. **人机交付效果（产品层）**：模型是否被用户真正接受——采纳率、修改率、用户满意度、对话完成率、兜底触发率。AI PM 的主战场。
3. **业务影响（业务层）**：上线后对核心业务指标的拉动——留存、转化、GMV、人效替代率。与传统产品复盘共有。

传统产品只关心第三层，AI 产品必须三层一起看。少看任何一层，复盘都会失真。

#### 1.3 技术归因：从数据到模型到服务的完整链条

找到问题后要做技术归因，UP 主原话是「**数据到模型到服务的这种完整链条去排查具体的问题所在**」。AI 复盘归因不是单一维度的「找原因」，而是沿一条链做穿透式排查：

```
数据层 → 模型层 → 服务层
   ↓         ↓         ↓
  标注      训练      部署
  分布      微调      监控
  漂移      推理      兜底
  反馈      路由      告警
```

任何 AI 系统的「问题」都可能出在这条链路的任何一个节点。AI PM 必须能沿链路一节一节问下去，才能找到真正的根因。

#### 1.4 迭代计划的维度升级：算法 + 数据 + 工程

找到问题之后，AI 产品的迭代计划会有**更多维度**——结合算法、数据和工程做综合性的系统调优方案。

AI PM 的「下一版本规划」不再是单纯的功能清单，而是一份三轴并行的方案：

- **数据轴**：重标注、补数据、数据增强、清洗脏数据。
- **算法轴**：微调、换模型、优化 Prompt、调路由策略。
- **工程轴**：加缓存、限流、改推理框架、重新部署。

任何一轴单兵突进都不能解决问题，必须三轴协同。这是 AI 产品迭代最大的特色。

#### 1.5 复盘节奏：实时监控 + 快速响应

AI 产品需要具备**实时监控 + 快速响应**的能力。这与传统产品的季度 / 月度复盘完全不同——AI 模型可能因数据漂移、Prompt 变化、流量结构变化随时劣化，必须分钟级、小时级响应。

这倒推出 AI PM 的工作模式：你不再是「开发完上线等数据」的被动角色，而是「模型在跑、我在盯、出问题立刻叫技术一起改」的主动角色。

#### 1.6 复盘协作模式：三方联合会诊

AI 产品复盘的核心角色要求**业务、产品、技术三方联合会诊**，而非传统那种逐步排查流程——先看是不是标准 Bug，不是的话产品看一下，再找业务聊是不是业务逻辑或需求澄清问题。

三方联合会诊：**业务、产品、技术在同一个房间里同时看同一个问题**，业务讲诉求、产品讲逻辑、技术讲实现，三方共同定位根因、共同定义优化动作、共同承担不确定性。

#### 1.7 AI 复盘的独特挑战：从绝对因果到概率归因

传统项目里对就是对、错就是错，是**绝对因果**。AI 因其不确定性，复盘要从绝对因果转化为**概率性的归因和假设**。

「这 100 个 Bad Case 不一定是同一个根因」「准确率下降 30% 概率来自数据漂移、40% 来自 Prompt 调整、30% 来自流量结构变化」——AI PM 必须接受并驾驭这种概率性思考。

#### 1.8 UP 主强调的三个关键点：场景在线 + 链路排查 + 归因分析

UP 主把整套复盘浓缩成三个关键点：

1. **场景在线**——还原当时是怎么做的，把当时的思考还原出来。
2. **链路排查**——从结果倒推，每条链路（数据准备 → 模型训练 → 微调 → 工程化 → 部署 → 监控）都排查一遍。
3. **归因分析**——哪个链路的哪个环节出了哪样的问题，具体情况具体分析。

这套「在线 → 排查 → 归因」三步法，是 AI 产品复盘的最小可执行单元。

#### 1.9 ML Ops 全链路：复盘的物理地图

UP 主点出的 ML Ops 完整链路，就是 AI 产品复盘的「物理地图」：

```
数据准备 → 模型训练 → 微调 → 工程化 → 部署 → 监控
   ↓         ↓        ↓       ↓       ↓      ↓
 标注      评测     LoRA    推理框架  灰度   告警
 清洗      验证     SFT     缓存      AB    漂移
 反馈      选型     RLHF    路由     上线   兜底
```

任何一次复盘都要把这个链路上的每个节点过一遍。**链路上哪个节点断了，复盘就追到哪个节点**。

### 第二部分：项目管理——从「排甘特图」到「写剧本」

#### 2.1 项目管理的根本目标：传统 vs AI

UP 主用 PMP 十大知识领域（范围、时间、进度、风险、干系人、质量等）作为坐标系，对比传统项目管理与 AI 项目管理。

传统项目管理的核心矛盾是**资源紧张**——因为时间或范围的不确定性，最终都会衍生到资源紧张，所以项目管理核心往往是协调资源去实现确定目标。

AI 项目管理的核心矛盾完全不同：**在巨大的技术不确定性和探索性当中，通过三方会诊找到一个可以落地、可以确定的交付路径，最终实现业务价值和目的**。

这是两种完全不同的项目管理逻辑：

- 传统 PM：**协调资源 → 实现确定目标**
- AI PM：**探索路径 → 找到可确定目标**

#### 2.2 范围管理：从「功能清单」到「能力达标标准」

AI 项目范围管理与传统项目最显著差别：**从功能清单转变成能力达标标准**。

UP 主原话：「比方说我的模型准确率达到多少、或者目前这种复检的识别准确率达到多少，我就可以上线。」——AI 项目的范围管理不是「要做哪些功能」，而是「模型能力要达到什么标准才能上线」。

这直接颠覆了传统 PRD 写法。AI 项目 PRD 必须包含两套标准：

- **功能标准**：要做什么流程、什么交互。
- **能力标准**：模型准确率 / 召回率 / 幻觉率达到多少阈值。

只有两套标准都达成，才算「范围达标」。

#### 2.3 时间管理：里程碑 + 柔性延期

传统项目管理不管是瀑布式还是敏捷式，都有一套里程碑和时间计划。

AI 项目因为高度依赖数据质量以及模型算法的不可预测性，里程碑当然可以订，但**相对会有一定的销伤（弹性）余地**——老板可能更可能接受项目延期，会给一定的柔性。

这个「柔性」不是管理松弛，而是 AI 项目管理的内在属性——算法效果本身不可完全预测，里程碑必须留出试错窗口。AI 项目的延期是常态。AI PM 必须主动管理预期，把「柔性」提前沟通进 OKR。

#### 2.4 风险管理：传统风险 + 数据 / 算法新增风险

传统项目风险主要是资源不足、需求变更、攻击延误。AI 项目还有两类新增风险：

- **数据层面**：标注延迟、数据合规、数据漂移、训练数据不足、长尾场景未覆盖。
- **算法层面**：模型效果不达预期、幻觉率失控、推理延迟过高、内容安全漏洞。

这两类风险在传统项目管理里几乎不存在，但在 AI 项目里高频且高破坏性。AI PM 必须把它们纳入风险登记册，并设计对应应急预案。

#### 2.5 干系人管理：传统四方 + 算法 + 工程 + 跨语言翻译

传统项目涉及业务、研发、测试、业务用户。AI PM 除此之外，还要和**算法、工程以及其他相关方**沟通，并且可能要「窒息（消化）」一些技术语言。

UP 主特意用「窒息」一词，是要把算法 / 工程黑话翻译成产品能听懂、业务能听懂的语言。AI PM 的干系人范围会**相应扩大**，协作复杂度也同步上升。

常见翻译场景：

- 算法说「Loss 不收敛」→「模型训练效果没达到预期，可能要调整学习率或数据」。
- 工程说「GPU 利用率上不去」→「算力浪费，可能要改推理框架或批处理策略」。
- 业务说「准确率太低」→「具体哪个场景、哪类输入的错误率最高」。

#### 2.6 质量管理：业务目标 + 模型质量 + 完整链路可靠性

传统质量管理看的是功能完成度、Bug 数、线上稳定性。AI 项目的质量管理还要关注**从底层数据到顶层交互的完整链路可靠性**。

具体三个层面：

1. **业务层**：上线后业务指标是否达标（留存、转化、GMV、用户满意度）。
2. **模型层**：模型指标是否达标（准确率、召回率、F1、幻觉率、响应延迟、合规率）。
3. **链路层**：数据采集 → 模型推理 → 输出展示 → 用户反馈回流的全链路是否稳定可靠。

任何一层断裂，质量都会出问题。

#### 2.7 成功交付：上线只是运营起点

UP 主把这个区别讲得最透彻：传统产品测试是上线前的标准动作，上线完成之后事情就结束了，**上线就是终点**。AI 项目上线只是**运营起点的开始**，上线之后还要通过用户反馈机制形成**数据和用户反馈的飞轮效应闭环**，达到正向循环。

这个认知差决定了 AI 产品经理的工作模式完全不同：不是「交付完就甩手」，而是「交付完才进入真正的运营」。上线即运营起点，是 AI 产品经理必须内化的核心心智。

#### 2.8 UP 主讲的六个方面：范围、计划、沟通、风险、质量、发布

UP 主把项目管理简化成六个方面：

```
1. 范围管理     -  能力达标标准 + 功能清单双轨
2. 计划管理     -  里程碑 + 柔性延期
3. 沟通管理     -  业务 + 算法 + 工程跨语言翻译
4. 风险管理     -  数据 / 算法新增风险预案
5. 质量管理     -  业务 + 模型 + 链路三层
6. 发布管理     -  上线是运营起点 + 飞轮闭环
```

UP 主特别提了一个现实：**中小厂 AI PM 职责没有那么明确，很可能一人管整个项目管理**；大厂则分得明确，由专门的项目经理承担；但无论哪种，懂一些项目管理都能让你更好地分配任务，这是核心的软能力。

#### 2.9 AI 特有的项目管理思考：算力分配

UP 主还给了一个 AI 项目管理特有的思考点——**算力的分配和争取**。

在大公司里，算力（GPU 卡）是有限度的资源，什么样的团队、什么样的任务、什么样的价值能用到这些卡，本身就是一个需要思考的问题。卡管够的公司除外，但即使卡管够，**怎么分配**也是大问题。

这倒推出为什么要学数据、为什么要学硬件——其实都是环环相扣，没有用不到的点。AI PM 对**整个 AI 的成本投入**，以及**算力的争取和分配**要有自己的思考。

#### 2.10 复盘和项目管理的合流点

把复盘和项目管理放在同一章，本质上是因为它们在「系统级调优」这个点上合流：

- **复盘告诉你过去哪里做错了**——历史维度。
- **项目管理告诉你未来怎么不再犯同样的错**——未来维度。
- **两者合流 = AI 产品的持续运营引擎**——系统维度。

每一次项目管理过程中的关键节点（模型选型、数据准备、灰度上线、效果验收），都是下一次复盘的素材；每一次复盘的产出（系统调优、数据标注改进、Prompt 优化），又回流到项目管理的下一阶段。两者合起来，才是 AI PM 从「交付功能」升级为「运营系统」的完整闭环。

---

## 结论 / 金句

> **复盘的本质**：从「找 Bug」升级为「调系统」。AI 产品的复盘不是回顾功能完成度，而是对模型、数据、算力、链路做系统性归因，落地为算法 + 数据 + 工程三轴并行的调优方案。

> **项目管理的本质**：从「排甘特图」升级为「写剧本」。AI 项目的核心矛盾不是协调资源实现确定目标，而是在巨大的技术不确定性中通过三方会诊找到可落地的交付路径。

> **复盘 + 项目管理 = AI 产品的反思与执行闭环**：复盘管「过去为什么变差」，项目管理管「未来怎么控制变化」，两者合流构成 AI 产品从「能跑」到「能跑好」的完整引擎。

> **AI 产品经理比传统 PM 多看的那一截**：系统级视角（数据 + 模型 + 服务全链路）+ 三方联合会诊的协作模式 + 概率性归因的思维方式。任何 AI 产品的复盘和项目管理，落不到这三件事上，就是传统思路。

| 三层复盘焦点 | 模型性能 / 人机交付效果 / 业务影响 | 任何 AI 产品复盘 | 三层缺一不可 |
| 数据-模型-服务链路归因 | 沿链路一节一节穿透排查 | AI 产品问题归因 | 标注 / 训练 / 推理 / 监控每个节点都要查 |
| 三轴迭代计划 | 算法 + 数据 + 工程三位一体 | AI 产品下一版本规划 | 单轴突进无效，必须三轴协同 |
| 实时监控 + 快速响应 | 分钟 / 小时级响应模型劣化 | 模型上线后全周期 | 不走版本号，直接系统干预 |
| 三方联合会诊 | 业务 + 产品 + 技术同房间同时看 | AI 产品复盘 / 重大问题排查 | 不按角色走流程 |
| 概率性归因 | 从绝对因果到概率假设 | AI 产品 Bad Case 分析 | 接受「不一定 100% 确定」 |
| 范围能力双轨 | 功能清单 + 能力达标标准 | AI 产品 PRD 编写 | 模型指标要写进验收 |
| 柔性延期管理 | 里程碑 + 弹性窗口 | AI 项目排期 | 提前沟通进 OKR |
| 数据 / 算法新增风险 | 标注 / 合规 / 漂移 + 效果 / 幻觉 / 延迟 | AI 项目风险登记册 | 传统风险 + 新增风险 |
| 跨语言翻译 | 算法 / 工程黑话 → 业务语言 | AI 产品经理沟通场景 | 三方语言即时切换 |
| 业务 + 模型 + 链路三层质量 | 业务层 + 模型层 + 链路层 | AI 产品验收 | 三层同时达标 |
| 上线即运营起点 | 上线不是终点，是飞轮起点 | AI 产品上线后 | 用户反馈 → 数据回流 → 模型迭代闭环 |
| 算力分配与争取 | 算力是有限资源，分配有策略 | 大公司 AI 项目管理 | 团队 / 任务 / 价值三维度争算力 |
| 复盘-项目管理闭环 | 复盘 → 调优 → 下一版项目管理 | AI 产品全生命周期 | 闭环速度 = 迭代速度 |

## 通用原则（脱 UP 主，可迁移）

1. **复盘的对象是系统**：AI 产品的复盘看的是数据 / 模型 / 服务链路的节点，不是某个功能做没做完。
2. **归因必须链路穿透**：必须沿数据 → 模型 → 服务链路一节一节排查，单点归因在 AI 产品里是危险的。
3. **产出必须三轴**：算法、数据、工程三轴并行的调优方案才是有效的 AI 复盘产出。
4. **节奏必须实时或近实时**：模型可能随时劣化，月度复盘等于没复盘。
5. **协作必须联合会诊**：业务 + 产品 + 技术同房间同时看问题是 AI 时代的标配。
6. **接受概率性归因**：AI 的不确定性要求我们接受概率思维，不要追求绝对因果。
7. **核心矛盾变了**：从「协调资源实现确定目标」到「探索路径找到可确定目标」，PM 从「资源调度者」变成「路径探索者」。
8. **范围双轨 + 时间柔性 + 风险新增**：功能清单 + 能力达标标准双轨；里程碑加弹性窗口；风险登记册必须加挂数据 + 算法两条新增线。
9. **上线不是终点，是运营起点**：PM 必须把「用户反馈 → 数据回流 → 模型迭代」的飞轮建起来。
10. **复盘 + 项目管理必须闭环**：两者断裂，AI 产品经理就退化成传统 PM。

## 可复用模式

- **AI 复盘三步法**：场景在线（还原当时怎么做、怎么想）→ 链路排查（数据 → 模型 → 服务全链路）→ 归因分析（哪个环节出哪类问题，具体情况具体分析）。
- **三层焦点平衡表**：每个 AI 复盘都建一张三层焦点表（模型性能 / 人机交付 / 业务影响），每层列出本次复盘的关键发现 + 改进动作，避免只盯一层。
- **链路归因七问**：标注准不准？数据够不够？分布偏没偏？模型选对了吗？训练收敛了吗？推理稳吗？监控告警到位吗？七问走完，链路问题无所遁形。
- **三轴迭代方案模板**：数据轴（标注 / 补数据 / 清洗）、算法轴（微调 / 换模型 / Prompt）、工程轴（缓存 / 限流 / 部署）。三轴联动写进下一版本 PRD。
- **三方联合会诊议程**：业务讲业务诉求 + 业务指标现状 → 产品讲产品逻辑 + Bad Case → 技术讲技术实现 + 链路问题 → 三方共同定位根因 → 定义改进动作 → 承担不确定性。
- **复盘节奏看板**：实时监控（分钟级告警）+ 日级响应（≤ 24h 干预）+ 周度复盘（系统级归因）+ 月度回顾（三轴调优进度）。
- **PRD 双轨模板**：每个 AI 产品的 PRD 都要包含「功能清单」+「能力达标标准」两套范围，验收时两套同时看。
- **柔性里程碑模板**：每个 AI 项目里程碑加一段「弹性窗口说明」，写清楚哪些可延期、延期上限、提前与老板对齐。
- **风险登记册扩展**：传统风险（资源 / 需求 / 攻击）+ AI 新增风险（标注 / 合规 / 漂移 + 效果 / 幻觉 / 延迟），每个风险写应急预案。
- **跨语言翻译手册**：算法 / 工程高频黑话 → 业务语言对照表，每个 AI 产品经理人手一份。
- **三层质量验收 checklist**：业务层 + 模型层 + 链路层，三层同时过才算验收通过。
- **飞轮闭环设计**：每个 AI 产品上线前画一张飞轮图——用户反馈 → 数据回流 → 数据标注 → 模型训练 → 模型上线 → 用户反馈。闭环速度越快，产品越好。
- **算力申请决策树**：团队（核心 / 探索 / 试点）× 任务（训练 / 推理 / 实验）× 价值（核心 / 战略 / 储备），三维评分后决定算力分配。
- **复盘-项目管理闭环表**：每个项目建一张闭环表——复盘发现 → 下一版本调优动作 → 调优验证结果 → 闭环速度记录。作为下一轮复盘输入。

# 借鉴篇 · 我们能借鉴的点

> 对应业务：王昕团队做**企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库**，以下每条都标注对应场景与可落地动作。

### 1. 用「复盘定位升级」建立 FDE 的项目复盘标准
**场景**：FDE 交付完项目，目前复盘往往只写「做完了 / 没做完」，不写「链路哪里出了问题、为什么、怎么改」。
**怎么做**：建立 FDE 项目复盘标准模板——场景还原（当时客户怎么提需求、我们怎么理解、怎么决策）+ 链路排查（数据 → 模型 → 服务全链路哪一节断了）+ 归因分析（哪类问题、为什么、下次怎么改）。每份复盘沉淀进 8895 知识库，下次同类项目直接复用。

### 2. 用「三层复盘焦点」做客户 AI 产品的效果验收
**场景**：客户 AI 产品上线后验收，目前只看业务指标（转化 / 留存），不看模型指标（准确率 / 幻觉率），更不看链路指标（数据漂移 / 推理稳定性）。
**怎么做**：把三层复盘焦点写进客户 AI 交付 SOW——模型性能层（准确率 / 召回率 / 幻觉率 / 延迟）、人机交付层（采纳率 / 修改率 / 满意度）、业务影响层（转化 / 留存 / GMV）。三层指标同时验收，缺一不算交付完成。

### 3. 用「链路归因」做 FDE 现场问题排查
**场景**：客户 AI 系统出问题，FDE 现场经常「不知道哪里坏了」，因为没有一套链路排查方法。
**怎么做**：把链路归因七问（标注 / 数据 / 分布 / 模型 / 训练 / 推理 / 监控）做成 FDE 现场 1 页 SOP。客户出问题 5 分钟内走完七问，定位节点，调技术资源。

### 4. 用「三轴迭代方案」做客户 AI 系统的调优交付
**场景**：客户 AI 系统效果不达预期，FDE 经常只改一处（只调 Prompt），效果有限，客户不满意。
**怎么做**：把三轴迭代方案（数据轴 + 算法轴 + 工程轴）做成标准交付模板——每次调优必须三轴联动，至少给出三侧各一个动作。三轴联动调优比单点调优见效快数倍，客户满意度显著提升。

### 5. 用「三方联合会诊」建立客户现场的快速响应机制
**场景**：客户 AI 系统出问题，FDE 一个人搞不定，需要业务、产品、技术三方一起看，但目前没有制度保证三方同步响应。
**怎么做**：建立「三方联合会诊」机制——客户 AI 系统出问题 24 小时内，必须召集客户业务负责人 + 我们 FDE + 后端算法 / 工程三方同房间（或视频会议），共同定位根因、共同定义改进动作、共同签字确认。

### 6. 用「概率性归因」训练 FDE 的 AI 思维
**场景**：FDE 在客户现场常被问「这 100 个错误是同一个原因吗」，传统 PM 思维会说「我去找根因」，但 AI 产品里往往不是单一根因。
**怎么做**：把「概率性归因」写进 FDE 培训手册——AI 产品的问题往往是概率分布，不是单一根因。FDE 现场沟通时避免「我找到根因了」的承诺式表达，改用「这 100 个错误大概 30% 来自 X、40% 来自 Y、30% 来自 Z，先解决占比最高的那个」的分布式表达。

### 7. 用「范围能力双轨」写客户 AI 项目的 PRD
**场景**：FDE 在客户现场写 PRD，目前往往只写功能清单，不写能力达标标准（模型准确率要多少、响应延迟要多少）。
**怎么做**：把 PRD 双轨模板（功能清单 + 能力达标标准）作为客户 AI 交付的强制模板。每个 PRD 必须写清楚功能范围 + 能力范围（模型指标达到什么阈值才能上线）。客户验收时两套范围同时签，避免上线后扯皮。

### 8. 用「柔性里程碑」管理客户预期
**场景**：AI 项目周期不可控，FDE 给客户的里程碑往往是硬时间点，结果经常延期，客户信任度下降。
**怎么做**：在客户 AI 项目里程碑表里加「弹性窗口说明」——每个里程碑标出最早、正常、最晚完成时间。提前与客户沟通「AI 项目存在试错周期，里程碑有弹性」。柔性里程碑比硬里程碑的客户满意度高，复购率更高。

### 9. 用「AI 新增风险登记」做客户 AI 项目的风控交付
**场景**：客户 AI 项目风险目前只写「需求变更」「人员变动」，不写「标注延迟」「数据合规」「模型效果不达预期」「幻觉率失控」等 AI 特有风险。
**怎么做**：把风险登记册扩展为「传统风险 + AI 新增风险」两栏。AI 新增风险必须覆盖：数据层（标注 / 合规 / 漂移）、算法层（效果 / 幻觉 / 延迟）、链路层（推理稳定性 / 监控告警）。每个 AI 风险都要写应急预案。

### 10. 用「跨语言翻译手册」建立 FDE 的专业度护城河
**场景**：FDE 在客户现场既要和客户的业务 / 高管对话，又要和我们内部的算法 / 工程对话，经常「两边都听不懂」。
**怎么做**：建立「跨语言翻译手册」——算法 / 工程高频黑话（Loss / 收敛 / GPU 利用率 / 推理框架 / 漂移 / 蒸馏）→ 客户能听懂的语言对照表，每个 FDE 人手一份。手册既是 FDE 培训材料，也是 FDE 在客户面前建立专业度护城河的武器。

### 11. 用「三层质量验收」建立客户 AI 项目的 KPI 体系
**场景**：客户 AI 系统上线后没有统一 KPI 看板，FDE / 客户都不知道「现在跑得好不好」。
**怎么做**：把三层质量验收（业务层 + 模型层 + 链路层）做成客户专属 KPI 看板。业务层（转化 / 留存 / GMV）+ 模型层（准确率 / 幻觉率 / 响应延迟）+ 链路层（数据漂移度 / 推理稳定性 / 告警覆盖率）。三层 KPI 写进 SLA 条款。

### 12. 用「上线即运营起点」建立客户 AI 系统的飞轮机制
**场景**：FDE 交付完项目后，客户往往认为「上线 = 结束」，不投入运营资源，结果模型效果很快劣化。
**怎么做**：在交付前就和客户对齐「上线即运营起点」的心智——上线后必须建立用户反馈机制、数据回流机制、模型迭代机制。把飞轮机制写进 SOW 的「运营服务」条款，让客户为运营服务付费，FDE 团队有持续的运营收入。

### 13. 用「算力分配决策树」做 FDE 的成本管理
**场景**：FDE 在客户现场做 PoC 时，对算力成本没概念，结果客户 TCO 超预算，项目亏钱。
**怎么做**：建立「算力分配决策树」——任务类型（PoC / 试点 / 生产）× 模型规模（7B / 13B / 70B）× 并发量，对应成本预估。FDE 给客户做方案时，先用决策树算一遍 TCO，再和客户对齐预算。避免 PoC 阶段就用最贵的模型导致成本失控。

### 14. 用「复盘-项目管理闭环表」沉淀 8895 知识库
**场景**：FDE 团队的项目经验目前散落在各个人的笔记里，没沉淀到 8895 知识库，新人来了要从头踩坑。
**怎么做**：把「复盘-项目管理闭环表」作为强制产出物——每个客户 AI 项目交付后，FDE 必须填写闭环表（复盘发现 + 下一版调优动作 + 验证结果 + 闭环速度）。闭环表自动沉淀进 8895 知识库，按行业 / 场景 / 模型类型分类索引。3-6 个月后，8895 知识库就能形成「场景化最佳实践」。

### 15. 用「场景化复盘」升级获客系统的客户判断能力
**场景**：获客系统目前给销售输出客户行业判断时，缺乏「客户场景能否做 AI」的专业判断能力。
**怎么做**：把三层复盘焦点做成获客系统的「AI 场景成熟度评估模型」——客户场景属于模型驱动 / 人机协同 / 业务拉动哪一层，每层有哪些典型案例、哪些常见坑。销售和客户聊的时候能用这套模型快速判断「这个场景我们能不能接、有什么风险、报价怎么定」，专业度直接拉满。
