## 4.2 @ 引用：Files / Folders / Terminal（1/2）

@Files 引用文件

让AI 阅读指定文件。

输入@ 后选择文件。

典型用法

@Files src/UserCard.tsx

参考风格创建新组件

注意

• 每次不超过5 个文件

• 优先引用类型文件

@Folders 引用目录

让AI 了解目录结构，不阅读每个文件。

典型用法

@Folders components

规划新模块文件结构

适合

• 规划文件组织

• 了解项目架构

@Terminal 引用终端

传递报错信息和日志。

典型用法

npm run build 出错后

引用终端输出让AI分析

最佳实践

• 只引用相关终端输出

• 报错+ 触发命令一起给

## 4.2 @ 引用：Docs / Code + 注意事项（2/2）

@Docs 引用文档

让AI 参考项目文档或外部API 文档

典型用法

@Docs 选择API 规范

•

让AI按文档实现接口

•

注意

点击Docs 后，还要选择具体文档

•

@Code 引用代码片段

选中编辑器中的代码比整个文件更精准

操作方式

选中代码段，在对话中@Code

•

只让AI 看你关心的那几行

•

使用注意事项

每次引用不超过5 个文件

优先类型和接口文件

对话变长时

及时开新窗口或用锚点回顾

## 4.3 四种上下文污染（1/2）

陈旧信息

引用已废弃旧代码

AI 生成兼容旧方案方向就错了

噪声过多

500 行文件全扔给AI

抓不住重点，输出质量急剧下降

矛盾信息

前面说REST 后面又说GraphQL

AI 左右为难

跨任务污染

一个对话讨论3个功能

AI 把功能搞混，上一任务干扰下一个

## 4.3 最小上下文原则（2/2）

核心：只给AI 看它完成当前任务所需的最少信息

不推荐

一次性引用10 个文件

Header/Footer/Sidebar...

AI 被无关信息淹没

黄金法则1

· 一个任务一个对话

· 避免跨任务污染

· 出问题先缩减上下文

急救手段

输出混乱时：

立刻缩减上下文+ 重开单任务对话

推荐

只引用3 个相关文件

SearchBar + useSearch + types（只看SearchResult）

黄金法则2

· 类型文件优先于实现

· 接口优先于内部逻辑

· 只给必要信息

核心公式

输出质量= 相关性× (1/噪声量)

减噪就是提质

## 4.5 负面上下文（2/2）

什么是负面上下文

告诉AI 不要做什么

有时比说要做什么更有效

适用于：

只想局部重构

不想改接口

项目已上线

不能破坏现有功能

错误vs 正确

错误示范

提示：'帮我优化这个组件'

↓

→ AI 可能改Props

→ 换样式框架

正确做法

约束：不改Props 接口

不引入新第三方库

不修改CSS 类名

只拆分内部逻辑

实际效果

未给禁止项时：

• AI 顺手改Props

• 替换样式体系

• 合入风险高

给出禁止项后：

• 聚焦内部拆分

• 可读性优化

• 可直接合并概率大幅提升
