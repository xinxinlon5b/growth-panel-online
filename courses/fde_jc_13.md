# 上篇 · 书籍内容

## 引子：为什么必须先看「行业落地全景」

大模型基础知识 UP 主在直播课里反复强调一件事：AI 应用不是「先有模型，再找场景」的单行道，而是「看清行业骨架，再决定在那一层下刀」的工程题。这一章是他花了整整一节课画出来的行业总览图——以 InfoQ 2024 AGI 市场发展报告为底，把 AI 行业从底到顶切成四层，再在「应用层」里挑出四个最值得拆解的行业（泛娱乐、教育、企业数字化、金融），逐个演示怎么把抽象的「拼装提示词 + 多 Agent 协同」落到具体产品形态里。

这一章要解决三个问题：
1. 一个 AI 行业的从业者，到底应该把精力放在四层架构的哪一层？
2. 同样的底层能力，在不同行业为什么会演化出完全不同的产品形态？
3. 哪些玩法是「技术含量高但商业价值低」，哪些是「技术含量低但商业价值高」？

## 主线：行业落地的方法流程

**Step 1｜行业分层定位**：先用四层架构（基础设施层 / 模型层 / 中间层 / 应用层）判断玩家位置——门槛、成本、目标客户完全不同。

**Step 2｜判断「AI 原生」还是「传统软件 + AI」**：AI 原生产品没有 AI 就不存在（如 AI 陪伴、ChatBI）；AI 增强产品是在原有软件里嵌入 AI 能力。

**Step 3｜拆产品骨架为四层**：所有应用层产品几乎都可以拆成「展示层 + 人设/逻辑层 + 记忆/数据层 + 运营玩法层」，逐层识别 AI 切入点。

**Step 4｜拼装提示词 = 千人千面**：把用户静态信息（数据库读取）、动态信息（情绪检测、记忆提取）、公共上下文（知识库检索 RAG）拼成系统提示词。

**Step 5｜运营玩法定生死**：在陪伴类、内容类、互动类产品里，运营玩法往往占到成功因素的一半以上。

**Step 6｜大客户的视角看全栈**：做 toB 大客户（尤其是金融、银行）时，不能只盯一层，要看全栈架构（自建算力、自训模型、知识库、中间层、应用层）。

## 逐点精读

### 一、行业四层架构全景

**怎么分**：
- **基础设施层**：算力、服务器、芯片（GPU/TPU）。典型企业：电信、移动、华为。
- **模型层**：训练基础大模型与多模态模型。代表：DeepSeek、MiniMax、Kimi、百川（AI 六小龙之外的主力）。
- **中间层**：介于模型层与应用层之间的桥梁。代表产品：Dify、Coze。提供 Prompt 工程、Agent 编排、RAG 等能力。
- **应用层**：面向终端用户的具体产品。这是本课程的重点。

**工具/模型**：分层视角是来自 InfoQ 2024 AGI 市场报告的标准框架；UP 主自己强调 25 年的报告「也快出来了」，但目前结论仍然代表现状。

**AI 产品经理多关注什么维度**：
- **门槛与成本曲线**：越往下层门槛越高、成本越高、玩家越少；越往上层门槛越低、产品形态越百花齐放。
- **价值锚点选择**：FDE/PM 一般落点在「中间层」或「应用层」——大公司做底层，小团队做应用是行业共识。
- **跨层视野**：做大客户时（如银行），要会看全栈，否则谈不下来。

### 二、泛娱乐行业——AI 陪伴类产品

#### 2.1 AI 原生产品的概念

UP 主开篇用一个引子引入 AI 原生（AI Native）概念：**这个产品如果没有 AI 根本就不会存在**。AI 原生产品分三类：
1. **个人助理类**：ChatGPT、Kimi Chat、DeepSeek App。
2. **AI 搜索类**：Perplexity、秘塔（Metaso）搜索。
3. **AI 陪伴类**：国外的 Character AI、国内的星野（Xingye）。

**AI 产品经理多关注什么维度**：判断一个产品是不是真正 AI 原生，看它的核心价值是否依赖大模型能力。如果去掉大模型产品就不成立，就是真 AI 原生；如果只是「传统软件 + AI 加分项」，就是 AI 增强型产品，定位和定价策略完全不同。

#### 2.2 腾讯报告：用户最想要的 AI 陪伴场景

腾讯调研的多选结果显示用户最感兴趣的 AI 陪伴类型：
1. **AI 虚拟故事角色**（单选最热门）——星野就是这类典型代表。
2. **AI 虚拟男友/女友**——情感陪伴类。
3. **AI 心理顾问**（多选更热门）。
4. **游戏陪玩**、**虚拟偶像**、**开放世界 NPC**。

#### 2.3 两个典型产品案例

**星野（Xingye）**：面向女性用户为主的 AI 虚拟故事角色平台。截图时显示某角色有 31 万左右的用户，绝大多数用户行为是与角色聊天。

**EVE（义务/伊娃）**：面向男性用户的 3D AI 陪伴产品，由「自然选择」公司（前游戏背景）开发。2023 年 10 月上线 B 站，**一个月内播放量破百万**。亮点是 3D 形象 + 视频通话般的体验。

**AI 产品经理多关注什么维度**：
- **用户性别 → 产品形态不同**：男性用户强需求「颜值 + 3D + 视频通话感」；女性用户接受度高，一张画就能聊很久。
- **来源场景差异**：星野走 UGC 路线（几千个角色多数由用户自定义），EVE 走精品路线（只做一个角色深度打磨）。

#### 2.4 AI 陪伴产品的四层骨架

UP 主用一张图把这类产品拆成四层（这是本章最重要的方法论之一）：

| 层级 | 内容 | 关键决策 |
|---|---|---|
| **展示层** | 形象、声音、3D/2D | 男性重 3D、女性重 2D 也能跑 |
| **人设层** | 基础人设 + 个性化人设 | 拼装到提示词 |
| **记忆层** | 公共记忆 + 专属记忆 | 向量化入知识库 + 存数据库 |
| **运营玩法层** | 限制对话、永久记忆、忘记对话、主动唤起 | 决定商业化与留存 |

**人设层详解**：
- **基础人设**：比如「霸道总裁-环球集团 CEO 林叶诚」或「邻家小哥哥-大学生爱打篮球」。
- **个性化人设**：来自用户的专属记忆 + 平台的公共记忆。同一基础人设（霸道总裁）对不同用户会演化出不同「专属关系」。

**运营玩法层详解**（这是 UP 主反复强调「占到产品成功一半以上」的部分）：
- **每日对话次数限制**：聊嗨了要付费解锁更多。
- **永久记忆购买**：免费用户记忆 7 天清空，付费可永久保留。
- **忘记对话服务**：聊崩了可付费立即清除历史。
- **主动唤起**：AI 不被动等用户，会主动发消息、推送，甚至「打电话」给用户。

#### 2.5 提示词拼装的完整方法

UP 主用星野的「个性化人设提示词」做了完整演示——这是 FDE 工作中最高频的方法之一。

**提示词结构**：
```
你是【小优】（陪伴角色名）
你的任务是长期陪伴【小玲】（用户起的名字）
用户喜欢：善解人意、温柔、有点幽默
用户基本信息（数据库读取）：昵称、年龄、城市、职业、兴趣
动态策略（每次聊天动态生成）：
  - 过去聊天关键信息（如：我有一只叫团团的猫）
  - 当前情绪（情绪检测模型判断）
  - 上下文摘要（前几轮对话摘要）
  - 当前时间/情境
以温柔自然的语气回应，认识很久了
```

**关键工程要点**：
- **静态信息**（昵称、年龄、城市）→ 用户填写 + 数据库读取。
- **动态信息**（情绪、记忆、上下文）→ 专门模型实时提取。
- **情绪检测**：独立模型判断，常见实现是另一个 LLM 跑分类。
- **记忆更新**：独立模型动态提取「关键记忆点」，比如用户新养了一只猫「圆圆」，记忆从「一只猫叫团团」变成「两只猫，团团和圆圆」。

#### 2.6 多 Agent 协同的进阶架构

EVE 创始人在访谈中提到的更深层架构（UP 主强调是「深度做这方面」的产品才会用的）：

```
[照回 Agent] → 从 [长期主动记忆系统]、[记忆槽位]、[短期对话历史] 检索
   ↓
[多个专门模型] → 拼接上下文
   ↓
[主大模型] → 输出
```

**核心**：每个环节都有专门的 Agent 负责提取和加工，最终拼装给主大模型。

**AI 产品经理多关注什么维度**：
- **拼装频次**：每次对话都拼装一次提示词（不是固定提示词），这是「千人千面」的核心。
- **更新策略**：记忆点是否每轮更新？没有标准答案——通常与「用户对话轮次 + 日活周活 + 产品评测数据」挂钩决定策略。

#### 2.7 总结：AI 陪伴产品的成功公式

UP 主用一句很形象的话总结：**「颜值激发荷尔蒙，大模型给他人性。」**

- 技术要求可高可低（EVE 做得很深，星野很多是 UGC 角色）。
- 运营要求很高（对人性的把握、玩法的设计）。
- **不是所有 AI 应用都是为了提效**——AI 陪伴是一个典型的不以提效为目标的产品。

### 三、教育行业——AI 师傅案例

#### 3.1 为什么教育是「最适合大模型的领域」

UP 主给出三个理由：
1. **教育本质是文本**——大模型本就擅长文本生成。
2. **教育天然需要交流**——大模型的对话能力极强。
3. **大模型已有的知识储备足够**——尤其是英语、编程等通用学科，模型自身知识就能教学。

#### 3.2 AI 在教育领域的全流程渗透

- **营销层**：AI 生成营销方案、AI 做物料、AI 销售助手（AI 客服）。
- **教研层**：备课（贝壳备课、科大讯飞）、课件生成（中国大学慕课已上线 AI 备课）。
- **授课层**：AI 师傅、AI 出题、AI 批改（作业帮、一扫码）、AI 写作批改。

#### 3.3 AI 师傅的产品形态

UP 主团队自己做的产品——**AI 师傅**——核心模式：
> **「专家主导，AI 教育，用户跟随，随时互动」**

**三大产品特征**：
- 所有课程都由 AI 教学，不是真人授课。
- 平台开源（GitHub 可访问）。
- 提供 SaaS 模式，企业可租用 / 私有部署。

#### 3.4 课程设计的三层流程

| 环节 | 谁来做 | 做什么 |
|---|---|---|
| **课程制作**（学什么） | 真人导师 | 设计课程结构、章节知识点 |
| **授课**（讲什么） | 真人导师完成 Prompt 工程 + AI 加工 | AI 进行所有回复 |
| **提问**（答疑） | 真人提供知识库 + AI 基于知识库回复 | 用户提问时检索知识库 |

**核心洞见**：「真人做教研，AI 来授课」——把教育产品的边际成本降到接近零。

#### 3.5 个性化教学的实现原理

**演示案例**：用户说「我是一名电商产品经理」，AI 立刻返回针对电商 PM 的个性化内容（生成商品报表、竞品价格变动、批量商品处理）。

**实现方式**：用户输入 → 拼装到系统提示词 + 用户提示词 → LLM 生成个性化回复。

**提示词结构示例**：
```
系统提示词：
- 你是 AI 师傅中的【孙小志】老师
- 学员【小李】的编程知识基础为零
- 学员背景：电商产品经理
- 喜欢什么样的授课风格：实战案例驱动

用户提示词：
- 当前用户背景是电商产品经理
- 请认真分析他的需求
- 策划 5 个符合他背景的具体需求
```

#### 3.6 AI 师傅的设计哲学

**1. 温度设置相对较高**——给 AI 一些发挥空间，不要求每轮回复一模一样。

**2. 开源 + SaaS + 私有部署三种形态都支持**——核心是为了借助社区生态 + 海外推广 + 大客户私有化需求。

**3. 响应速度不追求极快**——500ms 级别的代码补全需求不存在，老师讲解式的回复节奏更符合教学场景。

**4. 知识库的两种情况**：
- 大模型自带的知识（编程、英语）→ 不需要外挂知识库。
- 专业领域（行业教材、企业内训）→ 必须外挂知识库 + RAG 检索。

**AI 产品经理多关注什么维度**：
- **意图识别 + 防闲聊**：教学场景不能让用户闲聊跑题，提示词第一层就要做意图识别。
- **知识库动态更新**：规划中的外挂知识库要解决「教材更新滞后」问题。
- **不同场景的延迟容忍度**：陪伴场景「秒回反而不像真人」；教学场景「慢一点像老师」；代码场景「必须 500ms 内」。

### 四、企业数字化——ChatBI 案例

#### 4.1 企业数字化三阶段

1. **信息化**（过去）：纸质内容上系统。
2. **数字化**（2010-2022，大数据浪潮）：数据存储与挖掘。
3. **智能化**（现在）：基于数据做 AI 应用。

**逻辑链**：没有信息化就存不下数据，没有数字化就没法智能化。

#### 4.2 企业 AI 落地的两大方向

UP 主调研后给出两个落地最好的方向：
1. **基于知识库的数字员工**：智能客服、智能销售、智能行政助理。
2. **面向企业信息化的专业工具**：智能数据分析（ChatBI）、智能编程（Copilot 类）、智能运维。

#### 4.3 ChatBI 的核心价值

**传统流程**：
```
运营提出需求 → 数据分析师排期 → 写 SQL → 运行查询 → 返回结果
  → 如果错了 → 重新走流程
```

**ChatBI 流程**：
```
运营直接对话 → ChatBI 返回结果 → 不满意继续问
```

**核心节省**：从「5 步走 1 周」变成「1 步走 1 秒」。

#### 4.4 ChatBI 的工作原理

**核心**：在原有 BI 产品的基础上加一个「NL2SQL」环节——自然语言生成 SQL。

```
用户输入 → LLM 生成 SQL → SQL 执行器 → 数据库 → 结果可视化
```

**Prompt 拼装模板**：
```
你有一个 product 表（产品表）
字段：product_name（产品名称）、product_price（产品价格）
请基于用户的输入生成对应的 SQL 语句
只能输出 SQL，不能包含其他信息

用户输入：{user_query}
```

#### 4.5 ChatBI 的真实局限

UP 主坦诚指出了三个真实存在的局限：

**1. 复杂 SQL 的天花板**
- 几百行 SQL 的复杂查询，**用户根本描述不出来**——这不是 LLM 的问题，是需求表达的问题。
- 因此数据分析师不会失业，他们处理的是复杂需求；ChatBI 处理的是「简单但高频」的取数需求。

**2. 数据库命名规范要求高**
- 如果表叫 `a`、字段叫 `value`，LLM 猜不出来。
- 命名规范的产品（product、price 这种语义化命名），LLM 才能生成正确的 SQL。
- **结论：做 ChatBI 必须先规范数据库命名。**

**3. 行业黑话处理**
- 比如「C9 院校的高考录取分数线」——LLM 知道 C9 但不完整。
- **解决方案**：知识库 + RAG 检索。
  - 用户问「C9 院校分数线」→ 先到知识库检索「C9 = 清华/北大/浙大/复交等」→ 改写查询 → 再生成 SQL。

#### 4.6 ChatBI 的幻觉应对

UP 主给出了三个务实策略：
1. **AI 写两遍做验算**（降低幻觉概率）。
2. **换两个模型对比**。
3. **接受可控错误率**——「不要错的太多」就行。

#### 4.7 ChatBI 的工程复杂度

**ChatBI 看似简单，实际工程量不小**：
- **Prompt 拼装**（简单）→ 任何人都能写。
- **SQL 执行环境**（需要既有 BI 平台）→ 必须基于原有产品。
- **数据可视化**（需要图表代码能力）→ 通常用 Python 代码生成。
- **多表联查**（支持）→ 但要控制表数量。
- **表太多怎么办** → 先 RAG 检索相关表，再让 LLM 生成 SQL。

**FDE 启示**：ChatBI 的核心不在 LLM 本身，而在「原有的 BI 平台 + NL2SQL 增量」。UP 主反复强调的 FDE 哲学——「把工作流拆出来，找到中间可以用 AI 取代的部分」——这个案例是最经典的示范。

**AI 产品经理多关注什么维度**：
- **现有产品嵌入 AI 是 toB 主流模式**：不要总想从零做 AI Native，先看存量产品哪里能加 AI 能力。
- **从零到一 vs 提效**：AI 编程是「提效」，ChatBI 是「从零到一」——让原本不会 SQL 的运营能自助做数据分析，价值更大。
- **评测与对比**：SQL 生成用什么模型？UP 主建议 Claude（写代码最强）+ DeepSeek（开源最强）做对比评测。

### 五、金融行业——投顾知晓珠案例

#### 5.1 金融行业的四大特点

| 特点 | 说明 |
|---|---|
| **有钱** | 管钱的行业，资金充裕。 |
| **有数据** | 信用体系天然依赖数据，数据最全最丰富。 |
| **IT 强** | 各银行 IT 部门都很大，技术能力极强。 |
| **安全要求高** | 中国 99% 的银行不能上公有云，必须自建银行内部私有云。 |

**结果**：金融行业是 AGI 技术创新中最积极的行业之一。

#### 5.2 第一个行业大模型：BloombergGPT

UP 主提到一个历史性时刻：**2022 年 11 月 ChatGPT 发布 → 不到两个月（春节前后），彭博社就推出了 BloombergGPT**——这是 UP 主印象中第一个听到的「行业大模型」，早于国内所有「金融大模型」概念。

#### 5.3 金融大客户的全栈架构——北京银行案例

UP 主用北京银行的公开资料展示了金融客户的「全都要」：

```
基础设施层：自购算力、自建 GPU 平台
模型层：训练自己的专属大模型
中间层：构建知识库 + 模型开发平台
应用层：大量 Agent + 智能客服 + 会议纪要 + 投顾助手
```

**关键启示**：做 toB 大客户（银行、券商、保险），必须懂全栈——从算力到应用都要懂。这是 FDE 在金融行业的核心能力要求。

#### 5.4 金融 AI 应用的成熟度图谱

**成熟度较高的应用**（各行业通用）：智能助手、语音助手、智能客服、数字员工、智能编程——这些在金融行业也常见，没特色。

**金融特有 + 应用探索中的**：
- **智能投顾**（投资顾问）——代表性产品：蚂蚁集团的「知晓珠」。
- **分析师助手**——投研报告自动化。

#### 5.5 投顾知晓珠：多 Agent 协同的经典案例

蚂蚁集团的「投顾知晓珠」做的是：模拟投资顾问专家的分析框架，产出专业严谨的市场解读，让金融分析师专注于深度研究。

**核心架构：Peer 范式（多 Agent 协同）**

| Agent | 职责 |
|---|---|
| **Plan（计划）** | 基于框架描述 + 专家知识，做市场调研分析的计划 |
| **Execute（执行）** | 从金融数据库获取各种数据 |
| **Express（表达）** | 整理、摘要、分析数据，形成初步报告 |
| **Review（评价）** | 判断报告质量，达标才给用户看，否则重新生成 |

**流程**：
```
知识库（金融专业）+ Peer 多 Agent 协同
   ↓
Plan（计划）→ Execute（执行）→ Express（表达）→ Review（评价）
   ↓
达标 → 给用户展示
不达标 → 停止或重来
```

#### 5.6 Peer 范式的本质

UP 主强调 Peer（取首字母 Plan/Execute/Express/Review）其实就是 **「我要做一件事，先计划，再执行，再总结，再评价」**——这是通用方法论，不是金融独有。任何复杂分析任务都可以用这个四步法。

**开源情况**：
- **框架是开源的**（在 GitHub 可以找到）。
- **数据、工具不开源**——这部分才是蚂蚁的核心壁垒（外部没有同等的金融数据库 + 工具）。

**关键洞见**：蚂蚁敢开源框架，因为框架本身不是核心竞争力——真正难复制的是「数据 + 工具 + 专家经验」。这跟所有开源项目的逻辑一致：开源的是「方法」，闭源的是「资产」。

#### 5.7 金融行业的 FDE 视角

**AI 产品经理多关注什么维度**：
- **金融大客户必须看全栈**：谈银行客户不能只讲应用层，要讲算力 + 模型 + 中间层 + 应用层的整体方案。
- **复杂分析任务 = 多 Agent**：单 Agent 解决不了的复杂任务，必须拆成多 Agent 协同。
- **私有部署是标配**：金融行业 99% 不能用公有云，FDE 必须懂私有化部署。
- **数据资产是核心壁垒**：不要把核心竞争力放在 Prompt 工程上，要放在数据 + 工具的整合上。

### 六、结论与金句

UP 主在课程最后给出了一条贯穿四章的主线：

> **「看一个大模型的行业应用，要从基础层、模型层、中间层、应用层来看它究竟工作在哪一层还是好几层——尤其是建大客户、做 toB 业务时，要看它整体架构设计，不能只纠结在某一层。」**

**关键金句**：

1. 「颜值激发荷尔蒙，大模型给他人性。」——AI 陪伴产品成功的本质。

2. 「AI 陪伴产品里，运营玩法占到成功的一半以上。」——技术不是第一性原理。

3. 「不是所有 AI 应用都是为了提效。」——产品定位的多元化。

4. 「AI 师傅的本质是：真人做教研，AI 来授课。」——教育 AI 的成本结构颠覆。

5. 「ChatBI 的核心不是 LLM 本身，而是 NL2SQL 这个增量环节。」——FDE 的工作哲学：找到流程中可被 AI 替代的部分。

6. 「蚂蚁敢开源框架，因为框架不是核心——数据、工具、专家经验才是。」——开源策略的本质。

7. 「做一个 AI 应用不一定从零开始，可以从原有产品里找到可嵌入大模型能力的部分。」——AI 增强 vs AI 原生的战略选择。

8. 「金融行业的特色是：有钱、有数据、IT 强、安全要求高——所以它是大模型创新最积极的行业。」——行业特性的四要素总结。

# 下篇 · 方法论精华

## 一张速查表

| 行业 | 核心产品形态 | 关键方法 | 技术含量 | 运营含量 |
|---|---|---|---|---|
| **泛娱乐** | AI 陪伴（星野、EVE） | 展示层 + 人设层 + 记忆层 + 玩法层 | 可高可低 | 极高（>50%） |
| **教育** | AI 师傅（AI 教学） | 专家主导 + Prompt 工程 + 知识库 | 中等 | 中等 |
| **企业数字化** | ChatBI（NL2SQL） | 原 BI + NL2SQL 增量 | 中等 | 低 |
| **金融** | 投顾知晓珠（多 Agent） | 知识库 + Peer（Plan/Execute/Express/Review） | 高 | 中等 |

## 通用原则

### 原则 1：四层架构思维
所有 AI 应用都可以用「基础设施层 / 模型层 / 中间层 / 应用层」四层定位。FDE/PM 一般落点在中间层或应用层；做大客户要看全栈。

### 原则 2：AI 原生 vs AI 增强
- **AI 原生**：没有 AI 产品就不存在（AI 陪伴、AI 搜索、个人助理）。
- **AI 增强**：在原有软件嵌入 AI 能力（ChatBI、智能编程、智能客服）。

toC 创业选 AI 原生，toB 落地选 AI 增强——这是 UP 主反复暗示的策略。

### 原则 3：产品骨架的四层拆解
任何 AI 应用层产品几乎都能拆成四层：
- **展示层**（形象、界面、声音）
- **逻辑/人设层**（业务规则、角色设定）
- **数据/记忆层**（知识库、用户数据、对话历史）
- **运营/玩法层**（商业化、留存、互动机制）

每一层都可以独立评估 AI 切入点。

### 原则 4：Prompt 拼装的「动静分离」
- **静态信息**（用户基本信息、角色设定）→ 数据库读取 + 模板拼装。
- **动态信息**（情绪、记忆、上下文）→ 专门模型实时提取 + 动态拼装。

每次对话都重新拼装一次，才能做到「千人千面」。

### 原则 5：多 Agent 协同的 Peer 范式
复杂分析任务用四步法：
1. **Plan（计划）**：用框架描述 + 专家知识做计划。
2. **Execute（执行）**：从数据库/工具获取数据。
3. **Express（表达）**：整理、摘要、分析。
4. **Review（评价）**：判断质量，达标才输出。

## 可复用模式

### 模式 1：行业落地的 6 步流程
```
1. 行业分层定位（四层架构）
2. 判断 AI 原生 vs AI 增强
3. 拆产品骨架为四层
4. 拼装提示词（动静分离）
5. 运营玩法定生死
6. 大客户看全栈
```

### 模式 2：AI 陪伴类产品的提示词模板
```
你是【角色名】
陪伴对象：【用户起的名字】
用户基本信息（数据库）：昵称、年龄、城市、职业、兴趣
动态信息（每轮更新）：
  - 关键记忆点（记忆 Agent 提取）
  - 当前情绪（情绪 Agent 检测）
  - 上下文摘要（摘要 Agent 提取）
  - 当前时间/情境
回应要求：温柔自然、像认识很久的朋友
```

### 模式 3：ChatBI 类产品的 Prompt 模板
```
你有一个 {table_name} 表
字段：{field_1}, {field_2}, ...
字段含义：{语义说明}
请基于用户的输入生成 SQL
只能输出 SQL，不能包含其他信息

用户输入：{user_query}
```

### 模式 4：行业黑话处理的 RAG 模式
```
用户原始查询：{user_query}
   ↓
先到知识库检索黑话映射
   ↓
改写查询：补充黑话的具体含义
   ↓
LLM 基于改写后的查询生成最终输出
```

### 模式 5：多 Agent 协同的 Peer 模式
```
Plan Agent（计划）→ Execute Agent（执行）→ Express Agent（表达）→ Review Agent（评价）
                                                                   ↓
                                                              达标 → 输出
                                                              不达标 → 重来
```

### 模式 6：FDE 的「流程增量」思维
不一定要从零做 AI Native 产品。先看原有产品的工作流，找到「可以用 AI 替代的环节」，嵌入 AI 能力即可。

经典案例：
- **ChatBI**：在 BI 流程中嵌入 NL2SQL 环节。
- **AI 编程**：在 IDE 中嵌入代码补全环节。
- **AI 客服**：在客服流程中嵌入智能问答环节。

# 借鉴篇 · 我们能借鉴的点

> 结合王昕业务：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库

### 1. 把所有客户提案先按四层架构定位

**对应业务场景**：企业 AI 客户交付、获客系统的初次提案环节。

**怎么做**：每次面对潜在客户，先问四个问题：
1. 客户的痛点在「基础设施层 / 模型层 / 中间层 / 应用层」哪一层？
2. 客户属于「AI 原生」还是「AI 增强」需求？
3. 客户是否要私有部署？是否要自训模型？
4. 客户的预算是按「项目制」还是「订阅制」？

输出物：一页纸的「四层定位图」+ 一份「是否全栈方案」的判断书。这能让客户立刻感受到你懂他的层级，而不是上来就推销某个产品。

### 2. 推出「企业 AI 落地体检表」作为获客钩子

**对应业务场景**：获客系统、引流型内容。

**怎么做**：基于本章的「行业四层 + 产品四层」框架，做一张可下载的 Excel/Notion 模板「企业 AI 落地体检表」。企业填写：
- 你目前处于信息化 / 数字化 / 智能化的哪一阶段？
- 你的 AI 需求是 AI 原生还是 AI 增强？
- 你的目标产品可以拆成哪四层？
- 哪一层最值得优先做 AI 切入？

填完自动生成「你下一步该做什么」的建议。这张表免费送，作为获客系统的核心钩子，引导企业加微信、约咨询。

### 3. 把 ChatBI 模式封装成「NL2X」行业套件

**对应业务场景**：企业 AI 客户交付的主力产品线。

**怎么做**：基于「ChatBI = 原有 BI + NL2SQL」的思路，扩展到其他领域：
- **NL2SQL**（数据分析）→ ChatBI
- **NL2API**（系统操作）→ ChatOps
- **NL2Code**（编程辅助）→ Copilot
- **NL2Report**（报告生成）→ ChatReport
- **NL2CRM**（客户操作）→ 销售助手

每个套件的核心都是「原有产品 + 大模型增量」，卖的是「流程改造服务」而不是「模型本身」。这非常适合 FDE 团队——交付的是 Prompt 工程 + 集成能力 + 知识库，不是模型训练。

### 4. 用 Peer 范式封装 8895 知识库的问答 Agent

**对应业务场景**：8895 知识库的智能化升级。

**怎么做**：当前 8895 知识库大概率是「关键词检索 + 文档返回」的传统形态。可以用 Peer 模式升级：
- **Plan Agent**：根据用户提问，先规划要查哪些知识库、检索顺序。
- **Execute Agent**：从 8895 知识库 + 外部数据源获取相关内容。
- **Express Agent**：整理、摘要、形成结构化回答。
- **Review Agent**：判断回答质量（是否有幻觉、是否答非所问），达标才给用户。

这样 8895 知识库就从「文档检索工具」升级为「智能问答 Agent」，可以独立卖给企业做内部知识管理。

### 5. 把 AI 师傅的「真人做教研 + AI 来授课」模式卖给教培机构

**对应业务场景**：企业 AI 客户交付（教育行业）。

**怎么做**：AI 师傅的开源模式天然适合做 SaaS 卖给教培机构、K12 学校、企业内训部门。具体交付：
- **第一阶段**：教研团队帮客户把课程内容结构化（真人做教研）。
- **第二阶段**：Prompt 工程团队把课程内容转为 AI 提示词（真人做工程）。
- **第三阶段**：私有化部署到客户的服务器（满足数据合规）。
- **第四阶段**：运营陪跑 3 个月，教会客户团队使用和迭代。

按「项目制 + 年度服务费」收费，单客户客单价 50-200 万。

### 6. 把运营玩法层的经验沉淀为「AI 产品运营手册」

**对应业务场景**：内部知识沉淀、对客户的增值服务。

**怎么做**：UP 主反复强调「运营玩法 > 技术」，这是很多 AI 产品经理忽视的点。建议把以下经验沉淀为标准化手册：
- **用户增长玩法**：每日限制、付费解锁、推荐裂变。
- **用户留存玩法**：主动唤起、个性化记忆、专属人设。
- **商业化玩法**：订阅制、虚拟道具、永久记忆购买。

这本手册可以作为 FDE 交付时的「附加服务」送给客户，提升服务感和复购率。

### 7. 金融行业大客户打法：全栈方案 + 私有部署

**对应业务场景**：金融行业（银行、券商、保险）的客户交付。

**怎么做**：基于北京银行案例的全栈架构，做金融客户的「全栈方案 PPT」：
- **基础设施层**：算力选型（华为昇腾 / 寒武纪 / 英伟达）。
- **模型层**：是否需要自训金融大模型？还是用 DeepSeek 等开源基座微调？
- **中间层**：知识库构建、Agent 编排平台。
- **应用层**：智能客服、投顾助手、风控 Agent、会议纪要。

每个层级都要给出至少 2 个备选方案和报价区间。金融客户最在意的是「你懂全栈」和「你能私有化部署」。

### 8. 把行业黑话处理做成 RAG 标准模块

**对应业务场景**：所有 toB 客户的知识库建设。

**怎么做**：几乎每个行业都有大量黑话（金融的 C9、电商的 SKU、教育的一级教师）。把 RAG 黑话处理做成标准模块：
- **第一步**：客户整理行业黑话表（Excel）。
- **第二步**：导入向量数据库。
- **第三步**：所有 Agent 在生成回答前先检索黑话表。

这个模块可以独立打包卖，单价低、易复用，是走量的好产品。

### 9. 用「伦理底线 + 免责声明」框架降低合规风险

**对应业务场景**：AI 陪伴、心理咨询、医疗咨询等敏感行业。

**怎么做**：UP 主提到星野、EVE 这类产品都有「底线 + 免责」的设计。建议 FDE 在交付这类产品时，标准交付物包含：
- **伦理底线清单**（不能说的话、不能做的事）。
- **免责声明模板**（用户协议、隐私政策）。
- **人工审核机制**（关键词过滤、AI 反垃圾）。
- **应急关停预案**（出现问题立即下架某个角色）。

这能让客户安心，也是 FDE 体现专业性的关键。

### 10. 用「知识库 + Peer 多 Agent」封装企业级分析师助手

**对应业务场景**：金融、法律、咨询行业的中高端客户。

**怎么做**：投顾知晓珠的 Peer 范式是高度可复用的。可以把它封装成「分析师助手模板」，卖给不同行业：
- **金融版**：投顾分析师助手（参考蚂蚁投顾知晓珠）。
- **法律版**：法律分析师助手（合同审查、案例检索）。
- **咨询版**：行业研究助手（市场分析、竞品研究）。
- **医疗版**：医学研究助手（论文综述、病例分析）。

每个版本的核心差异是「知识库 + 工具链」，框架完全复用 Peer 范式。这是 FDE 团队最高客单价的产品线，单项目可以做到 500 万以上。
