# 上篇 · 书籍内容

## 引子：为什么要有 Agent

当我们直接调用大语言模型（LLM）的原生 API 时，看到的是一个非常「朴素」的过程：给一段输入，模型经过内部大量参数运算后返回一个输出。黑盒内部虽然跑着海量知识与推理，但用户感知的只有「Input → Output」一条直线。

构建一个真正能落地的 AI 应用，往往不能只靠这种「一问一答」。举一个生活例子：老板让你把一颗钉子钉进墙里。**光靠脑子想，钉子不会进墙**。你得先想到「需要一把锤子」，再想到「要先固定钉子，再挥锤」。这个过程里，除了「思考」，还有「记忆」「规划」「工具」「行动」四件事在协同。

Agent（智能体）就是把人类这种「带工具、带规划、带记忆」的思维方式**工程化地量化**给 LLM。它的本质是一段包裹在大模型外面的运行逻辑，让 LLM 不再只是「回答问题」，而是「理解目标 → 拆解任务 → 调工具 → 观察反馈 → 修正规划 → 完成目标」的完整执行体。

> Agent 不是替代 LLM 的新物种，而是**让 LLM 的能力被有序释放的工程框架**。这是这一章的根。

## 一、Agent 是什么：四大组件 + 决策闭环

### 1.1 四大组件

Agent 在结构上以一个核心引擎（通常是 LLM）为中枢，对外伸出四个必备组件：

| 组件 | 英文 | 含义 |
|---|---|---|
| 记忆 | Memory | 短期上下文 + 长期持久化偏好/历史 |
| 规划 | Planning | 把大任务拆成子任务，决定先干啥后干啥 |
| 行动 | Action | 当前循环真正要执行的那一步动作 |
| 工具 | Tools | LLM 自身不具备、靠外部接口补齐的能力 |

四者缺一不可。一个没有记忆的 Agent 无法承接多轮上下文；没有规划就只能「想到啥说啥」；没有行动等于零；没有工具就拿不到实时信息、算不动复杂数字、操作不了真实系统。

### 1.2 决策闭环：感知 → 规划 → 行动 → 观察

Agent 处理任务的最小循环由四个动作组成：

1. **感知（Perception）**：从外部环境接收输入（用户的 prompt、传感器数据、文件等）。
2. **规划（Planning）**：交给 LLM 拆解成若干子任务，得到 N 步执行计划。
3. **行动（Action）**：执行当前那一步的子任务，可能调用工具。
4. **观察（Observation）**：根据上一步的反馈判断「是否 OK」。OK 就进入下一步；不 OK 就**重新规划**（Replan）相关步骤。

循环直到所有子任务都被判定完成，才对外输出最终答案。

> **常见坑**：很多新人以为 Agent 就是「让 LLM 自己用工具」，结果工具一调就崩——问题往往出在「观察」环节没设计好。**没有明确的成功判据，Agent 就不知道什么时候算完成、什么时候该重做**。

### 1.3 一个具象案例：智能家居调温

把上面四步套到一个真实的智能家居场景里：

- **需求**：用户说「我有点冷，能不能把温度调高一些」。
- **感知**：语音识别 + 情感分析，识别出「用户嫌冷、要升温」。
- **规划**：① 读取当前室内温度；② 结合用户历史偏好（如去年设 20℃，今年偏好 23℃）决定目标温度；③ 调整温度设置并通知用户。
- **行动**：系统检测到当前 20℃，按偏好调至 23℃，语音播报「已调至 23℃，请稍候」。
- **观察**：若用户反馈「刚刚好」，任务完成；若仍嫌冷，则触发 Replan，可能改成逐度递增（23→24→25），也可能一次性跳到 25℃。

这正是 Agent 与纯 LLM 的关键差异——**LLM 没有手，Agent 装上了手**。

## 二、规划（Planning）：拆解与反思

规划是 Agent 的「大脑」，决定整个系统能不能做对复杂任务。它由两块能力组成：**子任务拆解**与**反思与改进**。

### 2.1 子任务拆解的四种思维模式

| 模式 | 思路 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| 标准 Input→Output | 不要求逐步思考 | 调用成本最低 | 复杂任务几乎做不对 | 单步事实问答 |
| 思维链（CoT, Chain of Thought） | 让模型「Let's think step by step」 | 显著提升推理准确率 | 线性思维，单链易错 | 中等复杂推理 |
| 自洽性（Self-Consistency） | 多条思维链投票取多数 | 比单链更稳 | 「真理常在少数人手中」，存在多数派暴政 | 能多次采样的题目 |
| 思维树（ToT, Tree of Thoughts） | 每步推理出多个分支，用启发式评分搜索 | 准确率最高 | Token 消耗最大 | 复杂决策、博弈题 |

**思维树实战例子——24 点游戏**：给四个数字（5、8、11、13）算 24。

- 目标：4 个数 → 3 个数 → 2 个数 → 1 个数 = 24。
- 每一步的「行动」有 4 种可能：加、减、乘、除。
- 每一步对每条分支打 20 分（满分 60），用 **BFS 或 DFS** 探索。
- 累计得分达到 60 的分支即为答案。

用标准 Prompt 让模型算 5、8、11、13，多数 LLM 会给出错误算式（如 5×11÷13×8≈24，但这是凑出来的小数巧合）。改成 ToT 框架后，会逐步收敛到正确路径，例如 13−5=8 → 11−8=3 → 8×3=24。这是「**用框架激活模型潜力**」最经典的范例。

> **常见坑**：ToT 不是银弹，它的 token 消耗是 CoT 的数十倍。生产环境里只在「高价值、低频次」的决策节点用 ToT，日常对话继续走 CoT。

### 2.2 反思与改进：把 ReAct 当主菜

光有「拆解」不够，模型拆完之后还要「回头看」。这一步主要靠 **ReAct**（Reason + Act）框架：

```
Question → Thought → Action → Observation → Thought → Action → ... → Final Answer
```

- **Thought（思考）**：基于当前观察，决定下一步该干什么。
- **Action（行动）**：执行一步操作，最常见的就是调工具（search、calculator、code interpreter…）。
- **Observation（观察）**：拿到 Action 的结果，把它写回上下文，再进入下一轮 Thought。

ReAct 与「仅推理」「仅行动」相比，核心优势是**结合内部推理与外部验证**：只推理容易闭门造车；只行动容易被海量外部资料淹没，不知道筛哪个。ReAct 让模型**先想清楚要什么，再去找，找回来再验证**。

举例：「100 美元能在纽约买几束玫瑰？」

- 仅推理：模型凭印象给个离谱答案。
- 仅行动：调搜索引擎，搜出一堆电商结果，模型直接堆砌输出。
- **ReAct**：先推理「需要先确定玫瑰单价」，调搜索 → 拿到单价 → 推理「100÷单价 = 束数」 → 输出答案。

> **常见坑**：ReAct 在面对简单任务时反而「过度设计」，多花 token。判断标准——**任务是否需要外部信息验证**？要，就用 ReAct；不要，纯 CoT 就够。

## 三、记忆（Memory）：短期 + 长期

### 3.1 人类记忆的三层映射

Agent 借鉴人类记忆做了三层映射：

| 人类记忆 | 时长 | 例子 | Agent 实现 |
|---|---|---|---|
| 感觉记忆 | 几秒 | 刷到一个美女视频，几秒后想不起她右边是什么 | 大模型上下文里的瞬时 token |
| 短期/工作记忆 | 几分钟到几天 | 背一个电话号码 | 当前会话的容器/列表变量 |
| 长期记忆 | 几分钟到一生 | 初恋的样子 | 持久化存储 + 向量检索 |

注意一个重要区分：**大模型本身的「参数记忆」不等于 Agent 的「记忆机制」**。前者是训练阶段固化在权重里的世界知识，后者是运行时**显式**维护的上下文。LLM 本质是预测模型，没有原生记忆功能，我们只是用上下文工程让它「看起来有记忆」。

### 3.2 短期记忆：容器里的会话上下文

- 实现：把多轮对话写入列表/字典，作为下次调 LLM 时的 `messages` 字段。
- 生命周期：随任务结束清空。
- 典型场景：单次脚本、调试 demo、不需要跨会话的产品试用。

### 3.3 长期记忆：持久化 + 向量数据库

- 实现：按 `session_id` / `user_id` 把对话持久化进数据库；用向量数据库（如 Chroma、Pinecone、Milvus）存储历史问答 embedding，支持相似度检索。
- 常见优化：不必全量存，而是**摘要 + 关键事件**入库，省 token 又保留关键信息。
- 典型场景：客服系统、个人助手、连续多日的项目管理。

> **常见坑**：很多产品把「所有历史对话」无脑塞进 prompt，结果 token 爆表、响应变慢、关键信息被淹没。**该总结就总结，该截断就截断**。

## 四、工具（Tools）：让 LLM 长出手脚

### 4.1 工具的两层分类

- **工具（Tool）**：单一能力的封装。又分两类：
  - **预置工具**：LangChain/LlamaIndex 等框架已经封装好的，如搜索引擎、计算器、代码执行器、文件系统读写。
  - **自定义工具**：业务专属能力，如查 ERP、查 CRM、查知识库 8895、调内部 API。
- **工具集（Toolkit）**：一组配套 API 的集合。典型代表是 LlamaIndex 的各种 `Tool`，可以一键挂载。

### 4.2 工具的本质：补齐模型权重之外的「新鲜信息」

模型权重在预训练之后就难以修改，但现实世界的信息（天气、股价、企业内部数据）每天都在变。工具就是让 Agent **绕过权重限制**，拿到这些动态或私有信息。

> **常见坑**：用搜索工具去查企业内部数据——结果是搜不到公司内部资料的。**生产环境的工具集应该对接内部 API/RAG，而不是公网搜索**。

## 五、五大认知框架横向对比

这是本章的技术密度峰值区。UP 主把当前主流的 Agent 认知框架拆成五个，逐个讲清适用场景。

### 5.1 Plan-and-Execute（计划并执行）

- **核心思路**：先把任务一次性拆成 N 个子任务，然后**依次执行**；执行过程中观察每个子任务的反馈，需要时 Replan。
- **关键差异**：与 ReAct 不同的是——**规划发生在循环之前**，而不是边执行边规划。
- **适用场景**：项目管理、多步决策、需要全局视角的复杂任务。
- **代码要点（基于 LangChain）**：
  - 导入 `PlanAndExecute` agent executor。
  - 加载 `load_tools` 与自定义工具。
  - 通过 `agent_executor.invoke({"input": ...})` 启动。
- **实战例子**：问「在纽约 100 美元能买几束玫瑰」。模型先 Replan 出 ① 查纽约玫瑰批发价 ② 计算可买束数，然后执行。模型能力弱时仍可能出错（如算出 0.0679 束），但思路是对的——**框架对了，错误可以通过换更强模型 / 更好 prompt 修正**。

> **常见坑**：Plan-and-Execute 依赖**一次性规划的质量**。如果第一步规划就是错的，整个执行链就废了。

### 5.2 Self-Ask（自问自答）

- **核心思路**：允许模型**对自己提出后续问题**，并自己回答，直到拼出完整答案。中间需要时调用搜索工具补强。
- **适用场景**：需要「验算」的题目——解题步骤都对，但中间数字算错。
- **实现**：LangChain 提供了 `SelfAskWithSearchAgent`，搭配 `serpapi` 等搜索工具。需要 `SERPAPI_API_KEY`。
- **典型例子**：问「上一届美国总统是谁？」模型先答「拜登（2021 就任）」→ 自问「他之前的总统是谁？」→ 调搜索确认「特朗普」→ 输出最终答案。
- **重要提醒**：Self-Ask **不是通用框架**，只在「自验算能显著降低错误率」的场景下用。

### 5.3 Thinking and Self-Reflection（思考与自我反思）

- **核心思路**：模型每走一步就自我评估，若认为本步不对，则**倒回去重做本步**，而不是直接进入下一步。
- **关键差异**：与 ReAct 的「观察 → 决定下一步」不同，本框架是「**观察 → 决定本步要不要重做**」。
- **适用场景**：复杂决策、模拟推演、需要多轮校准的任务。
- **实现形式**：本质是 LangChain 里的 LangSmith 调试机制，配合 `Nodes` 节点管理，可以监控每一步推理。
- **进阶玩法**：把若干步的思考**汇总归纳**后再判断，而不是一步一反思。

> **常见坑**：和「传话游戏」一样，**反思步骤越多，错误越容易累积**。每多一步反思，就多一次「画变鸭」的风险。要控制反思频率。

### 5.4 ReAct（Reason + Act）

- **核心思路**：Thought → Action → Observation → Thought → ... → Final Answer。**边推理边行动**。
- **适用场景**：需要实时外部信息验证、一步步逼近答案的任务。
- **实现**：LangChain 的 `create_react_agent` + `AgentExecutor`。
- **实战例子**：问「中国玫瑰花进价 + 加价 5% 该怎么定价？」
  - Thought：拆成两步——先找进价，再算 5% 加价。
  - Action 1：调搜索，拿到批发价（不同来源差异大，模型取中位数 30 元/束）。
  - Observation 1：得到 30。
  - Thought：调用计算器算 30×1.05。
  - Action 2：调 calculator，拿到 31.5。
  - Final Answer：建议定价 31.5 元/束。
- **关键洞察**：同一问题每次运行结果不同（搜索工具返回的内容不同），这就是 LLM 的**预测随机性**。生产里要靠**固定数据源 + 评分机制**来压住随机性。

### 5.5 ReAct + RAG（LlamaIndex 实现）

这是 **5.4 的企业级升级版**：把搜索工具换成**企业自己的知识库检索**。

- **核心思路**：用 LlamaIndex 把公司财报、合同、产品手册做成向量索引，挂载到 ReAct agent 上作为两个独立 Tool（如 `tool_a` 查 A 公司财报，`tool_b` 查 B 公司财报）。
- **实现步骤**：
  1. 用 `SimpleDirectoryReader` 把 PDF/财报读入 documents。
  2. `VectorStoreIndex.from_documents` 构建索引，可持久化到本地或向量数据库。
  3. 把两个索引包装成两个 QueryEngineTool，描述清晰（A 公司财务 / B 公司财务）。
  4. 用 LlamaIndex 的 `ReActAgent.from_tools` 创建 agent，`agent.chat()` 启动对话。
  5. 提问：「比较 A、B 两家电商公司销售情况」 → agent 自动选 tool_a → 选 tool_b → 综合分析。
- **关键洞察**：LlamaIndex 在 RAG 方面**比 LangChain 更专注**，抽象略多但干预空间也更大；LangChain 生态更丰富、上手更快。**两者内核相似，按场景选**——需要细致数据干预选 LlamaIndex；需要丰富生态选 LangChain。

> **常见坑**：ReAct + RAG 看似万能，但存在两大风险——① **幻觉**：模型可能在「工具没返回数据」时硬编一个；② **检索粒度**：文档切得太大就找不到细节，切得太细又丢失上下文。**配合人工 review + 严格 prompt**，别让模型裸跑。

## 六、Agent 整体能力地图与选型指南

把上述五个框架横向拉到一张图，方便选型：

| 框架 | 规划位置 | 是否依赖工具 | 复杂度 | 适用任务 |
|---|---|---|---|---|
| 纯 CoT | 无显式规划 | 否 | 低 | 单步推理 |
| Plan-and-Execute | 一次性 | 可选 | 中 | 多步项目管理 |
| Self-Ask | 边问边解 | 是（搜索） | 中 | 需要验算的题目 |
| Self-Reflection | 边做边反思 | 可选 | 中高 | 复杂决策校准 |
| ReAct | 边做边规划 | 强依赖 | 中 | 需要实时外部信息 |
| ReAct + RAG | 边做边规划 | 强依赖 | 高 | 企业知识库问答 |

**选型口诀**：

- 任务简单 → CoT。
- 任务多步但不需要实时信息 → Plan-and-Execute。
- 任务需要实时外部验证 → ReAct。
- 任务需要反复校准 → 加 Self-Reflection。
- 任务基于企业内部知识 → ReAct + RAG（LlamaIndex）。
- 任务需要验算 → Self-Ask。

## 结论 / 金句

1. **Agent 的本质是「让 LLM 的能力被有序释放的工程框架」**——它不是替代 LLM，而是 LLM 的「工程化外壳」。
2. **决策闭环四件套**：感知 → 规划 → 行动 → 观察。**观察缺失是 Agent 最常见的隐形 bug**。
3. **规划靠两件事**：拆解（CoT/Self-Consistency/ToT）+ 反思改进（ReAct/Self-Ask/Self-Reflection）。
4. **记忆分两层**：短期靠容器，长期靠持久化+向量数据库。**该总结就总结，别让 prompt 爆炸**。
5. **工具是补齐权重盲区**：实时信息、内部数据、复杂计算都靠工具。**搜索工具不等于万能工具**。
6. **框架选型看场景**：复杂度从低到高依次为 CoT → Plan-and-Execute → Self-Ask → Self-Reflection → ReAct → ReAct+RAG。

# 下篇 · 方法论精华

## 一张速查表

| 概念 | 一句话定义 | 关键 API/组件 | 易错点 |
|---|---|---|---|
| Agent | 包裹 LLM 的工程化执行体 | LangChain Agent / LlamaIndex ReActAgent | 把它当成「新物种」，忽视它只是 LLM 的外壳 |
| 决策闭环 | 感知 → 规划 → 行动 → 观察 | AgentExecutor 循环 | 没有「观察」的成功判据，循环不知道何时停 |
| 规划 | 拆解 + 反思 | CoT / ToT / ReAct | 把 CoT 当万能解，复杂任务单链不够稳 |
| 思维链 CoT | 强制模型 step-by-step | `Let's think step by step` | 适合中等任务，复杂题仍易错 |
| 自洽性 | 多链投票取多数 | 多次采样后取众数 | 「真理在少数人手中」，存在多数派暴政 |
| 思维树 ToT | 每步多分支 + 启发式评分 | BFS/DFS 搜索 + 评分机制 | token 消耗巨大，仅适合关键决策 |
| 记忆 | 短期上下文 + 长期持久化 | LangChain Memory / VectorStore | 无脑全量存导致 token 爆表 |
| 工具 | 补齐权重之外的能力 | `load_tools` / 自定义 Tool | 用公网搜索查内部数据 |
| Plan-and-Execute | 一次性规划后执行 | `PlanAndExecute` agent executor | 首次规划错误会带歪整条链 |
| Self-Ask | 自问自答 + 搜索验证 | `SelfAskWithSearchAgent` | 不通用，仅适合需要验算的场景 |
| Self-Reflection | 每步自评，必要时回退 | LangSmith Node 监控 | 反思步骤过多会导致错误累积 |
| ReAct | Thought→Action→Observation 循环 | `create_react_agent` | 简单任务上过度设计，浪费 token |
| ReAct + RAG | 把搜索换成企业内部检索 | LlamaIndex ReActAgent + Tool | 文档切分粒度直接影响检索质量 |

## 通用原则

1. **先想清楚再让模型拆**：Agent 不是「让模型自己想」，而是**用工程框架把人类思考过程显式化**。
2. **观察环节必须有判据**：每个 Action 后都要明确「什么算成功」，否则 Agent 永远不知道何时停。
3. **框架服务于场景，不是炫技**：简单任务硬上 ReAct 是浪费；复杂任务只用 CoT 是偷懒。
4. **工具即数据通道**：工具集的设计要服务于业务数据流（内部 API / 知识库），而不是堆功能。
5. **记忆要会剪枝**：长期记忆不是「全量日志」，而是「摘要 + 关键事件」。
6. **框架对了，错误通过换更强模型修正**：Plan-and-Execute 算错玫瑰价格，不是框架错，是模型/数据需要升级。

## 可复用模式

### 模式一：决策闭环四元组

任何 Agent 系统都可以拆成这四个动作的循环：

```
SENSE → PLAN → ACT → OBSERVE
  ↑                       │
  └───────────────────────┘
```

落地时为每个动作写明**输入**、**输出**、**成功判据**。

### 模式二：规划双轨

任何复杂任务都同时需要两条规划路径：

- **静态规划**：任务启动前一次性拆好的子任务列表。
- **动态规划**：执行中根据 Observation 触发的 Replan。

### 模式三：工具分层

工具按使用频次和数据敏感性分三层：

- **第一层**：高频通用工具（计算器、搜索、代码执行）。
- **第二层**：业务通用工具（数据库查询、API 调用）。
- **第三层**：业务专属工具（8895 知识库、企业 ERP、CRM）。

### 模式四：RAG + ReAct 标准配方

把企业内部知识库挂到 ReAct agent 上，是当前最主流的企业级 Agent 范式：

1. 文档 → chunks → embedding → 向量库（持久化）。
2. 把每个向量索引包成 Tool，描述清晰。
3. `ReActAgent.from_tools` 装载。
4. 给 agent 一个明确的 system prompt 约束行为边界。
5. 配合人工 review + 日志回放做质量监控。

### 模式五：框架选型决策树

```
                ┌─ 简单事实问答 → CoT
任务复杂度 ────┤
                └─ 复杂任务 ──┬─ 不需外部信息 → Plan-and-Execute
                              │
                              ├─ 需实时外部信息 → ReAct
                              │
                              ├─ 需反复校准 → ReAct + Self-Reflection
                              │
                              └─ 需企业内部知识 → ReAct + RAG
```

# 借鉴篇 · 我们能借鉴的点

> 结合王昕业务：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库

## 1. 客户交付项目启动模板：四元组决策闭环

**对应场景**：企业 AI 客户交付项目启动会议。
**怎么做**：每次启动会输出「感知（客户需求）→ 规划（拆分子任务）→ 行动（每周交付）→ 观察（客户反馈）」四元组工作流图，明确每个阶段的成功判据（如「客户签字确认需求文档」才算感知完成）。这样 Agent 项目就有了一张可对照执行的流程图。

## 2. 规划双轨：让项目计划既稳又活

**对应场景**：FDE 在客户现场做项目管理。
**怎么做**：交付前用静态规划产出 WBS 表格（一次拆到位）；执行中用动态规划处理变更（每周 Replan）。建议在项目管理系统里同时维护「主计划」和「变更日志」两张视图，规避 Plan-and-Execute 的「首错带歪整链」风险。

## 3. 短期记忆 → 长期记忆：客服场景的对话沉淀

**对应场景**：企业客服系统的多轮对话管理。
**怎么做**：把所有客服会话短期上下文先存到 Redis（短期记忆）；按 `session_id` 摘要后写入 8895 知识库（长期记忆）。下次同用户复访时，先从 8895 召回历史摘要，再叠加当前会话上下文，可显著提升个性化服务能力。

## 4. 工具分层：在 8895 知识库里挂三档工具集

**对应场景**：8895 知识库的 Agent 化升级。
**怎么做**：
- 第一档（通用）：计算器、SQL 执行器、HTTP 调用。
- 第二档（业务通用）：客户档案查询、订单查询、合同查询。
- 第三档（业务专属）：行业研报库、企业资质库、合规审查库。
**避免**：把 8895 直接当搜索用——它本质是结构化知识库，应该挂 API 而不是丢 prompt。

## 5. Self-Ask 验算机制：合同条款核对

**对应场景**：法务/合规场景下的条款核对。
**怎么做**：让 Agent 给出条款解读后，强制触发 Self-Ask——「这一条援引的法条是否正确？」「罚款比例是否合规？」每个自问都调一次法条库检索。**适合条款多、容错低的场景**，不要在所有对话里全开。

## 6. ReAct + RAG：8895 知识库的标准配方

**对应场景**：把 8895 知识库包装成企业级问答 Agent。
**怎么做**：
1. 把 8895 现有文档按「客户档案 / 项目案例 / 产品手册 / 合规审查」分类，分别构建向量索引（LlamaIndex）。
2. 每类索引包成一个 Tool，描述要清晰（名称 = 「8895-客户档案查询」，描述 = 「用于查询客户基本信息与历史合作」）。
3. 用 LlamaIndex 的 ReActAgent 装载所有 Tool。
4. System prompt 约束：「仅在 8895 知识库范围内作答，未检索到时明确告知。」
5. 配套：日志全量留痕 + 关键答案人工 review。
**这是企业级 Agent 落地的标杆配方**，值得在每个交付项目里复用。

## 7. 思维树 ToT：复杂报价/方案的评审

**对应场景**：复杂项目报价（涉及多种计费方式 + 折扣 + 风险溢价）。
**怎么做**：把报价拆成多条 ToT 分支（如「按人头计费」「按项目计费」「按效果计费」），每条分支打 20 分（成本可控性 / 客户接受度 / 利润空间 / 风险），累计得分最高的方案胜出。**适合高价值、低频次的决策**，日常小单不必这么重。

## 8. Self-Reflection：交付物的多轮自检

**对应场景**：FDE 交付物（PRD、调研报告、实施方案）的内部 review。
**怎么做**：让 Agent 先产出 V1，再触发 Self-Reflection——「这一段是否引用了最新数据？」「这一条建议是否考虑了客户的行业限制？」每问一次就倒回去重写对应段落。**反思 2~3 轮即可**，超过 5 轮容易出现「越改越偏」。

## 9. 框架选型决策树：FDE 工具箱

**对应场景**：FDE 在客户现场被问「我们该用哪个 Agent 框架？」
**怎么做**：直接打印上面那张决策树图（模式五），10 秒判断。客户问题简单 → CoT；要实时数据 → ReAct；要内部知识 → ReAct+RAG。**永远不要为了炫技上最复杂的框架**。

## 10. Agent 质量监控三件套：日志 + 评分 + Replay

**对应场景**：所有交付项目的 Agent 质量保障。
**怎么做**：
- **日志**：用 LangSmith 把每次 ReAct 的 Thought/Action/Observation 全量留痕。
- **评分**：每个 Final Answer 走「相关性 / 准确性 / 完整性」三维评分，定期人工抽样校对。
- **Replay**：出问题时把当时的 prompt + 工具调用 + 模型版本一并回放，快速定位是 prompt 错、工具错还是模型错。
**这是企业级 Agent 不可省的「运维三件套」**。

## 11. 获客系统的 Agent 化：用 ReAct 替代表单机器人

**对应场景**：获客官网的智能客服。
**怎么做**：把现有 FAQ 匹配升级为 ReAct Agent——Thought 判断用户意图 → Action 调工具（产品手册检索 / 案例库检索 / 留资接口）→ Observation 验证回答质量 → 不满意时 Replan。**ReAct 比传统 FAQ 灵活得多**，尤其能处理「我这个行业能不能用你们的方案」这类组合问题。

## 12. FDE 的 Prompt 工程心法：观察环节的判据设计

**对应场景**：FDE 写 Agent 的核心 prompt。
**怎么做**：**每个 Action 后必须设计「观察判据」**——「判断答案是否引用了 8895 知识库」「判断数字是否来自工具而非模型硬编」。把判据写进 prompt 里，让模型自己「质检」，再触发 Replan。**这是从「能动」到「动对」的关键一步**。
