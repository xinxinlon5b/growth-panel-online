## 上篇 · 书籍内容

### 引子：AI Agent 从概念到落地，要闯过的三道关

前面的章节里我们已经讲清楚了 Agent 是什么、它和大模型、传统自动化之间的本质差别。本章进入实操环节：要真正把一个 Agent 跑起来、在客户那里产生价值，必须打通三道关——**会做计划、会记东西、会用工具**。这是任何 Agent 系统的能力骨架，缺一不可。

当单 Agent 的能力堆叠已经触顶的时候，还要学会**多 Agent 协同**——让多个角色化的智能体分工合作，解决"单点能力拼不过一个超大模型"的瓶颈。本章以吴恩达（Andrew Ng）2024 年提出的 **Agentic System 四象限**为主线，用阿里 1688 的 AI 采购助手作为商业化样本，再用一个轻量但效果惊人的翻译工作流作为可复用的协同样板。

UP 主在直播里反复强调一句话，本章把它放到引子最前面：**"工作流越详细，效果越好。"** 这是 AI Agent 落地最反直觉但也最值钱的一条经验。

### 逐点精读

### 一、计划能力（Planning）：从 PDCA 到原生推理

#### 1.1 PDCA 循环与 Agent 的 Plan 能力同源

计划能力的第一层地基其实是管理学经典——**PDCA 循环**（Plan-Do-Check-Act：做计划 → 执行 → 检查差异 → 基于差异再处理并更新计划）。这条循环在 Agent 里被完整复刻：让大模型先做计划，再执行，再回头比对执行结果和计划的差异，最后基于差异调整下一轮计划。

它并不复杂，但很多产品经理会把 Agent 想成"问什么答什么"的对话工具。一旦你的客户场景涉及**多步骤、有依赖、有分支**，就必须把 Plan 这一步显式拆出来，否则大模型大概率会"漏步"。

**怎么做**：在 Agent 系统设计文档里，先画一条 PDCA 循环图，把每个阶段对应的提示词模板、工具调用、状态变量明确出来，再交给工程团队实现。

**工具/模型**：GPT-4、Claude 3.5/3.7、DeepSeek-R1；Dify / LangChain 等工作流编排框架。

**AI 产品经理关注维度**：任务的颗粒度（拆到多细）、计划的回滚机制（计划错了怎么回到上一步）、Check 环节的判定标准（什么算"执行完成"，什么算"需要调整"）。

#### 1.2 早期 AI 的"提示词式计划"

在大模型还没有强推理能力的年代，工程师用一个朴素但极有效的提示词技巧逼它先做计划——**"请一步一步来"（Step by Step）**。这一句话会触发模型在生成最终答案之前，把中间变量、推理步骤、子目标先列出来，从而显著提升复杂问题的正确率。

UP 主在 GPT-4 上举了一个早期演示：让模型直接算一道数学题会算错，但只要在提示词里加一句"请一步一步来"，它就会先列出中间变量、把推导过程写出来，最后给出正确答案。

更进一步的做法是让模型按"理解问题 → 制定计划 → 逐步执行 → 输出答案"四步走。这个四步法在 GPT-4 时代就已经是 Agent 设计的标准动作。

**怎么做**：在 Prompt 模板里固定"先复述问题 → 列中间变量 → 列子步骤 → 逐项执行 → 给出结论"五段式结构。

**工具/模型**：任意 LLM 都适用，弱模型效果提升更明显。

**AI 产品经理关注维度**：提示词模板的可复用性（不同业务能不能套同一套模板）、Token 消耗（多步输出会显著增加成本）。

#### 1.3 DeepSeek-R1 带来的原生规划

提示词式规划有两个局限：依赖模型"听话"，并且会显著增加 Token 消耗。**DeepSeek-R1 这类推理模型**把规划变成了模型的原生能力——你不再需要写"请一步一步来"，模型会自己先"思考"一大段注意事项、用词要求、认知对齐（例如"用小学生能理解的比喻"），再输出答案。

UP 主演示了同样的"小学生日记"任务：GPT-4 时代需要人作为评审者指出"形容词不够丰富"，模型才能改进；DeepSeek-R1 不需要任何提示，自己在思考链里就会列出"用词要符合小学生认知、要用比喻"等要求，相当于把人类评审提前做完。

**怎么做**：当业务涉及复杂推理（多步数学、多条件决策、长链条规划）时，直接选用推理模型，不要再用长提示词硬压弱模型。

**工具/模型**：DeepSeek-R1、OpenAI o1、Claude（带 thinking 的版本）。

**AI 产品经理关注维度**：模型能力评估（哪类任务必须用强推理模型）、Token 成本（推理模型的思考链很长，成本是普通模型的 3-5 倍）、延迟（推理模型响应时间更长，需要在 UX 上做兜底）。

#### 1.4 Reflection（反馈）：人帮 AI 做迭代

计划能力的另一面是 **Reflection（反馈）**。UP 主演示了"小学生写日记"的三轮迭代：让 GPT-4 写日记 → 人作为评审者指出"形容词不够丰富" → 模型基于反馈改进。这其实是把 PDCA 中的 Check 与 Act 步骤**人工化**了。

到了 DeepSeek-R1 时代，反馈这一动作开始内化为模型自发的"思考链"——它自己会先列出注意事项，类似于把人类评审要做的事提前做完。

**反馈机制的两种实现**：
- **人工反馈（HITL, Human-in-the-Loop）**：人工评审 AI 输出，AI 改进。稳定但慢、成本高、不可扩展。
- **模型自评（Self-Critique）**：让模型自己评审自己的输出。快、可扩展，但需要强模型支持，且自评结果不一定可靠。

**怎么做**：在 Agent 系统里设计"反馈节点"——既可以是人工审核（关键场景如合规、风控），也可以是模型自评（批量场景如内容生成）。

**AI 产品经理关注维度**：反馈频率（每轮反馈 vs 关键节点反馈）、反馈成本（人工 vs 自评）、反馈信号设计（什么样的反馈能让模型改进）。

### 二、记忆能力（Memory）：短期 + 长期

#### 2.1 短期记忆：上下文窗口

短期记忆本质就是大模型的 **Token 上下文**。Agent 在对话中产生的所有用户问句、模型回复、工具调用结果，都会被放进这个窗口，构成"短期记忆"。

在 Dify 这类低代码平台里，模型节点上的"记忆窗口"配置项决定短期记忆的容量上限。例如设为 10 轮，意味着 Agent 会把最近 10 轮对话全部塞进上下文，但不会在 UI 上展示。用户可以让 Agent 记住"我叫何同学"这件事撑 10 轮，超过就遗忘。

**短期记忆的取舍要点**：
- **轮数越大，记忆越久，但 Token 消耗越大、成本越高、响应越慢**。
- 经验值一般设在 **10 轮以内**，超过 20 轮就会出现明显的延迟和成本问题。
- 短期记忆适用于**会话级**的连贯性诉求，比如多轮客服、追问式咨询。

**怎么做**：在 Dify 模型节点的"记忆窗口"里设置 5-10 轮；如果是高价值客户场景，可以放宽到 15-20 轮，但要同步监控成本。

**工具/模型**：Dify 的"记忆窗口"配置；任何支持长上下文的 LLM（GPT-4o 128K、Claude 200K）。

**AI 产品经理关注维度**：记忆窗口设置 → 成本预算 → 响应时延三者的平衡；会话结束后的记忆留存（默认不留，需要外挂长期记忆）。

#### 2.2 长期记忆：知识库 + RAG

长期记忆的本质是**外部存储**，理论上近乎无限容量。Agent 不能把整本字典都背下来，但可以在每次任务开始前"查字典"——把相关资料从知识库里取出来，放进短期记忆，再开始工作。

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）模式：把文档灌进知识库，每次会话先去检索相关片段 → 注入上下文 → 让模型基于检索结果回答。

**长期记忆的关键认知**：**长期记忆 ≠ 全量记忆**。它的本质是"检索增强"，而不是"全量预加载"。如果设计成"每次都把整本知识库读一遍"，上下文一定爆。RAG 的检索质量（召回率、排序、切片粒度）才是决定长期记忆效果的关键。

**怎么做**：用 Dify 或 LangChain 搭知识库 → 上传文档 → 系统自动切片 → 每次会话检索 Top-K 片段注入 Prompt。

**工具/模型**：Dify 知识库、LangChain、LlamaIndex；Embedding 模型（如 BGE、OpenAI Embedding）。

**AI 产品经理关注维度**：
- **内容质量**：源文档是否权威、结构化、更新及时。
- **切片策略**：按段落切片、按标题切片、固定长度切片，不同切片策略对召回率影响极大。
- **检索召回率**：每周抽样 20 个高频问题做召回评测，目标 ≥ 85%。
- **更新频率**：业务文档变更后，知识库能否同步更新。

### 三、工具使用（Tool Use）：大模型影响物理世界的桥梁

#### 3.1 工具调用的本质

大模型本身只是一个对话玩具。如果它不能调用外部工具，就只能聊天、不能做事——不能查天气、不能算账、不能订机票、不能画图、不能查订单。

**工具调用（Tool Use）** 就是把"对话能力"转化为"行动能力"的桥梁。模型作为大脑，决定**要不要调用工具、调哪个、参数是什么**；工具作为手脚，真正完成搜索、计算、绘图、订票等物理动作。

工具调用对模型能力有硬性要求：**必须用强模型**（GPT-4o、Claude、DeepSeek-R1）。GPT-3.5、DeepSeek Chat 等弱模型通常不具备稳定的多步工具调用能力。意图识别、参数抽取、错误处理、失败重试，全都依赖模型的强推理能力。

**怎么做**：在 Agent 系统里维护一个"工具库"，每个工具定义清楚：工具名、功能描述、输入参数 Schema、调用示例。模型根据 Prompt 上下文决定调用哪个工具、传什么参数。

**工具/模型**：Dify 工作流、LangChain Tools、OpenAI Function Calling、Claude Tool Use。

**AI 产品经理关注维度**：工具的功能颗粒度（一个工具做一件事，不要大而全）、工具描述的清晰度（描述越清楚，模型调用越准）、工具调用的失败兜底（调用失败后怎么重试或降级）。

#### 3.2 案例：会画画的宠物狗

UP 主在 Dify 上做了一个轻量演示："会画画的宠物狗" Agent。提示词里写明：
- **角色**：单萌（萌系）语气；
- **行为约束**：每次回复必须带表情；
- **触发工具**：当用户请求画画时，调用一个外部图像生成 API。

不挂工具时，模型只能"绕着聊天"，无法出图；挂上工具后，用户说"给我画一只宠物狗"，模型会自动调用图像生成 API 输出图片。

值得注意的是，**这并不是"多模态能力"**——多模态指的是模型能"理解"输入的图片。这里 Agent 输出图片，靠的是它**调用了一个外部工具**，而不是模型自己具备画图能力。本质上是"一个大模型调用另一个大模型（图像生成模型）"。

UP 主特别强调：当用户输入一幅画时，模型能理解是它的多模态能力；当模型输出图片时，那是它调用工具的能力。两者方向不同，要区分清楚。

#### 3.3 Dify 简画版 vs 工作流版

Dify 的**简画版 Agent**把意图分类、工具调用的细节都封装起来了，用户看不到。但**真正实现的时候**，背后有一条这样的链路：

```
用户提问
   ↓
意图分类（分类器节点）
   ↓
   ├── 画画请求 → 调用绘画工具 → 输出图片
   ├── 抽奖请求 → 走抽奖逻辑 → 输出抽奖结果
   ├── 闲聊请求 → 走默认回复
   └── 其他请求 → 走兜底分支
```

这条链路是用 Dify 工作流画的，比简画版复杂，但**更可控、可调、可观察**。UP 主在直播里反复强调：**意图识别是 Agent 的命脉，意图分错了，下游全部跑偏**。意图识别必须用强模型（GPT-4o、DeepSeek-R1、Claude）。

**怎么做**：业务复杂时，强制使用 Dify 工作流；不要被简画版的"快速搭"诱惑——简画版是演示，工作流才是工程。

#### 3.4 工具调用的工程现实

**1. API 授权与成本**：调用外部工具本质上是调用别人的服务，需要服务方授权，并把成本提前充到平台账户。如果每个 Agent 都自己付费调用，成本不可控。

**2. 网络可用性**：Dify 的官方版本面向海外，很多第三方工具因为网络原因在国内不可用。Dify 在国内做了私有化部署，但并未部署所有工具，所以平台里可用的工具集是精选过的。

**3. 意图识别也是大模型**：很多人误以为 Dify 里的"问题分类器"是某种规则引擎，其实它本质也是一个大模型节点，只是用了结构化提示词模板来约束输出格式。**只要你愿意，直接用一个普通 LLM 节点 + 写好的分类提示词，也能完成分类**。

UP 主的金句：**"所有 AI 能力本质上都是大模型 + 提示词，没有例外。"**

### 四、阿里 1688 AI 采购助手案例

#### 4.1 业务背景

UP 主在课程里邀请了阿里巴巴 AI 采购助手的产品经理来分享案例。这个 AI 采购助手是 1688 App 内嵌的 Agent，典型场景：商家问"最近某品类哪些产品卖得最火？某 SKU 的供应商历史评价如何？某商品的近 90 天销售数据？"Agent 会查询 1688 的多源数据后给出答案。

它和前面讲的"会画画的宠物狗"原理上非常像：**上来先做意图识别 → 不同意图走不同处理流程 → 调用不同工具和不同知识 → 输出结果**。差别只在于规模——阿里这个产品背后涉及的数据源、工具、流程数量级要大很多倍。

#### 4.2 架构拆解

从 UP 主描述中可以还原出大致的架构骨架：

```
用户提问（自然语言）
   ↓
[意图识别层]  ← 大模型（GPT-4o / 强模型）
   ↓（分类）
[流程编排层]
   ├── 热销商品查询 → 调商品库 API + 销量统计
   ├── 供应商评价查询 → 调商家库 API + 评价聚合
   ├── 价格趋势查询 → 调订单库 + 时序分析
   ├── 物流时效查询 → 调物流 API + 地理数据
   └── 政策合规咨询 → 检索合规知识库
   ↓
[结果整合层]  ← 大模型
   ↓
最终答复（自然语言）
```

**四层结构**：
1. **意图识别层**：先用大模型把用户的口语化问题分类到具体场景。
2. **流程编排层**：每个场景对应一条独立处理流程，串接若干工具调用与知识检索步骤。
3. **工具与知识层**：每个流程背后挂着 1688 的商品库、商家库、订单库等内部 API，以及行业报告、政策法规等外部知识。
4. **结果整合层**：把多步工具调用与知识检索的结果汇拢到提示词里，让模型生成自然语言答复。

#### 4.3 AI 产品经理启示

- **业务场景驱动设计**：分类的颗粒度不是越多越好，而是要匹配客户的高频场景。1688 商家最常问什么，就先做什么。
- **工作流越详细，效果越好**：UP 主明确点出"工作流越详细、效果越好，越细化越好"。对于复杂业务，宁可多花时间画流程，也不要寄希望于模型"自己悟"。
- **意图分类用强模型**：意图识别这种"分对分错直接决定下游"的环节，必须用最强模型（GPT-4o、Claude、DeepSeek-R1）。弱模型的分类错误会被下游链路放大，最终表现就是"Agent 答非所问"。
- **复杂问题拆到想要的粒度**：当用户问题里包含多个需求（如"查价格 + 查评价 + 查物流"），必须拆成多条业务流并行处理，再汇总。不能指望一个 Agent 一口气答完。

### 五、多 Agent 协同设计

#### 5.1 吴恩达的 Agentic System 四象限

吴恩达在 2024 年 4 月提出了一个更工程化的视角：**不要纠结"什么是 Agent、什么不是 Agent"**——这只是个学术定义问题。他把工程视角下的 Agent 系统拆成四种设计模式，称为 **Agentic System**：

| 模式 | 含义 | 典型场景 |
|------|------|---------|
| **Reflection（反馈）** | 让 AI 基于反馈迭代改进 | 人工评审 AI 输出、AI 自我反思 |
| **Tool Use（工具使用）** | 调用外部工具 | 搜索、计算、API 调用 |
| **Planning（计划）** | 拆解任务、制定计划 | 复杂任务执行 |
| **Multi-Agent（多 Agent）** | 多个角色化智能体协同 | 软件开发、复杂决策 |

这四种模式**两两可以叠加**——多 Agent 系统里每个 Agent 内部也可以用 Tool Use 和 Planning；Reflection 可以叠加在任何一个环节上。一个完整的商业级 Agent 系统，往往是这四种模式的组合，而非单一使用。

UP 主把它和 OpenAI 内部对 Agent 的定义（Plan + Tool + Memory）做了对比：两种定义在 Plan、Tool、Reflection 上有重叠；OpenAI 强调 Memory，吴恩达没单独列；吴恩达单独列了 Multi-Agent，OpenAI 没强调。

**工程视角下的最佳实践**：把两种定义合并——**Plan + Memory + Tool + Reflection + Multi-Agent** 就是完整的 Agent 系统设计语言。

#### 5.2 学术先驱：斯坦福小镇

斯坦福大学的 Generative Agents 研究（俗称"斯坦福小镇"）是早期多 Agent 的代表：在一个虚拟小镇里部署 **25 个 Agent**，每个有独立人格、职业、记忆、社交关系。Agent 之间可以互相交流、形成小团体、传播消息、爆发八卦。研究者观察这些 Agent 在长期"生活"中是否会涌现类似社会行为。

这个项目验证了多 Agent 协同的可行性，但它的目标是学术研究，对工程实践的直接借鉴有限。UP 主推荐的 B 站 UP 主中文版重制把这一研究做成了可观察的游戏，更直观。

**工程意义**：多 Agent 协同在学术上被证明可行，工程上才有了底气去落地 MetaGPT、翻译工作流这类应用。

#### 5.3 MetaGPT：把多 Agent 落到软件开发

更工程化的多 Agent 框架是 **MetaGPT**。它的核心思路是把软件开发流程中的角色全部 Agent 化：

| 角色 | 职责 |
|------|------|
| 老板 | 提需求 |
| 产品经理 | 拆 PRD |
| 架构师 | 出技术方案 |
| 项目经理 | 拆任务、排期 |
| 程序员 | 写代码 |
| QA / 测试 | 验收 |

老板一句话"做一个 XXX 系统"，所有 Agent 按角色分工、相互协作，最终交付一个完整的软件项目。百度等公司也宣称采用了类似的多 Agent 架构来驱动 AI 软件生成（如文心一言的代码生成能力）。

**工程意义**：多 Agent 不再是学术玩具，已经能驱动真实的软件生产流程。

#### 5.4 吴恩达翻译工作流：三 Agent 协同的样板

吴恩达在 Agentic Workflow 论文里给出了一个惊艳的多 Agent 例子——**翻译工作流**。它只用了 3 个 Agent，但效果超过了头部商业翻译产品。

**Agent 1：初次翻译**
- 角色：专业语言学家，专门做"源语言 → 目标语言"的翻译。
- 提示词核心：设定 `source_language` 与 `target_language` 两个变量，专注做"首次翻译"。

**Agent 2：翻译优化（审校）**
- 角色：翻译审校专家。
- 任务：拿到原文 + Agent 1 的翻译后，**不直接做翻译**，而是给出**建设性批评和改进建议**。
- 关键设计：把"翻译"和"评审"分离，避免一个 Agent 既当运动员又当裁判员。

**Agent 3：终稿整合**
- 角色：终稿语言学家。
- 任务：综合初次翻译 + 优化建议，产出最终译文。

UP 主用 **GPT-4o mini**（被戏称"满血版"GPT-4o 的"残血版"）做了演示。三个都用弱模型，但效果依然优于单 Agent 直接翻译，甚至有时超过商业翻译软件。

**真实运行示例 1**：
- 输入："今天晚上觉得很开心"
- Agent 1 输出：`I feel very happy tonight`
- Agent 2 建议：不要用 `I feel very happy`，改用 `I am feeling really happy`，更自然
- Agent 3 输出：`I am feeling really happy this evening`

**真实运行示例 2**：
- 输入："好好学习，天天向上"
- Agent 1 输出：`Study hard and make progress every day`
- Agent 3 输出：`Walk diligently so you can strive for improvement every day`

吴恩达在专门的翻译评测集上做了对比评分，结论是：**三个能力平平的模型，通过精心设计的多 Agent 工作流，可以跑赢一个超强大模型**。这是多 Agent 协同最有冲击力的工程启示。

#### 5.5 多 Agent 设计的工程要点

1. **角色要单一**：每个 Agent 最好只承担一类职责，不要"什么都干"。翻译和审校分开，比一个 Agent 又翻又评更稳定。
2. **交接要显式**：Agent 之间的输入输出必须显式定义（变量、格式、字段），不能"凭感觉"传话。
3. **模型不一定都要最强**：弱模型 + 好工作流 > 强模型 + 烂工作流。但当任务极复杂时，关键 Agent 仍要选强模型。
4. **评测要建基准**：翻译工作流之所以敢说"超过商业产品"，是因为它在专门的翻译评测集上跑过对比。多 Agent 系统一定要有评测闭环，否则无法判断好坏。
5. **不要过度设计**：很多场景单 Agent + 工具调用就能解决，强行上多 Agent 只会增加复杂度和成本。先单 Agent 到顶，再考虑 Multi-Agent。

### 结论 / 金句

1. **Agent 三大核心能力骨架**：计划（Plan）、记忆（Memory）、工具使用（Tool Use），缺一不可。
2. **Agentic System 四象限**：Reflection、Tool Use、Planning、Multi-Agent；商业级系统通常是它们的组合，而非单一使用。
3. **短期记忆 = 上下文窗口；长期记忆 = 知识库 + RAG**。前者管会话内连贯，后者管专业深度。
4. **工具调用必须用强模型**：意图分类、参数抽取、错误处理都依赖强推理；弱模型只能用于执行类节点。
5. **工作流越详细，效果越好**：复杂场景必须落到工作流，不能寄希望于模型"自己悟"。
6. **三个弱模型 + 好工作流，可能跑赢一个超强大模型**——这是多 Agent 协同最有冲击力的工程启示。
7. **一切 AI 能力本质上都是大模型 + 提示词**：所谓的"问题分类器""Agent""工作流"，底层都是同一个东西。
8. **意图识别是 Agent 的命脉**：意图分错，下游全部跑偏；必须用最强模型 + 最详细的分类流程。
9. **多模态 ≠ 多 Agent**：模型能"理解图片"是多模态能力，模型"输出图片"是调用工具能力；两者方向不同，不能混淆。
10. **先单 Agent 到顶，再考虑 Multi-Agent**：不要一上来就堆多 Agent，单 Agent 三件套没打牢，多 Agent 只会更乱。

## 下篇 · 方法论精华

### 一张速查表

| 能力模块 | 子项 | 落地方式 | 工具 / 模型 | AI PM 关注维度 |
|---|---|---|---|---|
| **计划 Plan** | 提示词式计划 | 写"一步一步来"或四步法提示词 | GPT-4 / Claude | 提示词工程能力 |
| **计划 Plan** | 原生推理 | 选具备推理能力的模型 | DeepSeek-R1 / OpenAI o1 | 模型能力评估 |
| **计划 Plan** | 反馈 Reflection | 人工评审 / 模型自评 | LLM + Critic Agent | 反馈频率、成本 |
| **记忆 Memory** | 短期记忆 | 上下文窗口配置（≤10 轮） | Dify 记忆窗口 | 轮数 vs Token 成本 |
| **记忆 Memory** | 长期记忆 | 知识库 + RAG | Dify / LangChain / LlamaIndex | 切片、召回率、更新频率 |
| **工具 Tool** | 搜索 / 计算 | 大模型决定 + 调用 API | GPT-4o / Claude | 意图识别准确率 |
| **工具 Tool** | 图像 / 视频 | 大模型调用生图生视频模型 | DALL-E / 海螺 / 即梦 | 工具授权与计费 |
| **多 Agent** | 角色化协同 | 定义角色 + 显式交接 | MetaGPT / 自建工作流 | 评测基准、协作机制 |
| **评测** | 翻译 / 软件 / 业务 | 基准测试集 | BLEU / 自建评测集 | 效果稳定性 |

### 通用原则

1. **能力分层，逐级堆叠**：先确保 Plan / Memory / Tool 三件套各自可用，再考虑 Multi-Agent 加持。
2. **模型选型看任务，强弱搭配**：分类 / 规划用强模型，批量执行用弱模型省钱；关键 Agent 用强模型，配合 Agent 用弱模型。
3. **所有 AI 能力本质都是 LLM + 提示词**：不要被"分类器""Agent""工作流"这些名词迷惑，底层都是同一个东西。
4. **流程越细，效果越稳**：复杂业务不要寄希望于"AI 自己悟"，把流程画细、画死、画成可观察的中间产物。
5. **评测闭环是底线**：没有评测集，所有"效果好"都是主观感受；多 Agent 一定要对比"多 Agent 流程 vs 单 Agent 直出"的评测结果。
6. **意图识别是命脉**：分类错则全错；用最强模型 + 最详细的分类 Prompt + 充分的 few-shot 示例。
7. **先单 Agent 到顶，再上多 Agent**：单 Agent 三件套没打牢，多 Agent 只会增加复杂度。

### 可复用模式

#### 模式 A：单 Agent 三件套（Plan + Memory + Tool）

- **适用场景**：客服、咨询、轻度助手、单点任务自动化。
- **骨架**：意图识别 → 调用工具 / 检索知识 → 生成回复 → 可选 Reflection 节点。
- **代表**：会画画的宠物狗、阿里 1688 AI 采购助手。
- **模型选型**：意图分类节点用 GPT-4o / DeepSeek-R1；执行节点可用 GPT-4o mini / Claude Haiku 省钱。

#### 模式 B：多 Agent 串行协作（翻译 / 审校）

- **适用场景**：内容生产、翻译、写作、代码生成。
- **骨架**：Agent A 初稿 → Agent B 评审 → Agent C 终稿 → 输出。
- **代表**：吴恩达翻译工作流。
- **关键设计**：Agent 之间职责严格分离（运动员 vs 裁判员），交接用显式变量。

#### 模式 C：多 Agent 角色化协同（软件开发）

- **适用场景**：复杂决策链、跨职能任务、需多视角协作的场景。
- **骨架**：老板 → PM → 架构师 → 程序员 → QA，每步显式交接。
- **代表**：MetaGPT、百度文心代码生成。
- **关键设计**：每个角色有独立 Prompt 和工具集；角色间接口标准化。

#### 模式 D：反思型 Agent（Reflection Loop）

- **适用场景**：内容优化、代码生成、策略调优、需要迭代改进的任务。
- **骨架**：执行 → 自评（或人工评）→ 改进 → 重新执行，直到达标。
- **代表**：GPT-4 写日记 + 人工反馈；DeepSeek-R1 自带的思考链。
- **关键设计**：反馈信号要具体（"形容词不够丰富"比"写得好一点"有效）。

#### 模式 E：意图分类 + 多业务流编排

- **适用场景**：复杂 B 端场景，多业务线、多工具、多知识源。
- **骨架**：意图分类 → N 条业务流（每条挂自己的工具 + 知识）→ 结果整合 → 输出。
- **代表**：阿里 1688 AI 采购助手。
- **关键设计**：分类颗粒度匹配高频场景；业务流之间可复用工具。

## 借鉴篇 · 我们能借鉴的点（王昕业务：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库）

> 王昕业务范围：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库。
> 落地动作按业务场景编号，每条说清「对应哪个业务场景 + 怎么做」。

### 1. 企业 AI 客户交付 —— "Plan + Memory + Tool" 三件套作为交付标准

- **对应业务场景**：客户总问"Agent 到底能干什么"，我们需要一套能讲清楚的标准化能力图谱，让客户对 Agent 有正确预期。
- **怎么做**：把"计划 / 记忆 / 工具"三件套画成一张交付蓝图，每个客户演示前先讲三件套、再讲业务流程。客户听完能直接复用这套心智模型去拆解自己的需求。三件套也是 FDE 与客户沟通的统一语言——客户的任何需求都可以归到三件套里讨论，不会出现"你说的 Agent 和我说的 Agent 不是一回事"。

### 2. FDE 方法论 —— "工作流越详细，效果越好" 作为交付硬规则

- **对应业务场景**：FDE 在客户现场搭 Agent 时，常被"快速搭个能跑的版本"压力推着走，导致上线后效果不稳、客户投诉。
- **怎么做**：在 FDE SOP 里加入一条硬规则——**任何复杂场景必须先用工作流画细再上 Agent；不允许"用简画版 Agent 直接上线"**。同时把意图分类、数据接入、异常分支、兜底回复都画进工作流；上线前必须经过至少一轮内部 Demo + 客户评审。

### 3. 获客系统 —— 把多 Agent 协同用到"内容生成 + 评审"

- **对应业务场景**：销售线索生成需要批量生产个性化文案（邮件、朋友圈、LinkedIn Message），人工写慢、不稳定；单 Agent 直出又会出现合规风险、吸引力不足。
- **怎么做**：套用吴恩达翻译工作流的模板——**Agent 1 生成初稿 → Agent 2 评审合规性 / 吸引力 / 行业用语 → Agent 3 终稿**。三个 Agent 都可以用弱模型（GPT-4o mini），重点是评审 Agent 的提示词要细——列出所有合规红线（如不能承诺收益、不能用绝对化用语）和吸引力指标（如开头是否抓人、CTA 是否清晰）。批量生产可大幅降低获客文案成本。

### 4. 8895 知识库 —— 把"长期记忆"做成企业级知识基础设施

- **对应业务场景**：8895 知识库承载大量行业知识、客户案例、SOP 文档，目前以"人查"为主，没法被 Agent 直接调用。
- **怎么做**：把 8895 内容做 **RAG 化**（切片、向量化、灌入 Dify / LangChain），让交付给客户的 Agent 都能挂载 8895 作为长期记忆。关注切片粒度（建议按段落 + 标题双层切片）和召回率（每周抽样 20 个高频问题做召回评测，目标 ≥ 85%）。同时建立"知识更新 SOP"——业务文档变更后 24 小时内同步到知识库。

### 5. FDE 培训 —— 把"Agentic System 四象限"列为新人必修课

- **对应业务场景**：新入职 FDE 一上来就接触客户，没有统一的设计语言，沟通成本高；不同 FDE 设计的 Agent 风格各异，难以复用。
- **怎么做**：把 **Reflection / Tool Use / Planning / Multi-Agent 四象限** 作为 FDE 入职第一课。每个客户方案在汇报时强制套用四象限框架：先讲工具、再讲计划、再讲反馈、再讲多 Agent 协同。统一的语言能极大提升跨项目协作效率，也方便沉淀可复用的方案模板。

### 6. 客户案例库 —— 沉淀"阿里 1688 模式"作为标杆

- **对应业务场景**：客户常问"别人家是怎么做的"，我们需要一个标杆案例库来支撑销售对话和方案设计。
- **怎么做**：把阿里 1688 AI 采购助手的"意图识别 + 多流程编排"架构抽象成一个通用模板——**意图分类 → N 条业务流 → 每条流挂工具 + 知识 → 结果整合**。每个客户方案都按这个模板先搭骨架，再填业务细节。同时把翻译工作流作为"多 Agent 协同"的标杆案例，让客户直观看到"三个弱模型也能跑赢强模型"的工程价值。

### 7. 效果评估 —— 多 Agent 系统必须有评测闭环

- **对应业务场景**：之前我们交付的 Agent 经常被客户追问"效果到底怎么样"，没有量化指标，只能凭主观感受。
- **怎么做**：每个 Agent 项目交付前必须建立评测集——**至少 50 个真实用户问题 + 人工标注的"理想答案"**。Agent 跑一遍自动评分，把**准确率、响应时延、Token 成本**三项指标交付给客户。多 Agent 项目则要对比"多 Agent 流程 vs 单 Agent 直出"的评测结果，让客户看到协同的增量价值。评测集版本化管理，每次迭代都要回归。

### 8. 客户培训 —— "AI 提示词工程"作为客户赋能包

- **对应业务场景**：客户业务团队在 Agent 上线后会自己想调整提示词，但经常写坏；改坏了又找我们改，无限循环。
- **怎么做**：把课程里反复强调的"**所有 AI 能力 = 大模型 + 提示词**"作为客户培训第一课。让客户业务团队理解：调整 Agent 行为本质上就是调提示词，不需要写代码。基于这个认知，再开"提示词工程实战"工作坊，教客户掌握：角色设定、Few-shot 示例、CoT 链式思考、约束条件等核心技巧。客户能自己调提示词，就能大幅降低我们的运维成本。

### 9. 工具调用 —— 沉淀"Dify 工具选型矩阵"作为 FDE 工具箱

- **对应业务场景**：FDE 在客户现场经常需要临时接入第三方工具（翻译、生图、OCR、爬虫），但选哪个工具、怎么授权、成本多少，没有统一知识。
- **怎么做**：沉淀一份 **"Dify 工具选型矩阵"**——按"功能 / 海外可用性 / 价格 / 接入难度 / 典型场景"五列维护；FDE 接到新需求先查矩阵，再选工具。同时建立"工具调用失败兜底 SOP"——遇到工具调用失败（超时、限流、网络问题）的标准应对流程，避免每次都要临时决策。

### 10. 内部知识沉淀 —— 把"多 Agent 设计要点"做成 CheckList

- **对应业务场景**：FDE 在设计多 Agent 系统时容易踩坑（角色重叠、交接不清、模型选错、没建评测）。
- **怎么做**：把本章 5.5 节列出的"多 Agent 设计工程要点"做成一份 **CheckList**：① 角色单一 ② 交接显式 ③ 模型不强求最强 ④ 评测基准 ⑤ 不过度设计。每个多 Agent 方案在内部评审时逐项打勾，未打勾的不允许上线。
