## 引子：为什么 FDE 一定要亲手做一遍 Agent 项目

很多同学学 Agent、LangChain、LangGraph，看了一周文档，越看越绕——「图、节点、边、条件路由、State、ToolNode」一堆抽象概念悬在空中，怎么都连不到具体业务上。本章用两个**完整的实战项目**把概念落到代码：

1. **数字人模拟平台**：把 RAG（检索增强生成）、Agent、外部 RTC 服务、Docker 部署四块技术拼在一起，做出能对话、能用知识库回答的"2D 数字员工"。
2. **LangGraph 工具调用 Agent**：从零写一个 100 多行的 ReAct 架构 Agent，大模型自己思考要不要调工具、调哪个、传什么参数，循环到能回答为止。

读完后你会拥有三件可迁移的资产：
- **数字人项目的工程结构图**（后端 14 个文件之间的关系）
- **RAG 答案质量的对比方法**（文档原答案 vs 大模型生成答案，怎么量化）
- **ReAct Agent 的最小代码骨架**（StateGraph + 节点 + 条件边 + 工具绑定）

## 逐点精读

### 一、数字人模拟平台：项目结构与技术栈

#### 1. 项目定位与四块核心技术

UP 主把这个项目命名为**数字人模拟平台**——之所以叫"平台"，是因为后端 self 端（API 服务层）已经按不同应用场景封装好了接口，学生拿过去换业务场景就能二次开发。

后端 14 个文件里，**真正核心的就四块**：

| 模块 | 作用 | 不可替代的理由 |
|---|---|---|
| Agent | 让数字人具备"决策大脑"——决定要不要查知识库、要不要调外部接口 | 没有 Agent 只能做死板的一问一答 |
| RAG（IG/Index Generation） | 让数字人从企业文档里检索准确答案 | 没有 RAG，模型只能凭"通识"瞎编 |
| 外部 RTC 服务端 | 把文本转成流式语音 + 推流给前端 | 决定数字人能不能"开口说话" |
| Docker 部署 | 整套服务容器化交付 | 决定交付到客户现场能不能跑起来 |

前端 UI 是次要的——UP 主刻意没写完善，就是为了让不同业务方按自家风格二次开发。

#### 2. RAG 检索准确性怎么验证

UP 主用了一个**很值得借鉴的验证方法**：把 RAG 检索出来的答案与文档原答案**逐句对比**。

- 演示问题 1：「如何确定产品的优先级？」 → 文档原答案给出六大步骤（市场需求分析、战略目标、ROI 评估、紧急性、用户反馈、竞争情况），RAG 回答的六点顺序与原文高度一致，仅在措辞上做了一点泛化。
- 演示问题 2：「请描述如何制定产品的路线图」 → 同样做到了"骨架一致、表达自然"。
- 测试结论：UP 主自写的 RAG 服务，**纯检索场景准确率达 95%+**；含泛化生成的回答准确率也在 90%+。
- 支持的文件类型：PDF、Word、Markdown 都可以。

**FDE 借鉴点**：交付 RAG 项目时，不要只让客户看"我能不能问出东西"，一定要做**原文档 vs 生成答案的逐句 diff 报告**，这是说服甲方"AI 没有胡说"的最强证据。

#### 3. 数字人形象定制

- 默认使用平台原生虚拟形象（考虑隐私合规）。
- 通过**企业认证**后可以定制 2D 真人形象：站着录一段、坐着录一段、手势录一段，把视频喂给平台生成专属动作库。
- 费用：阿里、百度等平台约**几千元/年**。

**FDE 借鉴点**：给客户讲数字人方案时，"几百块通用形象 vs 几千元定制形象"是两个 SKU，对应不同预算和品牌需求。

#### 4. 历史对话摘要

UP 主在视频里提了一个增量功能：把用户的多次问答**挂在右侧小窗口**，并支持「我们前面聊些什么？」这种元问题——底层就是对历史 messages 做一次摘要。

#### 5. 部署到 Coze（扣子）

整套项目部署到扣子上运行——这是因为文件太大没法直接发，原代码不开放下载，需要的同学评论区留言，UP 主私信打包。

**FDE 借鉴点**：FDE 给客户做交付时，**扣子 / Dify / FastGPT** 这类低代码平台很适合做 PoC（概念验证）——客户一看"两天就能跑起来"，决策速度立刻加快。

### 二、LangGraph 工具调用 Agent：从零搭建 ReAct 架构

这一段是本章最硬的技术内容。UP 主带学生从空白 Pycharm 项目开始，**一行一行写出一个能跑的 ReAct Agent**。我们提炼骨架，不照抄代码。

#### 1. 为什么用 LangGraph 而不是直接调 API

直接调 ChatOpenAI 接口，模型只能输出文字。要让模型**自己决定调工具**，得用 Agent 框架。LangGraph 的好处是：
- 把 Agent 流程**显式画成图**（节点 + 边），调试时一眼能看到"走到哪一步了"。
- **State 自带消息列表**，多轮对话不用自己管理 history。
- **ToolNode 现成**——不用自己写"提取 tool_calls → 找 Python 函数 → 传参 → 执行 → 包装结果"这一坨样板代码。

#### 2. 依赖与导入清单

```text
requirements.txt
├── langgraph         # 图编排框架
└── langchain-openai  # 兼容 OpenAI 接口的客户端
```

代码里要导入的模块分四组：
1. **Python 自带**：`os`（读 API Key 环境变量）、`datetime`（做时间工具）。
2. **LangChain 客户端**：`ChatOpenAI`（兼容通义千问 / 阿里百炼等 OpenAI 格式服务）。
3. **LangGraph 核心**：`StateGraph`、`START`、`END`、`MessagesState`（内置消息白板）、`ToolNode`（prebuilt，工具执行器）。
4. **LangChain Core 消息类型**：`HumanMessage`、`AIMessage`、`ToolMessage`——三种角色，分别代表"用户说话 / 大模型说话 / 工具返回"。

#### 3. 概念：`@tool` 装饰器——把普通函数变成大模型能调用的工具

核心 API：`from langchain.tools import tool`，用法：

```python
@tool
def calculator(expression: str) -> str:
    """执行数学表达式计算。
    Args:
        expression: 数学表达式，例如 "25*10+12"
    """
    # ...
```

**两个铁律**：

| 铁律 | 原因 |
|---|---|
| 一定要写 `docstring` | 大模型就是靠这份"说明书"决定**何时调**、**传什么参数**。写得越清楚，调用越精准；写得含糊，模型就会乱传参数。 |
| 一定要写**类型注解** | 装饰器会扫描函数名、参数、返回值、类型注解，转成大模型能理解的 JSON Schema。类型错了，模型传参就错。 |

#### 4. 工具设计要点（calculator + get_current_time）

**calculator 工具**的关键设计：
- **白名单安全校验**：`allowed_chars = set("0123456789+-*/(). ")`，防止恶意注入（因为函数体里要用 `eval`）。
- **try-except 异常捕获**：把计算错误转成字符串返回给调用者，不让程序崩溃。
- **格式化输出**：`return f"计算结果：{expression} = {result}"`。

> **生产警告**：`eval` 在生产环境绝对不能直接用——白名单只是 PoC 兜底，真实场景必须用 `ast.literal_eval` 或独立的表达式解析库。

**get_current_time 工具**的关键设计：
- 参数 `unused: str = ""`——有些大模型调工具时不管你要不要参数，**硬塞一个空字符串**进来，给个默认值就不会报错。
- 返回值带**年月日时分秒 + 星期几**，方便人类阅读。

#### 5. 大模型初始化 + 工具绑定

```python
llm = ChatOpenAI(
    model="qwen3-max",          # 或阿里百炼上其他模型
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    temperature=0,              # 工具调用场景温度必须低
)
llm_with_tools = llm.bind_tools(tools)  # 关键一步
```

**`temperature=0` 是工具调用场景的铁律**：计算、查时间这种结果都是**确定的**，温度高了模型会"瞎发挥"——比如把 `25*10` 算成 251，把日期说错。温度归零，输出稳定。

**`bind_tools(tools)` 的作用**：把工具列表的 name / docstring / 参数 Schema 全部转换成 OpenAI tools 格式，**塞进每一次请求**。从这一行之后，模型就知道"我有 calculator 和 get_current_time 两个工具，分别需要 string 类型参数"。

#### 6. 概念：`MessagesState`——整个 Agent 的"记忆白板"

LangGraph 内置的状态类型：

```python
class MessagesState(TypedDict):
    messages: list[BaseMessage]
```

里面装的是**所有历史消息**——用户的、AI 的、工具返回的——按时间顺序排列。节点之间传递这个 state，就把对话历史带过去了。

#### 7. 节点 1：`agent_node`——大模型的大脑

```python
def agent_node(state: MessagesState) -> dict:
    messages = state["messages"]          # 拿全部历史
    response = llm_with_tools.invoke(messages)  # 调大模型
    return {"messages": [response]}      # 返回新消息
```

关键点：
- **多轮对话支持**：每次都把**全部历史**塞给模型，不是只塞最新一条。
- **返回值是 dict**：key 必须是 state 里定义的字段（这里是 `messages`），value 是要追加进去的新消息列表。
- **LangGraph 自动追加**：你不用手动 `messages.append(response)`，框架会把新消息合到 state 里。
- **返回结构含义**：
  - `response.content` 有内容 → 模型决定直接回答。
  - `response.tool_calls` 有内容 → 模型决定调用工具（含工具名 + 参数）。

#### 8. 节点 2：`ToolNode`——干活的手

```python
from langgraph.prebuilt import ToolNode
tool_node = ToolNode([calculator, get_current_time])
```

一行代码搞定工具执行器。它自动做四件事：
1. 从最后一条 AIMessage 里提取 `tool_calls`。
2. 根据 `tool_calls` 里的工具名找到对应的 Python 函数。
3. 把参数传进去执行。
4. 把执行结果包装成 `ToolMessage`，写回 state。

#### 9. 概念：条件路由函数 `should_continue`

```python
def should_continue(state: MessagesState) -> str:
    last = state["messages"][-1]
    if last.tool_calls:
        return "tools"   # 还有工具要调，去干活
    return END           # 干完了，结束
```

返回值是一个**字符串**，告诉 LangGraph「下一步去哪个节点」。要么返回节点名（如 `"tools"`），要么返回内置常量 `END`。

#### 10. 拼图：`StateGraph` + 节点 + 边

```python
builder = StateGraph(MessagesState)
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)

# 入口边：START → agent
builder.add_edge(START, "agent")

# 条件边：agent → 看路由函数返回值 → tools 或 END
builder.add_conditional_edges(
    "agent",
    should_continue,
    {"tools": "tools", END: END},
)

# 循环边：tools → agent（工具结果回到大脑继续推理）
builder.add_edge("tools", "agent")

graph = builder.compile()
```

**三种边**：
- **普通边**（`add_edge`）：A 直接到 B，无条件。
- **条件边**（`add_conditional_edges`）：A 出来后看路由函数返回值决定去哪。返回值字典显式列出所有可能，可读性更好。
- **循环边**：工具执行完一定要**回到 agent 节点**，否则大模型看不到工具结果。

#### 11. 运行：`graph.invoke()`

```python
def chat_with_debug(user_input: str):
    result = graph.invoke(
        {"messages": [HumanMessage(content=user_input)]},
        config={"configurable": {"thread_id": "debug"}},
    )
    # 打印每一步：用户问题 / AI 是否调工具 / 工具结果 / 最终回答
```

**`config={"configurable": {"thread_id": ...}}`** 是多轮对话记忆的钩子——同一个 `thread_id` 下，LangGraph 自动把历史 messages 串起来。今天用 `thread_id="debug"` 是写死的；真实场景应该按用户/会话动态生成。

#### 12. 概念：ReAct 循环

整个 Agent 的执行模式叫 **ReAct**（Reason + Act）：
1. **Reason（思考）**：agent_node 调大模型，看历史消息，决定要不要调工具。
2. **Act（行动）**：路由返回 `"tools"`，ToolNode 执行工具。
3. **Observe（观察）**：工具结果包装成 ToolMessage 写回 state。
4. **Reason（再思考）**：再次进入 agent_node，大模型看工具结果，决定继续调还是回答。
5. 直到某次 `should_continue` 返回 `END`，整个图终止。

#### 13. 常见坑——白名单漏掉空格

UP 主现场踩的坑：`25*10` 中间有空格，第一次没加进白名单，工具返回"表达式包含不允许的字符"；大模型看到错误后**自动修正参数**（去掉空格），第二次成功调用，最终算出 `262`。

**这个坑揭示了一个重要规律**：当工具返回错误时，大模型**会自己尝试调整参数重试**——这是 ReAct 的纠错能力，但也意味着工具的错误信息要**写得有指导性**（"请检查是否包含非法字符，当前只允许数字 + 四则运算符"），而不是空泛的"出错了"。

#### 14. 三个测试用例

| 测试 | 问题 | 期望路径 |
|---|---|---|
| 数学计算 | `25*10+12 等于多少` | agent → tools(算25×10) → agent → tools(算250+12) → agent → END |
| 获取时间 | `现在几点了？今天是几号？` | agent → tools(取时间) → agent → END |
| 不需工具 | `一句话解释什么是人工智能` | agent → END（直接回答，不调工具） |

三个测试覆盖了 ReAct 的三种典型路径：**多次调工具、单次调工具、不调工具**。

#### 15. 框架的调度权

学生最常问的问题：「我在 `chat_with_debug` 里**没有显式调用 agent_node**，为什么流程还是从 agent 开始的？」

答案是：**执行顺序在编译时就已经"焊"进图里了**。`graph.invoke()` 启动后：
- 框架从 `START` 节点开始（START 是一个**没有任何逻辑的起点标记**）。
- 根据边表，找到 `START` 连向的第一个节点——这里是 `agent`。
- 执行 `agent_node`，然后看它的出边——这里是条件边，调 `should_continue`。
- 根据返回值跳转到 `tools` 或 `END`。
- `tools` 节点执行完后，再根据边回到 `agent`——形成循环。
- 直到路由返回 `END`，框架把最终的 state 返回给调用者。

类比：**就像游乐园买票进门**，入口只有一个（START），第一个项目是固定的（agent），中间岔路口有工作人员举牌（should_continue），玩完一个项目只有一条路绕回大脑（循环边）。你**不用自己喊"我要玩哪个项目"**——顺着路走就行。

## 结论 / 金句

1. **数字人项目的本质是"四块技术 + 一个前端壳"**：Agent + RAG + RTC + Docker，缺一不可。FDE 交付时按这四块拆工作量，颗粒度刚好。
2. **RAG 准确率必须用"原文档 vs 生成答案"的逐句对比来验证**——这是说服甲方的硬证据，不是"我觉得挺准的"。
3. **`@tool` 装饰器的灵魂是 docstring**：写得清楚，模型调用就精准；写得含糊，模型就乱传参。给新同事写"工具使用说明书"的思路直接复用。
4. **`temperature=0` 是工具调用场景的铁律**：结果确定的场景（计算、查时间）必须归零，否则模型会"瞎发挥"。
5. **LangGraph 的本质是"把流程画成图"**：节点是做事的人，边是路，条件路由是岔路口的工作人员。流程图一旦画好，框架就按图自动跑——你**不用手动调度任何节点**。
6. **工具的错误信息要有指导性**：模型看到错误会自己重试，空泛的"出错了"只会让它反复撞墙；写明"当前只允许数字 + 四则运算符"，它立刻知道怎么改。
7. **生产环境 `eval` 必踩雷**：PoC 阶段用白名单凑合可以，但上客户现场必须换成 `ast.literal_eval` 或独立表达式解析库——这是 FDE 提交代码前必须检查的安全红线。

| `StateGraph` | 把流程画成图的构建器 | `builder.add_node/add_edge/add_conditional_edges` | ReAct 循环、多分支流程 |
| `ToolNode` | LangGraph 自带的工具执行器 | `ToolNode([tool1, tool2])` | 工具调用执行 |
| 条件路由 | 决定 Agent 下一步去哪 | `should_continue(state) -> str` | "是否继续调工具"的判断 |
| `bind_tools` | 把工具列表焊到每一次 LLM 请求里 | `llm.bind_tools(tools)` | 让模型知道有哪些工具可用 |
| ReAct 循环 | Reason → Act → Observe → Reason 循环 | START → agent → tools → agent → END | 所有需要外部信息的 Agent |
| `graph.invoke()` | 启动图执行 | `invoke({"messages": [...]}, config={...})` | 单次调用 / 多轮对话 |
| `thread_id` | 多轮对话记忆钩子 | `config.configurable.thread_id` | 同一会话的历史串接 |

## 通用原则

### 原则 1：拆复杂系统，永远先找"四块核心"

数字人项目里 UP 主说"四块技术搞懂就 OK"，前端是次要的。这个拆法可以迁移到任何 AI 项目：

| 项目类型 | 四块核心（举例） |
|---|---|
| 智能客服 | RAG + 工单系统对接 + 工单总结 + 人工兜底 |
| AI 面试官 | 题目生成 + 语音识别 + 评分模型 + 报告生成 |
| AI 营销助手 | 用户画像 + 内容生成 + 渠道对接 + 效果回流 |
| 企业知识库 | 文档接入 + 向量化 + 检索 Agent + 权限控制 |

**FDE 接到客户需求，第一件事就是拆出这四块**，然后告诉客户"这四块我们做，前端/UI 你们自己接"——边界清晰，工期可控。

### 原则 2：PoC 阶段用低代码平台，过 Demo 再谈自研

UP 主把整套项目部署到**扣子（Coze）**上而不是自己搭服务器——这是 PoC 的最佳实践：
- 两天搭起来，客户看到 Demo 决策速度翻倍。
- 文件大、代码不开放也没关系，因为**PoC 的目的是验证业务价值，不是验证技术细节**。
- 客户拍板要落地了，再把核心模块（Agent、RAG、Docker）拆出来重写。

### 原则 3：RAG 准确率验证必须做"逐句对比"

UP 主在视频里反复做的动作——把模型回答和文档原答案**一句一句对**，是 RAG 项目验收的**金标准**。可以做成自动化脚本：
- 用 N 个测试问题，对每个问题跑一遍 RAG。
- 用一个大模型当裁判，对每个回答打"事实一致性"分（0/1/2 三档）。
- 算出整体准确率，作为合同验收指标。

### 原则 4：工具设计 = 写说明书 + 加白名单 + 给默认值

每个 `@tool` 函数都要回答三个问题：
1. **什么时候用？**（docstring 写场景："用于执行四则运算"）
2. **参数是什么格式？**（类型注解 + docstring 举例："例如 '25*10+12'"）
3. **出错怎么办？**（try-except + 有指导性的错误信息）

外加两个安全细节：
- **白名单校验**：任何用到 `eval` / `exec` / SQL 拼接的工具必须有白名单。
- **参数默认值**：给可能"被硬塞参数"的工具参数设置默认值，避免爆错。

### 原则 5：`temperature` 按场景分层

| 场景 | 推荐 temperature |
|---|---|
| 工具调用（计算、查时间） | **0**（结果确定，不能发挥） |
| 知识库问答（RAG） | **0 ~ 0.3**（要忠实文档，不能编） |
| 创意写作、头脑风暴 | **0.7 ~ 1.0**（要多样性） |
| 多轮对话（无工具） | **0.5** 左右（自然但不散漫） |

### 原则 6：LangGraph 图设计三步法

每次画 StateGraph，都按这个顺序来：
1. **列节点**：把所有"做事的人"列出来（agent、tools、人审核、数据库查询……）。
2. **画普通边**：先画确定会走的路（START → agent，tools → agent）。
3. **画条件边**：在所有"需要决策的岔路口"加条件路由。

这样画出来的图可读性最高，新人看 5 分钟就能上手。

### 原则 7：错误信息是 Agent 的"教练信号"

当工具返回错误，大模型会**自动尝试调整参数重试**。这是 ReAct 的纠错能力。所以：
- 错误信息要**有指导性**："参数 X 必须是数字，当前收到 'abc'"。
- 错误信息要**结构化**：把"错误类型 / 错误位置 / 修复建议"分开。
- 不要返回空泛的"出错了"——模型会陷入循环重试。

## 可复用模式

### 模式 1：数字人 / 虚拟员工交付模板

```
项目骨架（按客户定制程度分三档）：

档位 1（PoC，1~3 天）
- 扣子 / Dify 搭 RAG + Agent 流程
- 用平台原生数字人形象
- 不开放代码，客户看到 Demo 即可

档位 2（小项目，1~2 周）
- 后端自建：FastAPI + LangGraph + Milvus/Chroma
- 前端可定制（Vue/React）
- 数字人用 RTC 服务（阿里/百度）
- Docker 打包部署

档位 3（企业级，1~3 月）
- 多 Agent 协作（Agent A 检索、Agent B 总结、Agent C 播报）
- 数字人形象定制（企业认证）
- 权限系统 + 审计日志
- 私有化部署
```

### 模式 2：LangGraph 工具调用 Agent 最小骨架

```text
# 骨架五件套（任何工具调用 Agent 都适用）

1. 工具列表（@tool 装饰的函数）
2. 大模型 + bind_tools
4. MessagesState（内置消息白板）
5. agent_node（调模型）+ ToolNode（执行工具）+ should_continue（路由）
6. StateGraph + 三种边 + compile
```

新业务只要替换第 1 步的"工具列表"和第 3 步的 State 字段，其他全是固定骨架。

### 模式 3：RAG 验收测试模板

```text
测试用例设计：
- 准备 N 个标准问题 + 文档原答案
- 每个问题跑 RAG 3 次（看稳定性）
- 用 LLM-as-Judge 打分（事实一致性 0/1/2）
- 输出：每个问题的得分 + 整体准确率 + 失败案例归因
```

### 模式 4：PoC 演示三件套

向客户演示 AI 项目时，永远准备三个测试用例：
1. **必须成功用例**（让客户有信心）：用客户最关心的核心问题。
2. **边界用例**（展示能力边界）：故意问文档里没有的问题，看 Agent 会不会"承认不知道"。
3. **对比用例**（让客户看到价值）：同一个问题，对比"传统搜索"和"AI 回答"的效果差异。

# 借鉴篇 · 我们能借鉴的点

> 结合王昕业务：企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库，逐条落地动作。

### 动作 1：用「四块核心」拆解每个客户需求，报价模板化

- **对应业务场景**：企业 AI 客户交付前的需求拆解与报价。
- **怎么做**：接到客户需求后，先按「数据接入 + AI 模型 + 业务对接 + 部署运维」四块拆工作量。前两块是技术核心，后两块是交付成本。报价单按四块分别列金额，客户一眼看到价值分布。**拒绝「按人天报价」的模糊方式**——四块拆完后每块多少工时、多少成本是清楚的。

### 动作 2：所有 PoC 项目用扣子 / Dify 先搭 Demo，验证业务价值后再谈自研

- **对应业务场景**：获客系统的客户教育与转化。
- **怎么做**：客户第一次接触 AI 产品时，**不要上来就讲 LangGraph / 向量化 / ReAct 这些技术词**。用扣子/Dify 两天搭一个能跑的 Demo，让客户亲手问几个问题，**用体验说话**。客户说"这个就是我们想要的"，再谈自研、私有化、深度定制——这时候客户预算也准备好了。

### 动作 3：把「原文档 vs AI 回答」的逐句对比做成 RAG 项目验收标准

- **对应业务场景**：8895 知识库的交付验收。
- **怎么做**：8895 知识库上线前，准备 50~100 个标准问答对，每个问题跑 RAG 3 次。用一个大模型当裁判，给每个回答打"事实一致性"分（0=编造，1=部分一致，2=完全一致）。**整体准确率 ≥ 85% 才算验收合格**，低于这个分数要回头调文档切分、向量化模型或检索策略。**这是把"AI 效果"从主观感受变成合同条款的关键**。

### 动作 4：建立企业内部「工具说明书」模板库，沉淀给客户的 `@tool` 文档标准

- **对应业务场景**：FDE 交付的所有 Agent 项目。
- **怎么做**：做一个标准 docstring 模板（场景描述 + 参数说明 + 例子 + 错误信息），所有给客户的 `@tool` 函数都按这个模板写。**docstring 质量 = 工具调用准确率 = 客户满意度**，这三件事是直接挂钩的。模板库放在内部 wiki 上，新人入职直接学。

### 动作 5：所有工具调用 Agent 的 `temperature` 按场景设默认值，禁止默认 1.0

- **对应业务场景**：所有 RAG / 工具调用 / 知识问答项目。
- **怎么做**：在内部 SDK 里封装 `ChatOpenAI` 初始化，**工具调用场景默认 `temperature=0`**，RAG 场景默认 `0~0.3`，禁止业务方随便调到 0.7 以上。FDE 提交代码前，**code review 必须看 temperature 设置**——这是"AI 稳定性"的第一道防线。

### 动作 6：所有工具的错误信息必须有「指导性文案」，不能只返回「失败」

- **对应业务场景**：FDE 交付的所有 Agent / RAG 项目。
- **怎么做**：建立错误信息模板：
  - 错误类型（如 "参数格式错误"）
  - 错误位置（如 "参数 X"）
  - 期望格式（如 "必须是数字字符串，如 '25*10'"）
  - 修复建议（如 "请检查是否包含非法字符"）

  这套模板让大模型能自己纠错——Agent 不用人工介入就能重试成功。**这是 ReAct 架构发挥自动纠错能力的前提**。

### 动作 7：把 LangGraph 图导出成「流程图截图」放进交付文档

- **对应业务场景**：企业 AI 客户交付的方案文档。
- **怎么做**：每个 Agent 项目交付时，把 StateGraph 的图导出成 PNG（LangGraph 自带 `graph.get_graph().draw_png()`），放进交付 PPT 的「架构设计」章节。客户技术团队一看图就懂流程，**不用读代码**——这是 FDE 把技术语言翻译成业务语言的标准动作。

### 动作 8：数字人项目按「PoC / 小项目 / 企业级」三档报价，对应不同客户预算

- **对应业务场景**：企业 AI 客户交付（尤其是客服、培训、面试场景）。
- **怎么做**：建立三档报价模板：
  - **PoC 档（万元级）**：扣子/Dify + 原生形象，1~3 天交付，验证业务可行性。
  - **小项目档（十万级）**：FastAPI + LangGraph + RTC，1~2 周交付，可二次开发。
  - **企业级档（百万级）**：多 Agent + 定制形象 + 权限/审计，1~3 月交付，可私有化部署。

  客户预算多少就推哪一档，**不要用"百万级方案"吓跑只有万元预算的客户**。

### 动作 9：把"多轮对话记忆"做成所有 Agent 项目的标配，用 `thread_id` 串接历史

- **对应业务场景**：所有面向 C 端用户 / 客服场景的 Agent。
- **怎么做**：每个 Agent 项目上线时，**强制配置 `thread_id` 存储**（Redis 或数据库都行）。同一个用户/会话的历史自动串接，AI 能回答"我们前面聊了什么"——这是"AI 真的有记忆"的最直接证据。**没做记忆的 Agent 在客户眼里就是"高级搜索框"**，做不出差异化。

### 动作 10：建立"AI 工具调用失败案例库"，沉淀常见坑（白名单 / 空格 / 编码）

- **对应业务场景**：FDE 团队的内部知识沉淀。
- **怎么做**：每次 Agent 项目踩坑都记录进 Notion / 飞书知识库：
  - 坑的现象（白名单漏空格导致重试）
  - 根因（eval 输入校验不全）
  - 修复方法（白名单加 ' '）
  - 防范手段（code review checklist 加一项）

  这个案例库积累 50 个以上后，**FDE 新人上手 Agent 项目的速度会快 3 倍**——大部分坑都是前人踩过的。

### 动作 11：用「企业级形象定制」打造差异化获客物料

- **对应业务场景**：获客系统 / 官网 / 销售物料。
- **怎么做**：花几千元在阿里/百度认证企业账号，定制一个**专属数字人形象**——录一段 2 分钟视频，生成动作库。后续所有获客场景（官网弹窗、抖音自动回复、微信视频号客服）都用这个数字人。**统一的数字人形象 = 品牌差异化 = 客户记忆点**。这是中小 AI 公司"用最小成本做出品牌感"的最优解。

### 动作 12：把"AI 模拟面试"做成 8895 知识库的标杆交付案例

- **对应业务场景**：8895 知识库的标杆客户开拓。
- **怎么做**：用本章数字人项目的架构，做一个"AI 模拟面试官"：
  - RAG 接入岗位 JD 和面试题库
  - Agent 负责追问、点评、打分
  - 数字人形象做面试官
  - 输出面试评估报告

  这是**HR / 培训机构最买单的场景之一**——用 8895 知识库的能力做出"AI 面试 SaaS"，可以快速复制到多个客户。
