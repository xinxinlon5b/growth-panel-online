## 上篇 · 书籍内容

### 引子：AI 产品经理为什么必须懂 Dify

前面的章节已经把 AI 产品的能力分层讲清楚了：底层是大模型、外部存储、第三方工具；中间是提示词工程、预处理等工程能力；再上层是 Co-Pilot、Agent、知识库。当我们要交付一个真正能跑、能上线、能被客户使用的 AI 应用时，就进入「产品形态」这一层。

Dify 是产品形态这一层最具代表性的低代码搭建平台。它把工作流、知识库、聊天助手、Agent 这几种最常见的 AI 应用形态封装成可视化节点，让 AI 产品经理不必从零写代码就能交付一个完整应用。更重要的是：Dify 出身苏州、出海成绩亮眼（在日本低代码 AI 搭建市场排第一），同时被大量央国企用作「全本地部署」的首选平台——这个事实本身就决定了它在国内 B 端市场的接受度。

本章的主线任务只有一个：用 Dify 从零搭建一个「AI 产品经理课程的智能客服」。我们围绕这一个落地案例，把 Dify 的核心节点、SOP 拆解、提示词编排、多轮对话、文件上传等高频问题全部拆开讲透。再用两个补充案例（吴恩达风格的文档翻译工作流、上节课的销售助理）把剩余的常见问题覆盖掉。

学完这一章，AI 产品经理应当具备的能力是：拿到任意一个业务场景，能在一天之内用 Dify 画出工作流、配置知识库、跑通对话、交付 MVP。

### 主线：方法流程

整章的认知顺序可以浓缩为以下五步：

1. **从 SOP 出发**：不写一行代码，先用流程图把业务 SOP 画清楚。
2. **把 SOP 拆成工作流节点**：用问题分类器把用户输入分流，每一类对应一条独立的处理路径。
3. **在每条路径上挂知识检索 + 大模型**：检索负责查证，大模型负责「把检索到的文档片段说人话」。
4. **用条件分支处理不确定性**：检索为空、文件未上传、超时未回复，都用条件分支兜底。
5. **用 Dify 的发布能力交付**：调试完毕一键发布，前端聊天界面直接可用。

这五步覆盖了 Dify 80% 的实战场景。下面逐点精读。

### 逐点精读

#### 一、Dify 的四类应用形态

Dify 把 AI 应用归纳为四类：Agent、聊天助手（基础编排）、聊天助手（高级版）、工作流（Chatflow/Workflow）。前三类偏向对话，最后一类偏一次性任务。AI 产品经理需要关注的是：每一类应用的「对话场景设计深度」不同。

聊天场景的封装是 Dify 的强项。具体能力包括：对话开场白（让用户一进聊天窗口就知道能问什么）、下一个问题建议（用历史问题推荐追问）、语音文字互转（适配移动端）、安全审查（合规过滤）、引用归属（让答案可溯源）。这三类应用都可以配置这些对话能力。

而工作流（Workflow）是「一次性完成、没有对话」的应用形态。它的核心是业务逻辑封装，UI 只是调试工具。Agent 可以调用工具；高级聊天助手可以调用工具；基础聊天助手不能调用工具；工作流也可以调用工具。外部记忆（主要是知识库）则四类基本都能挂。

| 形态 | 对话能力 | 工具调用 | 适用场景 |
|---|---|---|---|
| Agent | 强 | 可用 | 复杂任务、多步推理 |
| 聊天助手（基础编排） | 强 | 不可用 | 简单问答 |
| 聊天助手（高级版） | 强 | 可用 | 对话 + 工具 |
| 工作流 | 一次性 | 可用 | 流程化任务 |

**AI 产品经理多关注**：选错形态是新人最常踩的坑。选「基础聊天助手」做客服，发现不能调工具、不能挂工作流，又得推倒重来。判断标准很简单——如果业务是「一来一回」的问答，选聊天助手；如果业务有「多步分支」，选工作流或 Agent。

#### 二、工作流来源于业务 SOP

Dify 工作流不是凭空设计出来的，它必须从业务的 SOP（Standard Operating Procedure，标准作业流程）里提取。这是一个反直觉的判断：很多新人拿到业务第一反应是「AI 怎么实现」，但正确答案永远是「先把业务 SOP 画出来」。

以客服场景为例，最基础的 SOP 是：客户打开入口 → 发送问题 → 客服确认问题 → 知识库查找 → 回复解决方案 → 客户确认 → 客服记录结果 → 结束。这是最粗糙的版本，不够直接搬到工作流里。

把它拆细一层，就得到客服工作流的最小可用版：

1. 用户输入问题
2. **问题分类**：把问题分成五类
   - 订单资讯类
   - 课程内容资讯类
   - 产品建议类
   - 问题已解决类
   - 其他类（闲聊、不相关）
3. **每类单独走分支**：
   - 订单类 → 查订单知识库
   - 课程内容类 → 查课程内容知识库
   - 产品建议 → 直接回复「谢谢您的建议，我们会记录下来」
   - 问题已解决 → 直接回复「谢谢，有问题再来找我」
   - 其他 → 直接回复「请完整描述您对 AI 产品经理课程的问题」
4. 检索完成后做**条件分支**：检索结果是否为空
   - 为空 → 回复「对不起，我去跟老师确认后再回答你」
   - 不为空 → 进入大模型节点，把检索结果改写成「人话」
5. 大模型输出 → 直接回复

**关键金句**：拆得越细，AI 正确率越高。让一个大模型干十件事，每件事正确率 90%，十件叠加正确率只剩 35%；让十个大模型各干一件事，正确率反而飙升。这就是工作流相比「超长提示词」的核心优势。

**AI 产品经理多关注**：SOP 拆解的颗粒度直接决定工作流的复杂度。颗粒度太粗，AI 在大节点内乱跑；颗粒度太细，工作流难以维护。建议从「三类分支」起步，跑通后再细分。

#### 三、问题分类器——最关键的节点

问题分类器是整个工作流的大脑。Dify 把分类器做成一个独立节点，底层仍然是 LLM，但提示词模板被预置好，专门做意图识别。

分类器选模型有两个铁律：

1. **必须用强模型**：GPT-4o、O1、DeepSeek R1 等。用户输入五花八门，弱模型（如 GPT-3.5）分类经常出错。一处分类错，后面整条链路全错。
2. **必须给例子**：这是提示词工程里被反复验证的结论。同样一个分类任务，给三到五个例子的效果远好于不给。例子要覆盖典型表达和边缘表达。

本案例的五个分类提示词范例：

- **订单相关**：「这个课程多少钱？」「课程服务期是多久？」
- **课程内容相关**：「AI 产品经理都有哪些？」「AI 产品的核心技能是什么？」
- **课程建议**：「课程时间如果能再长一点就好了。」
- **问题已解决**：「谢谢，可以了。」「问题解决了。」
- **不属于以上任何一类**：留空作为兜底。

**AI 产品经理多关注**：分类器的输出稳定性是工作流质量的瓶颈。验收时要把真实用户问题跑一遍数据集，看每类的准确率和混淆矩阵。R1 分类效果也很好，但比 GPT-4o 慢。

#### 四、知识检索 + 大模型的协作

工作流中检索与大模型的配合是一个高频误区。

**误区 1**：检索到结果就直接发给用户，不经过大模型。错。知识库检索返回的是文档片段（可能是三段、五段原文），用户看起来非常杂乱，体验极差。

**误区 2**：让大模型脱离知识库自由发挥。错。大模型会幻觉，会编造答案。

**正解**：检索 + 大模型结合。检索负责「找到事实」，大模型负责「把事实改写成自然语言回复」。

提示词的固定模板：

```
系统提示词：
你是一个 [角色] 客服。
请根据知识库的内容来回复问题。
知识库内容在 <knowledge></knowledge> 两个标签之间。
注意事项：
- 只用知识库的内容来回答
- 不知道就说不知道
- 如果需要，要求澄清问题
- 不要说明你的回答来源于知识库

用户提示词：
{{sys.query}}（即用户原始输入）
```

其中 `<knowledge>` 是可改的标签（K 减弦、K-base 等都行），作用是把检索结果隔离出来，避免污染提示词的其余部分。

上下文变量绑定：把「知识检索节点」的输出填入 system prompt 的上下文位置，把「用户原始输入」（即开始节点的 `sys.query` 变量）填入 user prompt。

**AI 产品经理多关注**：模型选择会显著影响提示词的遵循度。同样一条「不要说明来源于知识库」的指令，GPT-4o 能遵守，DeepSeek V3 经常还是会写出「根据知识库内容」。如果产品对答案外观一致性要求高，必须选听话的强模型。

#### 五、条件分支兜底

工作流里所有的「不确定性」都必须用条件分支处理。本案例用到三处：

1. **检索是否为空**：这是最常见的条件。`if 检索结果为空 → 走兜底回复；else → 走大模型改写`。
2. **文件是否上传**：翻译工作流里的分支。`if 上传了文件 → 走文档提取器；else → 用原始文本`。
3. **超时未回复**：客服场景的分支。`if 客户超时未回复 → 直接结束；else → 再次分类`。本案例受限于 Dify 当前能力，超时判断这一段暂时打不出来，需要后续接入业务系统。

条件分支可以嵌套（if-else if-else if），分支数没有明确上限。**变量聚合器**是另一类相关节点：当多条分支汇入同一个下游节点时，用变量聚合器把多个分支的输出合并成一个变量，避免下游节点写两遍。

**AI 产品经理多关注**：兜底回复不要写「出错了」「系统繁忙」这种空话。要写得像真人客服：「对不起，我去跟老师确认后再回答你。」既掩盖了系统局限，又安抚了用户情绪。

#### 六、多轮对话的实现

Dify 自带多轮对话能力，关键在「记忆」开关。

分类器节点的高级设置里有「记忆」选项，可以设置记忆多少轮对话。打开后，Dify 会自动维护一个 `histories` 变量，把历史问答一起传给分类器。

例如用户先问「课程」，再问「多少钱」。第二次问的时候，分类器能结合历史知道「多少钱」指的是「课程的多少钱」，从而正确路由到订单类分支。

多轮对话的实现原理：Dify 内置提示词模板会自动把 `histories`（历史聊天记录）和最新的 `sys.query`（用户输入）拼在一起送给大模型。所以打开记忆开关就等于让大模型拿到完整上下文。

**AI 产品经理多关注**：多轮对话的轮数不是越多越好。轮数多了 token 消耗大、延迟增加。一般 5-10 轮够用。对于需要长期记忆（跨会话）的场景，Dify 当前做不到，需要外挂数据库：每次会话开始时从数据库拉历史，会话结束时把问答写回数据库。

#### 七、文件上传与文档提取

「工作流怎么上传文件」是群里高频问题。答案分两步：

**第一步**：开始节点里添加一个变量，类型选「文件」。这样前端就能出现上传按钮。Dify 支持 Word 等常见格式，上传的文件保存在 Dify 服务器上。

**第二步**：用「文档提取器」节点把上传的文件内容读出来。注意，文档提取器本身不做向量化、不做检索，纯粹是把文件内容转成文本字符串输出。

典型的翻译工作流结构：

```
开始（变量：原文、目标语言、文件）
  │
  ├─ 文件存在？── 是 → 文档提取器 → 变量聚合器
  │                       ↑
  └──────── 否 → 直接到变量聚合器
              ↓
         初次翻译（大模型）
              ↓
         翻译检查（大模型）
              ↓
         翻译改进（大模型）
              ↓
         直接回复
```

变量聚合器在这里起到「合流」作用：不管用户有没有上传文件，最后都把要翻译的文本统一交给初次翻译节点，下游只写一次。

**AI 产品经理多关注**：文档提取器 ≠ 知识库。知识库有向量化、有检索；文档提取器只是读取。当用户问题是「总结我刚上传的 PDF」，用文档提取器；当用户问题是「在我所有上传的合同里找关于付款条款的内容」，用知识库。

#### 八、Chatflow 与 Workflow 的区别

很多同学问「为什么这个例子用 Chatflow 不用 Workflow」。区别很明确：

| 维度 | Workflow | Chatflow |
|---|---|---|
| 是否带对话 | 否，一次性 | 是，多轮 |
| 起始变量 | 无 query | 有 sys.query |
| 适用场景 | 后台批处理 | 客服、对话类应用 |

**判断标准**：你的应用是否需要让用户反复输入？需要就 Chatflow，不需要就 Workflow。

#### 九、真实 AI 客服的全貌

本章搭建的客服只是一个最小可用版。真实的 AI 客服要比这复杂得多，通常包含多层兜底：

1. **问答对优先**：先在问答对库里做精确匹配，匹配上就直接返回。
2. **文档 RAG 兜底**：问答对没匹配上，再去文档库做 RAG（Retrieval-Augmented Generation）。
3. **人工兜底**：AI 都答不上时，自动转人工。
4. **学习闭环**：用 AI 算法持续收集「答不上」的问题，反哺问答对库和文档库。

**AI 产品经理多关注**：交付 MVP 时一定要明确告知客户「这是 1.0 版本」，并把后续迭代路径画清楚。客户期望管理比技术实现更重要。

#### 十、上节课的销售助理案例

上节课演示的销售助理是另一个典型工作流。结构与客服类似：

1. 问题分类：把销售问题分成三类
   - 小红书文案类
   - 海外营销文案类
   - 经销商服务类
2. 每类单独走分支，挂不同的角色提示词
   - 小红书投流专家
   - 海外营销文案专家
   - 经销商服务专家
3. 每类都挂自己的知识库，检索结果喂给对应角色的大模型
4. 大模型基于「角色 + 知识库 + 用户问题」生成回复

**关键金句**：不要在提示词里把多个角色混在一起写。「你是小红书专家，又是海外营销专家」这种写法，模型表现一定差于分开两条线、各自定义一个角色。角色越专一，表现越好。

例如对经销商场景，用户问「经销商对布进不辞进的认可度高，但担心运输成本，怎么办」，工作流走到经销商分支，调出「经销商核心痛点 + 解决方案」的知识库内容，叠加「经销商服务专家」的角色提示词，最终给出既突出产品优势、又回应运输成本担忧的回复。

### 结论 / 金句

1. **SOP 优先，AI 后置**：业务 SOP 画不清楚，AI 工作流一定画不清楚。
2. **拆得越细，正确率越高**：让一个大模型干十件事，正确率只有 35%；让十个模型各干一件事，正确率飙升。
3. **检索 + 大模型组合**：检索负责事实，大模型负责说人话。
4. **强模型 + 给例子**：分类器必须用强模型，必须给例子。
5. **兜底回复要像真人**：「我去跟老师确认后再回答你」远比「系统错误」更友好。
6. **角色单一化**：提示词里不要混多个角色，分类后挂不同分支、各自定义。
7. **工作流 ≠ 工作流审批**：不要试图用 Dify 工作流替代 OA 审批。
8. **多轮对话靠记忆开关**：Dify 自带，但轮数不要贪多。

## 下篇 · 方法论精华

### 一张速查表

| 场景 | Dify 形态 | 核心节点 | 模型建议 | 提示词要点 |
|---|---|---|---|---|
| 简单问答 | 聊天助手（基础） | 系统提示词 | GPT-4o | 单一角色 |
| 客服 / 销售 | Chatflow | 问题分类器 + 知识检索 + 大模型 | 分类用 GPT-4o/R1，回答用 GPT-4o | 每类给 3-5 个例子 |
| 翻译 / 总结 | Workflow | 文档提取器 + 变量聚合器 + 大模型 ×3 | GPT-4o | 三段式：初次翻译 → 检查 → 改进 |
| 复杂任务 | Agent | 工具调用 + 记忆 | GPT-4o | 明确工具描述 |
| 文件处理 | Workflow / Chatflow | 文件变量 + 文档提取器 | — | 文档提取器不做检索 |

### 通用原则

1. **业务先行，技术后置**：永远从 SOP 开始画。
2. **可视化优于长 prompt**：能用节点拆的，绝不写进 prompt。
3. **强模型打底，弱模型优化**：分类、核心逻辑用强模型；纯改写可以用便宜模型。
4. **错误兜底要拟人化**：兜底话术 = 真人话术，不是技术话术。
5. **知识库是工程活，不是技术活**：知识库的质量决定 RAG 的上限。
6. **前端只负责触发**：Dify 的 Chatflow 前端是调试工具，正式上线通常调用 Dify 提供的 API。
7. **全本地部署可行性**：央国企场景选 Dify 是因为支持全本地部署，AI 产品经理交付时必须确认部署方式。
8. **多轮对话的代价**：多轮 = 多 token + 多延迟。生产环境控制在 5-10 轮。

### 可复用模式

#### 模式 1：分类-检索-改写 三段式

适用：所有「先理解问题、再查资料、再回答」的客服 / 助手场景。

```
用户输入
  │
  问题分类器（强模型 + 给例子）
  │
  ├─ 类型 A → 知识检索 A → 大模型 A
  ├─ 类型 B → 知识检索 B → 大模型 B
  └─ 其他 → 直接回复
```

#### 模式 2：分支汇合 + 变量聚合器

适用：多入口、多来源的同一类任务。

```
用户输入
  │
  ├─ 条件：文件存在？── 是 → 文档提取器 ──┐
  └──────────────── 否 ──────────────────┴── 变量聚合器
                                              │
                                         下游统一处理
```

#### 模式 3：多角色专家路由

适用：业务跨多个领域，需要不同角色 prompt。

```
用户输入
  │
  问题分类器
  │
  ├─ 角色 A → 知识库 A + 角色 A 提示词
  ├─ 角色 B → 知识库 B + 角色 B 提示词
  └─ 角色 C → 知识库 C + 角色 C 提示词
```

#### 模式 4：拟人兜底回复

适用：所有需要礼貌掩盖系统局限的场景。

- 检索为空 → 「对不起，我去跟老师确认后再回答你。」
- 答不上来 → 「这个问题我暂时回答不上，我会反馈给我们的专家团队。」
- 用户闲聊 → 「我只能回答 AI 产品经理课程相关的问题，您可以换个问题试试。」

## 借鉴篇 · 我们能借鉴的点

以下动作结合王昕团队的实际业务场景（企业 AI 客户交付 / FDE / 获客系统 / 8895 知识库），逐条说明「对应哪个业务场景 + 怎么做」。

1. **企业 AI 客户交付首日模板化**
   - 场景：客户第一次接触时，对 AI 落地没有具象认知。
   - 动作：用 Dify 在 24 小时内搭建客户业务的最小可用客服（参考本章客服案例），让客户当天看到效果。这一招对央国企、政府客户尤其有效——他们最关心「能不能本地部署」，Dify 全本地部署能力正好对标。

2. **8895 知识库升级为多租户**
   - 场景：现有 8895 知识库是单租户，每次客户接入都要重新配置。
   - 动作：用 Dify 的知识库功能做多租户封装，每个客户一个知识库 ID。RAG 检索时按租户隔离，避免 A 客户的问题检索到 B 客户的资料。

3. **FDE 工作流标准库**
   - 场景：FDE 团队每次交付都从零画工作流，效率低。
   - 动作：把本章三类经典模板（客服、翻译、文档总结）沉淀为内部工作流标准库，新员工入职即可复用。可以进一步抽象为「行业模板包」：教育客服模板、电商客服模板、SaaS 客服模板。

4. **获客系统的智能前置客服**
   - 场景：获客系统承接的线索进入销售前，需要初步过滤和培育。
   - 动作：用 Chatflow 搭建前置客服，自动回答「你们做什么的」「价格多少」「怎么合作」等高频问题，识别出高意向线索后再转人工。分类器提示词专门针对获客场景优化，把「价格异议」「竞品对比」单独分支处理。

5. **王昕团队内部 SOP 数字化**
   - 场景：王昕团队的业务 SOP（交付流程、合同流程、客服流程）目前分散在飞书文档里。
   - 动作：把这些 SOP 拆成本章客服案例的形态，画成 Dify 工作流。每个节点对应一个真实步骤，AI 在节点上做提示词或分类，员工在节点上做决策。这样 SOP 既能被 AI 辅助执行，也方便新人快速上手。

6. **客户案例的可视化交付**
   - 场景：交付给客户的方案文档纯文字，客户读起来抽象。
   - 动作：交付时附上 Dify 工作流的截图和演示链接（参考本章），让客户直观看到「你的业务是这样被 AI 处理的」。截图 + 演示比 PDF 方案说服力强十倍。

7. **AI 客服 × 人工客服的派单闭环**
   - 场景：AI 客服答不上时，目前是直接回复「答不上」，客户体验差。
   - 动作：参考本章「真实 AI 客服全貌」，把「答不上」分支接到派单系统（如飞书多维表格 + 企微机器人），自动生成工单、分配给对应的人工客服。人工客服回复后，答案回写到知识库，下次 AI 就能答上。

8. **Dify 工作流的 API 化交付**
   - 场景：央国企客户的信息系统已有自己的前端，不能直接用 Dify 自带聊天窗口。
   - 动作：Dify 工作流发布后都提供 API。FDE 交付时，把 API 文档整理成客户能调用的接口，让客户的前端调 Dify 的 API，Dify 在客户内网全本地部署。这是央国企场景的标准交付模式。

9. **多轮对话的「业务上下文」增强**
   - 场景：Dify 自带多轮对话只记历史问答，不记业务上下文（如客户的购买历史、之前的工单）。
   - 动作：在开始节点之前用代码（Python/Go）查询业务数据库，把客户 ID、订单历史等业务上下文注入到 system prompt。这样 Dify 多轮对话能跨越「会话」级别记忆。

10. **章节作业的工程化**
    - 场景：UP 主布置的课后作业（自己搭一个 AI 客服）是一次性学习动作。
    - 动作：王昕团队把这个作业工程化——每位新 FDE 入职第一周必须交付一个 AI 客服工作流，并接入真实业务（如 8895 知识库）。通过即转正，不通过继续打磨。这样既完成了培训，又产出了真实资产。

11. **Dify × 飞书生态打通**
    - 场景：王昕团队日常协作在飞书，AI 应用却和飞书割裂。
    - 动作：Dify 支持把 chatbot 嵌入飞书群机器人、飞书文档、飞书会议。把团队内部的 AI 客服接入飞书机器人，员工在群里 `@客服` 就能调用。这条打通后，团队使用 AI 的频次会显著提升。

12. **借鉴「分类-检索-改写」模式做线索打分**
    - 场景：获客系统每天进来大量线索，目前靠人工筛选。
    - 动作：把线索分类（如「明确需求 / 模糊需求 / 竞品 / 同行 / 无效」）做成工作流，每类对应不同的处理路径（明确需求 → 销售立即跟进；模糊需求 → 内容培育；同行 → 屏蔽；无效 → 标记）。分类器用 GPT-4o，训练数据来自历史线索标注。

13. **Dify 工作流的版本管理与回滚**
    - 场景：客户的生产环境工作流被改坏了，没有快速回滚机制。
    - 动作：Dify 工作流每次发布前先导出 YAML（DSL 文件），存入 Git。出错时一键回滚到上一个稳定版本。这条经验对生产环境的稳定性至关重要。

14. **把知识库「喂养」做成日常动作**
    - 场景：8895 知识库建好后没人维护，越用越不准。
    - 动作：参考本章「学习闭环」思路，每周固定一个时段，团队把本周 AI 答不上、答错的问题收集起来，写进知识库。这是知识库的「持续喂养」机制，比一次性建库重要十倍。

15. **借鉴「角色单一化」原则优化现有提示词**
    - 场景：王昕团队现有的提示词经常把多个角色塞在一起，效果差。
    - 动作：审计所有现有提示词，凡是一个提示词里出现「你既是 A 又是 B」的，全部拆开，按分类路由到不同分支。这一条改动小、收益大。
